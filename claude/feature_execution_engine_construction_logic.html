执行引擎的本质 — 它解决什么问题
之前我们讨论了 Feature View "定义什么"、三条管线"跑什么"。本节要回答的核心问题是：Feature View 的声明式配置，如何被执行引擎自动"翻译"为可以在 Spark/Flink/C++ 上运行的具体 Job？ 这个过程类似数据库的 Query Planner — SQL 是声明式的，引擎将其翻译为物理执行计划。
一个类比理解执行引擎的角色:

Feature View 配置 ≈ SQL 查询语句 (声明"我要什么")
执行引擎 ≈ 数据库的 Query Planner + Executor (决定"怎么算"并执行)
DSL Compiler ≈ SQL Parser + Optimizer (语法解析 + 逻辑优化)
Job Builder ≈ Physical Plan Generator (生成物理执行计划)
Job Deployer ≈ Executor (调度到具体计算引擎执行)

算法工程师只需要写 Feature View 配置 (声明式)。执行引擎的职责是将其自动转化为在 Spark/Flink/YARN/K8s 上运行的具体作业，并管理作业的全生命周期。
1
执行引擎内部架构 — 七大核心子系统
执行引擎是一个 Java/Go 微服务 (字节内部名: ByteFeature Engine; 阿里: PAI-FeatureStore Materializer)，部署在 K8s 集群中，暴露 gRPC/REST API。
1.1 Plan Resolver (计划解析器)
接收 Feature View 变更事件 (来自元数据服务)，解析出需要构建/更新/删除的 Job 列表。

输入: Feature View 配置 (含 Entity、source、transform、store、schedule)
输出: ExecutionPlan (一个或多个 JobSpec 的有向无环图)

核心决策:
• source_type=BATCH → 生成 SparkJobSpec + AirflowDAGSpec
• source_type=STREAM → 生成 FlinkJobSpec
• source_type=ON_DEMAND → 生成 CppOperatorSpec
• 多个 Feature View 共享数据源 → 合并为一个 Job (Job Fusion)

Plan Resolver Metadata Service gRPC
1.2 DSL Compiler (编译器)
将 Transform DSL 编译为目标引擎的可执行代码。这是执行引擎最核心的技术组件。

编译器前端 (与引擎无关):
• Lexer (ANTLR4 生成) → Token Stream
• Parser → CST (Concrete Syntax Tree)
• AST Builder → AST (Abstract Syntax Tree)
• Semantic Analyzer → 类型推导 + 校验
• IR Generator → 中间表示 (Logical Plan)

编译器后端 (引擎特定):
• Spark CodeGen → SQL String + UDF Jar
• Flink CodeGen → Java Operator Class
• C++ CodeGen → Header + Source 文件
• Python CodeGen → UDF 函数

ANTLR4 Code Generator
1.3 Job Builder (作业构建器)
接收 DSL 编译产物 + Feature View 配置，构建完整的可提交作业。

对 Spark Job: 生成 JAR 包 + spark-submit 参数 + 资源配置
对 Flink Job: 生成 JobGraph (Source→Operator→Sink 的 DAG) + Flink 集群配置
对 C++ Operator: 编译为 .so 动态链接库

Job Builder 不只是"打包"，它负责:
• 资源估算: 根据数据量估算 executor/parallelism
• Sink 注入: 自动注入 Tair Sink + HDFS Snapshot Sink
• Quality Gate 注入: 自动在计算后插入质量校验步骤
• 监控埋点注入: 自动在 Job 中注入 Prometheus metrics

Job Builder Artifact Builder
1.4 Job Deployer (作业部署器)
将构建好的 Job Artifact 部署到目标执行环境。

Spark Job: → Airflow DAG 注册 + JAR 上传到 HDFS
Flink Job: → Flink Cluster 提交 (YARN/K8s) + Savepoint 管理
C++ Operator: → 编译产物推送到 Ad Server 的 artifact repo

部署策略:
• 蓝绿部署: 新版本 Job 启动成功后切换流量
• 金丝雀部署: Flink Job 新旧版本并行，shadow 模式验证
• 回滚: 保留最近 3 个版本的 Savepoint / Artifact

Job Deployer YARN / K8s API
1.5 Resource Estimator
自动估算 Job 所需的计算资源。

Batch Job 估算:
• 输入: 上游 Hive 表行数 + 列数 + Transform 复杂度
• 输出: executor 数量、内存、核数
• 算法: 基于历史 Job 的资源使用回归模型

Flink Job 估算:
• 输入: Kafka topic QPS + 窗口大小 + State 预估
• 输出: parallelism、TaskManager 内存、SSD 大小

Resource Model
1.6 Lifecycle Manager
管理 Job 的全生命周期状态。

状态机:
BUILDING → TESTING → DEPLOYING → RUNNING → UPDATING → STOPPING → STOPPED

核心能力:
• 自动重启失败的 Job
• 版本变更时的平滑升级
• 定期健康检查
• 资源弹性伸缩

Lifecycle FSM
1.7 Test Runner
在 Job 部署前执行自动化测试。

测试类型:
• 一致性测试: 多引擎结果对比
• 性能基线: 与前一版本对比
• 数据质量预检: Mock 数据验证

沙箱环境:
独立的 Spark/Flink mini-cluster 执行测试 Job，不影响生产。

构建流程全景 — 从 Feature View 变更到 Job 上线
一次 Feature View 注册/变更的完整构建链路
触发点: 算法工程师通过 SDK/Web UI 提交 Feature View 变更
├ 变更类型: 新建 / Transform 修改 / 新增字段 / 调度变更 / 资源调整
└ 写入 Feature Platform 元数据库 (MySQL), version++

Step 1: 变更事件分发 Event Bus ~100ms
├ 元数据库触发 Change Data Capture (Binlog / Debezium)
├ 变更事件发送到内部 Kafka topic: feature_view_changes
└ 执行引擎的 Plan Resolver 消费此事件

Step 2: Plan Resolver 解析执行计划 Plan Resolver ~500ms
├ 读取完整 Feature View 定义 (from Metadata Service gRPC)
├ 确定变更影响范围:
│ Transform 变更? → 需要重新编译 + 重建 Job
│ 仅新增字段? → FlatBuffer 向后兼容, 只需更新 Materialization 逻辑
│ 仅调度变更? → 只更新 Airflow DAG, 不重建 Job
│ 仅资源调整? → 只更新 YARN/K8s 资源配置
├ Job Fusion 决策: 是否与其他 Feature View 共享 Job?
│ (同一 Entity + 同一数据源 + 同一调度 → 合并为一个 Job)
└ 输出: ExecutionPlan { jobSpecs: [...], deployActions: [...] }

Step 3: DSL 编译 DSL Compiler ~2s
├ 3.1 前端编译:
│ DSL 源码 → ANTLR4 Lexer/Parser → CST → AST → Semantic Analysis
│ → 类型推导: "COUNT(action='click')" → 输出类型 INT64
│ → 窗口校验: SLIDING(1h, 5min) → slide < size, 合法
│ → IR 生成: LogicalPlan { source, filters, aggregations, projections }
├ 3.2 优化:
│ → 谓词下推: WHERE action='click' 推到 source 读取层
│ → 列裁剪: 只读取 DSL 引用的列
│ → 公共子表达式: ctr=click/imp, click 和 imp 已在窗口 A 计算 → 复用
│ → 窗口合并: 两个窗口相同但聚合不同 → 合并为一个窗口+多个聚合
├ 3.3 后端代码生成 (按 source_type 分支):
│ BATCH → SparkSQL 字符串 + UDF Java Class
│ STREAM → Flink AggregateFunction/ProcessFunction Java Class
│ ON_DEMAND → C++ Operator Header + Source
└ 3.4 产物缓存: Hash(DSL+version) 作为 key, 编译产物存入 Artifact Store

Step 4: Job 构建 Job Builder ~5s (Batch) / ~30s (Flink) / ~60s (C++)
├ 4.1 代码组装:
│ 编译产物 + 框架模板 (Spark/Flink boilerplate) + Sink 配置
│ → 完整可执行代码
├ 4.2 自动注入:
│ ├ Tair Sink (key_template, serializer, ttl, 限流参数)
│ ├ HDFS Snapshot Sink (snapshot_path, interval, format)
│ ├ Quality Gate (行数/NULL率/PSI 校验逻辑)
│ ├ Prometheus Metrics (计数器/直方图/Gauge 埋点)
│ └ Error Handler (异常捕获 + 告警 + 自动重试)
├ 4.3 打包:
│ Spark → uber JAR (Maven Shade) 上传到 HDFS artifact 目录
│ Flink → fat JAR 上传到 Flink artifact 目录
│ C++ → cmake build → .so 文件上传到 artifact repo
├ 4.4 资源配置生成:
│ Spark → spark-submit.conf (executors, memory, shuffle partitions)
│ Flink → flink-conf.yaml (parallelism, checkpoint, state backend)
├ 4.5 调度配置生成:
│ Batch → Airflow DAG Python 文件 (自动生成)
│ Stream → Flink Job 的 K8s Deployment YAML
└ 输出: JobArtifact { jar/so, config, dag, version, checksum }

Step 5: 自动化测试 Test Runner ~2min
├ 5.1 一致性测试: 1000 条 mock 数据 × 各引擎代码 → 结果全等?
├ 5.2 集成测试: 在沙箱 mini-cluster 提交 Job → 是否正常启动运行?
├ 5.3 性能基线: 处理 10万条数据的耗时 vs 上一版本 → 无回退?
└ 全部通过 → Step 6; 任一失败 → 中止 + 通知 Owner

Step 6: 部署上线 Job Deployer ~30s (Batch) / ~3min (Flink)
├ Batch Job: 将生成的 Airflow DAG 文件同步到 Airflow DAGs 目录
│ → Airflow Scheduler 自动检测新 DAG 并注册
├ Flink Job (新建): Flink REST API → 提交 Job → 等待 RUNNING 状态
├ Flink Job (更新): 触发 Savepoint → 停止旧 Job → 从 Savepoint 启动新 Job
├ C++ Operator: 推送 .so 到 artifact repo → 触发 Ad Server 滚动重启
└ 更新 Lifecycle Manager 状态: DEPLOYING → RUNNING

Step 7: 部署后验证 Post-Deploy Verifier ~5min
├ Batch: 等待下一次调度执行 → 验证输出 Hive 表正确
├ Flink: 观察 5min → Kafka Lag 正常 + 无 Checkpoint 失败 + Tair 写入正常
├ C++: Ad Server canary 实例验证 → Feature Serving 延迟无回退
└ 全部通过 → Feature View status: STAGING/PROD; 失败 → 自动回滚

DSL Compiler 深度拆解 — 执行引擎的技术核心
3.1 编译器前端: DSL → IR
DSL 语法设计原则:
• 类 SQL 语法 (降低学习成本)
• 只支持"离线和在线都能高效执行"的算子子集
• 不支持任意 UDF (防止一致性无法保证)
• 不支持 JOIN (JOIN 在平台层处理，不在 DSL 内)

编译阶段示例:
// DSL 源码 COUNT(action='click') OVER SLIDING(1h, 5min) AS click_1h // Lexer → Tokens [FUNC:COUNT, LPAREN, FIELD:action, EQ, STR:'click', RPAREN, OVER, WINDOW:SLIDING, LPAREN, DUR:1h, COMMA, DUR:5min, RPAREN, AS, ALIAS:click_1h] // Parser → AST WindowedAggregation { func: Count filter: BinaryOp(Eq, Field("action"), Lit("click")) window: Sliding(size=3600s, slide=300s) alias: "click_1h" output_type: INT64 // 类型推导 } // IR (Logical Plan) LogicalPlan { source: KafkaSource("user_behavior_log") filter: Predicate(action == "click") window: SlidingWindow(3600, 300, EventTime) agg: Count(*) project: [entity_key, click_1h, _trigger_time] }
3.2 IR 优化 (Logical Optimization)
优化规则 (按优先级依次执行):

Rule 1: 谓词下推 (Predicate Pushdown)
将 filter 条件推到 source 层。对 Kafka: 写入 Flink 的 FilterFunction 作为第一个算子。对 Hive: 写入 WHERE 条件利用 Parquet 的 predicate pushdown。

Rule 2: 列裁剪 (Column Pruning)
DSL 只引用 action, category_id, event_time → 从 source 只读这 3 列。对 Parquet 效果显著 (跳过其他列的 I/O)。

Rule 3: 窗口合并 (Window Merge)
同一 Feature View 中如果多个特征使用相同的窗口定义，合并为一个窗口 + 多个聚合:
// 优化前: 两个独立窗口 Window(1h,5min).agg(Count(click)) → click_1h Window(1h,5min).agg(Count(imp)) → imp_1h // 优化后: 一个窗口 + 多聚合 Window(1h,5min).agg( Count(click) → click_1h, Count(imp) → imp_1h )
减少 50% 的 state 和 window timer 开销。

Rule 4: 公共子表达式消除 (CSE)
ctr_1h = SUM(click) / SUM(imp)
如果 click_1h 和 imp_1h 已计算 → ctr_1h 直接引用，不重复聚合。

Rule 5: 增量聚合推导 (Incremental Agg)
分析聚合函数是否支持增量计算:
• COUNT/SUM/MAX/MIN → 可增量 → 用 AggregateFunction
• COLLECT_LIST/DISTINCT_COUNT → 不可增量 → 用 ProcessWindowFunction
• 自动选择最优实现

Optimizer Rule Engine
3.3 后端代码生成: IR → 引擎代码
同一个 IR 被翻译为完全不同的引擎代码:

生成 Spark SQL:
// IR: SlidingWindow(1h,5min) + Count(click) // → Spark SQL (离线回溯计算) SELECT user_id, COUNT(CASE WHEN action='click' THEN 1 END) AS click_1h, COUNT(CASE WHEN action='impression' THEN 1 END) AS imp_1h FROM user_events WHERE event_time BETWEEN '${target_time}' - INTERVAL 1 HOUR AND '${target_time}' GROUP BY user_id
生成 Flink Java:
// IR: SlidingWindow(1h,5min) + Count(click) // → Flink AggregateFunction public class ClickCountAgg implements AggregateFunction<Event, long[], long[]> { public long[] createAccumulator() { return new long[]{0, 0}; // [click, imp] } public long[] add(Event e, long[] acc) { if ("click".equals(e.action)) acc[0]++; if ("impression".equals(e.action)) acc[1]++; return acc; } public long[] getResult(long[] acc) { return acc; } public long[] merge(long[] a, long[] b) { return new long[]{a[0]+b[0], a[1]+b[1]}; } }
生成 C++ Operator (仅 OnDemand):
// IR: HOUR_OF_DAY(request_time) // → C++ inline function int64_t compute_hour_bucket(int64_t ts_ms) { time_t t = ts_ms / 1000; struct tm tm_buf; localtime_r(&t, &tm_buf); return tm_buf.tm_hour; }
3.4 编译产物管理 (Artifact Store)
编译产物以版本化的方式存储，支持回滚和复用。

Artifact Store 结构:
artifact_store/ user_realtime_stats_v3/ spark/ v3.1/ ← Transform DSL version feature_etl.jar (uber JAR) spark_submit.conf (资源配置) quality_gate.py (校验脚本) airflow_dag.py (DAG 定义) flink/ v3.1/ feature_stream.jar (fat JAR) flink_conf.yaml (Job 配置) flink_job_graph.bin (序列化 JobGraph) cpp/ v3.1/ libfeature_ops.so (动态库) feature_ops.h (头文件) test/ v3.1/ test_data.parquet (测试数据) expected_output.json (预期结果) consistency_report.json(一致性报告) metadata.json (版本元信息)
存储后端: HDFS (字节) / OSS (阿里)
缓存策略: 编译产物按 Hash(DSL + version) 缓存。DSL 未变更时直接复用，不重新编译。
保留策略: 最近 5 个版本保留，更早的自动清理。

Job Builder 深度拆解 — 从编译产物到可运行 Job
Job Builder 是执行引擎中"动手干活"的核心模块。它不写业务逻辑 (那是 DSL Compiler 的事)，而是负责将业务逻辑嵌入框架模板、注入平台能力、打包为可提交的作业。
4.1 Spark Job Builder
框架模板 (Boilerplate):
Job Builder 维护一个 Spark Job 的"骨架"代码 (Java/Scala)，编译产物被注入其中:
class FeatureETLJob { // ===== 平台注入: Source ===== val sourceDF = spark.read .format(viewConfig.sourceFormat) // "parquet" .load(viewConfig.sourcePath) // 动态填入 .select(prunedColumns) // 列裁剪 // ===== 编译注入: Transform ===== val transformedDF = sourceDF .sql(compiledSQL) // DSL 编译产物 // 或 .withColumn("x", compiledUDF(...)) // ===== 平台注入: Quality Gate ===== QualityGate.check(transformedDF, viewConfig.qualityRules) // ===== 平台注入: Materialization ===== TairWriter.write(transformedDF, viewConfig.storeConfig) // ===== 平台注入: HDFS Snapshot ===== if (viewConfig.snapshotEnabled) SnapshotWriter.write(transformedDF, snapshotPath) // ===== 平台注入: Metrics ===== MetricsReporter.report("row_count", transformedDF.count) }
编译产物只填充 Transform 部分，其余全部由 Job Builder 自动注入。

Airflow DAG 自动生成:
// Job Builder 根据 Feature View 配置生成: dag = DAG( dag_id=f"fv_{view_name}_{version}", schedule=viewConfig.schedule, default_args={retries: 2, retry_delay: 300} ) sensor = HivePartitionSensor( table=viewConfig.sourceTable, partition=f"ds={'{{'} yesterday {'}}'}") spark_task = SparkSubmitOperator( application=artifactPath("feature_etl.jar"), conf=resourceConfig) quality_task = PythonOperator(fn=quality_gate) materialize_task = PythonOperator(fn=materialize) sensor >> spark_task >> quality_task >> materialize_task

4.2 Flink Job Builder
JobGraph 构建:
Flink Job 不是简单的 JAR 提交——它需要构建一个完整的 StreamGraph → JobGraph:
StreamExecutionEnvironment env = ...; // ===== 平台注入: Source ===== KafkaSource source = KafkaSource.builder() .setTopics(viewConfig.kafkaTopic) .setGroupId(viewConfig.consumerGroup) .setDeserializer(new ProtobufDeserializer( viewConfig.messageSchema)) .build(); DataStream<Event> stream = env .fromSource(source, WatermarkStrategy.forBoundedOutOfOrderness( Duration.ofSeconds(viewConfig.watermark))) // ===== 平台注入: Filter ===== .filter(new ValidEventFilter()) // ===== 编译注入: KeyBy + Windows + Agg ===== .keyBy(e -> e.getUserId()) .window(SlidingEventTimeWindows.of( Time.seconds(viewConfig.windowSize), Time.seconds(viewConfig.windowSlide))) .aggregate( compiledAggregateFunction, // DSL 编译产物 compiledProcessFunction) // ===== 平台注入: Merge + Serialize ===== .map(new FlatBufferSerializer(viewConfig.schema)) // ===== 平台注入: Dual Sink ===== .addSink(new TairPipelineSink(viewConfig.storeConfig)) .addSink(new HDFSSnapshotSink(viewConfig.snapshotConfig)); // ===== 平台注入: Checkpoint 配置 ===== env.enableCheckpointing( viewConfig.checkpointInterval, CheckpointingMode.EXACTLY_ONCE); env.setStateBackend(new EmbeddedRocksDBStateBackend()); // 构建 JobGraph JobGraph jobGraph = env.getStreamGraph() .getJobGraph();
关键区别: Flink Job Builder 生成的不是 "代码文件"，而是一个序列化的 JobGraph 对象。这个 JobGraph 包含了所有算子的拓扑关系、并行度、State 配置等。提交给 Flink Cluster 时直接反序列化执行。

4.4 自动注入能力详解
Job Builder 向每个 Job 自动注入 6 类平台能力:

① Tair Sink:
根据 store_config 自动生成 Sink 代码: key 模板渲染、FlatBuffer 序列化、Pipeline MSet 批量写入、限流、重试。

② HDFS Snapshot Sink:
training_config.snapshot_enabled=true 时注入。Flink 用 BucketingSink (Parquet，按时间分桶)；Spark 直接 write.parquet()。

③ Quality Gate:
在 Transform 之后、Materialization 之前插入校验步骤。规则来自 Feature 配置的 monitoring 字段。

④ Prometheus Metrics:
自动注入计数器和直方图:
• feature_job_rows_processed_total
• feature_job_transform_latency_ms
• feature_job_tair_write_latency_ms
• feature_job_quality_check_pass (0/1)

⑤ Error Handler:
捕获所有异常 → 分类 (数据异常/系统异常/资源异常) → 告警 (飞书/PagerDuty) → 决策 (重试/跳过/中止)。

⑥ Lineage Tracker:
Job 启动和完成时上报血缘信息: 读了哪个 Hive 表/Kafka topic、输出到哪个 Tair namespace、处理了多少行。

Job Fusion (作业合并) — 多 Feature View 共享 Job
字节 DSP 有 ~300 个 Feature View 但只有 ~80 个 Flink Job 和 ~100 个 Spark DAG。原因是 Job Fusion——多个相关 Feature View 被合并到同一个 Job 中执行。
5.1 Fusion 触发条件
两个 Feature View 可以合并为一个 Job，当且仅当:

必须满足:
• 同一个 Entity (join_key 相同)
• 同一个数据源 (同一个 Kafka topic 或 Hive 表)
• 同一类管线 (都是 Batch 或都是 Stream)

加分条件 (可以合并但不强制):
• 相同的调度频率 (都是 "0 2 * * *" 或都是 realtime)
• 相同的 Owner (避免跨团队耦合)
• 总资源消耗在合理范围内 (合并后不超过单 Job 上限)

禁止合并:
• 不同 Entity (user vs ad)
• 不同数据源 (不同 Kafka topic)
• 不同管线类型 (Batch + Stream)
5.2 Fusion 实现机制
Flink Job Fusion:
多个 Feature View 的窗口+聚合共享同一个 KeyedStream:
stream.keyBy(user_id) // View 1: user_realtime_stats .window(Sliding(1h,5min)).aggregate(statsAgg) // View 2: user_behavior_seq .process(seqCollector) // View 3: user_click_dist .window(Tumbling(1h)).aggregate(distAgg) // 三个输出合并后写入各自的 Tair key union → TairSink( view1 → "uf:rts:{user_id}", view2 → "uf:seq:{user_id}", view3 → "uf:dist:{user_id}" )
Spark Job Fusion:
多个 Feature View 的 SQL 合并为一个 multi-output 的 Spark Job:
// 读取一次数据源 val source = spark.read.parquet(hive_table) // View 1 Transform val v1 = source.sql(compiled_sql_v1) // View 2 Transform val v2 = source.sql(compiled_sql_v2) // 各自写入不同的 Tair namespace TairWriter.write(v1, config_v1) TairWriter.write(v2, config_v2)
收益:
• Kafka 消费只一次 (省 I/O)
• Hive 表只读一次 (省 HDFS I/O)
• KeyBy 只做一次 (省 shuffle)
• Flink state 共享 TaskManager 资源
• 减少 Job 管理数量 (运维简化)

字节数据: Fusion 将 300 个 View 合并为 80 个 Flink Job，节省 ~40% 的计算资源。
Fusion 的风险与约束: 合并后一个 View 的 bug 可能影响同 Job 中的其他 View。字节的防御: ① 每个 View 的 Transform 在 Flink 中由独立的 Operator 处理，Operator 内部 try-catch 隔离异常；② 某个 View 的 Sink 写入失败不影响其他 View 的 Sink；③ 提供"Fusion Opt-out"选项——算法工程师可以在 Feature View 配置中设置 fusion_enabled: false 强制独立 Job。

资源估算与弹性伸缩 — 执行引擎的"智能"部分
6.1 Batch Job 资源估算模型
估算输入:
• 上游 Hive 表行数 (从 Hive Metastore 获取)
• 列数 + 数据类型 (Parquet footer 元信息)
• Transform 复杂度 (AST 节点数 + 是否有 UDF)
• 历史 Job 的资源使用记录

估算公式 (字节内部回归模型):
executors = max( ceil(input_size_gb / 2), // 每 executor 处理 2GB ceil(row_count / 5_000_000) // 每 executor 500万行 ) executor_memory = base_4g + (has_udf ? 2g : 0) + (has_join ? 4g : 0) executor_cores = 4 // 固定 shuffle_partitions = executors * 2.5
自适应调整:
首次运行用估算值。运行后记录实际 peak memory、shuffle 大小、GC time。下次运行用实际值 × 1.2 安全系数。

6.2 Flink Job 资源估算 + 弹性伸缩
初始估算:
parallelism = max( kafka_partitions, // 通常 1:1 ceil(peak_qps / 50000) // 每 slot 5万 QPS ) tm_memory = 4g + state_estimate // state_estimate = active_users * per_user_state // 例: 3亿 * 700B ≈ 200GB → 分摊到 128 TM ≈ 1.6GB/TM tm_ssd = state_estimate / parallelism * 1.5
运行时弹性伸缩 (Reactive Scaling):
字节使用 Flink 的 Reactive Mode (1.13+):
• Kubernetes HPA 监控 Kafka Lag 和 CPU
• Lag 持续 > 阈值 → 增加 TaskManager Pod
• Flink Reactive Mode 自动感知新 TM → 重新分配 subtask
• 缩容: 低峰时段 (凌晨) 减少 TM Pod

• 自动分析 Job 的 backpressure 热点

Job 状态机
BUILDING ──→ TESTING ──→ DEPLOYING ──→ RUNNING │ ├──→ UPDATING (新版本部署中) │ └──→ RUNNING (成功) │ └──→ ROLLING_BACK (失败) │ ├──→ DEGRADED (运行但有问题) │ └──→ RUNNING (自动恢复) │ └──→ STOPPED (多次恢复失败) │ ├──→ SCALING (弹性伸缩中) │ └──→ RUNNING │ └──→ STOPPING ──→ STOPPED ──→ DELETED
7.1 版本升级 (UPDATING)
Batch Job 升级 (简单):
• 替换 Airflow DAG 文件 + JAR 文件
• 下次调度自动使用新版本
• 旧版本 JAR 保留 (可回滚)

Flink Job 升级 (复杂):
Step 1: 触发旧 Job 的 Savepoint POST /jobs/{id}/savepoints 等待 Savepoint 完成 (~30s) Step 2: Cancel 旧 Job PATCH /jobs/{id} {state: CANCELLING} 等待 CANCELLED 状态 Step 3: 提交新版本 Job (从 Savepoint 恢复) POST /jobs { jarId: new_jar_id, savepointPath: savepoint_path, parallelism: new_config.parallelism } Step 4: 验证新 Job RUNNING + Kafka Lag 正常 Step 5: 失败回滚 如果 Step 3 失败 → 从 Savepoint 启动旧版本
关键: Savepoint 保证了 State 的连续性——新 Job 从旧 Job 停止的位置继续处理，不丢数据不重复。但 State schema 变更 (如新增字段) 需要 State 兼容性处理。

C++ Operator 升级:
新 .so 文件推送 → Ad Server 热加载 (dlopen) → 通过版本路由新旧请求
7.2 故障恢复 (DEGRADED → RUNNING)
Batch Job 故障:
• Spark Job 失败 → Airflow retry (配置 2 次)
• 2 次都失败 → 告警 + 线上用昨天数据 (TTL 兜底)
• 人工修复后手动触发重跑

Flink Job 故障:
故障类型及应对: TaskManager OOM: → 自动从 Checkpoint 恢复 (fixed-delay × 3) → 成功 → RUNNING → 3次都 OOM → 告警 + 增加 TM memory 后重启 Checkpoint 超时: → 降低 Checkpoint 频率 (60s → 120s) → 如果持续超时 → State 过大, 需要优化 Kafka 消费超时: → 检查 Kafka Broker 健康 → 自动重启 Consumer Tair Sink 写入失败: → 背压限流 + 重试 → 持续失败 → 熔断 Sink, 数据暂存内存/本地 → Tair 恢复后补写
Lifecycle Manager 的健康检查:
每 30s 通过 Flink REST API 检查 Job 状态。发现异常自动触发恢复流程。
