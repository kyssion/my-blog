三条管线全景 — 执行引擎如何调度 Feature View

链路一: 离线批量计算管线 — Spark + Airflow 深度拆解
完整执行流程 (凌晨 02:00~05:00)
Phase 0: 调度触发 Airflow / DolphinScheduler
├ Airflow DAG 定义: 每个 Batch Feature View → 一个 DAG
├ 触发方式: cron 表达式 (如 "0 2 * * *" 每天 02:00)
├ 依赖检查 (Sensor): 上游 Hive 分区 ds=yesterday 是否就绪？
│ → HivePartitionSensor 轮询 (30s 间隔，最长等 2h，超时告警)
├ 跨 DAG 依赖: user_interest_tags DAG 依赖 user_profile DAG 完成
│ → ExternalTaskSensor 或 TriggerDagRunOperator
└ 依赖满足 → 触发 SparkSubmitOperator

Phase 1: DSL 编译 DSL Compiler Service
├ 从 Feature Platform 元数据库读取 Feature View 定义
├ Transform DSL → ANTLR Parser → AST
├ 语义校验: 类型检查、函数签名、窗口合法性
├ 优化: 常量折叠、列裁剪 (只读需要的列)
├ Code Generation → Spark SQL 字符串 + 自定义 UDF Jar
└ 缓存: 相同 DSL version 的编译结果缓存，不重复编译

Phase 2: Spark Job 执行 Spark 3.x on YARN/K8s
├ 提交: spark-submit --class FeatureETLJob --master yarn
│ --num-executors 200 --executor-cores 4 --executor-memory 8g
├ Step 1: 读取上游 Hive 表 (Parquet 格式，列裁剪 + 谓词下推)
├ Step 2: 执行编译后的 Spark SQL (含 UDF 调用)
│ SELECT user_id, BUCKET(age, [18,25,35,45]) AS age_bucket,
│ gender, city_id, ... FROM dw.user_profile WHERE ds='${yesterday}'
├ Step 3: 输出中间 Hive 表 feature_output.user_profile_v2/ds=today
└ 耗时: 5 亿行 ~40min, shuffle ~200GB

Phase 3: 数据质量校验 Quality Gate
├ 行数校验: |today_count - yesterday_count| / yesterday_count < 5%
├ NULL 率: 每个 Feature 字段 NULL 率 < 配置阈值
├ 值域: 离散特征值 ∈ 合法枚举集合
├ PSI: 与前 7 天基线对比 PSI < 0.25
├ 一致性抽样: 1000 条数据用 C++ 算子重算，与 Spark 输出 diff=0
└ 任一失败 → 中止 Materialization + P1 告警 + 线上继续用昨天数据

Phase 4: Materialization (写入在线 KV) Tair BulkLoad / Pipeline Write
├ 方式选择: 变更量 >30% → BulkLoad (全量); ≤30% → Pipeline (增量)
├ BulkLoad 流程:
│ Spark → FlatBuffer 序列化 → SST 文件 → Tair Ingest API → 双缓冲切换
│ 吞吐: ~50 万 key/s, 5 亿 key ~15min
├ Pipeline 流程:
│ Spark → 按 Tair 分片分区 → 每分区内 Pipeline MSet → 限流 20 万 QPS
│ 吞吐: ~20 万 key/s, 5000 万变更 key ~5min
└ 完成后: 校验 KV 与 Hive 一致 → 原子切换 → 记录血缘日志

Spark Job 关键优化
① AQE (Adaptive Query Execution)
Spark 3.x 开启 AQE 自动优化 shuffle partition 数量。避免"200 个分区但 90% 的数据集中在 10 个分区"的数据倾斜。

② 列裁剪 + 谓词下推
上游 Hive 表可能有 500 列，Feature View 只用 20 列。Spark 编译后的 SQL 自动做 Column Pruning，只读需要的列。对 Parquet 格式效果极佳 (跳过不需要的 column chunk)。

③ Broadcast Join
画像加工常需 JOIN 维度表 (如 city_dim, category_dim)。维度表通常 <100MB，Spark 自动 Broadcast，避免 Shuffle Join。

④ 分区裁剪
只读 ds=yesterday 的分区，不扫描全表。Hive Metastore 提供分区元信息，Spark 精确定位 HDFS 文件路径。

⑤ Repartition by entity_key
Materialization 前按 CRC16(user_id) % N repartition，使同一个 Tair 分片的 key 在同一个 Spark partition，减少写入时的跨分片网络开销。

BulkLoad vs Pipeline Write 的选择策略

BulkLoad (SST Ingest): Spark 直接生成 Tair 底层存储引擎 (类 RocksDB) 的 SST 文件，通过 Tair 的 Ingest API 直接注入存储层，绕过 Tair 的写入链路。优点是吞吐极高 (50万/s)，缺点是必须全量写入一个完整的 namespace，不支持部分 key 更新。适用于全量 Materialization。

Pipeline Write: Spark 通过 Tair 客户端 SDK 发送 Pipeline MSet 命令逐批写入。优点是支持增量 (只更新变化的 key)，缺点是受 Tair 写入链路的 QPS 限制，需要限流。适用于增量 Materialization。

字节实践: 工作日用 Pipeline (增量, ~5000万 key, 5min)；周末用 BulkLoad (全量, ~5亿 key, 15min) 做 Clean Sweep 修正累积误差。平台根据 Feature View 配置的 materialization.mode 自动选择。mode="auto" 时由平台根据当日变更比率动态决定。

链路二: 实时流式计算管线 — Flink 深度拆解
实时流式管线是三条中工程复杂度最高的。它不像 Batch 有明确的"开始-结束"，而是 7×24 小时持续运行的常驻 Job。字节 DSP 的 ~80 个 Flink Job 服务 ~150 个 Stream Feature View。
Flink Job 完整架构 (以 user_realtime_stats 为例)
Source: Kafka Consumer Kafka 3.x
├ Topic: user_behavior_log (128 partitions, ~10M msg/s 峰值)
├ Deserialization: Protobuf → Java POJO (UserBehaviorEvent)
│ fields: user_id, event_time, action(impression/click/convert),
│ ad_id, category_id, advertiser_id, app_id, ...
├ Consumer Group: fv_user_realtime_stats_v3
├ Offset Commit: Flink Checkpoint 驱动 (不依赖 Kafka auto-commit)
└ 消费策略: EARLIEST (Job 首次启动) / LATEST (正常重启)

Step 1: 预处理
├ Filter: 过滤无效事件 (event_time=null, user_id为空, 非广告行为)
├ Watermark: BoundedOutOfOrdernessWatermarks(maxOutOfOrderness=10s)
│ 作用: 容忍 10 秒的乱序数据。超过 10s 的 late event 被丢弃 (或进入 side output)
├ Late Event 处理: 写入 late_event_kafka_topic 供离线修正
└ KeyBy(user_id): 按用户分区，保证同一用户的事件在同一 Task

Step 2: 窗口聚合 (核心计算) Flink Window API
├ 同一个 KeyedStream 上注册多个并行窗口:
│
│ Window A: SlidingEventTimeWindows(1h, 5min)
│ AggregateFunction: { click_count: Long, imp_count: Long }
│ 触发器: 每 5min 输出一次当前窗口状态
│ 输出: (user_id, click_1h, imp_1h, trigger_time)
│
│ Window B: SlidingEventTimeWindows(6h, 30min)
│ AggregateFunction: { click_sum: Long, imp_sum: Long }
│ 输出: (user_id, ctr_6h = click_sum/imp_sum, trigger_time)
│
│ Window C: SlidingEventTimeWindows(30min, 1min)
│ AggregateFunction: { category_list: List[Int] }
│ ProcessWindowFunction: 截断到 Top-20 → click_cat_seq
│
└ Window D: Global Window + ContinuousProcessingTimeTrigger(1min)
ProcessFunction: 维护行为序列 state，事件到达立刻追加
输出: (user_id, last_click_ts)

Step 3: 窗口结果合并
├ 各窗口输出 Union → CoProcessFunction
├ 按 user_id 聚合: 将各窗口的输出字段合并为完整的 Feature View value
├ FlatBuffer 序列化: Pack(click_1h, imp_1h, ctr_6h, click_cat_seq, ...)
└ 去重: 同一 user_id 在同一 micro-batch 内多次输出 → 只保留最新

Step 4: 双写 Sink
├─ Sink A: Tair (在线 KV)
│ ├ Micro-batch 攒批: 每 5s 收集一批 (BufferingSink)
│ ├ 合并: 同一 user_id 多条 → 只保留最新
│ ├ Pipeline MSet: 每批 1000~5000 key
│ ├ 限流: max_write_qps=100000，超过则背压
│ ├ 幂等: Tair MSet 天然幂等 (last-write-wins)
│ └ key: "uf:rts:{user_id}", TTL=86400 (1天)
│
└─ Sink B: HDFS Snapshot (训练快照)
├ 每 5min 触发一次 rolling file 关闭
├ 输出 Parquet 文件到 HDFS:
│ hdfs:///snapshots/user_rts_v3/dt=2024-11-20/hh=10/mm=05/part-0.parquet
├ 用于训练时 Point-in-time Join
└ 保留 7 天, 之后自动清理
Flink State 管理 (最大工程挑战)
State Backend: RocksDB
窗口聚合的中间状态 (计数器、列表) 存在 RocksDB 中 (本地 NVMe SSD)。

状态大小估算:
• 活跃用户 ~3 亿
• 每用户状态: 窗口 A+B 计数器 ~64 Bytes + 窗口 C 列表 ~400 Bytes + 窗口 D 序列 ~200 Bytes ≈ 664 Bytes
• 总 state: 3 亿 × 664B ≈ 200GB

Checkpoint 配置:
checkpoint.interval: 60s checkpoint.mode: EXACTLY_ONCE state.backend: rocksdb state.backend.incremental: true state.backend.rocksdb.block.cache-size: 256MB state.checkpoints.dir: hdfs:///flink-checkpoints/ state.savepoints.dir: hdfs:///flink-savepoints/
增量 Checkpoint: 只上传 RocksDB 的 delta SST 文件到 HDFS，而非全量 snapshot。200GB state 的增量 checkpoint 通常 <5GB，耗时 <30s。

State TTL: 设为最大窗口 × 1.5 (如 6h × 1.5 = 9h)。超过 9h 未更新的用户 state 自动清理，防止不活跃用户累积。

增量聚合 vs 全量聚合
增量聚合 (AggregateFunction):
只在 state 中保存聚合中间状态 (如 COUNT → 一个 Long 计数器)。每条事件到达: counter += 1。窗口触发时直接输出 counter 值。
state 大小: O(1) per key — 极小
适用: COUNT, SUM, AVG, MAX, MIN

全量聚合 (ProcessWindowFunction):
在 state 中保存窗口内的全部原始事件。窗口触发时遍历所有事件计算结果。
state 大小: O(N) per key — 巨大
适用: COLLECT_LIST, TOP_K, DISTINCT_COUNT, 复杂自定义逻辑

字节的优化方案:
对 COLLECT_LIST (行为序列) 使用预聚合 ProcessFunction: 维护一个固定大小的 RingBuffer (max_len=50)，事件到达时追加到 RingBuffer 尾部，满时淘汰最早的。State 大小固定为 O(max_len)，比 ProcessWindowFunction 节省 10 倍+ 空间。

对 DISTINCT_COUNT 使用 HyperLogLog 近似计算。State 从 O(N) 降到 O(1)，误差 <2%。
数据倾斜与热 Key 处理
问题: 少量高活跃用户 (Bot、头部 KOL) 产生大量事件，导致单个 KeyBy 后的 Task 过载。

方案一: 两阶段聚合 (Local-Global)
// Stage 1: Local Pre-Aggregate KeyBy(user_id + random(0..9)) // 分散到 10 个 sub-key .window(...) .aggregate(partialAgg) // 局部聚合 // Stage 2: Global Aggregate KeyBy(user_id) // 归回原 key .window(...) .aggregate(mergeAgg) // 合并局部结果
方案二: Hot Key 旁路
维护 Hot Key 列表 (定期从监控系统拉取)。事件到达时检查 user_id 是否 Hot Key → 是则走旁路 (单独的处理逻辑，降低聚合精度换性能)。

方案三: Flink Operator Chaining 关闭
对 KeyBy 后的重算子禁用 Operator Chaining，让 Flink 将其调度到不同 slot，利用更多 TaskManager 资源。

Local-Global Agg Hot Key Bypass
Flink Job 故障恢复完整流程:
① TaskManager 崩溃 (JVM OOM / 节点宕机)
② JobManager 检测到 Task failure → 触发 Job restart
③ 从 HDFS 上最近一次成功的 checkpoint 恢复 state (增量 SST 文件合并)
④ Kafka Consumer 回溯 offset 到 checkpoint 时刻
⑤ 重新消费 checkpoint 之后的数据 (数据重放，但 Tair Sink 是 last-write-wins 幂等)
⑥ 追赶消费直到 Lag 降为 0 (通常 1~3min)
⑦ 期间线上使用 Tair 中的旧值 (容忍分钟级延迟，不影响服务可用性)

极端情况: 3 次 fixed-delay restart 均失败 → Job 进入 FAILED 状态 → P0 告警 → 人工排查。Feature Serving 侧自动熔断该 View，全部使用 default_value。

链路三: 近线微批计算管线 — 介于批和流之间
近线管线是批和流的折中方案。它消费与实时流相同的 Kafka 数据源，但不做持续窗口聚合，而是由调度系统每 5~30 分钟触发一次 micro-batch 作业。字节和阿里在实践中发现，~10% 的特征既不需要 T+1 的粗粒度，也不需要秒级的细粒度，5~30 分钟的更新频率恰好满足需求且成本大幅低于常驻 Flink Job。
近线管线的两种实现方式
方式一: Spark Structured Streaming (字节部分场景)
spark.readStream .format("kafka") .option("subscribe", "user_behavior_log") .option("startingOffsets", "latest") .load() .withWatermark("event_time", "2 minutes") .groupBy( window("event_time", "1 hour", "5 minutes"), col("user_id") ) .agg(count("click").as("click_1h")) .writeStream .trigger(processingTime="5 minutes") // 每5min 一个 micro-batch .foreachBatch { (batchDF, batchId) => // 写入 Tair materializeToTair(batchDF) } .start()
特点: 用 Spark 的 micro-batch 模型 (每 5min 消费一批 Kafka 数据 → Spark Job 处理 → 输出)。每次是一个完整的 Spark Job (申请资源 → 执行 → 释放)。

方式二: Flink Batch Mode on Streaming Data (阿里实践)
Airflow 每 15min 触发一次 Flink batch job，消费最近 15min 的 Kafka 数据 (指定 offset 范围)，执行聚合后写入 Tair。
本质是"定时触发的小批量 Flink Job"，而非常驻 Job。
近线 vs 实时流: 选择标准
维度近线 (micro-batch)实时 (streaming)
延迟5~30min秒~分钟
计算成本按需申请释放 (低)常驻集群 (高 3~5x)
State 管理无状态 (每批独立)有状态 (RocksDB)
运维复杂度低 (普通调度)高 (checkpoint/savepoint)
Exactly-once天然 (批处理)需 checkpoint 保证

选择近线的典型场景:
• 小时级兴趣标签更新 (30min 更新一次足够)
• Look-alike 人群扩展 (每 15min 扩散一次)
• 准实时广告质量分 (每 10min 重算)
• 模型特征回填补丁 (修复特定 Feature 的值)

选择实时流的典型场景:
• 行为序列 (点击后立刻影响下次推荐)
• 实时 CTR/CVR (秒级变化的竞价景观)
• 频次控制 (即时生效的曝光计数)
近线管线完整执行流程 (以 Airflow + Spark Structured Streaming 为例)
每 15 分钟触发一次 Airflow
├ 02:00, 02:15, 02:30, 02:45, ...
└ 触发 SparkSubmitOperator (micro-batch mode)

Step 1: 读取 Kafka
├ 读取最近 15min 的数据 (通过 Kafka offset 范围)
├ 数据量: ~15min × 10M msg/s ≈ 90 亿条
└ Spark 申请资源: 50 executors × 4 cores

Step 2: Transform + 聚合
├ 执行 DSL 编译后的 Spark SQL
├ 窗口: TUMBLING(15min) 聚合 (无 state 跨批次)
├ 注意: 与 Batch 不同，这里的数据源是 Kafka 而非 Hive
└ 耗时: ~3min (数据量比 T+1 小很多)

Step 3: 质量校验 (轻量版)
├ 行数校验: 与前一批次对比波动 <30%
└ 值域校验: 抽样 100 条检查

Step 4: 写入 Tair (增量)
├ Pipeline MSet 写入变更的 key
├ 限流 10 万 QPS
└ 完成 → 释放 Spark 资源

Step 5: HDFS 快照 (可选)
├ 将本批次输出写一份 Parquet 到 HDFS
└ 路径: hdfs:///snapshots/user_hourly_agg/dt=today/hh=02/mm=15/
近线管线与离线/实时的"覆盖"关系

三条管线可能同时向同一个 Tair key 写入，覆盖策略是 last-write-wins:
• 离线管线凌晨写入全量基线 (覆盖所有 key)
• 近线管线白天每 15min 增量更新 (只覆盖活跃用户)
• 实时管线每秒更新 (只覆盖高频事件用户)

关键设计: 近线/实时的 TTL 短于离线。当近线特征过期后，查到的是离线的基线值——自动 "回退"。例如: 离线 TTL=30d, 近线 TTL=1d。昨天的近线值今天过期 → 查到的是离线画像 → 仍然有效。这个设计让三条管线无需显式协调，通过 TTL 机制自然衔接。

DSL 编译器 — 一份 DSL 如何驱动三条管线
DSL 编译器是三条管线的统一入口。算法工程师写一次 Transform DSL，编译器自动生成三种执行引擎的代码。
DSL 编译全流程
Transform DSL 源码
"COUNT(action='click') OVER SLIDING(1h, 5min) AS click_1h"
↓

窗口语义的跨引擎翻译
同一个 SLIDING(1h, 5min) 在不同引擎中的实现完全不同:

Spark (离线):
没有"滑动窗口"概念。编译器将其翻译为 SQL 的时间范围 WHERE 条件:
WHERE event_time BETWEEN timestamp - INTERVAL 1 HOUR AND timestamp
因为离线是回溯计算，"当前时刻"就是样本的 event_time。

Flink (实时):
直接映射为 Flink 的 SlidingEventTimeWindows(size=1h, slide=5min)。Flink 自动维护窗口 state 和触发逻辑。

Spark Structured Streaming (近线):
映射为 Spark 的 window() 函数 + micro-batch trigger。每 5min 触发一批，聚合最近 1h 的数据。

C++ (在线):
OnDemand 特征通常不涉及窗口 (它只计算当前请求的上下文)。如果 DSL 包含窗口聚合，编译器拒绝为 C++ 生成代码 → 该 View 不能是 ON_DEMAND 类型。
一致性保证机制
编译器级保证:
• 所有引擎的输出 schema 相同 (字段名、类型、顺序)
• 聚合函数的语义严格定义 (如 COUNT NULL 行为: 统一不计 NULL)
• 浮点精度: 统一使用 FLOAT64 中间计算，输出时 cast 到 FLOAT32

自动化校验 (注册时):
一致性测试流程: 1. 准备 test_data (1000 行 mock 事件) 2. 分别用 4 个引擎执行: - spark_result = run_spark_udf(test_data) - flink_result = run_flink_op(test_data) - cpp_result = run_cpp_op(test_data) - python_result= run_python_udf(test_data) 3. Assert: all_equal(spark, flink, cpp, python) 4. 任一不等 → 注册失败 → 编译器 bug
运行时校验 (每周):
抽样 1% 在线请求，用离线链路 (Spark) 重算特征值，与在线 serving 的实际值对比。diff > 0.1% → P1 告警。

离线→在线同步机制 — Materialization 引擎深度拆解
Materialization 是将离线/近线/实时计算结果"物化"到在线 KV 存储的过程。它是三条管线的最后一个环节，也是对在线服务影响最直接的环节。
5.1 BulkLoad 引擎 (离线全量)
原理: 绕过 Tair 的写入链路 (接收 → 解析 → 写 WAL → 写 MemTable → Flush → Compaction)，直接生成 Tair 底层存储引擎的 SST 文件，通过 Ingest API 注入。

流程:
Spark DataFrame (user_id, features) ↓ repartition by CRC16(user_id) % shard_count ↓ sortWithinPartitions by user_id ↓ mapPartitions: for each row: key = "uf:p:" + user_id value = FlatBuffer.pack(features) SSTFileWriter.add(key, value) SSTFileWriter.finish() → /tmp/sst/shard_N/xxx.sst ↓ upload SST files to Tair shadow namespace ↓ Tair.IngestSST(shard_N, sst_path) ↓ 双缓冲原子切换
关键优化:
• Spark partition 与 Tair shard 一一对应 (repartition by CRC16)，每个 partition 直接生成对应 shard 的 SST
• SST 文件内 key 按字典序排列 (Tair/RocksDB 要求)，Spark sortWithinPartitions 保证
• 压缩: LZ4 (Tair 默认压缩算法)，SST 文件比原始数据小 30~50%

5.2 双缓冲切换机制
问题: 全量 BulkLoad 需要 15~40min。期间如果直接写入线上 namespace，线上会出现"新旧混合"状态。

解法: A/B Namespace 交替
Day 1: 线上用 namespace_A BulkLoad → 写入 namespace_B 校验 B 完整性 原子切换: active = B Day 2: 线上用 namespace_B BulkLoad → 写入 namespace_A 校验 A 完整性 原子切换: active = A
原子切换实现:
配置中心 (Consul/Nacos) 中维护一个 flag:
feature_view.user_profile_v2.active_namespace = "B"
Feature Serving SDK 监听此 flag 的变化。flag 变更后，所有 Ad Server 实例在 ~1s 内同时切换读取目标 namespace。

回滚: 如果新 namespace 上线后发现问题，直接将 flag 切回旧 namespace。旧数据仍然完整保留。

5.3 Pipeline Write (增量写入)
适用场景: 只更新变化的 key (增量 Materialization + 近线管线)

流程:
Spark / Flink 输出 (user_id, features) ↓ 按 Tair 分片分组 ↓ 每组内攒批: batch_size=5000 key ↓ Pipeline MSet 发送到对应 Tair 节点 ↓ 限流: TokenBucket(max_qps=100000) ↓ 重试: 失败 key 放入 retry_queue, 3 次重试
限流策略:
• Token Bucket 算法: 每秒补充 100000 token，每个 key 消耗 1 token
• 背压: 当 Tair 响应延迟 P99 >10ms 时，自动降低写入速率 50%
• 凌晨 vs 白天: 凌晨 (离线 Batch) 限流 20 万 QPS；白天 (近线) 限流 10 万 QPS (留资源给在线读)

幂等性:
Tair MSet 天然 last-write-wins。同一个 key 多次写入不会产生脏数据——最后一次写入的值生效。对于 Flink exactly-once 语义，checkpoint 恢复后重放的数据虽然重复写入，但因为幂等性不影响正确性。
5.4 三条链路的写入协调
同一个 key 可能被三条管线写入:
例如 user_realtime_stats 可能同时有:
• 离线 Batch: 凌晨全量写入基线值
• 实时 Flink: 白天持续更新

协调规则:
① TTL 分层: 离线 TTL=30d, 实时 TTL=1d
② 时间自然覆盖: 实时写入覆盖离线值 (last-write-wins)；实时值过期后自动露出离线值
③ Key 命名隔离 (可选): 有些团队选择为离线/实时使用不同的 key 前缀 (如 uf:rts_batch:U123 vs uf:rts_stream:U123)。Feature Serving 先查 stream key，miss 后回退查 batch key。但字节更多使用同一个 key + TTL的方案——更简单，运维成本低。

写入优先级:
• Tair 层面无优先级 (谁后写谁生效)
• 时间顺序保证: 实时管线的写入时间戳总是晚于离线管线 → 自然覆盖
• 近线管线介于两者之间: 15min 粒度的写入覆盖离线但被实时覆盖

端到端质量保障 — 跨管线一致性
训练-Serving 一致性闭环
三条管线不仅服务在线 serving，也服务训练样本拼接。一致性的"闭环"是:

Feature View DSL (唯一 source of truth) ├→ 离线 Spark UDF → Hive 特征表 → 训练样本拼接 ├→ 实时 Flink Op → Tair (在线) + HDFS 快照 (训练 PIT Join) ├→ 近线 Spark/Flink → Tair (在线) + HDFS 快照 └→ C++ Operator → Feature Serving (在线计算) 闭环校验: 在线 serving 实际使用的值 ← 记录到曝光日志 训练样本拼接的值 ← Point-in-time Join 获取 Assert: serving_value ≈ training_value (diff < 0.1%)
字节 ByteFeature 的做法:
每周自动跑一次 "Consistency Audit Job":
① 随机抽 100 万条曝光日志 (含 serving 时记录的特征值)
② 用 Sample Factory 的 PIT Join 重新拼接这些样本的特征值
③ 对比 serving 值 vs PIT Join 值
④ 输出 diff report (按 Feature View 分组)
⑤ diff > 0.1% 的 View 自动标记为 "consistency warning"
端到端延迟 SLA
管线延迟 SLA监控方式
离线 Batch06:00 前全部完成Airflow DAG 完成时间告警
实时 Stream数据产生 → 在线可查 <2minKafka Lag + Tair 写入延迟

延迟分解 (实时管线):
• 客户端埋点 → Kafka: ~1s (上报 SDK batch)
• Kafka → Flink 消费: ~0.1s
• Flink 窗口处理: 取决于 slide (最差 =slide 间隔)
• Flink → Tair 写入: ~5s (micro-batch 攒批)
• 总延迟: 1s + 0.1s + 5min (slide) + 5s ≈ 5~6min

优化: Process-time 旁路
对 click_1h 等核心特征，额外注册一个 ContinuousProcessingTimeTrigger(1s)，事件到达后 1s 内就输出到 Tair。延迟: 1s + 0.1s + 1s + 5s ≈ 7s (接近实时)。
