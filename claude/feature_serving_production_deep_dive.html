Feature Serving 的定位 — 它到底做什么
Feature Serving 是 Feature Store 面向在线推理的服务层。它的职责是：在 Ad Server 收到一次广告请求后，在 ≤7ms 内，将分散在 Tair/Redis、本地缓存、在线计算等多处的特征值，按照模型配置的 slot 顺序拼接为一个完整的特征向量 (FeatureBatch)，交给模型 Serving 做推理。
Feature Serving 不是一个独立的微服务。在字节和阿里的架构中，Feature Serving 是以 SDK/Library 的形式嵌入 Ad Server 进程中的 (C++ 静态库 / Go package)。不走网络调用，直接在进程内完成。这样做的原因是：如果 Feature Serving 是独立服务，一次 gRPC 调用就要 0.5~1ms 的网络开销，而精排需要对 500 个候选做特征拼接——500 次 gRPC 远程调用完全不可接受。

与 Model Serving 的关系: Feature Serving 输出 FeatureBatch → gRPC → Model Serving (TF Serving/Triton) → 返回 pCTR/pCVR。这是唯一一次网络调用，因为模型推理需要 GPU，必须在独立进程。

1. Config Manager
职责: 加载并管理 feature_config.pb (模型特征配置)

核心数据:
• Model → Feature View 绑定关系
• 每个 slot 的特征名、dtype、来源、KV key 模板、默认值、Embedding 维度
• 版本号 + 灰度分桶信息

更新机制:
启动时从配置中心 (Consul/Nacos) 拉取完整配置；运行中监听配置变更事件，热加载新版本 (无需重启进程)。

2. Key Generator
职责: 根据 Entity join_keys + key_template 批量生成 KV key

输入: user_id + [ad_id_1..ad_id_500]
输出: 一组按 Tair 分片聚合的 key 集合

核心优化:
• Key 分片预排序: 对每个 key 计算 CRC16(key) % 16384 (Tair slot)，按 slot 聚合，同一分片的 key 合并为一次 Pipeline MGet
• User/Ad key 分离: User key 只生成一次 (所有候选共享)；Ad key 按候选列表批量生成
• Cross key 动态拼接: user_id + ad_id/advertiser_id 动态拼接

Key Router Shard Calculator

职责: 管理三级缓存的读写策略

L0 进程内 LRU:
Go: sync.Map + 自定义 LRU 淘汰
C++: 分片 LRU (16 个 shard，减少锁竞争)
容量 ~100K key, ~500MB 内存

L1 本机 RocksDB:
嵌入式 KV，NVMe SSD 存储
容量 ~50GB，用于当日活跃用户预热

L2 Tair Client:
分布式 KV 连接池 + Pipeline

读取路径: L0 → L1 → L2 → 缺失处理

职责: 执行 OnDemand Feature View 的 Transform

由 DSL Compiler 编译出的 C++ 算子组成。请求到达时，从 Bid Request 中提取原始字段 → 执行 Transform 链 → 输出特征值。

算子类型:

• 分桶类: BUCKET

职责: 将各来源的特征值拼接为模型输入

按 feature_config 中定义的 slot 顺序，将特征值填入 FeatureBatch 矩阵。核心是共享-个性化分离策略:

输入: user_id="U123", candidate_ads=[ad_001..ad_500], bid_request_context

│ Ad 侧: ad_meta(v2), ad_stats(v1), ad_embedding(v1)
│ Cross: user_x_advertiser(v1)
│ OnDemand: user_context(v1)
└ 计算优先级: user_profile > user_behavior_seq > user_realtime_stats > ...

T+0.4ms — Key Generator 批量生成 KV key
├ User keys (固定，不随候选变化): 5 个
│ "uf:p:U123", "uf:tag:U123", "uf:seq:U123", "uf:rts:U123", "uf:emb:U123"
├ Ad keys (每个候选 3 个): 500 × 3 = 1500 个
│ "af:m:{ad_id}", "af:s:{ad_id}", "af:e:{ad_id}"
├ Cross keys (每个候选 1 个): ~500 个
│ "cf:uxadv:U123_{advertiser_id}" (同广告主的广告共用一个 key → 去重后 ~200)
├ 去重后总计: ~1705 个 unique key
└ 按 Tair slot 分桶: 聚合到 ~8 个分片

T+0.5ms — 三条并行路径同时启动
┌─ Path A: OnDemand 计算 (CPU, 非阻塞)
│ HOUR_OF_DAY(ts)→14, IS_WEEKEND→0, GEOHASH(lat,lng,5)→"wx4g0",
│ DEVICE_TYPE→2, NETWORK→1, SCREEN_BUCKET→2, ...
│ 完成: T+0.8ms (耗时 0.3ms)
│
├─ Path B: User 特征拉取 (5 key, 异步 I/O)
│ L0 Cache 查询: uf:p:U123 命中! (该用户最近有请求)
│ L0 Cache 查询: uf:rts:U123 命中! (30s 前刚更新)
│ L0 miss → L1 RocksDB: uf:seq:U123 命中! (当日活跃预热)
│ L0/L1 miss → Tair MGet: ["uf:tag:U123","uf:emb:U123"] (2 key)
│ Tair 响应: T+2.5ms (网络 RTT ~1.5ms + Tair 处理 ~0.5ms)
│ 写回 L0 Cache
│ 完成: T+2.8ms
│
└─ Path C: Ad + Cross 特征拉取 (~1700 key, 异步 I/O)
L0 Cache 批量查询: 热门广告 af:* key 命中 ~900 个 (头部广告)
L0 miss → 按 Tair 分片聚合剩余 ~800 key → 8 个 Pipeline MGet 并行发出
Tair 响应: T+3.5ms (最慢的分片决定耗时)
写回 L0 Cache (仅广告特征，Cross 特征不缓存——user×ad 组合太稀疏)
完成: T+4.0ms

T+4.0ms — 三条路径全部完成，进入 Feature Assembler
├ FlatBuffer 零拷贝反序列化: 从 Tair value 中读取各字段 (不分配内存)
├ 缺失处理: 检查每个 slot，NULL → 使用 Feature.default_value
│ 统计类缺失 (ctr_7d): 层级回退 ad→advertiser→category→global
│ ID 类缺失: 填 slot-0 (default embedding)
│ SEQ 缺失: 填空序列 + padding 到 max_seq_len
├ 共享特征广播: User+Context 特征只填一份，500 个候选通过 offset 引用
├ 个性化特征填充: 遍历 500 个候选，逐条填 Ad+Cross 特征
└ FlatBuffer 序列化: 输出 FeatureBatch (约 500 × 200 slots)

T+5.5ms — FeatureBatch 就绪，通过 gRPC 发送到 Model Serving
├ FeatureBatch 大小: ~120KB (FlatBuffer 紧凑格式)
├ gRPC 传输: ~0.5ms (同机房，共享内存或 Unix socket 更快)
└ Model Serving 开始 GPU 推理...

T+6.0ms — Feature Serving 任务完成
总耗时分解: Key生成 0.4ms + 并行I/O 3.5ms + 拼接序列化 1.5ms + gRPC 0.5ms ≈ 6ms

三级缓存架构 — Feature Serving 性能的核心
缓存是 Feature Serving 能在 7ms 内完成的关键。没有缓存，每次请求 2500 key 全部查 Tair，P99 延迟会飙到 15~20ms。三级缓存将实际 Tair 查询量降低到 30% 以下。
L0: 进程内 LRU Cache
技术实现:
C++: 16 个分片 LRU (key hash 到分片，每个分片一把 mutex，减少锁竞争)
Go: sync.Map (读多写少场景最优) + 后台 goroutine 做 LRU 淘汰

容量: ~100K key, ~500MB 内存
TTL: 30~60s (短 TTL 保证近线特征的时效性)
命中率: 60~85% (取决于流量集中度)
延迟: <0.01ms

缓存什么:
• 热门广告特征 (头部 1000 条广告被大量请求复用)
• 高频活跃用户特征 (短时间内多次请求的用户)

不缓存什么:
• Cross 特征 (user×ad 组合太稀疏，缓存效率极低)
• 低频用户特征 (只出现一次就淘汰，浪费缓存空间)

淘汰策略: LRU + TTL 双重淘汰。key 到 TTL 强制过期 (保证时效)；空间满时按 LRU 淘汰最久未访问的 key。
L1: 本机 RocksDB
技术实现:
嵌入式 RocksDB，存储在本机 NVMe SSD
Block Cache 128MB (热数据内存缓存)

容量: ~50GB (SSD)
TTL: 1~7d
命中率: 15~25% (L0 miss 后)
延迟: <0.1ms (SSD 随机读)

预热策略:
每天凌晨 Batch Materialization 完成后，触发 L1 预热 Job:
• 从 Tair 中拉取当日预计活跃用户的特征 (根据昨日活跃用户列表预测)
• 写入本机 RocksDB
• 覆盖 ~80% 的当日请求用户

字节实践: L1 预热覆盖了大部分 User 特征查询。Ad 特征因为广告上下线频繁，不做 L1 预热——用 L0 短 TTL 缓存更合适。

写入方式: Batch Ingest (SSTFileWriter 直接写 SST 文件) 而非逐条 Put，吞吐提升 10 倍。
L2: Tair / Redis Cluster
技术实现:
Tair 集群 (字节) / Redis Cluster (开源方案) / ABFS (阿里)

集群规模 (字节 DSP):
• 200+ 节点
• 总内存 ~20TB
• 16384 个 hash slot

连接池:
每个 Ad Server 进程维护到每个 Tair 分片的长连接池 (Go: 每分片 8~16 连接; C++: 每分片 4~8 连接)。连接复用，避免 TCP 握手开销。

Pipeline 模式:
同一分片的多个 key 合并为一次 Pipeline MGet 命令。一次网络往返可查 200~500 key。实际上 2500 key 只需要 8~10 次网络往返 (按分片并行)。

延迟: P50 0.5ms, P99 2ms, P999 5ms (同机房)

跨机房: P99 5~8ms (主从复制，就近读)
缓存命中率的关键影响因素

广告侧 L0 命中率高: 广告系统的特点是头部效应极强——Top 1000 条广告占全部曝光的 60%+。这 1000 条广告的 af:meta/af:stats/af:emb 在 L0 中几乎常驻。

Cross 特征无法缓存: user_id × advertiser_id 的组合空间是亿级，L0 容量 100K key 根本装不下。即使缓存了，下一次请求的 user×ad 组合大概率与上次不同，命中率 <1%。因此 Cross 特征总是查 Tair (L2)。这也是 Cross Feature View 的 serving 成本最高的原因。

字节的优化: 对 Cross 特征做广告主粒度聚合——key 是 user_id × advertiser_id (而非 user_id × ad_id)。同一广告主的多条广告共享一个 Cross key，去重后 Cross key 从 ~500 降到 ~200。

Tair Client 深度优化 — 毫秒级的生死线
4.1 Pipeline MGet 批量化
原理: Redis/Tair 的 Pipeline 模式允许客户端一次发送 N 个命令，服务端批量处理后一次性返回 N 个结果。网络往返从 N 次降到 1 次。

实现步骤:
① Key Generator 输出 2500 key
② 对每个 key 计算 CRC16(key) % 16384 → Tair slot → 物理节点
③ 按物理节点分组: { node_A: [key1,key2...], node_B: [key3,key4...] }
④ 对每个 node，发送一个 Pipeline MGet 命令
⑤ 并行等待所有 node 响应 (Go: goroutine per node; C++: epoll 多路复用)
⑥ 合并结果，返回 key→value map

性能: 2500 key 散布在 ~8 个物理节点 → 8 次并行 Pipeline MGet → 总耗时 = max(单节点延迟) ≈ 2ms
4.2 连接池管理
池化策略 (Go 实现):
type TairConnPool struct { pools map[string]*connPool // 每个 Tair 节点一个池 poolSize int // 每节点连接数: 8~16 idleTimeout time.Duration // 空闲连接超时: 5min maxRetries int // 重试次数: 2 }
连接复用: 从池中 Get 连接 → 发送 Pipeline → 收到响应 → Put 回池。连接不关闭，跨请求复用。

故障处理:
• 连接断开: 自动重连 + 从池中剔除坏连接
• 节点下线: 从集群拓扑更新中感知，重新路由到新节点
• 超时: 单次 Pipeline 设 5ms 超时，超时后放弃并使用 default_value

字节实践: 使用自研 Go Tair Client (基于 go-redis 魔改)，核心优化是异步批量发送——不等上一个 Pipeline 响应就发送下一个节点的请求。
4.3 Shard-Aware 路由
问题: Tair Cluster 有 16384 个逻辑 slot，映射到 N 个物理节点。客户端需要知道哪个 key 在哪个节点。

实现:
① 启动时: 执行 CLUSTER SLOTS 命令获取 slot → node 映射表
② 缓存映射表到内存 (Map[slotRange]→node_addr)
③ 每个 key: CRC16(key) % 16384 → 查映射表 → 目标 node
④ 定期刷新映射表 (每 30s，或遇到 MOVED/ASK 重定向时立即刷新)

ASK/MOVED 处理:
Tair 在线扩缩容时，部分 slot 在迁移中。收到 MOVED → 更新映射表 → 重试到新节点。收到 ASK → 临时查询新节点 (不更新映射表)。

Slot Map CRC16 Router
4.4 热 Key 保护
问题: 品牌广告 (如 iPhone 开屏广告) 的特征 key 被所有请求查询，单个 Tair 节点扛不住。

检测:
Ad Server 内维护 HeavyHitter 计数器 (基于 Count-Min Sketch)。每秒统计各 key 的访问频次，超过阈值 (如 10000 QPS) 的 key 标记为热 key。

保护策略:
① L0 延长 TTL: 热 key 在 L0 的 TTL 从 30s 延长到 300s
② 本地复制: 热 key 在 16 个 L0 Cache shard 中全部复制一份，任意 shard 都能命中 (避免单 shard 锁竞争)
③ Tair 侧 LocalCache: Tair Proxy 层对热 key 开启 LocalCache (Tair 自带功能，只读缓存 1s)

效果: 热 key 的 Tair 查询降到几乎为 0。

Feature Assembler — 特征拼接的核心逻辑
5.1 共享-个性化分离策略
精排 500 个候选的特征矩阵 (500 × 200 slots) 中，User + Context 特征对所有候选相同，Ad + Cross 特征每个候选不同。

内存布局:
FeatureBatch { shared_features: Buffer // User+Context, 只存一份 shared_slot_ids: [int] // 共享 slot 的编号列表 per_item_features: Buffer[] // 500 个候选各自的 Ad+Cross per_item_slot_ids: [int] // 个性化 slot 的编号列表 num_candidates: int // 500 }
Model Serving 侧处理:
TF Serving 的 Custom Op 或 Triton 的 Ensemble 负责将 shared 部分 broadcast 到 500 行，拼接 per_item 部分，组成完整的 (500, 200) 输入矩阵。

节省: 共享特征约 80 个 slot，每个 slot 平均 8 Bytes → 80×8=640B。不共享的话 500×640B=320KB；共享后 640B + 指针。内存节省 99.8%。
5.2 缺失处理 (Missing Value Handling)
缺失的三种来源:
① Tair 中无该 key (新用户/新广告)
② Tair 中有 key 但该字段为 NULL (部分字段缺失)
③ Tair 查询超时 (网络/服务异常)

处理策略 (按优先级):

策略 A: 精确默认值
Feature 注册时指定 default_value。
• INT64 默认 0 → Embedding Table 的 slot-0 (可训练的 default embedding)
• FLOAT 默认 -1.0 → 模型学到 -1 意味着缺失
• SEQ 默认 [] → 零向量 / padding

策略 B: 层级回退 (统计类特征)
ad_ctr_7d 缺失 → 查 advertiser_ctr_7d → 查 category_ctr_7d → 全局 global_ctr_7d
回退链在 feature_config 中预配置。

策略 C: 模型侧处理
增加 is_missing 指示特征。Feature Assembler 对缺失 slot 同时设置 value=default 和 is_missing=1。模型学到"当 is_missing=1 时忽略该特征的值"。
5.3 FlatBuffer 零拷贝反序列化
为什么不用 Protobuf？
Protobuf 的反序列化过程: 读取 wire format → 分配内存 → 逐字段解码填充到 struct/class。对一个 200 Bytes 的 value 反序列化需要 ~5μs。500 个候选 × 3 个 Ad View = 1500 次反序列化 → 7.5ms。比整个 Tair 查询还慢。

FlatBuffer 的做法:
不反序列化。value 的 byte buffer 就是最终内存布局。读取字段 = 读 buffer 的固定 offset → O(1)。

// FlatBuffer 读取 (C++, 零拷贝) auto view = GetFeatureView(tair_value_buffer); int64_t gender = view->gender(); // 读偏移量 4 float ctr = view->ctr_7d(); // 读偏移量 12 auto seq = view->click_seq(); // 读指针+长度 // 没有内存分配，没有解码，直接读原始 bytes
性能: 1500 次 FlatBuffer "反序列化" < 0.1ms (vs Protobuf 7.5ms)。

代价: FlatBuffer 的 value 比 Protobuf 大 10~20% (对齐填充)。但在网络 I/O 和存储层面这点开销远低于序列化省下的 CPU。
5.4 序列特征 (SEQ) 的特殊处理
问题: 行为序列特征 (click_ad_seq) 长度不固定，且模型要求固定长度输入。

处理步骤:
① 截断: 序列长度 > max_seq_len (50) → 只保留最近的 50 个
② Padding: 序列长度 < 50 → 末尾用 padding_id=0 填充到 50
③ 生成 mask: valid_len=真实长度，模型用 mask 区分真实元素和 padding

输出:
seq_slot: [ad_23, ad_45, ad_12, ..., 0, 0, 0] // 长度 50 mask_slot: 35 // 真实长度 35, 后 15 个是 padding
Target Attention 特殊处理:
DIN/DIEN 模型的 Target Attention 需要候选广告 embedding作为 Query。Feature Assembler 在填充序列时，同时将当前候选广告的 ad_id 填入一个 target_id slot，让模型知道"用哪个广告做 attention query"。

SIM 长序列优化: 对 1000+ 行为序列，Feature Assembler 先用 Hard Search (品类匹配) 过滤到 Top-K (K=50~100) 相关行为，只填入 K 条。减少模型 Attention 计算量。

广告系统的 SLA 要求 99.99% 可用性。Feature Serving 必须在任何异常下都能返回结果 (哪怕是降级结果)，绝不能阻塞请求。
六层降级策略 (从轻到重)
级别触发条件降级行为影响范围模型效果影响
L1单个 key 查询超时 (>5ms)该 key 使用 default_value，其他 key 正常单条特征几乎无感 (<0.01%)
L2单个 Tair 节点延迟飙升 (P99 >10ms)该节点上的所有 key 使用 default_value；自动将该节点标记为"慢节点"，后续请求跳过直接走 default~1/N 的 key (N=节点数)可控 (<0.5%)
L3单个 Feature View 缺失率 >50%熔断该 View: 所有 key 全部使用 default_value。停止向 Tair 发送该 View 的查询一个完整 View 的所有特征可感知 (0.5~2%)
L4全局 Tair 延迟 P99 >8ms关闭低优先级 View (如 user_interest_tags, ad_embedding)，只保留核心 View (user_profile, ad_meta, user_behavior_seq)~40% 的 Feature View显著 (2~5%)
L5Tair 集群不可用完全依赖 L0+L1 缓存 + OnDemand 特征。L0 命中的部分正常，L0 miss 全部 default除缓存命中外的全部特征严重 (5~15%)
L6Ad Server 内存压力 (OOM 风险)禁用 L0+L1 缓存，只使用 OnDemand + default_value。极端兜底全部远端特征极端 (>15%)
6.1 熔断器实现 (Circuit Breaker)
每个 Feature View 有独立的熔断器。基于滑动窗口计数器:

struct ViewCircuitBreaker { window_size: 10s // 滑动窗口 buckets: 10 // 每秒一个 bucket failure_threshold: 50% // 失败率超过 50% 触发熔断 half_open_after: 30s // 熔断后 30s 尝试半开 half_open_requests: 10 // 半开状态只放行 10 个请求 state: CLOSED | OPEN | HALF_OPEN }
状态转换:
CLOSED (正常) → 失败率超阈值 → OPEN (熔断，全部 default)
OPEN → 等待 half_open_after → HALF_OPEN (试探性放行少量请求)
HALF_OPEN → 试探成功率 >80% → CLOSED (恢复)
HALF_OPEN → 试探仍然失败 → OPEN (继续熔断)

与 Hystrix 的区别: 纯内存实现，没有线程池隔离 (Feature Serving 是嵌入式 SDK，不能创建额外线程池)。通过异步 I/O + 超时控制实现隔离。
6.2 超时预算分配 (Timeout Budget)
精排总延迟预算: ~25ms
其中 Feature Serving: ≤7ms
其中 Model Serving (GPU): ≤15ms
其中网络+调度: ≤3ms

Feature Serving 内部的 7ms 预算再细分:
Config + KeyGen: 0.5ms (硬上限) Parallel I/O: 4.5ms (Tair 超时上限) ├ L0 查询: 0.01ms ├ L1 查询: 0.1ms └ L2 Tair: 4.5ms ← 最大瓶颈 OnDemand 计算: 0.5ms (并行执行) Assemble + 序列化: 1.5ms (硬上限)
自适应超时:
非固定 4.5ms。Feature Serving 监控当前请求已消耗的时间:
• T+3ms 时 Tair 还没响应 → 降低剩余 View 的优先级
• T+5ms 时 Tair 还没响应 → 立即中断等待，使用已返回的部分结果 + default
• 核心 View (user_profile, ad_meta) 的超时比非核心 View 长 1ms

与 Model Serving 的对接 — FeatureBatch 到 GPU 推理
8.1 传输协议
方案一: gRPC + FlatBuffer (字节首选)
Feature Assembler 输出 FlatBuffer 序列化的 FeatureBatch → gRPC 传输到 TF Serving → Custom Op 直接读取 FlatBuffer buffer (零拷贝到 GPU memory)。

方案二: 共享内存 (阿里 PAI-EAS)
Ad Server 和 Model Serving 部署在同一台物理机。FeatureBatch 写入共享内存 (mmap)。Model Serving 通过文件描述符直接访问。省去 gRPC 序列化/反序列化 + 网络传输。
延迟从 0.5ms 降到 <0.05ms。

方案三: RDMA (实验性)
字节部分集群使用 RDMA (Remote Direct Memory Access) 代替 TCP。FeatureBatch 直接 DMA 到 GPU Server 的内存。延迟 <0.1ms。但硬件成本高，仅用于核心模型。

gRPC Shared Memory RDMA
8.2 Embedding 在哪里查表？
Feature Serving 输出的是特征 ID (如 ad_category=23, user_city=110100)，不是 Embedding 向量。Embedding Lookup 发生在 Model Serving 侧。

原因:
① Embedding Table 总量 ~100GB (亿级参数)，存在 GPU 显存/PS 中，Feature Serving 进程无法容纳
② Embedding 是模型参数的一部分，随模型训练更新。如果 Feature Serving 做 Lookup，需要同步模型参数更新
③ GPU 做 Embedding Lookup 比 CPU 快 10 倍+ (gather 操作)

例外: 预训练 Embedding
user_dssm_embedding (双塔预计算的 128d 向量) 和 creative_embedding (ResNet 提取的 128d 向量) 作为 FLOAT 数组存在 Tair 中，由 Feature Serving 直接拉取，不走 Embedding Table。这类特征是"固定向量"，不随模型训练更新。

Feature Serving 输出格式:
slot_01: INT64 → 23 // ad_category ID slot_02: INT64 → 110100 // user_city ID slot_03: FLOAT[] → [0.12, -0.34, ...] // user_embedding 128d slot_04: SEQ_INT64 → [45, 12, 78, ...] // click_seq 50 个 ID
Model Serving 对 slot_01/02/04 做 Embedding Lookup；对 slot_03 直接作为 dense feature 输入 MLP。
