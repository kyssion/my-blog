核心概念 — 什么是 Feature Entity
Feature Entity 是 Feature Store 的核心抽象。它不是一个简单的"表"，而是以业务实体为中心组织特征的元模型(Meta-model)。它定义了"谁(Entity)有什么属性(Feature)，这些属性从哪来(Source)、怎么算(Transform)、存哪里(Store)、怎么服务(Serving)"的完整生命周期。
为什么需要 Feature Entity，而不是直接管理特征表？

传统做法: 算法工程师各自维护 Hive 表 + Redis key，没有统一抽象。
导致的问题: ① 同一个特征不同团队重复开发 (字节曾统计有 30%+ 的特征是重复的)；② 训练/serving 特征不一致无法自动发现；③ 特征血缘不可追踪，上游表变更不知道影响哪些模型；④ 特征缺失/异常无统一监控。

Feature Entity 通过在"特征"上建立统一的元信息层，将特征从"散落的表字段"提升为"有明确定义、来源、生命周期的一等公民"。这是字节 ByteFeature 和阿里 PAI-FeatureStore 的核心设计哲学。
Entity (实体)
业务对象的唯一标识

典型实体:
• User user_id
• Ad ad_id
• Advertiser advertiser_id
• Creative creative_id
• Campaign campaign_id
• App app_id
• AdSlot slot_id

复合实体 (交叉):
• User×Ad
• User×Advertiser
• User×Category
• Ad×Slot
Feature View (特征视图)
挂载在实体上的一组相关特征

一个 Entity 可以有多个 Feature View，每个 View 代表一个特征生产管线的输出。

示例:
User 实体下:
• user_profile 基础画像
• user_behavior 行为序列
• user_realtime_stats 实时统计
• user_embedding 向量特征

每个 View 有独立的:
更新频率、存储策略、TTL、Owner
Feature (特征字段)
Feature View 中的具体字段

属性定义:
• name: 特征名
• dtype: INT64/FLOAT/STRING/EMBEDDING/SEQ
• default_value: 缺失时的默认值
• description: 业务含义
• transform: 处理逻辑 DSL
• emb_dim: Embedding 维度
• bucket_config: 分桶配置
• monitoring: 监控规则

示例:
user_profile.gender → INT64
user_behavior.click_seq → SEQ[INT64]
user_embedding.dssm_vec → FLOAT[128]

元数据模型 — Feature Entity 的完整数据结构
Feature Entity 的元数据存储在 MySQL/PostgreSQL 中，通过 Feature Platform 的管理后台或 SDK 进行注册。以下是字节 ByteFeature 内部的完整元模型结构。
// ========== Entity 定义 ========== Entity { entity_id: INT AUTO_INCREMENT // 实体唯一 ID entity_name: VARCHAR(64) UNIQUE // 如 "user", "ad", "user_x_ad" join_keys: JSON // ["user_id"] 或 ["user_id", "ad_id"] description: TEXT // 业务描述 owner: VARCHAR(64) // 负责团队/个人 created_at: TIMESTAMP updated_at: TIMESTAMP } // ========== Feature View 定义 ========== FeatureView { view_id: INT AUTO_INCREMENT view_name: VARCHAR(128) UNIQUE // 如 "user_profile_v2" entity_id: INT → Entity.entity_id // 归属实体 source_type: ENUM(BATCH, STREAM, ONLINE) // 数据源类型 source_config: JSON // Hive表/Kafka topic/在线计算配置 transform_dsl: TEXT // 特征转换逻辑 (统一 DSL) store_config: JSON // 存储配置 (Tair key模板/TTL/序列化) schedule: VARCHAR(64) // "0 2 * * *" (cron) 或 "realtime" version: INT // 版本号，每次变更自增 status: ENUM(DEV, STAGING, PROD, DEPRECATED) created_by: VARCHAR(64) tags: JSON // ["广告", "用户画像", "核心"] } // ========== Feature 字段定义 ========== Feature { feature_id: INT AUTO_INCREMENT view_id: INT → FeatureView.view_id feature_name: VARCHAR(128) // 如 "gender", "age_bucket" dtype: ENUM(INT64, FLOAT32, FLOAT64, STRING, EMBEDDING, SEQ_INT64, SEQ_FLOAT, MAP) default_value: VARCHAR(256) // 缺失填充值 transform: TEXT // 字段级转换: "BUCKET(age, [18,25,35,45])" emb_dim: INT NULL // Embedding 维度 (仅 ID/SEQ 类型) emb_hash_bucket: INT NULL // Hash 桶数 max_seq_len: INT NULL // 序列最大长度 (仅 SEQ 类型) monitoring: JSON // {"psi_threshold":0.25, "missing_rate_max":0.3} description: TEXT importance: FLOAT NULL // 模型中的特征重要性 (定期自动回填) } // ========== Feature View 与 Model 的绑定 ========== ModelFeatureBinding { model_id: VARCHAR(128) // 模型唯一标识 view_id: INT → FeatureView.view_id feature_ids: JSON // 该模型使用的 Feature IDs slot_mapping: JSON // feature_id → model_slot_id 映射 created_at: TIMESTAMP }
关键设计决策说明

① 为什么 Entity 和 Feature View 分离？
同一个 User 实体可以有 10+ 个 Feature View (画像、行为序列、实时统计、embedding...)，每个 View 有不同的更新频率和 Owner。分离后可以独立管理生命周期——下线一个 View 不影响其他 View。

② 为什么有 version？
特征逻辑变更 (如 age 分桶边界调整) 会产生新版本。旧模型继续使用旧版本，新模型使用新版本。通过 version 实现特征的平滑迁移，避免"改一个特征崩所有模型"。

③ join_keys 复合实体设计
交叉特征 (如 user×ad 的曝光次数) 需要复合 key。join_keys=["user_id","ad_id"] 意味着这个 Entity 的 KV key 是两个 ID 的拼接。在线 serving 时需要对每个候选广告动态拼接 key。

④ transform_dsl 统一表达
字节 ByteFeature 使用自研 DSL (类 SQL 语法)，如: SELECT BUCKET(age,[18,25,35,45]) AS age_bucket, COUNT(click) OVER (SLIDING 1h) AS click_1h FROM user_events
这段 DSL 同时编译为 Spark UDF (离线) 和 C++ 算子 (在线)，从根源保证训练-serving 一致性。

特征注册流程 — 从定义到上线的完整工作流
特征上线全流程 (字节内部实践，通常 2~5 天)
Step 1: 需求评审 算法 + 工程
├ 算法工程师提出特征需求 (特征名、业务含义、预期收益)
├ 评估是否已有同类特征可复用 (查特征市场)
└ 确定特征 Entity 归属、更新频率、存储预算

Step 2: 特征注册 Feature Platform SDK / Web UI
├ 通过 SDK 或管理后台填写 Entity → FeatureView → Feature 三层定义
├ 编写 Transform DSL (特征加工逻辑)
├ 配置 KV key 模板、序列化格式、TTL、默认值
└ 自动生成 feature_config.pb (模型侧引用配置)

Step 3: 数据验证 自动化
├ 离线回放: 用历史数据跑 Transform DSL，验证输出值域和分布
├ Schema 检查: dtype 与上游数据源类型匹配
├ 一致性测试: 对同一批数据分别跑离线链路和在线链路，对比输出 diff < 0.01%
└ 穿越检测: 检查 Transform 中是否引用了未来时间点的数据

Step 4: 离线评估 自动化 AB
├ 将新特征加入训练样本，重训模型
├ 对比 AUC/GAUC/NDCG 等离线指标提升
└ 特征重要性 (Gain/SHAP) 排名，确认新特征有正向贡献

Step 5: 灰度上线 AB 实验平台
├ Feature View status: DEV → STAGING (灰度 5% 流量)
├ 观察在线指标: CTR/CVR/RPM 变化、特征缺失率、延迟
├ 通过后扩量: STAGING → PROD (100% 流量)
└ 失败自动回滚: 监控到指标恶化 → 自动切回旧特征版本

Step 6: 持续运维 自动化监控
├ PSI 漂移监控 (每日自动计算)
├ 缺失率/覆盖率日报
├ 定期特征裁剪 (重要性低于阈值的特征标记 DEPRECATED)
└ 血缘追踪: 上游表变更自动通知下游模型 Owner

Transform DSL 引擎 — 一份代码，两条链路
Transform DSL 是 Feature Entity 体系中保证训练-serving 一致性的核心技术。一段 DSL 声明式地描述特征加工逻辑，由编译器自动生成离线代码 (Spark/Flink) 和在线代码 (C++/Go)。
DSL 编译器架构
Transform DSL 源码 (统一声明式语法)
↓ Parser → AST (抽象语法树)
↓ 语义校验: 类型检查、函数签名校验、时间窗口合法性
↓ 优化: 常量折叠、公共子表达式消除

分支编译 (Code Generation):
├─→ Spark UDF (Java/Scala) → 离线批计算链路 (T+1)
├─→ Flink Operator (Java) → 近线流计算链路 (分钟级)
├─→ C++ Operator → 在线 Ad Server 嵌入式计算 (毫秒级)
└─→ Python UDF → 训练样本拼接 (样本工厂)

DSL 一致性校验机制
① 编译期校验
DSL Parser 对每个算子做强类型检查。如 BUCKET(x, ...) 要求 x 为数值类型，编译期报错而非运行时。

② 单元测试自动生成
注册时平台自动用历史数据生成 100 条 test case，分别跑 Spark UDF 和 C++ Operator，assert 输出完全相同。

③ 在线 shadow 模式
新版本 DSL 上线前，在线服务同时跑新旧两个版本 (旧版本作为实际输出，新版本仅计算不使用)，对比输出 diff。连续 24h diff < 0.01% 才允许切换。

④ 定期回放校验
每周自动抽样 1% 在线请求，用离线链路重算特征值，与在线 serving 的实际值对比。diff > 0.1% 触发 P1 告警。

DSL Compiler Shadow Runner Consistency Checker
字节内部的一个真实案例: 某团队手动在 C++ serving 代码中将 age 分桶实现为 age/10 (整除)，但离线 Spark 中用了 BUCKET(age,[0,18,25,35,45,55]) (不等宽)。这个不一致导致线上 CTR 模型的 AUC 比离线低了 0.8%，直到 3 个月后才被发现。这是推动 ByteFeature DSL 引擎立项的直接原因。
4
存储架构 — Feature Entity 的多层存储体系
Feature Entity 的特征值最终需要存储在高性能 KV 系统中供在线 serving 使用。但不同时效性的特征有不同的写入和读取模式，因此需要分层存储。
4.1 KV key 设计规范
Key 模板: {namespace}:{view_abbr}:{entity_keys}

具体示例:
uf:profile:123456 → User#123456 的画像特征
uf:stats:123456 → User#123456 的统计特征
af:meta:789012 → Ad#789012 的基础属性
cf:uxad:123456_789012 → User×Ad 交叉特征
af:emb:789012 → Ad#789012 的 embedding

命名空间: uf=user feature, af=ad feature, cf=cross feature, sf=slot feature

Value 序列化: FlatBuffer (字节首选，零拷贝反序列化) 或 Protobuf (阿里首选)。一个 key 对应一个 Feature View 的所有字段打包在一起，避免多次 KV 查询。
4.2 存储分层策略
层级技术容量延迟用途
L0 进程内LRU Cache
(Go sync.Map /
C++ unordered_map)		~100K key
~500MB		<0.01ms热门广告特征、高频用户
L1 本机RocksDB
(嵌入式 KV)		~50GB
SSD		<0.1ms当日活跃用户画像预热
L2 分布式Tair / Redis Cluster
(ByteKV / ABFS)		~10TB
分布式内存		0.5~2ms
(同机房)		全量在线特征存储
L3 离线Hive / HDFS
/ OSS		~PB 级秒~分钟训练数据、历史快照

读取路径: L0 miss → L1 miss → L2 查询 → 填充 L0/L1
写入路径: 离线 BulkLoad → L2 ; 近线 Flink → L2 ; 热 key 预热 → L1
Tair/ByteKV 集群的典型配置 (字节 DSP 线上规模)

集群规模: 200+ 节点，总内存 ~20TB，支撑 ~5 亿 key
读 QPS: 峰值 ~2000万/s (Pipeline MGet 合并后)
写 QPS: 离线批量导入 ~50万/s (凌晨)，近线写入 ~100万/s (全天)
P99 延迟: Get <1ms, MGet(100key) <2ms (同机房)，跨机房 <5ms
数据分片: 按 entity_key 一致性 Hash 分片，同一用户的所有特征落在同一分片
过期策略: 离线特征 TTL=30d，近线特征 TTL=1~7d，在线特征不持久化
序列化: FlatBuffer (同一 Feature View 的所有字段打包为一个 value)，单个 value 平均 ~200 Bytes，最大 ~10KB (含行为序列)
4.3 离线批量导入 (BulkLoad)
流程:
Spark Job 输出 → SST 文件 (Tair 底层格式) → 直接 Ingest 到 Tair

优势: 绕过 Tair 的写入链路，直接写底层存储引擎，吞吐提升 10 倍+

全量 vs 增量:
• 全量: 每天凌晨 2:00~5:00，重建全量用户画像 (~5亿 key)，耗时 ~2h
• 增量: 每天 6:00~8:00，仅更新当天有行为的用户 (~5000万 key)，耗时 ~20min

双缓冲切换: 写入到 shadow 表 → 验证通过 → 原子切换指针，对线上零影响

4.4 近线流式写入
流程:
Kafka → Flink 窗口聚合 → Micro-batch 写入 Tair

写入优化:
• Flink Sink 使用 Micro-batch (每 5s 攒批) 而非逐条写入
• Pipeline 模式批量 MSet，单批 1000~5000 key
• 写入限流: 峰值 QPS 限制，防止打爆 Tair

幂等写入:
Flink checkpoint + Tair CAS (Compare And Swap) 保证 exactly-once

近线覆盖离线:
同一个 key 的值以最新写入为准 (last-write-wins)。近线特征的 TTL 短于离线特征，过期后自动回退到离线版本

在线 serving 架构 — Feature Entity 如何服务一次广告请求
在线 serving 是 Feature Entity 对外的核心接口。Ad Server 的 Feature Assembler 模块根据 Entity + Feature View 定义，自动拼接特征。
Feature Assembler 处理一次精排请求的完整时序
T+0ms — 请求到达 解析 Bid Request
├ 提取 device_id → 查 OneID mapping → user_id = "U123456"
├ 提取候选广告列表: [ad_001, ad_002, ..., ad_500] (精排 500 条)
└ 提取上下文: app_id, slot_id, timestamp, ip, geo

T+0.5ms — 构造 KV key 集合 (Feature Key Generator)
├ 遍历模型的 ModelFeatureBinding，获取所需 Feature View 列表
├ User Entity keys (固定，不随候选变化):
│ "uf:profile:U123456", "uf:stats:U123456",
│ "uf:seq:U123456", "uf:emb:U123456" → 4 keys
├ Ad Entity keys (每个候选一组):
│ "af:meta:{ad_id}", "af:stats:{ad_id}",
│ "af:emb:{ad_id}" → 500 × 3 = 1500 keys
├ Cross Entity keys (每个候选一组):
│ "cf:uxad:U123456_{ad_id}",
│ "cf:uxadv:U123456_{adv_id}" → ~1000 keys
└ 总计: ~2500 keys (去重后)

T+1ms — 并行 MGet (异步 I/O)
├ L0 LRU Cache 命中: ~60% (热门广告的 af:* key)
├ L1 RocksDB 命中: ~25% (当日活跃用户的 uf:* key)
├ L2 Tair Pipeline MGet: 剩余 ~375 keys → 一次网络往返
└ 同一 Tair 分片的 keys 合并为一个 MGet 命令 (通常 3~5 个分片)

T+4ms — 反序列化 + 特征提取
├ FlatBuffer 零拷贝反序列化 (不需要内存分配)
├ 从每个 View 的 value 中提取需要的 Feature 字段
└ 对 SEQ 类型字段做截断 (max_seq_len) 和 padding

T+5ms — 在线特征计算 (Context Features)
├ HOUR_OF_DAY(timestamp) → hour_bucket
├ GEOHASH(lat, lng, 5) → geohash_code
├ 竞价景观: 候选广告数量、出价分布统计
└ Transform DSL (在线版) 执行 C++ 算子

T+6ms — 特征拼接 (Slot Assignment)
├ 按 ModelFeatureBinding.slot_mapping 将每个特征值分配到对应 slot
├ 共享特征 (User + Context): 只填充一份，500 条样本复用指针
├ 个性化特征 (Ad + Cross): 每条样本独立填充
├ 缺失值处理: 按 Feature.default_value 填充
│ → INT64 缺失: 填 0 (映射到 default embedding)
│ → FLOAT 缺失: 填 -1.0 (模型学习到 -1 意味着缺失)
│ → 统计类缺失: 层级回退 (ad→advertiser→category→global)
└ 输出: FeatureBatch (FlatBuffer 序列化的 500 × N_slots 矩阵)

T+7ms — 发送到模型 serving
└ gRPC 发送 FeatureBatch → TF Serving / Triton → 返回 pCTR/pCVR
Feature Assembler 核心优化
① 预取 (Prefetch)
用户特征在请求进入的第一毫秒就启动异步拉取，与 OneID mapping、流量过滤并行执行。等到精排需要特征时，用户特征已就绪。

② 共享特征零拷贝
User + Context 特征在 500 个样本中完全相同。Feature Assembler 只存一份，模型 serving 侧通过 broadcast 机制复用，避免 500 倍内存放大。

③ Key 批量合并
将落在同一 Tair 分片的 keys 合并为一个 Pipeline MGet 命令。假设 10 个分片，2500 keys 变成 10 次 MGet (每次 ~250 key)，总网络往返只有 1~2 次 (并行)。

④ 热 key 保护
头部广告的 key 极热 (如品牌广告)，L0 缓存命中率 >99%。对 Tair 侧做热 key 自动识别 + 本地缓存复制，防止单分片过载。
降级与容错策略
① Tair 超时降级
MGet 设置 5ms 超时。超时后放弃未返回的 key，使用 default_value。线上观测: Tair P99.9 偶发 >5ms (毛刺)，但特征缺失对单次请求影响可控。

② Feature View 级别熔断
如果某个 View (如 user_realtime_stats) 的缺失率突增 >50%，自动熔断该 View，全部使用 default_value。防止上游 Flink 故障导致模型效果雪崩。

③ 离线特征兜底
近线特征 TTL 过期后，自动回退到离线版本。设计原则: 离线特征的 TTL 必须长于近线特征。

④ 全局降级开关
极端情况 (Tair 集群不可用): 关闭远端特征拉取，仅使用在线计算的 Context 特征 + L0/L1 缓存的用户特征。模型效果下降但服务不中断。

Circuit Breaker Fallback Manager
6
训练集成 — Point-in-time Join 与样本工厂
Feature Entity 不仅服务在线 serving，也服务离线训练。核心挑战是：训练样本的特征值必须是"事件发生时刻"的特征值，而非"现在"的值。这就是 Point-in-time Join。
6.1 Point-in-time Join 原理
问题场景:
样本: 用户 U1 在 T=10:05 点击了广告 A1
训练需要 T=10:05 时刻 U1 的特征值 (而非当前的)

错误做法:
直接用最新的 user_profile 表 join，拿到的是 T+1 的值 → 特征穿越

正确做法 (Point-in-time Join):
对每条样本的 event_time，找到该时刻之前最近的特征快照

SELECT s.*, f.* FROM samples s ASOF JOIN feature_snapshots f ON s.user_id = f.user_id AND f.snapshot_time <= s.event_time ORDER BY f.snapshot_time DESC LIMIT 1

阿里 PAI-FeatureStore 原生支持 ASOF JOIN 语义，自动处理时间对齐。
字节 ByteFeature 的样本工厂 (Sample Factory) 实现了同样功能。
6.2 样本工厂 (Sample Factory)
完整流程:

① Label 生成:
曝光日志 (T) + 点击日志 (T+Δ) + 转化日志 (T+Δ') → Flink Interval Join → 带 label 的样本骨架 (user_id, ad_id, event_time, click, convert)

② 特征回填:
样本骨架 × Feature Entity 的离线快照 → Point-in-time Join → 完整训练样本

对每个 Feature View:
• 离线 View: 用当天 (或前一天) 的 Hive 分区 join
• 近线 View: 用 Flink 输出的分钟级快照 (存在 HDFS 的 mini-batch 文件) join
• 在线 View: 用请求日志中的 Context 字段直接填充 (无需 join)

③ 样本输出:
TFRecord / Parquet 格式 → HDFS → 模型训练 Pipeline

Flink Join Spark PIT Join HDFS
近线特征的 Point-in-time Join 难点

近线特征 (如 user_click_1h) 是分钟级更新的，不像离线特征有明确的日分区。解决方案: Flink 在输出到 Tair 的同时，将每个窗口的聚合结果同步写一份到 HDFS (Mini-batch Snapshot，按 5min 分片)。样本工厂在做 PIT Join 时，找到 event_time 所在的 5min 区间，取对应快照。

字节的实现: Flink Sink 双写 (Tair + HDFS Parquet)，HDFS 端按 view_name/dt=2024-01-15/hh=10/mm=05/ 路径组织，支持高效的时间范围查找。

7.4 特征生命周期管理
状态机:
DEV → STAGING → PROD → DEPRECATED → DELETED

自动化策略:
• DEV → STAGING: 通过数据校验 + 离线评估后自动流转
• STAGING → PROD: 灰度 AB 实验通过后人工审批
• PROD → DEPRECATED: 90天无 Model 引用 → 自动标记
• DEPRECATED → DELETED: 标记后 30天，Owner 不反对则自动删除

版本管理:
每次 Transform DSL 变更产生新 version。旧 version 不删除，直到所有引用的 Model 迁移到新 version。支持一键回滚到任意历史 version
