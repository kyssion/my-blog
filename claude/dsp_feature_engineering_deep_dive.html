2
特征处理 — 原始数据到模型输入的转换
特征不能直接喂给模型，需要经过一系列处理将异构数据 (ID、数值、文本、序列) 统一编码为模型可消费的数值向量。
2.1 ID 类特征 → Embedding 查表
处理方式: Hash(ID) % bucket_size → Embedding Table Lookup → 向量

适用特征: user_id, ad_id, advertiser_id, campaign_id, creative_id, app_id, slot_id, category_id, brand_id, city_id, device_model 等

关键参数:
• Embedding 维度: 通常 8~64d，高频 ID 用大维度
• Hash 桶数: 10M~100M (user_id)，1M~10M (ad_id)。Hash 冲突率控制在 <5%
• 字节方案: Monolith 支持动态 Embedding，低频 ID 自动淘汰；阿里方案: XDL 支持千亿级稀疏参数

冲突处理: 多 Hash 函数 + 残差补偿网络 (DCN-V2 中的 Mixed-dimension Embedding)
Embedding Table PS/GPU
2.2 数值型特征 → 离散化 / 归一化
方式一: 等频分桶 (推荐)
按分位数切 10~50 个桶。如 age: [0-18, 18-25, 25-35, 35-45, 45+] → bucket_id → Embedding

方式二: 等宽分桶
固定步长切分，适用于分布均匀的特征 (如 hour_of_day)

方式三: 对数变换 + 归一化
price, impression_count 等长尾分布特征: log(1+x) → MinMaxScaler → [0,1]

方式四: 自动分桶 (AutoDis)
字节在 DLRM 中用可学习的分桶边界，端到端训练

处理后: 分桶 ID → Embedding 查表 (与 ID 类特征统一处理)
Bucketizer AutoDis
2.3 序列特征 → Pooling / Attention
行为序列处理管线:
原始序列 [item_id_1, item_id_2, ..., item_id_N]
↓ 每个 item_id → Embedding Lookup → N × d 矩阵
↓ 附加位置编码 + 时间衰减权重
↓ Pooling 策略 (二选一):

Average Pooling: 简单平均，粗排常用
Target Attention: 以候选广告为 Query，序列中每个 item 为 Key/Value，计算注意力加权和。DIN 核心机制，精排必用

长序列优化 (SIM/SDIM):
用户行为序列 > 1000 条时，先用 Hard Search (类目/品牌匹配) 或 Soft Search (embedding 近邻) 筛出 Top-K 相关行为 (K=50~100)，再做 Attention
DIN/DIEN SIM
2.4 多值/集合特征 → Multi-hot Embedding
适用场景: 用户兴趣标签列表、App 安装列表、搜索关键词集合等

处理方式:
[tag_1, tag_2, ..., tag_K] → 每个 tag Embedding Lookup → K × d 矩阵 → Sum/Mean Pooling → 1 × d 向量

带权版本:
每个 tag 有置信度分数: [(tag_1, 0.9), (tag_2, 0.7), ...]
→ Weighted Sum Pooling: Σ(weight_i × embedding_i)

注意: 需做截断，保留 Top-K 高权重标签 (K=20~50)，避免 padding 过长影响效率
Multi-hot Weighted Pool
2.5 文本特征 → 预训练 Embedding
广告标题/描述: 离线通过 BERT/SentenceTransformer 提取句向量 (64~256d)，存入特征 KV

搜索 Query: 在线实时 tokenize → 轻量 Bi-Encoder 推理 → 64d 向量

关键词集合: 分词后转 Multi-hot Embedding (同 2.4)

字节方案: 自研 ByteTransformer 做文本编码，推理耗时 < 2ms
阿里方案: M6 多模态预训练模型统一处理文本 + 图像
BERT ByteTransformer
2.6 交叉特征 → 显式 / 隐式交叉
显式交叉 (离线预计算):
• user_city × ad_category → 拼接后 Hash → Embedding
• user_gender × hour_of_day → 拼接后 Hash → Embedding
• 只做少量 (5~10 组) 业务先验强的交叉

隐式交叉 (模型内学习):
• DCN-V2: Cross Network 自动学习高阶交叉
• AutoInt: Multi-head Self-Attention 做特征交叉
• CAN (Co-Action Network): 阿里提出的参数化交叉

原则: 离线做确定性强的交叉，模型内做探索性交叉
DCN-V2 CAN
特征处理统一视角: 不论原始类型，最终所有特征都转化为 Embedding 向量，然后 Concat 成一个大向量 (通常 200~500d)，输入 DNN 上层网络。这就是 "Embedding + MLP" 范式的核心思想。字节在 Monolith 论文中明确提到，他们的特征处理层统一为 Embedding Layer → Interaction Layer → MLP Layer 三层架构。
3
特征处理的关键注意点 — 踩坑与防线
3.1 训练-serving 一致性 (最重要)
问题: 训练时用离线 Hive 数据处理特征，serving 时用在线 C++/Go 处理，两套代码逻辑不一致导致特征值偏差 → 模型效果线下好线上差

解决方案 (字节 ByteFeature):
• 特征处理逻辑统一注册，生成 DSL (领域特定语言)
• DSL 同时编译为 Spark UDF (离线) 和 C++ 算子 (在线)
• 自动化一致性校验: 定期抽样对比离线/在线特征值，diff > 0.1% 报警

解决方案 (阿里 PAI-FeatureStore):
• Feature Transform 定义一次，自动生成离线 (MaxCompute) + 在线 (ABFS) 双链路代码
• 用 "Point-in-time Join" 确保训练样本的特征值与当时 serving 一致
3.2 特征穿越 (Feature leakage)
问题: 训练时误用了 "未来信息"。典型: 用 T 时刻的统计特征预测 T 时刻的点击行为

常见穿越场景:
• 用当天全天 CTR 训练当天样本 (应该用截至当前请求时刻的 CTR)
• 样本拼接时用了点击/转化后才产生的特征
• 近线特征窗口包含了标签事件本身

防御手段:
• 样本拼接严格按时间戳 join (Point-in-time Join)
• Flink 窗口设置 "水位线" (watermark)，确保窗口关闭后才输出
• 离线回放校验: 随机抽 1% 样本，用请求时刻重算特征，与训练特征对比
3.3 特征缺失 & 默认值
问题: 新用户/新广告没有历史数据，特征缺失率可达 10~30%

策略:
• ID 类缺失: 使用默认 Embedding (全局均值或可训练的 default embedding)。字节 Monolith 中每个 Embedding Table 有一个 slot-0 作为 default
• 数值类缺失: 填中位数或全局均值 + 增加 "is_missing" 二值指示特征
• 统计类缺失 (冷启动): 用上级粒度平滑。如广告无 CTR → 用广告主 CTR → 用品类 CTR → 全局 CTR。层级回退
• 序列类缺失: 空序列 → 零向量 or 全局平均 embedding
3.4 特征稳定性 & 监控
问题: 特征分布漂移 (data drift) 导致模型效果衰减

监控指标:
• PSI (Population Stability Index): 对比训练集 vs 线上分布，PSI > 0.25 报警
• 缺失率: 超过历史均值 2 倍报警
• 覆盖率: 特征非零值占比突降报警
• 值域异常: 出现超出训练集 min/max 的极端值报警

字节实践: ByteFeature 内置特征质量看板，自动计算每个特征的日级 PSI，超阈值触发 PagerDuty 告警并自动回滚到上一版本特征
3.5 特征维度爆炸 & 效率
问题: 千万级广告 × 亿级用户 → 交叉特征空间爆炸

控制手段:
• Hash Trick: 限定桶数 (如 user_id Hash 到 10M 桶) 控制参数量
• 特征裁剪: 定期通过特征重要性 (Gain/SHAP) 淘汰低价值特征。字节每月做一次全量特征评估
• Embedding 维度自适应: 高频 ID 用 32d，低频用 8d (Mixed-dimension Embedding)
• 量化压缩: FP32 → FP16/INT8 embedding，内存减半性能几乎无损
3.6 样本拼接延迟 & 归因窗口
问题: 点击发生在曝光后几秒，转化可能在几天后，样本何时 "关闭"？

样本拼接管线:
• 曝光日志 (立即产生) → Kafka
• 点击日志 (延迟 ~秒) → Kafka
• 转化日志 (延迟 ~小时/天) → Kafka
• Flink 用 Event Time + 归因窗口做 Interval Join:
- 点击归因: 曝光后 30min 内的点击
- 转化归因: 点击后 7d / 曝光后 1d

延迟标签: 转化延迟样本用 "延迟反馈模型" (DFM/ESDF) 修正 CVR 估计偏差
字节内部经验: 线上效果问题 80% 是特征问题。模型架构迭代带来的增益通常是 0.1~0.5%，而特征 bug (穿越、不一致、缺失) 造成的损失可以达到 5~10%。因此特征工程的 "防守" (一致性、监控、回滚) 比 "进攻" (新特征) 更重要。
4
工程架构 — Feature Store 全景
Feature Store 是特征工程的核心基础设施，承担特征的定义、生产、存储、服务、监控全生命周期管理。
4.1 离线特征生产管线 (Batch Pipeline)
用户行为日志 (HDFS) + 广告元数据 (MySQL) + 转化日志 (Hive)
↓ 调度: Airflow DAG, 每天 02:00~06:00 执行
Spark SQL / PySpark 特征加工 (聚合、分桶、交叉)
↓ 输出: 特征 Hive 表 (分区: ds=日期)
Spark BulkLoad / DataX 批量导入在线存储
↓
Tair (阿里) / ByteKV (字节) — KV 存储，key = feature_name:entity_id，value = 序列化特征值
全量导入 + 增量 merge，TTL = 30d，写入 QPS 峰值 ~500K/s
4.2 近线特征生产管线 (Streaming Pipeline)
客户端埋点 SDK → 数据采集 (Scribe/LogAgent)
↓
Kafka Topic (行为日志: 点击/浏览/搜索/转化，QPS 峰值 ~10M/s)
↓
Flink Job 集群 — 特征实时聚合
• 窗口函数: Sliding(30min, 5min), Tumbling(1h, 6h, 1d)
• 聚合算子: COUNT, SUM, AVG, DISTINCT_COUNT, TOP_K, LAST_N
• Embedding 更新: 增量 Average (加权) 更新用户兴趣向量
↓ Sink: 异步批量写入 (micro-batch 5s)
Tair / Redis Cluster — 与离线特征使用相同 KV 命名空间
近线特征 TTL 较短 (1~7d)，覆盖离线同名特征 (新值优先)
4.3 在线特征服务 (Online Serving)
Bid Request 到达 Ad Server
↓ Step 1: 请求解析 + 在线特征实时计算 (~1ms)
• 解析 device_id → OneID 映射 (本地 LRU Cache 命中率 ~90%，miss 查 Tair)
• 提取 context 特征: 时间分桶、设备信息、地理编码
• 计算在线统计: 竞价景观、预算实时余额
↓ Step 2: 批量拉取远端特征 (~5-8ms)
Feature Serving 模块 根据 user_id + candidate_ad_ids 批量构造 keys
↓ 并行 MGet (Pipeline 模式)
Tair/Redis Cluster — 一次 MGet 拉取该用户所有特征 (通常 50~100 个 key)
• P99 延迟 < 3ms (同机房)
• 本地 LRU Cache: 热 key 命中率 > 85%，大幅降低远端访问
↓ Step 3: 特征拼接 + 编码 (~2ms)
Feature Assembler
• 按模型配置 (feature_config.pb) 指定的顺序拼接特征
• 缺失填充: 根据配置选择 default_value / 上级粒度回退
• 序列化为 FlatBuffer / Protobuf 传给模型 Serving
↓
模型推理 (TF Serving / Triton) — Embedding Layer 接收特征 ID，进行查表 + 前向传播
Feature Serving 的核心优化技巧

① 批量化 (Batching): 精排有 200~500 个候选广告，每个需要拉取广告特征。将所有广告 ID 的特征 key 合并为一次 MGet，而非逐条查询。一次 MGet 500 个 key 的耗时 ≈ 一次 Get 1 个 key。

② 用户特征只拉一次: 用户特征对所有候选广告相同，只拉取一次缓存在内存中。广告特征按候选集动态拉取。上下文特征在线计算不需要远端访问。

③ 预取 (Prefetch): 在召回阶段就启动用户特征的异步拉取，与召回计算并行。等到特征拼接阶段时，用户特征已就绪。字节的做法是在请求进入时立刻启动一个 goroutine 拉取用户特征。

④ 本地缓存分层: L1 = 进程内 LRU (Go sync.Map / C++ LRUCache，容量 ~100K key)，L2 = 本机 RocksDB (SSD)，L3 = Tair/Redis。热门广告特征可以在 L1 命中 > 95%。

⑤ 特征压缩: Embedding 使用 FP16 存储 (vs FP32)，序列特征截断到 Top-K，多值特征只保留 Top-20 高权重标签。总特征传输量控制在每请求 < 10KB。
5
特征拼接实战 — 一次请求中的完整拼接流程
以精排阶段为例，展示一个请求中 500 个候选广告如何完成特征拼接。
精排特征拼接时序 (单次请求，~10ms)
T+0ms — 请求到达，解析 Bid Request
├ 提取 device_id, ip, ua, app_id, slot_id, geo
├ device_id → OneID 映射 (本地 Cache 查询)
└ 在线 Context 特征就地计算 (hour_bucket, device_type, network_type, geohash)

T+1ms — 并行启动两个异步任务
├ 任务 A: MGet 用户特征 (50~80 个 key)
│ → user_profile, user_tags, user_embedding, user_behavior_seq,
│ user_stats_1h, user_stats_6h, user_stats_7d, crowd_bitmap
└ 任务 B: MGet 广告特征 (500 个候选 × 5~8 个特征 ≈ 2500~4000 key)
→ ad_meta, ad_embedding, ad_stats, creative_embedding, quality_score

T+5ms — 用户特征 + 广告特征就绪
├ MGet 交叉特征 (user×advertiser, user×category, user×ad 曝光次数)
└ 按 feature_config 规定的 slot 顺序组装特征向量

T+8ms — 特征拼接完成，构造模型输入
├ 共享特征 (用户 + 上下文): 所有候选共用 1 份，不重复拷贝
├ 个性化特征 (广告 + 交叉): 每个候选独有
├ 缺失特征填充 default value
└ 序列化为 FlatBuffer batch (500 条样本 × ~200 个特征 slot)

T+9ms — 发送到 TF Serving / Triton GPU 推理
└ Embedding Lookup + DNN Forward，返回 500 个 pCTR/pCVR 分数
Feature Config (特征配置表) 示例
特征配置是一个 Protobuf 文件，定义了模型期望的每个特征 slot:

slot_id: 1 | name: "user_gender" | type: ID | source: TAIR | key_tpl: "uf:gender:{user_id}" | default: 0 | emb_dim: 4
slot_id: 2 | name: "user_age_bucket" | type: ID | source: TAIR | key_tpl: "uf:age:{user_id}" | default: 0 | emb_dim: 8
slot_id: 3 | name: "user_city" | type: ID | source: TAIR | key_tpl: "uf:city:{user_id}" | default: 0 | emb_dim: 16
slot_id: 10 | name: "user_behavior_seq" | type: SEQ | source: TAIR | key_tpl: "uf:seq:{user_id}" | max_len: 50 | emb_dim: 32
slot_id: 20 | name: "ad_category" | type: ID | source: TAIR | key_tpl: "af:cat:{ad_id}" | default: 0 | emb_dim: 16
slot_id: 30 | name: "hour_of_day" | type: ID | source: ONLINE | default: 0 | emb_dim: 8
slot_id: 40 | name: "user_x_advertiser_ctr" | type: FLOAT | source: TAIR | key_tpl: "cf:ua_ctr:{user_id}_{adv_id}" | default: -1

每个 slot 定义了特征名、类型、来源、KV key 模板、默认值、Embedding 维度。Feature Assembler 遍历此配置，逐 slot 填充值。

特征平台核心能力 (字节 ByteFeature)
特征注册中心: 统一元信息管理，每个特征有唯一 ID + 版本 + Owner + 血缘关系
DSL 引擎: 一份逻辑定义，编译为离线 Spark UDF + 在线 C++ 算子
特征市场: 跨团队特征共享与复用，避免重复开发
AB 实验集成: 特征与模型绑定实验分桶，支持灰度上线
自动化回测: 新特征上线前自动跑离线 AUC/GAUC 评估
特征平台核心能力 (阿里 PAI-FeatureStore)
Feature Entity: 以实体 (User/Item/Context) 为中心组织特征
Feature View: 特征逻辑视图，自动生成离线 + 在线双链路
Point-in-time Join: 训练样本自动按事件时间拼接历史特征，防穿越
ABFS (阿里巴巴特征服务): 在线特征服务，P99 < 2ms
特征血缘追踪: 从数据源 → 特征表 → 模型的全链路血缘
特征拼接延迟预算: 总计 ≤10ms | OneID 映射 ~1ms | 用户特征 MGet ~3ms (并行) | 广告特征 MGet ~3ms (并行) | 交叉特征 MGet ~2ms | 拼接编码 ~1ms
