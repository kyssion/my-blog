已确认 来源: Feast 开源代码中，Entity 和 FeatureView 是平级的 Python class，FeatureView 通过 entities 字段引用 Entity。阿里 PAI-FeatureStore 文档中也是相同结构。三者不是嵌套关系，而是通过外键关联的平级对象。
1
Feature Entity — 极简的主键定义
Entity 的职责只有一件事：定义一个业务对象的唯一标识方式。它不包含任何特征定义、计算逻辑或存储配置。
已确认 Feast 源码 + 阿里 PAI-FeatureStore 文档 // ===== Entity 数据结构 ===== // 来源: Feast sdk/python/feast/entity.py + 阿里 PAI-FeatureStore API Entity { name: STRING // 实体名称，全局唯一 // 例: "user", "ad", "advertiser" join_keys: LIST[STRING] // 主键字段名列表 (关联特征时的 JOIN key) // 单主键: ["user_id"] // 复合主键: ["user_id", "advertiser_id"] description: STRING // 可选，业务描述 owner: STRING // 可选，负责人 tags: MAP[STRING, STRING] // 可选，自定义标签 }
纠正前面的错误: 之前 "Feature Entity 全解" 中，我将 FeatureView、Feature、ModelFeatureBinding 的完整数据模型都放在了 Entity 的元模型中展示。这是错误的。Entity 本身就只有上面这几个字段。它是整个 Feature Store 中最简单的对象。
Entity 的实际 MySQL 表
合理推断 表结构基于 Feast schema 推导 CREATE TABLE entities ( id BIGINT AUTO_INCREMENT PRIMARY KEY, project_id BIGINT NOT NULL, -- 多租户隔离 name VARCHAR(64) NOT NULL, join_keys JSON NOT NULL, -- ["user_id"] description TEXT, owner VARCHAR(128), tags JSON, created_at TIMESTAMP DEFAULT NOW(), updated_at TIMESTAMP, UNIQUE (project_id, name) );
就这些。没有 source_config，没有 transform_dsl，没有 store_config。那些全部属于 Feature View。

Feature View — 真正的重量级对象
Feature View 是 Feature Store 中信息密度最高的对象。它定义了一条完整的特征管线——数据从哪来、怎么算、存哪里、多久更新、输出哪些字段。
已确认 Feast FeatureView 类定义 (核心字段) 合理推断 生产级扩展字段 (基于阿里 PAI-FeatureStore 文档) // ===== Feature View 数据结构 ===== FeatureView { // --- 基础信息 --- (已确认: Feast + PAI-FeatureStore 共有) name: STRING // 全局唯一，如 "user_realtime_stats" entities: LIST[STRING] // 关联的 Entity name 列表 // 如 ["user"] 或 ["user", "advertiser"] description: STRING owner: STRING tags: MAP[STRING, STRING] // --- 数据源 --- (已确认: Feast DataSource / PAI-FeatureStore 数据源配置) source: DataSource // 详见下方 DataSource 定义 // --- Schema (特征字段列表) --- (已确认: Feast schema 字段) schema: LIST[Feature] // 该 View 包含的特征字段列表 // 详见下方 Feature 定义 // --- 在线存储配置 --- (合理推断: Feast 有 online_store 配置项) online_config: OnlineStoreConfig // KV key 模板, TTL, 序列化方式等 // --- 以下为生产级扩展，Feast 无但大公司内部系统有 --- // --- 版本 --- (合理推断: 生产系统必备) version: INT // 每次 schema/transform 变更自增 status: ENUM // DEV / STAGING / PROD / DEPRECATED // --- 物化配置 --- (合理推断: 基于阿里 PAI-FeatureStore "物化"概念) materialization: MaterializationConfig // 调度/资源/写入策略等 // --- 训练集成 --- (已确认: Feast 有 offline_store 相关配置) training_config: TrainingConfig // 是否开启快照, Point-in-time Join 配置 }
已确认 Feast 中 FeatureView 的核心字段: name, entities, schema (Field 列表), source (DataSource), online (bool), ttl。这些字段在 Feast 源码 sdk/python/feast/feature_view.py 中可以直接看到。

已确认 阿里 PAI-FeatureStore 中 FeatureView 的概念: 阿里文档将 FeatureView 定义为"特征视图，用于描述一组相关特征的来源、加工方式和在线存储方式"。与 Feast 的定位完全一致。

合理推断 version、status、materialization_config 这些字段是生产级系统的必然扩展。Feast 开源版本只有最简形态 (没有 version/status 概念)，但 Tecton (商业 Feature Store) 和企业内部系统一定有这些。
DataSource (数据源定义)
已确认 Feast DataSource 类 DataSource { // Feast 支持多种 Source 类型: type: ENUM // BATCH 类型: | FILE_SOURCE // 文件 (Parquet/CSV) | BIGQUERY_SOURCE // BigQuery | REDSHIFT_SOURCE // Redshift | HIVE_SOURCE // Hive (via SparkSource) // STREAM 类型: | KAFKA_SOURCE // Kafka topic | KINESIS_SOURCE // Kinesis stream // ON_DEMAND: | REQUEST_SOURCE // 请求上下文 // Batch Source 配置 table: STRING // Hive 表名或路径 timestamp_field: STRING // 事件时间字段 created_timestamp_column: STRING // Stream Source 配置 (已确认: Feast StreamSource) kafka_topic: STRING message_format: ENUM(AVRO, PROTOBUF, JSON) watermark: DURATION }
已确认 Feast 支持 BatchSource 和 StreamSource 两大类，具体子类型因部署环境不同。阿里 PAI-FeatureStore 支持 MaxCompute (Hive 等价) 和 DataHub/Kafka 作为数据源。
OnlineStoreConfig (在线存储配置)
合理推断 基于 Feast online_store + 行业实践 OnlineStoreConfig { // Feast 中 online_store 在 feature_store.yaml 全局配置 // 生产系统中更可能是 per-View 级别配置: key_template: STRING // KV key 模板 // "uf:profile:{user_id}" // "cf:uxadv:{user_id}_{advertiser_id}" ttl: DURATION // 过期时间 // 离线 View: 30d // 近线 View: 1~7d serializer: ENUM // 序列化方式 // PROTOBUF / JSON / FLATBUFFER / MSGPACK // (具体选择因系统而异) }
已确认 Feast 的 online_store 在 feature_store.yaml 中配置 (Redis/DynamoDB/SQLite 等)。

合理推断 key_template 和 per-View TTL 是生产级扩展。Feast 开源版中 online_store 是全局配置而非 per-View 配置。
MaterializationConfig (物化配置)
合理推断 基于阿里 PAI-FeatureStore "物化"概念 MaterializationConfig { // Batch View schedule: STRING // cron 表达式 "0 2 * * *" mode: ENUM // FULL / INCREMENTAL // Stream View // (无 schedule, 常驻 Job) parallelism: INT // Flink 并行度 checkpoint_interval: DURATION // 通用 write_mode: ENUM // BULK_LOAD / PIPELINE_WRITE max_write_qps: INT // 写入限流 }
已确认 Feast 中 Materialization 是将离线数据写入 online store 的过程 (feast materialize 命令)。阿里 PAI-FeatureStore 文档明确提到"物化"概念和增量/全量两种模式。

合理推断 具体的 parallelism, checkpoint_interval 等 Flink 配置是生产级扩展。
TrainingConfig (训练集成配置)
合理推断 基于 Feast get_historical_features + PIT Join TrainingConfig { snapshot_enabled: BOOL // 是否写 HDFS 快照 snapshot_interval: DURATION // 快照间隔 (Stream View) snapshot_path: STRING // HDFS 路径 snapshot_retention: DURATION // 快照保留天数 }
已确认 Feast 的核心能力之一是 get_historical_features()，它实现 Point-in-time Join 来生成训练数据。这要求离线存储中有历史快照。

合理推断 snapshot_interval / snapshot_path 等具体字段是 Stream View 场景的生产级需求。Feast 开源版本中 Batch View 的历史数据直接来自 offline store (如 BigQuery)，不需要额外快照机制。但 Stream View 必须有快照才能做 PIT Join。
Feature View 的实际 MySQL 表 (校正版):
需要注意 Feast 开源版中 Feature View 定义存储在一个序列化的 Protobuf 文件 (registry.pb) 中而非 MySQL。只有在生产级自研 Feature Store 中才会用 MySQL 做元数据存储。阿里 PAI-FeatureStore 使用 MySQL 存储元数据 (阿里文档可确认)。
合理推断 基于 Feast Protobuf schema + 关系化拆分 CREATE TABLE feature_views ( id BIGINT AUTO_INCREMENT PRIMARY KEY, project_id BIGINT NOT NULL, name VARCHAR(128) NOT NULL, entity_names JSON NOT NULL, -- ["user"] 或 ["user","advertiser"] source_type ENUM('BATCH','STREAM','ON_DEMAND'), source_config JSON, -- DataSource 序列化 online_config JSON, -- OnlineStoreConfig 序列化 materialization_config JSON, -- MaterializationConfig 序列化 training_config JSON, -- TrainingConfig 序列化 current_version INT DEFAULT 1, status ENUM('DEV','STAGING','PROD','DEPRECATED'), owner VARCHAR(128), tags JSON, created_at TIMESTAMP, updated_at TIMESTAMP, UNIQUE (project_id, name) ); -- 版本历史表 (生产级扩展) CREATE TABLE feature_view_versions ( view_id BIGINT NOT NULL REFERENCES feature_views(id), version INT NOT NULL, source_config JSON, -- 该版本的完整配置快照 online_config JSON, schema_hash CHAR(64), -- 所有 Feature 定义的 hash status ENUM('DEV','STAGING','PROD','DEPRECATED'), changelog TEXT, created_by VARCHAR(128), created_at TIMESTAMP, PRIMARY KEY (view_id, version) );

Feature Registry — 元数据的持久化层
Feature Registry 不是一个独立的"产品"——它是 Feature Store 中负责元数据持久化和查询的子系统。在 Feast 中它叫 Registry，在阿里 PAI-FeatureStore 中它是后端的 MetaService。
已确认 Feast Registry 的两种实现 // Feast Registry 的存储后端 (已确认, 源码可见): // 1. FileRegistry → 单个 registry.pb 文件 (本地/S3/GCS) // 适用: 开发/小规模场景 // 缺点: 并发写入问题, 无搜索/血缘能力 // // 2. SQLRegistry → MySQL/PostgreSQL/SQLite // 适用: 生产环境 // 优点: 支持并发, 支持查询 // // 阿里 PAI-FeatureStore (已确认, 文档可见): // 后端 MetaService → MySQL 持久化
已确认 Feast 支持 FileRegistry (序列化 Protobuf 文件) 和 SQLRegistry (SQL 数据库) 两种后端。SQLRegistry 在 Feast 0.20+ 引入，使用 SQLAlchemy ORM 支持 MySQL/PostgreSQL/SQLite。阿里 PAI-FeatureStore 使用 MySQL 存储元数据，通过 REST API 暴露。

Feast 中一个容易混淆的概念: Feature Service

已确认 Feast 中有一个叫 FeatureService 的概念 (不是 Feature Serving)。它的作用是将多个 Feature View 打包成一个"服务集合"——类似于前面讨论的 Model Binding。

// Feast FeatureService (已确认, 源码可见) FeatureService( name="ctr_model_features", features=[ user_profile_view[["gender", "age_bucket"]], user_stats_view[["click_1h", "ctr_7d"]], ad_meta_view[["category", "brand"]], ] )
这个概念在我之前的讨论中被叫做"Model Binding"。两者的作用相同: 定义一个模型需要哪些 Feature View 的哪些 Feature。Feast 的命名是 FeatureService，不是 ModelBinding。

校正后的完整关系图
已确认 对象关系 (Feast + PAI-FeatureStore 共同验证) 合理推断 版本/血缘/监控 扩展 Feature Registry (MySQL / Protobuf File) │ ├── Entity (极轻量) │ name: "user" │ join_keys: ["user_id"] │ -- 就这些，没有其他 -- │ ├── Feature View (重量级) │ name: "user_realtime_stats" │ entities: ["user"] ← 引用 Entity │ source: KafkaSource(...) ← 数据从哪来 │ schema: [Feature(...), ...] ← 包含哪些字段 │ online_config: {...} ← 存到哪、怎么存 │ materialization: {...} ← 怎么调度、怎么写入 │ version: 3 ← (生产扩展) │ status: PROD ← (生产扩展) │ │ │ └── Feature (字段定义) │ name: "click_1h" │ dtype: INT64 │ default_value: "0" │ -- Feature 隶属于 Feature View 的某个 version -- │ ├── Feature Service / Model Binding │ name: "ctr_model_features" │ features: [ │ user_realtime_stats["click_1h", "ctr_6h"], ← 引用 View + Feature │ ad_meta["category"], │ ] │ -- 定义"一个模型需要哪些特征" -- │ ├── (生产扩展) Lineage Edges │ user_behavior_log → user_realtime_stats → click_1h → ctr_model_v5 │ ├── (生产扩展) Quality Metrics │ click_1h: { date: 2024-11-20, psi: 0.12, missing_rate: 0.03 } │ └── (生产扩展) Audit Logs { operator: alice, action: UPDATE, view: user_realtime_stats, v2→v3 }
关键纠正总结:

① Entity 极简: 只有 name + join_keys。不包含任何 View/Feature/Store 配置。
② Feature View 是核心: source, schema, online_config, materialization 全部在 View 上。
③ Feature 是 View 的子对象: 通过 view_id + version 外键关联，不独立存在。
④ 三者是平级对象: Entity 和 Feature View 通过 entities 字段关联 (View 引用 Entity name)，不是嵌套关系。
⑤ Feature Service (Feast) = Model Binding (我之前的说法): 将多个 View 的 Feature 打包，定义模型需要什么。
⑥ Registry 是持久化层: 存储上述所有对象。Feast 用文件或 SQL，生产系统用 MySQL + 缓存 + 搜索索引。
