Feature View 的定位 — 它到底是什么
Feature View 是 Feature Entity 体系中最核心的执行单元。如果说 Entity 定义了"谁"，Feature 定义了"什么属性"，那 Feature View 定义的是"这些属性从哪来、怎么算、存哪里、怎么更新、怎么服务"的完整管线。每个 Feature View 是一条从数据源到在线 KV 的端到端特征管线 (Pipeline)。
一个类比帮助理解: 如果把 Feature Store 比作数据库，那么 Entity 相当于表的主键定义，Feature 相当于列定义，而 Feature View 相当于物化视图 (Materialized View)——它指定了数据源 (FROM)、转换逻辑 (SELECT)、刷新策略 (REFRESH)、存储引擎 (STORED AS)。这也是它叫 "View" 的原因。

与 Entity 的关系: 一个 Entity 下通常挂载 3~8 个 Feature View，每个 View 代表一个独立的特征生产管线。例如 User Entity 下:
user_profile 离线画像 | user_behavior_seq 近线行为序列 | user_realtime_stats 实时统计 | user_embedding 向量特征
它们有不同的数据源、更新频率、Owner，但通过同一个 user_id (Entity join_key) 关联。
Batch Feature View
数据源: Hive/MaxCompute 表
更新频率: T+1 (每天凌晨)
计算引擎: Spark SQL / PySpark
调度: Airflow cron DAG
典型特征: 用户画像、长期兴趣、消费能力分层、广告质量分、创意 embedding
特点: 覆盖率高 (90%+)、数据完整、但时效差
Stream Feature View
数据源: Kafka / RocketMQ topic
更新频率: 分钟~小时级
计算引擎: Flink (窗口聚合)
调度: 常驻 Flink Job
典型特征: 近 N 小时行为统计、实时兴趣漂移、短期 CTR/CVR、行为序列
特点: 时效好、能捕捉短期信号、但计算资源消耗大
OnDemand Feature View
数据源: 请求上下文 (Bid Request)
更新频率: 每次请求实时计算
计算引擎: Ad Server 内嵌 C++/Go
调度: 无 (请求驱动)
典型特征: 时间分桶、设备信息、地理编码、竞价景观、预算余额
特点: 零延迟、不落存储、但只能用请求内信息

15 个核心配置项中最关键的 5 个设计决策

① key_template 决定了在线查询的性能: 同一 Entity 的所有 Feature View 使用不同的 key 前缀 (uf:profile, uf:rts, uf:seq)，但 Entity key 部分相同 (user_id)。这样在线 MGet 时可以按前缀分批，同一 Tair 分片的 key 自然聚集。

② serializer 选择 FlatBuffer 的原因: FlatBuffer 支持零拷贝反序列化——不需要将整个 value 解析到内存对象，而是直接在序列化 buffer 上随机访问字段。对比 Protobuf (需要完整反序列化)，在线 serving 场景 FlatBuffer 快 3~5 倍。字节内部几乎全部使用 FlatBuffer。

③ snapshot_enabled 是 PIT Join 的前提: 没有快照，训练样本拼接只能用"当前时刻"的特征值，导致穿越。开启后 Flink Sink 双写 (Tair + HDFS)，每 5 分钟输出一份 Parquet 快照。代价是 HDFS 存储 (+20%~30%)。

④ watermark 影响数据完整性 vs 延迟的 tradeoff: watermark="10s" 意味着允许 10 秒的乱序数据。设太小会丢数据，设太大会增加特征更新延迟。字节经验值: 用户行为日志 watermark=10s，转化日志 watermark=300s (转化回调延迟大)。

⑤ batch_interval 决定 Tair 写入压力: Flink 逐条写 Tair 会产生百万级 QPS 洪峰。batch_interval="5s" 将同一窗口内的更新攒批为一次 Pipeline MSet，将写 QPS 从 200 万降到 10 万。

Batch Feature View — 离线管线深度拆解
Batch FV 端到端执行流程 (以 user_profile 为例)
02:00 — Airflow DAG 触发
├ 依赖检查: 上游 Hive 表 dw.user_events (ds=昨天) 分区就绪？
├ 依赖检查: dw.user_registration 表最新分区存在？
└ 全部就绪 → 启动 Spark Job

02:05 — Spark Job Phase 1: Transform 执行
├ DSL Compiler 将 Feature View 的 transform 编译为 Spark SQL
├ 执行 SQL: SELECT user_id, BUCKET(age,[18,25,35,45]) AS age_bucket,
│ gender, city_id, purchase_level, ... FROM dw.user_profile_daily
│ WHERE ds = '${yesterday}'
├ 输出: 中间 Hive 表 feature_output.user_profile_v2 (ds=今天)
└ 行数: ~5 亿 (全量活跃用户), 耗时 ~40min, 资源: 200 executor × 4core

02:50 — Spark Job Phase 2: 数据质量校验
├ 行数校验: 与昨天对比波动 < 5%？ (防止上游数据丢失)
├ NULL 率校验: 每个 Feature 的 NULL 率 < monitoring.missing_max？
├ 值域校验: age_bucket ∈ {0,1,2,3,4}？ gender ∈ {0,1,2}？
├ PSI 校验: 与前 7 天分布对比 PSI < 0.25？
├ 抽样校验: 随机 1000 条，用在线 C++ 算子重算，对比 diff < 0.01%
└ 全部通过 → Phase 3; 任一失败 → 告警 + 中止，线上继续用昨天数据

03:30 — Phase 3: Materialization (写入在线 KV)
├ 方式一 (BulkLoad): Spark 直接生成 Tair SST 文件 → Ingest 导入
│ → 吞吐 ~50万 key/s, 全量 5 亿 key 耗时 ~15min
├ 方式二 (Pipeline Write): Spark → Tair Pipeline MSet
│ → 吞吐 ~20万 key/s, 耗时 ~40min, 适合增量更新
├ 写入内容: key="uf:profile:{user_id}", value=FlatBuffer(所有 Feature 字段打包)
└ 双缓冲切换: 写入 shadow namespace → 校验 → 原子 swap 指针

04:00 — Phase 4: 验证上线
├ 从在线 KV 随机读 10000 条，与 Hive 表对比完全一致
├ 原子切换: 将线上读取指针从旧 namespace 切到新 namespace
└ 记录日志: 本次 Materialization 成功，耗时、行数、KV 写入量
全量 vs 增量 Materialization
全量 (FULL):
每次重建全部 key。适用于画像类特征 (数据量大但逻辑简单)。
优点: 简单可靠，不累积数据一致性问题
缺点: 资源消耗大，5 亿 key 全量写入需 15~40min

增量 (INCREMENTAL):
只更新有变化的 key (通过上游增量表/CDC 识别)。
优点: 资源消耗小 (通常只更新 5~10% 的 key)
缺点: 长期运行可能累积脏数据，需要定期全量 "Clean Sweep"

字节实践: 工作日用增量 (快速，06:00 前完成)，周末跑一次全量 (修正增量累积误差)。阿里 PAI-FeatureStore 的 Materialization 默认支持自动切换——数据变更 >30% 时自动触发全量。
双缓冲 (Double Buffering) 机制
问题: 如果直接覆盖写线上 KV 的 key，写入期间 (15~40min) 会出现"新旧混合"——部分 key 是今天的值，部分还是昨天的。模型面对混合分布的特征可能表现异常。

解决方案:
维护两个 namespace (A 和 B)。假设当前线上用 A:
① 新数据全量写入 B (offline，线上无感知)
② B 写入完成 → 质量校验通过
③ 原子操作: 将读取路由从 A 切到 B
④ 下一天: 新数据写入 A，切换回 A

实现: Tair 层面通过 namespace/table 切换；业务层面通过配置中心 (Consul/Nacos) 的一个 flag 指向当前 active namespace。

Stream Feature View — 近线流式管线深度拆解
Stream Feature View 是三类中工程复杂度最高的，因为它要在"分钟级时效性"和"计算正确性"之间找到平衡。字节 DSP 内部约 60% 的新增特征来自 Stream View。
Stream FV 的 Flink Job 内部架构
Kafka Source (user_behavior_log, ~10M msg/s 峰值)
↓ Deserialization: Protobuf → Java POJO (user_id, event_time, action, category_id, ad_id, ...)
↓ Filter: 过滤无效事件 (event_time 为空, user_id 为空, 非广告相关行为)
↓
Watermark Assigner (BoundedOutOfOrdernessWatermarks, maxOutOfOrderness=10s)
↓
KeyBy(user_id) → 按用户分区，保证同一用户的事件在同一个 Task 处理
↓
分支并行处理 (同一个 KeyedStream 上注册多个窗口):

├─ Window 1: SLIDING(1h, 5min)
│ → 计算 click_1h = COUNT(action='click')
│ → 计算 imp_1h = COUNT(action='impression')
│ → 每 5min 触发一次窗口输出
│
├─ Window 2: SLIDING(6h, 30min)
│ → 计算 ctr_6h = SAFE_DIV(SUM(click), SUM(imp))
│ → 每 30min 触发一次窗口输出
│
├─ Window 3: SLIDING(30min, 1min)
│ → 计算 click_cat_seq = COLLECT_LIST(category_id) LIMIT 20
│ → 每 1min 触发一次窗口输出
│
└─ Window 4: SLIDING(1h, 1min)
→ 计算 active_minutes = COUNT_DISTINCT(FLOOR(event_time/60000))

↓ 各窗口输出合并 (Union) → 同一 user_id 的多个窗口结果 merge 为完整 Feature View
↓
Tair Sink (Micro-batch)
├ 攒批: 每 5s 收集一批输出，合并同一 user_id 的多次更新
├ 序列化: FlatBuffer Pack (所有字段打包为一个 value)
├ 写入: Pipeline MSet → Tair (key = "uf:rts:{user_id}")
└ 限流: max_write_qps=100000，超过则背压 (backpressure)

HDFS Snapshot Sink (并行)
├ 每 5min 将窗口输出写一份 Parquet 快照到 HDFS
├ 路径: hdfs:///feature_snapshots/user_rts_v3/dt=2024-11-20/hh=10/mm=05/
└ 用于训练时 Point-in-time Join
Flink Job 关键配置参数
参数值 (字节线上)说明
parallelism64~128根据 Kafka partition 数设置，通常 1:1 或 2:1
checkpoint interval60sFlink 状态快照间隔。太短影响吞吐，太长故障恢复慢

state ttl= 最大窗口 × 1.5如最大窗口 6h，state TTL=9h。防止状态无限膨胀

Stream FV 特有的难点与解法
① 窗口状态膨胀
问题: SLIDING(6h, 30min) 窗口需要在 state 中保留 6h 的原始事件
解法: 对 COUNT/SUM 使用增量聚合 (AggregateFunction)，只保存聚合中间状态 (计数器)，不保存原始事件。状态从 GB 级降到 MB 级。对 COLLECT_LIST 类算子无法增量化，需保留原始事件，用 state TTL 兜底。

② 窗口触发延迟
问题: SLIDING(1h, 5min) 意味着每 5min 才触发一次输出。最坏情况特征延迟 5min。
解法: 字节对核心特征 (click_1h) 额外注册一个每事件触发 (ProcessFunction) 版本，事件到达立刻更新。两个版本写同一个 key，process 版覆盖 window 版。

③ 数据倾斜 (Hot User)
问题: 少量高活跃用户 (如 bot) 产生大量事件，导致单个 Task 过载。
解法: 两阶段聚合 (Local Aggregate + Global Aggregate)。先按 user_id + random_suffix KeyBy 做本地预聚合，再按 user_id 做全局合并。
Flink Job 故障恢复流程: Job 崩溃 → 从最近一次 checkpoint 恢复 (回退 ~60s) → Kafka offset 回溯到 checkpoint 时刻 → 重新消费重放 → 窗口状态从 RocksDB snapshot 恢复 → 追赶消费直到追上实时位点 (通常 1~3min)。期间线上使用 Tair 中的旧值 (容忍分钟级延迟)。字节实践: 核心 Stream FV 的 Flink Job 配置了自动重启策略 (fixed-delay, 3 次重试, 间隔 30s)，非核心 Job 允许更长恢复时间。

OnDemand Feature View — 在线实时计算管线
OnDemand Feature View 不需要离线/近线管线，但需要在 Ad Server 内部嵌入高性能计算逻辑，在毫秒内完成。
OnDemand FV 的执行位置
OnDemand FV 的 Transform 逻辑被编译为 C++ 算子，直接嵌入 Ad Server 进程中执行。不涉及任何网络 I/O 或外部存储查询。

输入来源:
• Bid Request 中的原始字段 (timestamp, device_info, ip, app_id, slot_id, geo)
• 来自其他 Feature View 的已拉取值 (可以引用)
• Ad Server 内部状态 (如当前竞价候选数量)

输出:
直接写入 FeatureBatch 的对应 slot，不落存储。

性能:
单次计算全部 OnDemand 特征耗时 < 0.5ms (纯 CPU 计算)
典型 OnDemand 特征及其 Transform
特征Transform DSL
hour_bucketHOUR_OF_DAY(request_time)
day_of_weekDAY_OF_WEEK(request_time)
is_weekendIS_WEEKEND(request_time)
device_typeCASE WHEN os='iOS' THEN 1 WHEN os='Android' THEN 2 ELSE 0
network_typeHASH(network, 4)
WiFi=0,4G=1,5G=2,other=3
geohashGEOHASH(lat, lng, 5)
screen_bucketBUCKET(screen_width*screen_height, [480000, 921600, 2073600])
candidate_countLEN(candidate_ad_list)
time_since_last_clickTIME_DIFF(request_time, user_feature['last_click_ts'], 'minute')
引用其他 View 的值
OnDemand FV 的训练样本处理: OnDemand 特征不落存储，但训练需要。解法: Ad Server 在返回 Bid Response 后，将当前请求的所有 OnDemand 特征值附加到曝光日志中 (作为日志字段一起写入 Kafka)。Sample Factory 从日志中直接提取 OnDemand 特征值，不需要 PIT Join。这是最简单也最可靠的方式——"用了什么值，就记录什么值"。

版本管理 & Schema 演进 — 线上不停机变更
Feature View 的 Schema (特征字段、Transform 逻辑) 必然会频繁变更。如何在不中断线上服务的情况下安全地演进，是生产级系统的核心挑战。
5.1 三种变更类型及处理策略
Type A: 新增字段 (最常见, ~70%)
在现有 View 中增加新 Feature。
处理: 新字段的 default_value 确保旧模型不受影响。FlatBuffer 天然支持向后兼容——新字段追加在 schema 末尾，旧 reader 忽略新字段。
流程: 注册新 Feature → 更新 Materialization (新 Spark/Flink job 同时输出新字段) → 新模型引用新字段 → 旧模型不受影响
风险: 低

Type B: Transform 逻辑变更 (~25%)
修改现有 Feature 的计算方式 (如分桶边界调整)。
处理: 必须新建 version (如 v2→v3)。旧 version 不修改，新旧并行运行。
流程: 创建 v3 → 新 Materialization job 写入新 namespace → Shadow 验证 → 新模型绑定 v3 → 旧模型继续用 v2 → 确认旧模型全部迁移后下线 v2
风险: 中 (需确保新旧 version 的 KV namespace 隔离)

Type C: 删除字段 (罕见, ~5%)
移除不再使用的 Feature。
处理: 先检查 ModelFeatureBinding——有模型引用则拒绝删除。无引用后标记 DEPRECATED，30 天后物理删除。
风险: 低 (有依赖检查保护)
5.2 版本并行运行机制
为什么需要并行运行？
模型 A 依赖 user_profile_v2 (age 分桶边界 [18,25,35,45])。
模型 B (新训练) 依赖 user_profile_v3 (age 分桶边界 [18,22,30,40,50,60])。
两个模型可能同时在线 (AB 实验)，因此 v2 和 v3 必须同时存在。

实现方式:
每个 version 有独立的:
• KV key namespace: uf:profile_v2:{uid} vs uf:profile_v3:{uid}
• Materialization job: 独立的 Spark/Flink job
• 监控面板: 独立的 PSI/缺失率指标

资源优化:
共享上游数据源 (同一个 Hive 表/Kafka topic)。v2 和 v3 的 Spark Job 可以合并为一个 Job，输出到不同 namespace。Flink Job 也可以在同一个 JobGraph 中注册多个 Sink (v2 sink + v3 sink)。

生命周期:
v2 PROD + v3 STAGING → v3 验证通过 → v2 DEPRECATED + v3 PROD → 旧模型全部迁移 → v2 DELETED

字节内部规定: DEPRECATED 后最长保留 90 天。超时自动 DELETED + 回收 KV 存储。
FlatBuffer 的向后/向前兼容性设计

FlatBuffer schema 的演进规则 (字节内部强制执行):
• 新增字段只能追加到末尾，不能插入中间
• 字段一旦发布不能删除或修改类型 (只能标记 deprecated)
• 字段 ID (slot number) 是永久的，删除字段后其 ID 保留不复用
• 旧 reader 遇到新 schema 的 value → 忽略末尾的新字段 (向前兼容)
• 新 reader 遇到旧 schema 的 value → 新字段返回 default_value (向后兼容)

这意味着 Type A (新增字段) 变更是零风险的——不需要停机，不需要全量重写 KV，新 Materialization job 输出新格式的 value，旧 value 在 TTL 内自然过期被替换。

真实生产案例 — 字节 DSP User Entity 下的全部 Feature View
以下是字节跳动 DSP 广告系统中 User Entity 下典型的 Feature View 全景，展示不同类型的 View 如何协作。
FV-1: user_profile (Batch, T+1)
数据源: dw.user_profile_daily (Hive, 每天 01:30 就绪)
特征数: 12 个字段 — gender, age_bucket, city_id, province_id, education, device_brand, device_price_bucket, os_type, carrier, purchase_level, register_days_bucket, app_install_count_bucket
KV key: uf:p:{user_id} | TTL=30d | Value ~80 Bytes
更新: Airflow cron 02:00, Spark Job ~40min, BulkLoad ~15min | Materialization: FULL (每日全量)
在线缺失率: ~3% (仅极冷用户缺失) | 引用模型数: 28 (几乎所有广告模型)
FV-2: user_interest_tags (Batch, T+1)
数据源: dw.user_interest_model_output (Hive, Topic Model 输出)
特征数: 3 个字段 — interest_tag_ids (SEQ_INT64, top-20 标签 ID), interest_tag_weights (SEQ_FLOAT32), interest_level_1_ids (SEQ_INT64, top-5 一级品类)
KV key: uf:tag:{user_id} | TTL=30d | Value ~200 Bytes
更新: Airflow cron 03:00, 依赖 FV-1 完成 | Materialization: INCREMENTAL (仅更新活跃用户)
引用模型数: 15
FV-3: user_dssm_embedding (Batch, T+1)
数据源: 双塔模型 User Tower 推理输出 (每天全量用户前向推理)
特征数: 1 个字段 — user_vec (EMBEDDING, FLOAT16[128])
KV key: uf:emb:{user_id} | TTL=7d | Value ~260 Bytes (128维 × FP16)
更新: 依赖双塔模型训练完成 (通常 04:00~06:00) | 特殊处理: FP16 量化 (vs FP32 省一半存储)
引用模型数: 5 (召回 + 粗排)
FV-4: user_behavior_seq (Stream, 分钟级)
数据源: Kafka: user_ad_interaction_log
特征数: 4 个字段 — click_ad_seq (最近 50 条点击广告 ID), click_cat_seq (最近 50 条点击品类 ID), click_ts_seq (对应时间戳), convert_ad_seq (最近 20 条转化广告 ID)
KV key: uf:seq:{user_id} | TTL=3d | Value ~600 Bytes
Flink: parallelism=128, SLIDING(24h, 1min), RocksDB state ~500GB
引用模型数: 12 (精排 DIN/DIEN 的核心输入)
Snapshot: 每 5min 写 HDFS Parquet
FV-5: user_realtime_stats (Stream, 分钟级)
数据源: Kafka: user_behavior_log
特征数: 8 个字段 — click_1h, imp_1h, ctr_6h, click_cat_dist_1h (品类点击分布 MAP), active_minutes_1h, session_count_6h, avg_dwell_time_1h, last_click_ts
KV key: uf:rts:{user_id} | TTL=1d | Value ~120 Bytes
Flink: parallelism=64, 多窗口 (1h/6h) 并行 | 增量聚合 (state ~50GB)
引用模型数: 18
特殊: click_1h 额外有 ProcessFunction 版本，事件到达立刻更新
FV-6: user_context (OnDemand, 毫秒级)
数据源: Bid Request 字段
特征数: 9 个字段 — hour_bucket, day_of_week, is_weekend, device_type, network_type, geohash, screen_bucket, app_category, slot_type
存储: 无 (不落 KV) | 计算: C++ 算子，<0.3ms
训练: 特征值写入曝光日志，Sample Factory 直接提取
引用模型数: 所有模型 (30+)
User Entity 下 6 个 View 的在线查询时序

T+0ms: 解析请求 → T+0.5ms: 异步并行启动 FV-1~5 的 Tair MGet (共 5 个 key)
T+0.5ms: 同时启动 FV-6 OnDemand 计算 (CPU)
T+1ms: FV-6 完成 → T+3ms: FV-1~5 Tair 响应返回 (P99)
T+3.5ms: 全部用户特征就绪，进入 Feature Assembler

总耗时: ~3.5ms (用户侧特征拉取)。这 5 个 key 通常落在 Tair 的同一个分片 (因为 key 后缀都是同一个 user_id 的 Hash)，所以可以合并为一次 Pipeline MGet。
