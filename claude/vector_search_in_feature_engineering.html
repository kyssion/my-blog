字节/阿里的核心选择: 字节使用自研 VE-KNN (内部名 ByteANN)，阿里使用自研 Proxima/Aitheta。两者都不直接使用 Faiss/Milvus 作为在线服务引擎，原因是：① 广告场景对延迟极度敏感 (<5ms)，通用向量数据库的 RPC 开销不可接受；② 需要与广告属性过滤 (品类/地域/预算) 深度融合，通用引擎的 filter 性能不够；③ 亿级广告库 + 每秒百万级查询的规模，需要定制化的分布式方案。Faiss 仍然被广泛使用——但主要是作为离线工具库 (索引构建、Embedding 质量评估、离线 KNN 计算)，而非在线 Serving 引擎。

场景一: 向量召回 (ANN Recall) — 最核心的应用
向量召回是广告系统中向量检索引擎最重要的应用。它从千万级广告库中，用用户 Embedding 做 ANN (Approximate Nearest Neighbor) 检索，找出语义最相关的 Top-K 广告候选。
向量召回全链路 (字节 VE-KNN 方案)
离线阶段: 索引构建 每小时/每天更新
├ 双塔模型 (DSSM/YoutubeDNN) 训练完成 → 输出 Ad Tower 参数
├ 全量广告 forward 推理 → 每条广告得到 ad_embedding (128d FP16)
├ Embedding + 广告元信息 → 构建 HNSW+PQ 混合索引
│ ├ HNSW 图索引: M=32, efConstruction=200
│ ├ PQ 量化: 128d → 64 子空间 × 8bit 码本 = 64 Bytes/向量
│ └ 索引大小: 1000万广告 × (64B PQ + ~200B HNSW 图) ≈ 2.5GB
├ 附加属性索引: category_id, region_id, budget_status → 倒排/Bitmap 索引
├ 分片: 按 ad_id hash 分成 N 个 shard (通常 8~16 个)
└ 部署: 新索引构建完成 → 双缓冲切换 → 在线生效

在线阶段: 向量检索 每次广告请求, <5ms
├ Step 1: User Embedding 获取
│ 方式 A: 预计算 (从 Tair 读取离线生成的 user_embedding) → 90% 用户
│ 方式 B: 实时推理 (User Tower 在线前向) → 10% 新/冷用户
├ Step 2: 属性预过滤 (Pre-filter)
│ 广告主定向条件 → 倒排索引过滤出合法广告子集
│ 如: region=北京 AND category∈{游戏,电商} AND budget_remaining>0
│ 过滤后: 1000 万 → ~50 万候选
├ Step 3: ANN 检索
│ user_embedding (128d) → HNSW 图遍历 → PQ 距离粗筛 → Top-200
│ 搜索参数: ef_search=100, nprobe=32 (IVF 模式时)
│ 在 Pre-filter 的候选子集上做 ANN (不是全量搜索)
├ Step 4: Rerank (可选)
│ Top-200 用精确内积重排 → Top-200 (FP32 精确计算, 修正 PQ 量化误差)
└ 输出: 200 个广告 ID → 合并到召回候选集
向量索引构建管线 (与 Feature Store 的关系)
向量索引构建是一种特殊的 Materialization——它不是写入 Tair KV，而是写入向量索引引擎。在 Feature Store 体系中，它被建模为一种特殊的 Sink:

FeatureView: ad_dssm_embedding entity: Ad source: 双塔模型推理输出 store_config: store_type: VECTOR_INDEX // 特殊存储类型 engine: VE_KNN index_type: HNSW_PQ dimension: 128 metric: INNER_PRODUCT pq_subquantizers: 64 hnsw_m: 32 shard_count: 16 attribute_columns: [category_id, region_id, advertiser_id, budget_status] refresh_interval: "1h" // 每小时全量重建
执行引擎 (Job Builder) 看到 store_type=VECTOR_INDEX 时，生成的不是 Tair BulkLoad Job，而是索引构建 Job:
① Spark Job 读取 Ad Embedding 表 → ② 调用 Faiss 构建 HNSW+PQ 索引 → ③ 索引分片 → ④ 上传到 VE-KNN 集群 → ⑤ 双缓冲切换

Faiss (离线构建) VE-KNN (在线服务)
Pre-filter + ANN 的混合检索
为什么需要 Pre-filter?
广告主设定了定向条件: "只投北京地区的 18-35 岁男性"。如果不过滤直接 ANN，Top-200 中可能有大量不满足定向的广告——白白浪费了召回配额。

Pre-filter 的两种实现:

方式一: 先过滤再检索 (字节 VE-KNN)
在向量索引旁维护属性倒排索引。先用倒排索引筛出合法 ad_id 集合 → 在这个子集上做 ANN。
优点: 精确过滤，不浪费 Top-K 配额
缺点: 子集太小时 HNSW 图变稀疏，检索质量下降

方式二: 检索时过滤 (阿里 Proxima)
ANN 遍历 HNSW 图时，每到一个节点先检查属性条件。不满足则跳过，不计入 Top-K。
优点: 不需要额外的倒排索引
缺点: 过滤率高时需要遍历更多节点，延迟不可控

字节实践: 默认用方式一 (先过滤)。当过滤后子集 <1000 条时自动切换为暴力搜索 (子集太小 HNSW 退化)。

场景二: I2I 相似广告/商品检索 — 特征生产中的向量应用
I2I (Item-to-Item) 是特征工程中一个被低估的向量检索应用。它不只是一个召回通道——它的输出直接作为特征供排序模型使用。
I2I 作为召回通道
触发逻辑: 用户近期点击/转化的广告 → 取这些广告的 Embedding → 在向量索引中检索相似广告

// 行为触发 I2I 召回 user_clicked_ads = [ad_101, ad_205, ad_389] for seed_ad in user_clicked_ads: seed_emb = tair.get(f"af:emb:{seed_ad}") similar_ads = ve_knn.search( query=seed_emb, top_k=50, filter="advertiser_id != seed_ad.advertiser_id" ) recall_candidates.extend(similar_ads)
与 U2I 的区别:
U2I (场景一): 用用户的 Embedding 检索广告 → 泛化性强
I2I: 用已交互广告的 Embedding 检索相似广告 → 精准性强

两者通常并行作为多路召回的不同通道，结果取并集。

VE-KNN Proxima
I2I 相似度作为排序特征
这是更隐蔽但非常有价值的应用。

I2I 检索的结果不仅用于召回，其相似度分数本身被作为精排模型的输入特征:

// Feature View: user_ad_i2i_similarity // Entity: User × Ad (交叉特征) features: i2i_max_sim: // 候选广告与用户近期点击广告的最大余弦相似度 i2i_avg_sim: // 平均相似度 i2i_click_count: // 用户近期点击的广告中有多少与候选广告相似度>0.7
计算方式:
① 候选广告 ad_embedding (128d) — 来自 Feature Store
② 用户点击历史中每条广告的 embedding — 来自 Feature Store
③ 逐一计算内积/余弦相似度 → 取 max/avg/count

为什么有价值:
这个特征告诉精排模型："这个候选广告和用户之前喜欢的广告有多像"。它提供了一种语义级别的相关性信号，比简单的品类匹配更精细。字节内部实验: 加入 i2i_sim 特征后精排 AUC 提升 0.15%。

场景三: 长序列行为建模 (SIM/SDIM) — 精排中的向量检索
这是向量检索在特征工程中最精妙的应用。当用户行为序列长达 1000+ 条时，精排模型无法对全部行为做 Attention (计算量太大)。解法是: 先用向量检索从 1000 条行为中筛出与候选广告最相关的 Top-K 条，再做 Attention。
SIM (Search-based Interest Model) 中向量检索的角色
背景: 用户最近 30 天的广告交互序列可能有 1000~10000 条
直接做 Target Attention: O(1000 × 128d) → 单次推理 ~5ms → 500 候选 × 5ms = 2500ms → 完全不可接受

SIM 的两阶段方案:

Stage 1: General Search Unit (GSU) — 向量检索 <1ms
├ 候选广告 embedding (128d) 作为 query
├ 用户行为序列中每条广告的 embedding 作为 document 集合
├ 在 document 集合中做 Top-K ANN 检索 (K=50~100)
│ 方式 A (Hard Search): 按品类/广告主 ID 精确匹配过滤 (倒排)
│ 方式 B (Soft Search): 向量内积 ANN 检索 (Faiss/自研)
└ 输出: 该候选广告最相关的 K 条历史行为 ID + 时间戳

Stage 2: Exact Search Unit (ESU) — 精细 Attention ~1ms
├ K 条行为的 embedding → DIN/DIEN style Target Attention
├ 计算量: O(K × 128d) = O(50 × 128) → 极快
└ 输出: 用户对该候选广告的兴趣向量 (注意力加权)

复杂度对比:
朴素 Attention: O(N × d) = O(1000 × 128) = 128,000 次乘法/候选
SIM: O(检索) + O(K × d) = O(~100) + O(50 × 128) = ~6,500 次乘法/候选
加速比: ~20 倍
GSU 的向量检索实现细节
在线 Per-user 索引 vs 预计算:

方案一: 在线构建 Mini-Index (字节早期)
每个用户的行为序列 (50~200 条) 在 Feature Serving 阶段从 Tair 拉取后，在内存中构建一个 tiny Faiss index (Flat, 暴力搜索)。对 50 条行为的暴力搜索耗时 <0.1ms，不需要 ANN。

方案二: 品类匹配 Hard Search (字节主流)
不用向量检索，而是用属性倒排: 候选广告的 category_id → 从用户行为序列中找同品类的行为。简单但效果接近 Soft Search。

方案三: 预计算 User-side KNN (阿里 SDIM)
离线用 Spark 对每个用户的行为序列构建 PQ 码本 → 在线用候选广告 Embedding 做 PQ 距离计算。避免在线建索引的开销。

核心 insight: SIM/SDIM 场景中的"向量检索"规模很小 (每用户只有几百到几千条 document)，不需要 Milvus/VE-KNN 这种大规模引擎。Faiss Flat/mini-PQ 或纯倒排就够了。

Faiss Flat Inverted Index
SIM 在 Feature Store 中的建模
SIM 的 GSU 检索结果需要作为 Feature 传给模型。在 Feature Store 中它是这样建模的:

// Feature View: user_sim_topk_behaviors // Entity: User × Ad (交叉特征!) // 这是精排阶段为每个候选广告动态计算的 source_type: ON_DEMAND // 在线实时计算 features: sim_topk_ad_ids: SEQ_INT64[50] // GSU 检索出的 Top-50 行为广告 ID sim_topk_timestamps: SEQ_INT64[50] // 对应的时间戳 sim_topk_actions: SEQ_INT64[50] // 对应的行为类型 (click/convert) sim_topk_scores: SEQ_FLOAT[50] // 对应的检索相似度分数 // 计算逻辑 (OnDemand C++ Operator): // 1. 从 user_behavior_seq Feature View 获取完整行为序列 // 2. 对每个候选广告 ad_embedding, 在序列中做 TopK 检索 // 3. 输出 Top-50 的行为 ID/时间/分数
关键: sim_topk_ad_ids 随后由模型的 Embedding Layer 做 Lookup → 得到 50 个 embedding → ESU Target Attention → 输出兴趣向量。

这就是 SIM 的核心: 向量检索变成了特征工程的一部分，它的输出 (TopK 行为 ID) 直接作为模型输入特征。

场景四: Look-alike 人群扩展 — 离线特征生产中的向量应用
广告主上传一批种子用户 (如已购买用户)，平台需要找到"长得像"的潜在用户群体。这是 DMP (数据管理平台) 的核心能力，底层依赖向量检索。
Look-alike 的向量检索管线
Step 1: 种子用户 Embedding 聚合
广告主提供 10000 个种子用户 ID → 从 Feature Store 拉取每个用户的 user_embedding (128d) → 计算质心 (Centroid): 所有 embedding 的加权平均向量

Step 2: KNN 扩展
用质心向量在全量用户 Embedding 索引中做 ANN 检索:
centroid_embedding = mean(seed_user_embeddings) expanded_users = faiss_index.search( query=centroid_embedding, top_k=1_000_000, // 扩展 100 万用户 ef_search=200 )
检索引擎: 离线用 Faiss (IndexHNSWFlat, 亿级用户索引，~30GB)

Step 3: 输出人群包
100 万用户 ID → 写入 Tair Bitmap (RoaringBitmap 压缩)
key: crowd:lookalike:{campaign_id}
在线召回阶段用 Bitmap 做定向匹配

更新频率: 每天凌晨 Spark Job 重算 (用户 embedding 每天更新，人群包随之更新)

Faiss IndexHNSW RoaringBitmap
Look-alike 在 Feature Store 中的建模
Look-alike 的输出 (人群包) 是一种 User 维度的离线特征:

// Feature View: user_crowd_tags // Entity: User // source_type: BATCH (T+1) features: is_in_crowd_A: INT64 // 是否在人群包 A 中 (0/1) is_in_crowd_B: INT64 // 是否在人群包 B 中 crowd_similarity_A: FLOAT32 // 与人群包 A 质心的距离 // ... 可能有 50+ 个人群包标记 // Materialization: // Spark Job 遍历全量用户，对每个人群包检查 Bitmap 成员关系 // 输出写入 Tair: key="uf:crowd:{user_id}"
向量检索参与的环节:
① Faiss 构建全量用户 Embedding 索引 (亿级)
② Faiss KNN 检索扩展人群
③ 扩展结果 → Bitmap → 用户特征

字节实践: 同时支持"标准 KNN"和"带约束 KNN"——如扩展时排除近 30 天已看到广告的用户 (去重)，通过 Faiss 的 ID Filter 实现。

阿里实践: 使用 Proxima 做 Look-alike，支持"分层扩展"——先扩展高相似度核心层 (Top 10万)，再扩展中等相似度外围层 (Top 100万)，广告主可按层出价。

场景五: 创意素材理解与去重 — 多模态向量应用
广告创意 (图片/视频/文案) 的 Embedding 在特征工程中有两个核心作用: 作为广告侧特征供模型使用，以及做创意去重/相似检测。
5.1 创意 Embedding 作为广告特征
// Feature View: ad_creative_embedding // Entity: Ad (具体是 Creative) // source_type: BATCH (新创意上传时触发) features: img_embedding: EMBEDDING[128] // ResNet/ViT 图片向量 text_embedding: EMBEDDING[64] // BERT 文案向量 video_embedding: EMBEDDING[128] // 视频封面帧向量 multimodal_embedding: EMBEDDING[256] // 多模态融合向量 // 生产方式: // 新创意上传 → Kafka 事件 → Flink Job 触发推理 // → CV 模型 (ResNet/ViT) 提取 img_embedding // → NLP 模型 (BERT) 提取 text_embedding // → 多模态模型 (CLIP/M6) 融合 → multimodal_embedding // → 写入 Tair + 更新向量索引
字节方案: ByteTransformer (自研多模态模型) 对图片+文案联合编码，输出 256d 向量。用于广告侧向量召回和精排特征。

阿里方案: M6 (Multi-Modality to Multi-Modality Multitask Mega-transformer) 统一处理图文视频。

在精排中的使用:
multimodal_embedding 直接作为精排模型的 dense feature 输入 MLP (不走 Embedding Table lookup)。它为模型提供了"这个创意视觉上/语义上是什么样的"信息。
5.2 创意去重与相似检测
问题: 同一广告主上传大量相似创意 (微调文案或裁剪图片)，导致用户在一次请求中看到多个"几乎相同"的广告。

解法: 创意向量聚类 + 去重:

离线聚类:
所有创意的 multimodal_embedding → Faiss K-Means 聚类 (K=10000) → 每个创意分配到一个 cluster → 同 cluster 的创意被视为"近似重复"

// 创意去重 Feature View // Entity: Ad features: creative_cluster_id: INT64 // 所属聚类 ID // 重排阶段使用: // 同一 cluster 的广告只保留 eCPM 最高的一条 // 实现: 重排模块按 creative_cluster_id 做 group-wise 去重
在线相似检测 (实时上传场景):
新创意上传 → 提取 embedding → 在创意向量索引中检索 Top-5 最相似创意 → 余弦相似度 >0.95 → 标记为"近似重复"，拒绝投放或限制预算。

使用的引擎:
离线聚类: Faiss K-Means (GPU 加速)
在线去重: Milvus / Proxima (支持实时增删改)

字节数据: 创意去重使创意多样性提升 ~30%，用户体验改善带来 CTR 提升 0.3%。

场景六: 用户 Embedding 实时更新 — 近线特征中的向量应用
用户 Embedding 不是一成不变的——用户的实时行为应该立刻反映到 Embedding 中。这需要一套"Embedding 增量更新"机制，向量检索引擎在其中扮演索引实时更新的角色。
6.1 用户 Embedding 增量更新
离线 Embedding (T+1):
双塔模型 User Tower 每天对全量用户前向推理 → 存入 Tair (uf:emb:{user_id})。覆盖 90%+ 用户但时效性差。

近线 Embedding 更新 (分钟级):
// Stream Feature View: user_embedding_realtime // Flink Job 逻辑: // 1. 消费 Kafka 用户行为日志 // 2. 用户新点击一条广告 → 获取该广告的 ad_embedding // 3. 用指数移动平均 (EMA) 更新用户 embedding: // new_user_emb = α × ad_embedding + (1-α) × old_user_emb // α = 0.1 (学习率, 控制更新幅度) // 4. 写入 Tair: uf:emb_rt:{user_id} (近线版, TTL=1d)
在线 Serving 策略:
Feature Serving 先查 uf:emb_rt:{user_id} (近线版)，miss 则查 uf:emb:{user_id} (离线版)。近线版 TTL=1d 过期后自动回退到离线版。

6.2 向量索引实时更新
问题: 广告侧向量索引每小时全量重建 (1000 万广告)。但新广告上线后需要立刻可被召回，不能等下一次全量重建。

解法: 实时增量索引:

字节 VE-KNN 方案:
• 基础索引: 每小时全量重建的 HNSW+PQ 索引 (只读)
• 增量缓冲: 新广告的 Embedding 写入一个实时增量缓冲区 (内存中的小型 Flat Index)
• 检索时: 同时搜索"基础索引 + 增量缓冲"，结果合并取 Top-K
• 每小时: 增量缓冲 merge 到基础索引 → 清空缓冲

阿里 Proxima 方案:
Proxima 原生支持 Real-time Insert/Delete (基于 HNSW 的动态图更新)。新广告直接 insert 到 HNSW 图中，无需增量缓冲。但频繁 insert 会导致 HNSW 图质量退化，因此仍需定期 rebuild。

Milvus 方案 (开源参考):
Milvus 使用 Growing Segment + Sealed Segment 架构。新数据写入 Growing Segment (内存, brute-force)；后台异步 flush 为 Sealed Segment (磁盘, 带索引)。检索时两者 merge。

广告上线延迟:
VE-KNN: ~10s (写入增量缓冲后立刻可检索)
Proxima: ~5s (HNSW 动态 insert)
全量重建: ~1h (等待下次 rebuild)

向量检索引擎在整体架构中的位置
向量检索引擎与 Feature Store 各层的交互关系
特征生产层 (离线/近线)
├ Embedding 生产: 双塔模型/CV模型/NLP模型 → ad/user/creative embedding
├ 索引构建: Spark + Faiss → 构建 HNSW/PQ 离线索引
├ Look-alike: Faiss KNN → 人群扩展 → Bitmap 人群包特征
├ 创意聚类: Faiss K-Means → creative_cluster_id 特征
└ I2I 预计算: Faiss → 相似广告 Pair 表 → I2I 特征

在线 Serving 层 (毫秒级)
├ 向量召回: VE-KNN / Proxima → U2I/I2I Top-K 候选
├ SIM/SDIM: Feature Serving 内嵌 Faiss Flat → 长序列 Top-K 检索
├ 创意去重: Milvus / Proxima → 相似创意检测
└ 实时增量: VE-KNN 增量缓冲 → 新广告即时可检索

训练层
├ 负样本采样: Faiss → Hard Negative Mining (检索与正样本最相似的负样本)
├ Embedding 质量评估: Faiss → KNN Recall@K / Hit Rate 计算
└ 向量空间可视化: Faiss PCA/t-SNE → Embedding 分布诊断
关键总结: Faiss 是"离线万金油"，VE-KNN/Proxima 是"在线专用引擎"

在字节/阿里的实际架构中，向量检索的使用模式非常清晰:
• Faiss: 离线工具库，用于索引构建、Look-alike、聚类、评估、负样本挖掘。它不直接服务在线流量，而是作为 Spark Job 中的库被调用。
• VE-KNN / Proxima: 在线检索引擎，专门服务毫秒级的向量召回。它们是独立部署的分布式集群，通过 gRPC 被 Ad Server 调用。
• Milvus: 在字节/阿里核心链路中不是首选 (自研方案性能更优)，但在中小规模场景 (如创意去重、非核心召回通道) 中被使用。开源方案首选。
• Jina / Weaviate: 偏向语义搜索产品化，在广告特征工程的核心链路中不常见。
