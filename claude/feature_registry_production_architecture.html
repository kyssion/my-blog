Feature Registry 的本质 — 它是整个 Feature Store 的元数据中枢
之前讨论的所有组件——Entity、Feature View、执行引擎、Feature Serving、向量索引——都需要一个地方来"注册自己的存在"并查询其他组件的信息。Feature Registry 就是这个中枢。它不存储特征值本身 (那是 Tair 的事)，而是存储关于特征的信息 (元数据)。
一个类比: 如果 Feature Store 是一家图书馆——Tair 是书架 (存放实际的书/特征值)，Feature Serving 是借阅服务 (帮你找书)，执行引擎是编目加工室 (生产新书)——那 Feature Registry 就是图书馆目录系统 (知道每本书叫什么名、在哪个架子、谁写的、什么时候入库的、被谁借过)。没有目录系统，图书馆的其他一切都无法运转。

Feature Registry 的核心职责可归纳为七个字: "注册、发现、治理"。

内部架构 — Registry Service 的五大子系统
Feature Registry 部署架构
Registry API (gRPC + REST) — 对外统一入口
├ gRPC: 供 Feature Serving SDK / 执行引擎 / 模型平台调用 (高性能，内部系统)
├ REST: 供 Web UI (Feature Market) / Python SDK / CLI 调用 (易用性)
└ K8s Deployment: 4 Pod, 无状态, 水平扩缩

Metadata Store (MySQL 主库 + 只读副本) — 元数据持久化
├ MySQL 8.0, 主从复制 (1 主 + 2 只读)
├ 10 张核心表: entities, feature_views, features, model_bindings, ...
├ 写入量: ~100 QPS (注册/变更低频操作)
└ 读取量: 只读副本承接查询，主库只处理写入

Cache Layer (Redis + 进程内 LRU) — 高频读加速
├ Redis: 缓存 feature_config.pb (序列化的 Protobuf)，TTL=5min
├ 进程内 LRU: Registry API Pod 内的 Go sync.Map, TTL=30s
├ 命中路径: Feature Serving 启动时拉取全量 → 之后增量更新 (Watch 模式)
└ 缓存失效: CDC 事件触发 (MySQL Binlog → 主动失效对应 key)

Event Bus (Kafka topic: feature_registry_events) — 变更通知
├ 任何元数据变更 → 产生事件 → 发送到 Kafka
├ 消费者: 执行引擎 (触发 Job 重建)、Feature Serving (热更新配置)
│ 监控系统 (更新告警规则)、Lineage Service (更新血缘图)
└ 事件类型: VIEW_CREATED, VIEW_UPDATED, VIEW_DEPRECATED, FEATURE_ADDED, ...

Search Index (Elasticsearch) — 特征发现与搜索
├ 索引: Registry 中所有对象的 name/description/tags/owner
├ 支持全文搜索: "找一个和用户消费能力相关的特征"
├ 支持 faceted filter: 按 Entity、Owner、Status 过滤
└ 同步方式: MySQL CDC → Kafka → ES Sink

七大核心能力 — Feature Registry 必须实现什么
能力一: CRUD + 版本管理
基础 CRUD: 注册/查询/更新/删除 Entity、Feature View、Feature。

版本管理是 Registry 区别于普通数据库表的核心能力:
• Feature View 每次 Transform DSL 或 Schema 变更 → version++
• 旧 version 不删除，保留完整定义 (供回滚和旧模型引用)
• 每个 version 有独立的 status 状态机: DEV→STAGING→PROD→DEPRECATED→DELETED

// 版本表设计 feature_view_versions { view_id: INT version: INT transform_dsl: TEXT // 该版本的完整 DSL schema_hash: CHAR(64) // Schema fingerprint status: ENUM(DEV,STAGING,PROD,DEPRECATED) created_at: TIMESTAMP created_by: VARCHAR changelog: TEXT // 变更说明 PRIMARY KEY (view_id, version) }
字节规则: PROD 状态的 version 不可修改 (immutable)。要变更只能创建新 version。这保证了线上正在使用的特征定义永远不会被意外修改。
能力二: 特征发现 (Feature Discovery)
问题: 300 个 Feature View、3000 个 Feature。算法工程师怎么知道自己需要的特征是否已存在？

Feature Market (特征市场) — 基于 Registry 的搜索前端:

搜索: 全文搜索 + 标签过滤
• "用户消费" → 命中 user_profile.purchase_level
• tag=["广告","用户侧"] → 列出所有用户广告特征
• entity="User" AND status="PROD" → 所有在线用户特征

详情页 (每个 Feature View):
• 定义: Transform DSL、Schema、更新频率
• 质量: 近 7 天 PSI 图、缺失率趋势
• 使用方: 哪些模型引用了它 (来自 Model Binding)
• 数据样本: 最近一批产出的 Top-10 采样
• Owner: 负责人邮箱/飞书群
• 评分: 基于质量指标 + 使用广度的综合评分

一键引用: 算法工程师点击"使用此特征" → 自动生成 Model Binding 代码片段

Elasticsearch React Frontend
能力三: 血缘追踪 (Lineage)
血缘是一个有向无环图 (DAG)，描述数据从源到消费的完整链路:

Hive Table: dw.user_events ↓ (source_of) Feature View: user_realtime_stats_v3 ↓ (produces) Feature: click_1h, ctr_6h, ... ↓ (used_by) Model Binding: ctr_model_v5 ↓ (deployed_in) AB Experiment: exp_20241120_ctr
血缘的三大用途:

① 影响分析 (Impact Analysis):
上游 Hive 表 dw.user_events 要加一列 → 自动找出所有受影响的 Feature View → 通知 Owner → 避免 Schema 变更导致下游 Job 崩溃。

② 根因定位 (Root Cause):
模型 CTR 下降 → 反查所有使用的 Feature → 哪个 Feature 的 PSI 异常 → 追溯到哪个 Hive 表数据缺失。全链路 5 分钟内定位根因。

③ 废弃检测 (Dead Feature Detection):
某 Feature View 90 天内没有任何 Model Binding 引用 → 自动标记 DEPRECATED → 节省 Tair 存储和 Flink 计算资源。

实现: 血缘关系存储在 MySQL 的关系表 (lineage_edges) 中，用 Neo4j 或 JanusGraph 做图查询加速 (字节早期用 MySQL 递归 CTE，后迁移到图数据库)。

MySQL lineage_edges Neo4j (可选)
能力四: 变更通知 (Change Propagation)
Registry 中的每一次写操作都必须触发下游系统响应。这是 Registry 的"神经传导"功能。

事件驱动机制:
// Registry 写操作 → 事件产生 MySQL INSERT/UPDATE ↓ (Debezium CDC) Kafka topic: feature_registry_events ↓ (多消费者) ├→ 执行引擎: VIEW_UPDATED → 重新编译 DSL + 重建 Job ├→ Feature Serving: VIEW_UPDATED → 热更新 feature_config ├→ 监控系统: FEATURE_ADDED → 注册新的监控规则 ├→ Lineage Service: 更新血缘图 ├→ Search Index: 更新 ES 索引 └→ Audit Log: 记录变更历史 (谁在什么时候改了什么)
事件格式:
{ "event_type": "FEATURE_VIEW_UPDATED", "timestamp": "2024-11-20T10:30:00Z", "entity_type": "FeatureView", "entity_id": 42, "view_name": "user_realtime_stats_v3", "old_version": 2, "new_version": 3, "changed_fields": ["transform_dsl", "features"], "operator": "alice@bytedance.com", "change_summary": "新增 active_minutes 特征" }
Debezium CDC Kafka
能力五: feature_config 生成与分发
这是 Registry 最高频的在线能力。feature_config 是 Feature Serving 的"菜单"——它告诉 Serving SDK 每个模型需要哪些特征、从哪里取、slot 编号是什么。

// feature_config.pb (Protobuf 序列化) // 由 Registry 根据 Model Binding + View + Feature 自动生成 model_config { model_id: "ctr_model_v5" shared_views: [ // User + Context (所有候选共享) { view_name: "user_profile_v2", features: [ {slot:1, name:"gender", type:ID, key:"uf:p:{user_id}", default:0}, {slot:2, name:"age_bucket", type:ID, key:"uf:p:{user_id}", default:0}, ]}, { view_name: "user_context_v1", features: [ {slot:30, name:"hour_bucket", type:ID, source:ON_DEMAND, default:0}, ]} ] per_item_views: [ // Ad + Cross (每个候选独立) { view_name: "ad_meta_v2", features: [ {slot:20, name:"category", type:ID, key:"af:m:{ad_id}", default:0}, ]}, { view_name: "user_x_advertiser_v1", features: [ {slot:40, name:"cross_ctr_7d", type:FLOAT, key:"cf:uxadv:{user_id}_{advertiser_id}", default:-1.0}, ]} ] }
生成时机:
• Model Binding 变更时 → 重新生成
• Feature View 新增字段时 → 增量更新
• Feature View 版本切换时 → 整体替换

分发机制:
① 生成后写入 Redis (key=config:{model_id})
② Feature Serving SDK 启动时全量拉取
③ 运行中通过 Kafka 事件增量更新 (热更新，无需重启)

Protobuf Config Gen Redis Cache
能力六: 权限与多租户
多租户 (Project) 隔离:
字节内部有多个广告业务线 (穿山甲/巨量引擎/电商广告)，每个业务线是一个 Project，Feature Registry 用 Project 隔离元数据。

Project: ads_chuanshanjia └ Entity: user, ad, creative, ... └ Feature View: user_profile_v2, ... Project: ads_juliang └ Entity: user, ad, ... // 与穿山甲独立 └ Feature View: user_profile_v3, ...
权限模型 (RBAC):
Role | Create View | Read View | Update View | Delete -----------+-------------+-----------+-------------+-------- Admin | All | All | All | All Owner | Own Project | All | Own Views | Own Member | Own Project | All | No | No Viewer | No | All | No | No
跨 Project 共享:
user_profile 等基础特征被多个 Project 共享。通过"共享 Feature View"机制: Owner Project 标记 View 为 shared → 其他 Project 可以 reference (只读)。

RBAC Project Isolation
能力七: Schema 兼容性校验
Registry 在接受 Feature View 变更时，必须自动校验新版本与旧版本的兼容性，防止"改一个字段崩全部模型"。

四类校验规则:

Rule 1: 新增字段 → 允许 (FlatBuffer 向后兼容。新字段追加在末尾，旧 reader 忽略。)
Rule 2: 删除字段 → 检查引用 (有 Model Binding 引用 → 拒绝。无引用 → 允许但标记 deprecated。)
Rule 3: 修改字段类型 → 拒绝 (INT64→FLOAT32 会导致反序列化错误。必须创建新 Feature + 迁移。)
Rule 4: 修改 Transform DSL → 要求新版本 (不允许原地修改 PROD version 的 DSL。)

校验时机: 在 Registry API 的写入层 (before MySQL INSERT/UPDATE)。校验不通过 → 返回详细的兼容性错误信息 → 写入被拒绝。

Registry API 设计 — 对外暴露的核心接口
写入类 API (低频, ~100 QPS)
// Entity 管理 RegisterEntity(name, join_keys, desc, owner) → entity_id UpdateEntity(entity_id, desc, owner) DeleteEntity(entity_id) // 需检查无 View 引用 // Feature View 管理 RegisterFeatureView(entity, name, source, transform, store, schedule, features[], owner) → view_id, version UpdateFeatureView(view_id, ...) → new_version // 自动: 兼容性校验 → version++ → 生成新 schema_hash ChangeViewStatus(view_id, version, new_status) // DEV→STAGING: 需通过自动化测试 // STAGING→PROD: 需人工审批 (灰度通过后) // PROD→DEPRECATED: 需检查无 Model 引用 // Model Binding 管理 BindModelToViews(model_id, [{view_id, version, feature_ids, slot_mapping}]) UnbindModel(model_id, view_id) // 质量指标写入 ReportQualityMetrics(feature_id, date, psi, missing_rate, ...)
读取类 API (高频, ~10K QPS)
// 配置拉取 (Feature Serving 核心接口) GetModelFeatureConfig(model_id) → feature_config.pb // 返回该模型的完整特征配置 (含 slot mapping) // 高频调用, 必须走 Redis 缓存 // 元数据查询 GetEntity(entity_id) → Entity GetFeatureView(view_id, version?) → FeatureView GetFeature(feature_id) → Feature ListFeatureViews(entity_id?, status?, tags?) → []FeatureView // 搜索 (走 Elasticsearch) SearchFeatures(query, filters) → SearchResult // 血缘查询 GetUpstream(object_type, object_id, depth?) → LineageGraph GetDownstream(object_type, object_id, depth?) → LineageGraph GetImpactAnalysis(object_type, object_id) → ImpactReport // 质量查询 GetQualityHistory(feature_id, start_date, end_date) → []Metrics // Watch (长轮询/gRPC Stream) WatchConfigChanges(model_id) → Stream // Feature Serving 用此接口实现热更新
GetModelFeatureConfig 是 Registry 中最关键的 API。Feature Serving SDK 在 Ad Server 启动时调用它一次获取全量配置，之后通过 WatchConfigChanges 接收增量更新。由于 Ad Server 有 ~3000 台实例，启动时的并发全量拉取会产生瞬时 QPS 洪峰。

解法: feature_config.pb 序列化后存入 Redis (key=config:{model_id})。Feature Serving SDK 先查 Redis (P99 <1ms)，Redis miss 才查 Registry API (P99 ~5ms)。Redis 的 TTL=5min，但 CDC 事件驱动主动失效——变更后 ~1s 内所有缓存就失效，SDK 的下一次拉取会获得新配置。

Registry 与 Feature Serving 的交互 — 配置热更新机制
Feature Serving SDK 如何消费 Registry
启动阶段 (Ad Server 进程启动)
├ Feature Serving SDK 初始化
├ 调用 Registry: GetModelFeatureConfig(model_ids=[...]) → 全量 configs
├ 解析 feature_config.pb → 构建内存数据结构:
│ ConfigManager { model_id → ViewConfig[] → SlotConfig[] }
├ 根据 config 中的 key_template 初始化 Key Generator
├ 根据 config 中的 store_config 初始化 Tair 连接池
└ SDK Ready → 开始接受请求

运行阶段 (持续)
├ 后台 goroutine: WatchConfigChanges(model_ids) → gRPC Stream
├ 收到变更事件:
│ 事件类型 A: Feature 新增 → 追加到 ConfigManager (原子操作)
│ 事件类型 B: Feature View 版本切换 → 替换整个 ViewConfig (原子操作)
│ 事件类型 C: Model Binding 变更 → 重新拉取全量 config
├ 所有更新都是原子操作 (Go: atomic.Value / C++: shared_ptr swap)
│ 当前正在处理的请求继续使用旧 config，新请求使用新 config
└ 无需重启 Ad Server，零停机时间
Watch 机制的容错
gRPC Stream 断开怎么办？
• 自动重连 (指数退避: 1s, 2s, 4s, 最大 30s)
• 重连后重新全量拉取一次 config (防止断开期间错过事件)
• 断开期间使用内存中的旧 config (不影响服务)

Registry 不可用怎么办？
• Feature Serving SDK 在本地磁盘缓存最后一次成功拉取的 config (JSON 文件)
• Registry 不可用时从本地磁盘加载 → 可以正常服务 (用旧 config)
• 代价: 错过 Registry 中的变更，直到 Registry 恢复

字节实践: SDK 的本地缓存路径: /var/cache/bytefeature/configs/{model_id}.pb。每次从 Registry 成功拉取后更新此文件。启动时加载顺序: Redis → Registry API → 本地磁盘缓存。三级 fallback 确保 100% 可启动。
配置一致性保证
问题: 3000 台 Ad Server 同时运行。Feature View 版本切换后，如何保证所有实例在"几乎同时"切换到新 config？

当前方案 (最终一致性, 字节):
• CDC 事件 → Kafka → 各 SDK 消费 → ~1~3s 内全部更新
• 短暂的不一致窗口 (~3s) 中，部分实例用旧 config、部分用新 config
• 对广告系统可接受 (不是金融系统，几秒不一致不影响业务)

强一致方案 (未采用):
• 配置中心 (Consul/Nacos) 做版本原子切换
• 所有 SDK Watch 同一个 Consul key
• key 变更后所有 Watcher 在 ~100ms 内收到通知
• 字节未采用是因为 Consul 作为单点的可用性风险 > 几秒不一致的业务风险

真正需要强一致的场景: 双缓冲 Tair namespace 切换。这个由 Consul 的 atomic flag 控制，而非 Registry Event。
