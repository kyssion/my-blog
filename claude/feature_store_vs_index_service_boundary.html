Feature Store vs 索引构建服务 — 职责边界
真实生产系统中 Embedding 从"特征"变为"可检索索引"的过程，涉及两个不同系统的协作
0
核心结论 — Feature Store 的职责在 Embedding 写入 KV 后结束
你的判断完全正确。在字节和阿里的真实架构中，Feature Store 负责的是 Embedding 的生产和 KV 存储，而向量索引的构建和部署由另一个独立系统负责——在字节叫召回引擎服务 (Recall Engine Service)，在阿里叫BE (Basic Engine) / HA3 索引构建平台。

两者的边界可以用一句话概括：
Feature Store 产出 Embedding 值 → 存入 Tair/Hive (到此为止)
Index Builder 从 Tair/Hive 读取 Embedding → 构建向量索引 → 部署到 VE-KNN/Proxima (另一个系统)

Feature Store 不知道也不关心 Embedding 最终会被谁消费——它可能被 Feature Serving 直接拉取作为精排特征 (这是 Feature Store 的管辖范围)，也可能被 Index Builder 读取去构建向量索引 (这不是 Feature Store 的管辖范围)。
1
三个独立系统及其各自职责
完整的 Embedding 生命周期涉及三个系统
系统 A: Feature Store (ByteFeature / PAI-FeatureStore)
├ 职责: Embedding 的生产、存储、版本管理、质量监控
├ 输入: 模型推理输出 (双塔 User/Ad Tower 的 forward 结果)
├ 输出 1: Tair KV → key="uf:emb:{user_id}", value=FP16[128]
│ (供 Feature Serving 在线拉取，作为精排模型的 dense 特征)
├ 输出 2: Hive 表 → feature_output.ad_embedding/ds=today
│ (供 Index Builder 离线读取构建索引)
└ 边界: 到此结束。Feature Store 不负责索引构建。

系统 B: Index Builder (索引构建服务)
├ 职责: 从 Feature Store 的存储中读取 Embedding，构建向量索引并部署
├ 输入: Hive 表中的 ad_embedding (从 Feature Store 产出)
│ + 广告元信息 (品类/地域/预算状态，来自广告投放系统)
├ 做什么:
│ ① 读取全量广告 Embedding + 属性 (Spark Job)
│ ② 调用 Faiss 构建 HNSW+PQ 索引
│ ③ 构建属性倒排/Bitmap 索引
│ ④ 索引分片 + 上传到索引存储 (HDFS)
│ ⑤ 通知 Recall Engine 加载新索引 (双缓冲切换)
├ 调度: 独立的 Airflow DAG (如每小时 xx:30 触发)
│ 依赖 Feature Store 的 Embedding 产出完成
└ Owner: 通常是召回/检索团队，不是特征团队

系统 C: Recall Engine (在线召回引擎)
├ 职责: 加载索引、服务在线 ANN 检索请求
├ 引擎: VE-KNN (字节) / Proxima (阿里) / Milvus (开源)
├ 做什么:
│ ① 从 HDFS 加载 Index Builder 产出的索引文件
│ ② 服务在线 gRPC 请求: query_embedding → Top-K ad_ids
│ ③ 管理增量缓冲 (新广告实时写入)
└ Owner: 召回/检索团队
组织架构上的分离: 在字节跳动内部，Feature Store (ByteFeature) 由基础架构/数据平台团队维护，Index Builder 和 Recall Engine 由广告引擎/召回团队维护。两个团队通过 Hive 表和 Tair 作为数据契约 (Data Contract) 交互，各自独立迭代。这种组织边界直接反映在系统架构上。
2
系统间的数据流和依赖关系
以广告 Embedding 为例的完整数据流
02:00 — Feature Store 触发 ad_dssm_embedding 的 Batch Materialization
├ 双塔模型 Ad Tower 对全量广告做 forward 推理
├ 输出 Hive 表: feature_output.ad_embedding_v1/ds=today
│ Schema: (ad_id BIGINT, embedding ARRAY<FLOAT>, category_id INT, ...)
├ 同时写入 Tair: key="af:emb:{ad_id}" (供 Feature Serving 精排使用)
├ 完成时间: ~03:30
└ Feature Store 的工作到此结束

03:30 — Index Builder 的 Airflow DAG 被依赖触发
├ HivePartitionSensor 检测到 feature_output.ad_embedding_v1/ds=today 就绪
├ 同时读取广告投放系统的元数据 (广告状态/预算/定向条件)
├ JOIN: embedding 表 × 广告元数据表 → 完整的索引输入
├ 过滤: 只索引"在投"状态的广告 (下线/暂停的不入索引)
├ Spark Job 中调用 Faiss 构建 HNSW+PQ 索引
├ 构建属性倒排索引 (category, region, budget_status)
├ 索引分片 + 上传 HDFS
└ 完成时间: ~04:30

04:30 — Recall Engine 加载新索引
├ Index Builder 通知 Recall Engine: "新索引就绪"
├ Recall Engine 从 HDFS 下载索引文件到本地
├ 加载到内存 (双缓冲: 新索引加载完毕后原子切换)
└ 新索引上线，开始服务在线检索请求
依赖关系的实现方式:

Index Builder 如何知道 Feature Store 的 Embedding 已经产出完毕？两种主流方式:

方式一: Airflow 跨 DAG 依赖 (字节)
Feature Store 的 DAG (fv_ad_embedding_v1) 完成后，Index Builder 的 DAG (idx_ad_recall) 中的 ExternalTaskSensor 感知到上游完成 → 触发索引构建。两个 DAG 在同一个 Airflow 集群但属于不同 Owner。

方式二: 数据就绪事件 (阿里)
Feature Store 的 Materialization 完成后，向 MetaService 发送"分区就绪"事件 (类似 Hive metastore 的 partition event)。Index Builder 订阅此事件，收到后启动构建。更加解耦，不需要 Airflow 跨 DAG 依赖。
3
为什么要分离 — 不让 Feature Store 直接写向量索引的原因
原因一: 关注点不同
Feature Store 关心的是特征的"生产、存储、版本、质量"——它管理的是 KV 形态的数据 (key=entity_id, value=特征值)。

Index Builder 关心的是"索引算法、分片策略、查询性能"——它管理的是专用检索数据结构 (HNSW 图、PQ 码本、倒排表)。

两者的技术栈完全不同: Feature Store 是数据工程 (Spark/Flink/Tair)；Index Builder 是检索工程 (Faiss/自研 ANN/C++ 高性能)。让一个系统同时精通两个领域是不现实的。
原因二: 索引需要额外信息
向量索引不只是"把 Embedding 存进去"这么简单。它还需要:

• 广告状态过滤: 下线/暂停/预算耗尽的广告不应该入索引。这个信息来自广告投放系统，不在 Feature Store 中。

• 属性索引构建: category_id, region_id 等倒排索引需要来自广告投放系统的定向配置，Feature Store 不持有这些数据。

• 索引参数调优: HNSW 的 M、efConstruction、PQ 子空间数等参数由召回团队根据检索精度/延迟 tradeoff 调优，与 Feature Store 无关。

Index Builder 需要 JOIN 多个数据源——Feature Store 只是其中之一。
原因三: 更新频率不同
Feature Store 中 Embedding 的更新频率和索引重建频率不一定一致:

• Feature Store 的 ad_embedding: 每天凌晨全量更新 (T+1)
• Index Builder 的索引重建: 每小时一次 (因为广告状态每小时变化——新广告上线、旧广告预算耗尽)

索引每小时重建时，Embedding 不变 (还是 T+1 的版本)，但广告的"是否在投"状态变了。Index Builder 需要用最新的广告状态重新过滤 + 重建属性索引，而向量索引部分可以复用。

这说明索引重建的触发条件和 Embedding 更新的触发条件是解耦的。
原因四: 故障隔离
Feature Store 故障 (如 Embedding 产出延迟) 不应该直接导致向量召回不可用。Index Builder 有自己的容错机制:

• 今天的 Embedding 没产出？Index Builder 用昨天的 Embedding + 今天的广告状态重建索引。召回质量略降但服务不中断。

• Tair 故障导致 Embedding KV 不可读？只影响 Feature Serving 的精排特征拉取。Index Builder 从 Hive 读，不受 Tair 影响。

• Index Builder 自身故障？Recall Engine 继续用上一版索引服务。Feature Store 完全不受影响。

分离后任何一个系统的故障都被控制在自己的范围内。
4
同一份 Embedding 的两条消费路径
Feature Store 产出的同一份 ad_embedding 被两个完全不同的下游系统消费，用于不同目的。这是"生产者-消费者"模式的典型实践。
路径一: Feature Serving 消费 (精排)
消费者: Feature Serving SDK (嵌入 Ad Server)
读取源: Tair KV (key="af:emb:{ad_id}")
用途: 作为精排模型的 dense 输入特征。候选广告的 128d 向量直接送入 MLP。
读取时机: 每次广告请求，实时拉取
延迟要求: <2ms (Tair P99)
数据格式: FlatBuffer 序列化的 FP16 数组

这条路径完全在 Feature Store 的管辖范围内——从 Materialization 到 Tair 到 Feature Serving，全链路由 Feature Store 平台管理。
路径二: Index Builder 消费 (召回)
消费者: Index Builder (召回团队的独立服务)
读取源: Hive 表 (feature_output.ad_embedding_v1)
用途: 构建 HNSW+PQ 向量索引，部署到 VE-KNN/Proxima
读取时机: 每小时/每天定时任务
延迟要求: 小时级 (离线批处理)
数据格式: Hive Parquet 中的 ARRAY<FLOAT> 列

这条路径在 Feature Store 的管辖范围之外——Feature Store 只负责确保 Hive 表分区按时就绪，不关心下游怎么使用。Index Builder 从 Hive 读取后，执行索引构建、分片、部署等一系列操作。
为什么 Index Builder 从 Hive 读而不从 Tair 读?

理论上 Index Builder 可以从 Tair 批量读取 Embedding。但实际中几乎不这么做，原因:

① 批量 scan 会冲击在线 Tair: 索引构建需要全量读取 1000 万条 Embedding。从 Tair 批量 scan 会产生巨大的读 QPS 洪峰，影响在线 Feature Serving 的延迟。Hive/HDFS 是天然的批量读取存储，对在线系统零影响。

② Hive 有分区版本: Hive 表按 ds 分区，天然支持"读昨天/读今天"的版本选择。如果今天的 Embedding 有问题，Index Builder 可以回退到 ds=yesterday 重建索引。Tair 是 last-write-wins，没有版本回溯能力。

③ 属性 JOIN 在 Hive 中做更自然: Index Builder 需要 JOIN 广告元数据。在 Spark SQL 中 JOIN 两张 Hive 表是最自然的。从 Tair 读 Embedding + 从 MySQL 读广告属性 → 再在内存中 JOIN，工程复杂且容易出错。

例外情况 — Feature Store 确实会直接写向量引擎的场景
虽然主流是分离的，但有少数场景 Feature Store 会直接与向量引擎交互。
例外一: 小规模向量索引
一些非核心场景 (如创意去重的向量索引) 的规模较小 (~500万向量)，不需要专门的 Index Builder。Feature Store 的 Batch Materialization Job 可以直接将 Embedding 写入 Milvus (通过 Milvus SDK 作为一种特殊的 Sink)。

这类场景通常将 Milvus 视为"另一种在线存储" (类似 Tair)，在 Feature View 配置中指定 store_type: MILVUS。

但核心召回引擎 (VE-KNN/Proxima) 的索引构建从不由 Feature Store 直接执行。
例外二: 实时增量写入
新广告上线时，广告投放系统会触发一个事件 → 模型推理服务生成 ad_embedding → 同时写入两个地方:

① Tair (Feature Store 管辖) — 精排特征
② Recall Engine 的实时增量接口 (Recall Engine 管辖) — 实时可检索

这两个写入通常由同一个 Flink Job 或微服务完成 (称为 "Ad Lifecycle Service")，它既不属于 Feature Store 也不属于 Recall Engine，而是广告投放系统的一部分。

Feature Store 的 Flink Stream Job 只负责用户侧 Embedding 的更新 (用户维度)，不负责广告上线/下线的生命周期事件 (广告维度)。
总结: Feature Store 是 Embedding 的"生产工厂"和"KV 仓库"，Index Builder 是"索引工匠"，Recall Engine 是"在线搜索引擎"。三者通过 Hive 表 + Tair KV 作为数据契约交互，各自独立迭代和运维。这种职责分离是大型广告系统架构成熟度的标志。
