可以的，1w+ QPS 在“有召回+粗排+精排+竞价”的体系下是做得到的，关键在于：

1. **你想象的是：每次请求都从几百万广告里全扫一遍 + 跑大模型。**
2. **真实线上是：绝大部分重活提前/旁路做掉，线上只做“非常轻、非常窄的一条链路”。**

我分几点拆给你看。

---

## 一、先算一笔账：1w QPS 其实没你想的那么夸张

假设一台机器 32 vCPU：

- 1w QPS / 32 核 ≈ 312 请求 / 秒 / 每核  
- 等价于：**每个核平均有 ~3.2ms CPU 时间来处理一条请求**（在 100% 利用率下）
- 实际上我们会控制在 50–70% CPU 利用率，那就给每条请求预留个 1–2ms 左右的 CPU 时间

**也就是说：只要你能把“每次请求的所有逻辑”控制在 1–2ms CPU 开销（多核并发），10K QPS 完全现实。**  

所以关键问题不是“1w QPS 不可能”，而是：**怎么把每次请求的工作量压到 1–2ms 以内**。

---

## 二、召回/粗排/精排/竞价不是真的“一条链全放在一个进程里做所有事”

真实生产架构里，一般是这样拆的（不同公司名字不同，思路类似）：

1. **离线 & 近线做掉重活**
   - 训练大模型、生成广告/用户向量、建索引、挖规则、人群包等
   - 把广告按各种 targeting 条件建好**倒排索引 / 向量索引**，加载在内存

2. **在线一条请求真正做的事（极简版）：**
   1. RTB 请求到达 → 解析请求、拿到设备ID/地理位置/基本画像 ID
   2. **用定向+索引快速过滤掉绝大多数广告**，只留几百～几千条候选（召回）
   3. **粗排：用很轻的模型/打分规则，把几百～几千缩到几十～几百**
   4. **精排：用稍微重一点的模型，只在 top K（比如 20～100 条）上跑**
   5. 竞价：按 eCPM 之类规则排序，选出胜出广告，出一个出价

> 重点：**不是“几百万广告都跑了一遍召回+粗排+精排+模型”**，而是  
> 每次请求**只对一个非常小的候选集跑很轻的逻辑 & 小模型。**

---

## 三、每一层实际是怎么做到“很快”的？

### 1. 召回：靠索引 + 预处理，不是全表扫描

常见做法：

- 把广告按各种维度建索引：  
  - 地域、时间段、性别、兴趣标签、人群包、预算状态、频次状态…
- 每个维度是一堆**内存里的 posting list / bitmap / hash 表**，做交集即可：
  - 例如：  
    - 地域 = 北京 → 一个广告ID集合  
    - 行业 = 教育 → 一个广告ID集合  
    - 人群包 = “高意向人群包A” → 一个广告ID集合  
    - 最终候选 = 这几个集合的交集 → 通常只有几百～几千广告

这个过程：

- 全部在**内存+CPU**里完成
- 逻辑是**大量位运算 / 索引查找**，非常快
- 典型延迟：**几十到几百微秒级**

---

### 2. 粗排：便宜的模型 + 很少特征 + 单机内存特征

粗排最主要目的：**快速把几百～几千条候选缩到几十～几百条**，所以：

- 常用的模型非常轻：
  - 线性模型（LR）
  - 小规模 GBDT（几十棵树）
  - 简单打分公式（历史 CTR、出价、质量分的组合）

- 特征来源：
  - 广告侧：出价、类型、行业、历史统计特征（CTR/CVR）、质量分…
  - 用户侧：age/sex/兴趣大类、人群包标签ID 等简单画像  
  - 这些特征**大多预先存在内存 KV / 本机内存结构里**，一次请求是本地读

- 性能大致能做到：
  - 每个候选广告**打一次分在 1～5 微秒级**（C++/Go 优化后）
  - 1000 条候选 × 5µs = 5ms（这只是单线程上限，实际会多线程/向量化/批处理，实耗更低）

所以**粗排放在一个独立服务 + 多线程 + 批处理后，单位请求的整体 CPU 时间是可控的**。

---

### 3. 精排：模型重一点，但只在很少的 top-K 上运行

精排常见设计：

- 用稍微复杂一点的模型：
  - GBDT+LR
  - 小 DNN（几层 MLP，几十到几百维 embedding）
  - 或者用大模型 distillation 之后的“学生模型”

- 但关键是：  
  - **只在 top 50 ～ top 100 之类的候选上跑**  
  - 每次请求不会超过几百次 inference

- 性能方面：
  - 小 DNN 单次前向（几十～百维输入）做得好的情况下：
    - 单核几十微秒～一两百微秒一条都可以做到
  - **再加上批处理**（同一批请求打成 batch，在张量库里一次向量化计算），会明显更快：

大致量级（举例，方便你有感）：

- 假设：  
  - 精排模型一次 batch 里处理 128 条候选广告
  - 整个 batch 前向耗时 1ms
- 等价于：**每条候选 ≈ 1ms / 128 ≈ 7.8µs CPU 时间**

在一个 32 核节点里，用多线程+批量，你完全可以支撑：

- 10k QPS × 每请求 50 条候选  
→ 50 万次打分 / 秒  
- 以每 10µs 一次打分估算 → 5 秒 CPU 时间 / 秒 ≈ 500% core CPU  
- 折成 32 核，就是每核 15% 左右的负载——**完全可行**

（上面只是说明级别：模型小、候选少+批量，算力是够用的）

---

### 4. 竞价：基本是 O(K) 的轻量级逻辑

最后的竞价通常就是：

- 对精排后的少量候选（几十个）
- 做一堆非常轻的操作：
  - eCPM 计算
  - 预算/频次检查
  - 简单 rule（封顶价、Pacing调整）
  - 排序取 Top1/TopN

这部分的 CPU 开销通常是**几十微秒级**，在整体链路里几乎可以忽略。

---

## 四、真正拖慢 RTB 的，往往不是模型，而是「乱七八糟的 RPC + I/O」

所以高 QPS 的关键反而是避免：

1. **请求链路里有大量同步 RPC：**
   - 比如：每次都实时拉用户画像、实时查数据库、实时查 Redis 好几次…
   - 这些如果没做好缓存 / 限流，一下子就把延迟拉爆

2. **磁盘 I/O：**
   - 正常 RTB 决策链路是**绝对不能有磁盘随机 I/O** 的，一切都要 in-memory

真实的高性能 RTB 系统会做这些事：

- 用户画像、广告特征、统计特征：**全部在内存 KV 或本机内存结构里**
- 真要访问远程 Redis / KV，也会有：
  - 本地缓存 + 热 key 预取
  - 异步更新 / 降级策略
- 各个阶段（召回、粗排、精排）拆成不同服务，用：
  - 多线程
  - 无锁 / 少锁结构
  - 批处理 + 向量化
  - 高性能序列化（Protobuf、自研二进制协议）

所以**真正影响你能不能 10k+ QPS 的，是“有没有把所有慢 I/O、重逻辑挪出 RTB 核心链路”**。

---

## 五、总结一下你问题里的两个点

> 1）“召回、粗排、精排、竞价这整条链，怎么做到单机 1w+ QPS？”

- 不是“对所有广告做整条链”，而是：
  - 召回用内存索引快速从海量广告中挑出少数候选
  - 粗排用轻模型在几百～几千候选上快速打分筛到几十～几百
  - 精排用稍重一点的模型，只在很少的 top-K（几十～一百）上跑
  - 竞价本身非常轻
- 每条请求实际 CPU 开销**控制在 1～2ms**，多核 + 并发 → 1w+ QPS 没问题。

> 2）“走模型出价不是很慢吗？”

- 真正上线的**在线模型一般都很小**：  
  - LR / GBDT / 小 DNN / 蒸馏学生模型
- 大模型用来：
  - 离线生成特征 / embedding
  - 教学生模型（知识蒸馏）
- 在线模型：
  - 特征多是预计算+内存读
  - 模型本身极度优化+批量预测  
  → 单次预测耗时是**微秒级到十几微秒级**，完全可以承受。

精排粗排，这些模型是直接跑在RTB服务里面的吗？ 还是有专门的精排和粗排服务》？

两种做法都有，但**成熟的大厂通常不是“所有模型都塞进一个 RTB 进程里”**，而是做成**多服务协同**，同时又尽量把重逻辑往边上挪，保证 RTB 主链路够轻。

可以分三类典型架构来理解：

---

## 1. 业界比较主流的一种拆法（偏大规模）

逻辑上大致是这样：

1. **RTB 接入 / 竞价服务（Gateway/Bidder）**
   - 收到外部的 bid request（OpenRTB、自研协议）
   - 做基础过滤、解析、路由
   - 调用后面的「召回 + 排序」链路
   - 最后根据出价、预算、频次等规则选 winner，返回 bid response

2. **广告检索 / 召回服务**
   - 基于：
     - 定向（地域、时段、性别、兴趣、人群包、预算状态…）
     - 内存倒排索引 / bitmap / 向量索引
   - 在海量广告里快速筛出**几百～几千**条候选
   - 这部分大多**直接在服务内存里做索引运算**，模型很轻甚至没有模型

3. **排序服务（内部再拆：粗排 + 精排）**
   - 可以是一个服务里做两层，也可以是两个服务：
     - **粗排**：轻模型（LR/GBDT/简单打分），把几百～几千缩到几十～几百
     - **精排**：复杂一点的模型（小 DNN、GBDT+LR 等），在 topK 上打分
   - 返回一个带分数的候选广告列表给 RTB 服务

4. **预算 / 频控 / 竞价决策服务（可能跟 RTB 合一）**
   - 检查广告主预算、节奏控制（pacing）
   - 频次控制（单用户不超频）
   - 算 eCPM/出价，选 Top1 或 TopN
   - 记录日志、上报曝光/点击/转化数据

在这种模式下：

- **粗排 / 精排模型通常跑在专门的「排序 / 预估服务」里**，不是死嵌在 RTB 接入代码里。
- RTB 服务只负责：
  - 调用召回 / 排序
  - 做拍卖与规则
  - 控制整体超时时间（比如总共 50ms 以内）

---

## 2. “模型内嵌在 RTB 服务” vs “单独的排序服务”

### 方案 A：模型直接跑在 RTB / Bidder 进程里

常见于：小规模 DSP、或大厂里的某些简化链路，比如只跑一个很轻的 LR/GBDT 模型。

**特点：**

- 优点：
  - 没有额外网络耗时（无 RPC），延迟最低
  - 实现简单，一个服务部署就搞定
- 缺点：
  - **模型更新要跟着 RTB 部署**（耦合大）
  - 想用 Python / GPU / 复杂框架比较难，通常得 C++/Go/Java 内嵌推理库
  - 多条业务线/多团队难以共享同一套“预估能力”

**现实用法：**

- 轻量逻辑、简单模型（比如粗排）经常这么干：
  - 在 RTB 里内嵌一个 xgboost / onnxruntime / 自研 LR 打分
  - 甚至写成几行规则打分，根本不叫“模型”

---

### 方案 B：专门的粗排 / 精排（预估）服务

这是大厂更常见的做法：

- 把各种模型统一放到一个或一簇**模型推理 / 排序服务**里：
  - 提供 pCTR、pCVR、pCTR×pCVR 等多种预估
  - 支持不同业务线（广告、内容推荐、搜索排序）共同调用

**优点：**

- 模型迭代和 RTB 解耦：
  - 调整特征、结构、权重只动排序服务，不必动 RTB
- 可以用更合适的技术栈：
  - 后台可以用 C++/Rust/Go + TensorRT/ONNXRuntime/TorchScript
  - 甚至内部用 Python 训练，导出成统一推理格式
- 多业务线复用一套基础设施：
  - 特征服务、模型服务统一管理
  - A/B 实验、灰度发布、监控更集中

**缺点：**

- 多了一跳 RPC：
  - 即使是 IDC 内 gRPC，也要多消耗 0.x～几 ms
  - 所以模型服务需要做**极致优化 + 批处理**，否则延迟吃不消

**现实用法：**

- **精排模型大多在这类服务里跑**：
  - 因为模型重、迭代快、多个系统共用
- 粗排有时也会合并在同一个排序服务里，一次 RPC 做两层排序（内部管线化）

---

## 3. 召回 / 粗排 / 精排 各自常见的部署方式

综合一下常见组合（真实系统里也会混用）：

1. **召回：**  
   - 几乎一定是**专门的检索/召回服务**，和广告索引强绑定
   - 逻辑：
     - 条件过滤（定向、预算、状态）
     - 倒排索引 / bitmap 运算
     - 有时加一点轻模型或向量检索（ANN）
   - 一般不叫“模型服务”，更像是高性能检索系统

2. **粗排：**
   - 轻模型、简单特征，常见两种：
     1. **内嵌在召回服务 / RTB 服务**  
        - 召回完立刻在本机做一轮粗排打分
        - 减少一次 RPC
     2. **跟精排一起在排序服务里**  
        - 排序服务内部先粗排再精排，对外只暴露一个接口

3. **精排：**
   - 重模型、复杂特征，一般都是：
     - **独立的排序 / 预估服务集群**
     - RTB 或召回服务调用它，传入（用户+广告）的特征，拿回分数
   - 为了性能，常见优化：
     - 特征服务 + 排序服务合并部署，减少一跳
     - 批处理多个请求一起预测
     - 用压缩/量化后的模型（小 DNN / 蒸馏模型）

---

## 4. 怎么在这种拆法下还做到 1w+ QPS？

关键点不是“到底是放在一个服务里还是三个服务”，而是：

1. **RTB 主链路的总耗时要控制好**，比如：
   - 接入 + 召回：几 ms 以内
   - 排序服务（粗+精）：几 ms 以内
   - 决策 + 出价：亚 ms～1ms
   - 总和控制在几十 ms 内（RTB 通常要 < 50–100ms）

2. **重逻辑尽量批量、在内存、少 RPC**：
   - 召回/筛选 → 全内存索引操作，无磁盘 I/O
   - 排序 → 批处理模型预测
   - 避免链路上到处是同步 Redis/MySQL 调用

3. **模型服务本身要高性能：**
   - C++/Go + 高性能推理引擎
   - 多线程 + 批量 + 向量化
   - 业务上控制精排候选数量（比如 50～100 条）

在这个前提下，即使中间有“召回服务 + 排序服务”，**单机 1w+ QPS 完全是现实的**。

- **不是所有公司都一样**：  
  - 小体量 / 简单链路：粗排/精排模型有时直接内嵌在 RTB 里跑。  
  - 中大型广告系统：**更常见的是有专门的召回服务 + 排序/预估服务**，RTB 只是 orchestrator 和竞价执行者。

可以先把“粗排要解决的问题”说清楚，再看一般用什么技术。

## 一、粗排在整个链路里的目标

- 输入：召回后的候选广告，一般是 **几百～几千条**  
- 输出：给精排一批更小的候选，一般是 **几十～几百条**  
- 约束：  
  - 延迟非常敏感，**单次请求最好控制在亚毫秒～几毫秒级**  
  - 不能依赖复杂特征拉取和大模型推理

所以粗排的技术特点就是：**轻模型 + 少特征 + 全内存 + 高并发**。

---

## 二、粗排常用的技术/模型类型

### 1. 规则打分 / 线性打分（最常见的基础形态）

很多系统一开始的粗排其实就是一套规则或线性公式，例如：

- `score = α * 预测CTR + β * 出价 + γ * 质量分 + …`
- 甚至更简单：
  - 先按出价过滤一部分
  - 再按历史CTR或质量分做排序截断

**技术实现：**

- 手写规则引擎 / 简单排序函数
- 只用**预先算好的统计特征**（如广告历史CTR、广告质量等级）
- 全部在内存中算，几乎没有额外 RPC

**优点：**

- 极快，延迟几乎可以忽略
- 逻辑可控、容易 debug

**缺点：**

- 精度有限，需要后面的精排模型兜底

---

### 2. 经典机器学习模型（LR / GBDT 等）

这是现在粗排最常见的一类技术：

1. **LR（Logistic Regression / 线性模型）**
   - 特点：计算量非常小，本质就是若干特征乘权重再求和，最后走一个 sigmoid。
   - 常配合：  
     - 手工特征（出价、位置信息、广告类型等）  
     - 预先 embedding 后的 ID 特征（广告ID、user bucket 等）

2. **GBDT / XGBoost / LightGBM（小模型版本）**
   - 特点：几十棵树以内的小模型，深度不大（例如深度 4～6）。
   - 优点：能处理非线性关系，效果比单纯 LR 好不少。
   - 常用于：粗排阶段的 pCTR 粗估。

**工程实现：**

- 使用 C++/Go 内嵌：
  - xgboost / LightGBM 的 C++ 预测库  
  - 自家导出的“树模型执行器”
- 所有特征：
  - 要么是**在线预处理后放内存 KV**  
  - 要么是**简单实时计算**（比如出价、广告时长、设备类型）

**为什么适合粗排：**

- 推理非常快：单条样本微秒级
- 实现成熟：训练工具链和线上预测库都很完善

---

### 3. 简单的 DNN / MLP（小神经网络）

有些系统的粗排也会用很小的 DNN 模型，比如：

- 2～3 层 MLP
- 每层几十～一两百维
- 输入是 embedding 后的特征拼接（user vector + ad vector + context）

**使用场景：**

- 当你已经有一套成熟的 DNN 精排体系，希望粗排也能共享一部分 embedding & 模型架构时
- 但为了性能，粗排用的是**更小的学生模型**或蒸馏后的模型

**工程要点：**

- 通常不会用 Python 直接在线推理，而是：
  - 导出为 ONNX / TorchScript / TensorRT  
  - 在 C++/Go 服务中加载推理引擎
- 必须配合批量预测、线程池等高性能手段，否则容易拖延迟

---

## 三、粗排相关的系统/工程技术

粗排不仅是“用什么模型”，更重要的是这类工程技术：

1. **特征预处理 & 内存KV**
   - 大部分统计特征（历史CTR、曝光次数、用户桶信息）提前离线/近线算好
   - 丢到：
     - 内存KV（自研 / Redis-like）
     - 本进程内存结构
   - 粗排阶段只做 O(1) 查表或简单计算

2. **多线程 + 批处理**
   - 同一请求的一批候选广告，会：
     - 拆分到多线程并发打分，或者
     - 组成 batch 一起喂给模型（向量化加速）
   - 减少一次 RPC/系统调用带来的固定成本

3. **就近部署 / 合并服务**
   - 很多时候**召回 + 粗排会在同一服务里完成**：
     - 召回完直接在本机粗排
     - 避免“召回服务 → 粗排服务”的额外 RPC

4. **轻特征、轻逻辑**
   - 粗排阶段一般不会用特别复杂的交叉特征：
     - 不做太多在线 join
     - 不依赖远程 DB 查询
   - 重特征/复杂组合留给精排

## 四、粗排 vs 精排：技术的取舍

可以简单对比一下：

| 阶段   | 模型复杂度              | 特征数量/复杂度         | 延迟预算（单次请求） | 典型模型                   |
|--------|-------------------------|-------------------------|----------------------|----------------------------|
| 召回   | 无 / 轻规则 / 向量检索 | 少，更多是索引条件     | 几百微秒～数毫秒     | 倒排索引、ANN              |
| 粗排   | 轻模型                  | 少量统计+结构化特征     | 亚毫秒～几毫秒       | 规则打分、LR、小 GBDT、小DNN |
| 精排   | 中重模型                | 特征丰富，交叉较多     | 几毫秒～十几毫秒     | GBDT+LR、大点的DNN/深度模型 |

粗排的核心就是：**在保证延迟极小的前提下，尽可能提高“把好广告留到精排”的命中率**，所以技术选型通常是：

- 有资源、有基础设施：小 GBDT / 小 DNN  
- 资源有限 / 初期：规则 + LR / GBDT

## 一、广告历史 CTR 是怎么准备好的？

### 1. 数据从哪来

典型链路：

1. RTB / 展示 / 点击 日志写入日志系统（Kafka / 日志文件）
2. **离线/流式计算**系统（Flink / Spark Streaming / 自研）消费日志
3. 按关键维度聚合：  
   - 主键：`ad_id`（也可以有 ad_group_id、campaign_id 等多层级）  
   - 统计字段：曝光数、点击数、转化数等，按 **不同时间窗口** 维护：
     - `show_cnt_1h / click_cnt_1h`
     - `show_cnt_1d / click_cnt_1d`
     - `show_cnt_7d / click_cnt_7d` …

4. 聚合结果写入：
   - 在线特征库 / 内存 KV（自研 KV、RocksDB + 内存 cache、Redis）
   - 或者写到 HBase / MySQL 再由特征服务拉到内存

### 2. 算法层面：CTR 怎么算

不会直接用裸的 `click / show`，而是带**平滑和多时间窗**：

- 基本形式（加性平滑）：

  ```text
  ctr = (click + α) / (show + β)
  ```

  - α、β 是先验，常基于全局或类目平均 CTR 调出来的值，避免样本太少时 CTR 极端。

- 多粒度、多时间窗：
  - `ctr_1h`：反映最新趋势，抖动大
  - `ctr_1d`：相对稳定
  - `ctr_7d`：长期水平
  - 模型/打分时可能用多个窗的组合，或者做指数加权平均：

    ```text
    ctr_ewma = λ * ctr_近 + (1-λ) * ctr_远
    ```

- 有的还会做位置偏置修正（position bias）、设备/媒体归一等，这些通常在特征工程里完成。

### 3. 在线使用：粗排怎么拿到这些 CTR

- 在粗排/排序服务里：
  - 收到候选广告列表 `[ad1, ad2, …]`
  - 对每个 ad_id 调一次 **本地或就近的特征 KV**：
    - 拿到一串预计算字段：
      - `show_1d, click_1d, ctr_1d, ctr_7d, recent_ctr, …`
  - 直接作为粗排模型（LR/GBDT/小DNN）的输入特征之一。

- 性能关键点：
  - **绝不允许每条请求现扫日志或查磁盘**，全部是内存结构 + 批量读。
  - 常见做法是：在粗排进程里有一层本地 cache，定时从特征服务/底层 KV 拉热数据。

## 二、广告质量等级（质量分）怎么来的？

“广告质量等级 / 质量分”一般是一个 **0–1 或 0–100 的综合指标**，背后会综合很多信号：

### 1. 典型会用到的信号

- 正向信号：
  - 历史 CTR / CVR（点击率、转化率）
  - 停留时长、页面深度、二跳率
  - 转化价值（GMV、有效线索率）

- 负向信号：
  - 用户负反馈：点“不感兴趣”“屏蔽此广告”“举报”等
  - 快速关闭/返回率异常高
  - 安装后快速卸载率（对应用广告）
  - 售后投诉率、退款率等（电商）

- 审核 & 合规：
  - 文案/图片是否违反政策
  - 是否使用过激、低俗内容
  - 是否有“夸大宣传”标签等

### 2. 质量分如何计算

常见两种思路：

1. **规则 + 打分公式**
   - 各指标先做归一化、打档：

     ```text
     ctr_score   ∈ [0,1]
     bad_fb_rate ∈ [0,1]
     complaint   ∈ [0,1]
     ...
     ```

   - 再线性组合或分段规则：

     ```text
     q = w1*ctr_score + w2*cvr_score - w3*bad_fb_rate - w4*complaint - w5*refund_rate
     ```

   - 最后映射到 0–100 或几档：“优 / 良 / 中 / 差”。

2. **训练一个“质量预估模型”**
   - 用历史数据标记哪些广告“优质/差”，用 GBDT / LR / DNN 学一个质量得分
   - 线上直接用这个模型输出的 score 当质量分或其重要输入之一

### 3. 更新与下发

- 计算频率：一般是 **小时级 / 天级** 更新质量分
- 下发方式：
  - 写入特征库 / KV，按 `ad_id -> quality_score`
  - 粗排/精排时读这个字段：
    - 粗排可以直接把质量分作为打分因子之一
    - 质量过低的直接过滤掉（不参与竞价）

## 三、冷启动广告怎么办（没有历史 CTR / 质量分）

冷启动是“新广告/新创意刚上来，没有历史统计”的场景。常用的手段有几类：

### 1. 用“分层平滑”的方式给个合理起点

CTR 这类统计特征，常用 **多层级 + 贝叶斯平滑**：

- 层级示意：

  ```text
  全局层面：       global_ctr
  行业/类目层面：  category_ctr
  广告主/账户层：  advertiser_ctr
  计划/单元层：    campaign_ctr
  广告ID层：       ad_id_ctr （新广告为冷启动）
  ```

- 对于新广告：
  - 如果广告主/计划有历史：
    - 初始 CTR ≈ `campaign_ctr` 或 `advertiser_ctr`
  - 如果广告主也是新号：
    - 初始 CTR ≈ `category_ctr` 或 `global_ctr`

- 实现上就是：  
  当 `ad_id` 级别缺失时，粗排模型读到的是上层平滑后的值，而不是 0。

**示例：**

```text
ctr_ad = (click_ad + α * ctr_parent) / (show_ad + α)
```

- `ctr_parent` 可以是该广告主 / 行业 / 计划的平均 CTR
- `α` 控制“继承程度”，show_ad 越多，越接近自己的实际 CTR

### 2. 质量分的冷启动

质量分同样会做分层 + 默认值：

- 刚审核通过的新广告：
  - 给一个中性档位，例如：质量分 = 60（满分 100）
  - 同时打一个 `is_new_ad=1` 的特征，让模型知道它是冷启动
- 如果广告主整体质量历史较好，可以适当高一点，反之稍低一点：
  - `quality_ad_init = f(quality_advertiser, quality_category, ...)`

随着曝光/点击/负反馈累积：

- 质量分在小时/天级任务里被不断更新
- 低质量会被扣分甚至下线，高质量会被奖励更多流量

### 3. 探索流量（避免新广告永远没机会）

如果粗排/精排只相信“历史特征”，新广告永远输给老广告，所以会显式预留**探索流量**：

- 典型方法：
  - epsilon-greedy：  
    - 90% 流量按现有打分走  
    - 10% 流量在候选中随机/半随机给新广告机会
  - UCB / Thompson Sampling 等多臂老虎机方法（更复杂一点）

- 工程上看：
  - 在粗排/精排的打分里，对 `is_new_ad=1` 的广告做一些“鼓励”:
    - 加一点探索奖励
    - 或者在某个二级排序阶段单独插入一部分新广告

### 4. 利用内容/结构特征做冷启动估计

除了“统计分层”，现在也常用**内容侧/结构侧的相似性**来帮助冷启动：

- 文本、图片、视频内容 embedding：
  - 看这个创意在语义/视觉上更像哪些老广告
  - 用相似广告的 CTR/质量分做一个 prior
- 利用广告主/账户历史：
  - 如果这个广告主之前的广告整体质量不错，新广告初始就给高一点预期
- 使用“模型端冷启动特征”：
  - 文案长度、关键词、落地页结构、按钮文案等，模型可以学到一定质量信号

这些通常是在**精排**里用得更多，但粗排也可以利用简单版本，比如“类目+创意模版类型”的平均 CTR。

---

### 小结

- **历史 CTR / 质量分**：
  - 都是通过日志 → 离线/流式聚合 → 写入特征库 / KV  
  - 粗排时只是 O(1) 查一下，绝不在线现算历史统计。
- **冷启动**：
  - 不会简单地当 0，用 **分层平滑** 从全局/类目/广告主/计划等上层继承一个合理 prior。
  - 质量分给中性起点 + `is_new_ad` 特征。
  - 通过探索流量、内容相似度等方式，给新广告足够试水机会。
