### 第一部分：广告业务架构与核心逻辑（必考，区分度最高）

这部分考察你是否懂广告系统是怎么跑起来的，这是你能否快速上手的关键。

**1. 广告系统的全链路流程是怎样的？**
*   **考点：** 宏观架构能力。
*   **参考回答要点：** 流量方（SSP） -> 广告交易平台（ADX） -> 需求方平台（DSP）。内部流程：请求解析 -> 用户画像获取（DMP） -> 召回（Retrieval/Matching） -> 粗排（Light Ranking） -> 精排（Deep Ranking/CTR预估） -> 策略过滤（频控、黑名单） -> 竞价（Bidding/GSP机制） -> 计费与展示。

**2. 如何设计一个广告召回引擎（Retrieval System）？**
*   **考点：** 倒排索引设计、布尔表达式检索。
*   **核心细节：**
    *   如何存储定向条件（地域、年龄、兴趣）？（倒排索引）。
    *   如何处理复杂的组合逻辑（比如：(北京 OR 上海) AND (男性)）？
    *   **进阶：** 了解 **Roaring Bitmap** 吗？为什么在广告检索中常用它做倒排链的交并差运算？（省内存、位运算快）。
    *   **进阶：** 了解 WAND 算法（Weak AND）吗？如何在召回阶段提前截断低分广告？

**3. 广告计费系统（Billing）如何保证不扣错钱、不超扣？**
*   **考点：** 分布式事务、高并发计数、数据一致性。
*   **场景：** 广告主预算只有100元，瞬间来了1万个点击，如何保证只扣100元？
*   **解法：**
    *   **分布式锁？** 性能太差。
    *   **预扣款/分段锁机制：** 也就是预算拆分（Budget Sharding），将预算分发到不同的扣费实例中。
    *   **高性能计数器：** Redis Lua脚本原子扣减。
    *   **延迟与最终一致性：** 在线部分快速判定是否超限，离线/近线部分做精确对账和回补。

**4. 什么是广告的平滑预算控制（Budget Pacing/Smooth Pacing）？**
*   **考点：** 流量控制算法。
*   **问题：** 如何让广告主的预算在一天内均匀消耗，而不是早上8点就花光了？
*   **解法：** 涉及 PID控制算法 或 概率丢弃算法（根据当前时间进度和预算消耗进度的差异，计算一个概率P，决定是否参竞）。

**5. 广告频控（Frequency Capping）怎么设计？**
*   **场景：** 一个用户一天最多看3次某广告。
*   **难点：** 读写比极高，QPS大。
*   **架构：** 本地缓存（Local Cache）+ 分布式缓存（Redis Cluster）。如何解决数据不一致导致的超限？（通常允许少量误差，或者使用Redis的Hash结构存储计数）。

### 第二部分：高并发系统设计（System Design）

大厂广告工程最看重“在极端压力下系统的稳定性”。

**1. 广告系统的全链路超时（Timeout）如何管理？**
*   **背景：** 整个广告请求必须在 100ms 内返回，否则媒体方会算超时。
*   **考点：** 漏斗式超时控制。
*   **解答：** ADX给DSP 80ms，DSP内部给召回 20ms，给精排 30ms。使用 Context 传递超时时间。如果下游超时，上游怎么处理？（降级、熔断、返回默认兜底广告）。

**2. 面对突发流量（Hot Key / QPS暴增），系统如何自我保护？**
*   **熔断（Circuit Breaking）：** 某个下游服务挂了，直接断开，保护主流程。
*   **降级（Degradation）：** 比如精排算力不足，能不能只走粗排？或者减少召回队列的长度？
*   **限流（Rate Limiting）：** 令牌桶算法、漏桶算法。
*   **热点Key解决：** 某个明星出轨新闻导致流量暴增，Redis热Key怎么解？（LocalCache、热Key探测、Key拆分）。

**3. 特征存储（Feature Store）设计**
*   **场景：** 每次请求需要读取用户画像（User Profile），数据量大且读QPS极高。
*   **考点：** 存储选型。
*   **解答：** 通常使用 Redis Cluster 或 自研的KV存储（如字节的Abase/ByteGraph）。重点考察序列化协议（Protobuf vs JSON）、压缩算法（Snappy/LZ4）、多级缓存策略。

**3. Kafka/消息队列：**

### 第四部分：手撕代码（Coding）

广告工程不像纯算法岗考很难的DP，更偏向**数据结构与实用算法**。

1.  **Top K 问题：**
    *   题目：从海量日志中找出访问最多的10个IP。
    *   解法：Hash分治 + 最小堆（Min-Heap）。
2.  **多路归并（Merge K Sorted Lists）：**
    *   场景：广告召回阶段，有多个队列（比如按CTR排序、按价格排序），如何合并成一个有序列表？
3.  **字符串匹配：**
    *   场景：敏感词过滤。
    *   算法：Trie树（字典树）、AC自动机（多模式匹配）。
4.  **LRU Cache 实现：**
    *   场景：本地缓存淘汰策略。
    *   数据结构：HashMap + 双向链表。
5.  **加权随机算法：**
    *   场景：AB Test分流，或者根据CTR概率选择广告。
    *   算法：前缀和 + 二分查找，或者 Alias Method。

### 第一深挖场景：索引的“准实时”更新（NRT Indexing）

**面试官潜台词：** 广告主修改了出价，或者广告预算花完了，多久能生效？如果延迟1分钟，广告主可能损失几十万，公司可能被投诉。

**1. 题目：广告主把出价从10元改成1元，或者暂停了广告，系统如何保证在秒级（Seconds）内全网生效？**
*   **传统做法的死穴：** 倒排索引通常是每天全量构建一次（Batch），这就导致修改延迟极高。
*   **高阶解法：增量索引（Incremental Indexing）+ 实时流（Real-time Stream）。**
    *   **架构设计：**
        1.  **全量索引（Base Index）：** 每天凌晨生成，只读，使用 mmap 加载，查找快。
        2.  **增量索引（Patch Index）：** 内存中的动态结构（如 SkipList 或 ConcurrentHashMap）。
        3.  **流式更新：** 修改操作 -> MySQL Binlog -> Canal -> Kafka -> 检索服务消费。
    *   **关键点：** 检索时，必须同时查 Base 和 Patch，然后做**合并（Merge）**。
    *   **追问：** 如果 Patch 越来越大，内存爆了怎么办？
        *   **答：** 触发**Compact（合并）机制**。当 Patch 达到阈值，后台异步将 Base + Patch 合并成一个新的 Base，原子替换（Double Buffer Switching）。

### 第二深挖场景：转化归因（Attribution）—— 广告最复杂的逻辑

**面试官潜台词：** 点击发生在广告平台，安装发生在App Store，打开发生在用户的手机上。这三个跨越时空的行为，怎么串起来扣费？（OCPC/CPA业务核心）

**2. 题目：用户早上8点点击了抖音的广告（未下载），下午5点在应用商店下载并激活了App。如何把这个“激活”匹配到早上的“点击”，从而向广告主收钱？**
*   **核心难点：** 跨端、时延（Time Delay）、数据匹配。
*   **工程解法：**
    1.  **点击存储：** 用户点击时，生成全局唯一 ID（ClickID），收集指纹信息（IP+UA+设备ID），存入高吞吐 KV 存储（如 Redis/HBase），设置过期时间（如 7 天）。
    2.  **延迟匹配（Delayed Matching）：** 广告主通过 API 回传激活数据（带设备ID）。后端收到后，去 KV 库里查这个设备ID最近有没有点击记录。
    3.  **归因窗口（Attribution Window）：** 比如规定“点击后24小时内的激活算有效”。
    4.  **Last Click 归因模型：** 如果用户点了3次不同广告，最后激活了，算谁的？（通常算最后一次点击的）。这需要 KV 存储支持覆盖写或列表存储。

### 第三深挖场景：LBS 地理位置定向（Geo-Targeting）

**面试官潜台词：** 倒排索引查关键词很快，但查“我方圆3公里内的广告”怎么查？

**3. 题目：我要投放广告给“北京西二旗方圆 5km 内的用户”，检索系统怎么设计？**
*   **错误回答：** 遍历所有广告算距离。（计算量爆炸）。
*   **初级回答：** 用 Redis 的 GeoHash。（并发高时 Redis 单线程是瓶颈）。
*   **高阶解法：空间索引（Spatial Indexing）—— S2 Geometry (Google) 或 H3 (Uber)。**
    *   **原理：** 将地球表面切分成网格（Cell）。每个网格有一个唯一的 ID（整数或字符串）。
    *   **实现：**
        1.  **广告侧：** 广告主选定圆心+半径。系统将该圆形覆盖的 S2 Cell ID 计算出来，存入倒排索引。 Key = CellID, Value = AdList。
        2.  **用户侧：** 用户请求带经纬度 -> 转换为对应的 S2 Cell ID -> 直接查倒排索引。
    *   **进阶：** 边缘效应怎么处理？（用户在格子边缘）。答：查询时不仅查用户所在的 Cell，还查周围一圈的 8 个 Neighbors。

### 第四深挖场景：流量实验与分层架构（Experimentation）

**面试官潜台词：** 字节/腾讯的广告算法每周迭代几十次，如何保证不同实验之间不冲突，且流量分配公平？

**4. 题目：我们需要同时进行“样式实验”（大图vs小图）和“算法实验”（模型A vs 模型B）。如何设计流量分配，使得做样式实验的人，覆盖到的用户既有模型A的也有模型B的（正交性）？**
*   **考点：** **Google 的重叠实验框架（Overlapping Experiment Infrastructure）**。
*   **解法：** **分层实验（Layered Experimentation）。**
    *   **流量哈希：** `Bucket_ID = Hash(User_ID + Layer_Salt) % 100`。
    *   **正交性（Orthogonality）：** 每一层（UI层、召回层、精排层）使用不同的 Salt（盐值）。
    *   **效果：** 用户在 UI 层被分到“大图组”，进入下一层时，由于 Salt 不同，他又被重新随机打散，均匀分布到“模型A”和“模型B”中。这样两个实验互不干扰。

*   **考点：** 实时流式计算 + 滑动窗口。
*   **解法：**
    1.  **数据流：** 点击日志 -> Kafka -> Flink/Spark Streaming。
    2.  **计算逻辑：** 时间窗口（Windowing）。比如统计“每分钟、单IP、点击次数”。
    3.  **拦截策略：** 如果 `Count > Threshold`，将该 IP 写入 Redis 黑名单。
    4.  **工程难点：** 内存状态太大怎么办？（使用 Bloom Filter 过滤白名单，或 HyperLogLog 做非精确计数）。
    5.  **特征工程：** 什么是**点击注入（Click Injection）**？（比如监测到 Android 安装广播后瞬间伪造点击）。如何防？（检查 点击时间戳 和 安装时间戳 的差值，如果小于正常人类反应时间，判作弊）。

### 第二深挖场景：转化归因（Attribution）—— 广告最复杂的逻辑

**面试官潜台词：** 点击发生在广告平台，安装发生在App Store，打开发生在用户的手机上。这三个跨越时空的行为，怎么串起来扣费？（OCPC/CPA业务核心）

**2. 题目：用户早上8点点击了抖音的广告（未下载），下午5点在应用商店下载并激活了App。如何把这个“激活”匹配到早上的“点击”，从而向广告主收钱？**
*   **核心难点：** 跨端、时延（Time Delay）、数据匹配。
*   **工程解法：**
    1.  **点击存储：** 用户点击时，生成全局唯一 ID（ClickID），收集指纹信息（IP+UA+设备ID），存入高吞吐 KV 存储（如 Redis/HBase），设置过期时间（如 7 天）。
    2.  **延迟匹配（Delayed Matching）：** 广告主通过 API 回传激活数据（带设备ID）。后端收到后，去 KV 库里查这个设备ID最近有没有点击记录。
    3.  **归因窗口（Attribution Window）：** 比如规定“点击后24小时内的激活算有效”。
    4.  **Last Click 归因模型：** 如果用户点了3次不同广告，最后激活了，算谁的？（通常算最后一次点击的）。这需要 KV 存储支持覆盖写或列表存储。

### 第三深挖场景：LBS 地理位置定向（Geo-Targeting）

**面试官潜台词：** 倒排索引查关键词很快，但查“我方圆3公里内的广告”怎么查？

**3. 题目：我要投放广告给“北京西二旗方圆 5km 内的用户”，检索系统怎么设计？**
*   **错误回答：** 遍历所有广告算距离。（计算量爆炸）。
*   **初级回答：** 用 Redis 的 GeoHash。（并发高时 Redis 单线程是瓶颈）。
*   **高阶解法：空间索引（Spatial Indexing）—— S2 Geometry (Google) 或 H3 (Uber)。**
    *   **原理：** 将地球表面切分成网格（Cell）。每个网格有一个唯一的 ID（整数或字符串）。
    *   **实现：**
        1.  **广告侧：** 广告主选定圆心+半径。系统将该圆形覆盖的 S2 Cell ID 计算出来，存入倒排索引。 Key = CellID, Value = AdList。
        2.  **用户侧：** 用户请求带经纬度 -> 转换为对应的 S2 Cell ID -> 直接查倒排索引。
    *   **进阶：** 边缘效应怎么处理？（用户在格子边缘）。答：查询时不仅查用户所在的 Cell，还查周围一圈的 8 个 Neighbors。

### 第四深挖场景：流量实验与分层架构（Experimentation）

**面试官潜台词：** 字节/腾讯的广告算法每周迭代几十次，如何保证不同实验之间不冲突，且流量分配公平？

**4. 题目：我们需要同时进行“样式实验”（大图vs小图）和“算法实验”（模型A vs 模型B）。如何设计流量分配，使得做样式实验的人，覆盖到的用户既有模型A的也有模型B的（正交性）？**
*   **考点：** **Google 的重叠实验框架（Overlapping Experiment Infrastructure）**。
*   **解法：** **分层实验（Layered Experimentation）。**
    *   **流量哈希：** `Bucket_ID = Hash(User_ID + Layer_Salt) % 100`。
    *   **正交性（Orthogonality）：** 每一层（UI层、召回层、精排层）使用不同的 Salt（盐值）。
    *   **效果：** 用户在 UI 层被分到“大图组”，进入下一层时，由于 Salt 不同，他又被重新随机打散，均匀分布到“模型A”和“模型B”中。这样两个实验互不干扰。

### 第五深挖场景：反作弊与风控（Anti-Fraud）

**面试官潜台词：** 广告涉及到钱，如果有人刷点击骗钱怎么办？工程上怎么拦截？

**5. 题目：发现某个 IP 短时间内产生了大量点击，如何实时拦截？（离线清洗来不及）**
*   **考点：** 实时流式计算 + 滑动窗口。
*   **解法：**
    1.  **数据流：** 点击日志 -> Kafka -> Flink/Spark Streaming。
    2.  **计算逻辑：** 时间窗口（Windowing）。比如统计“每分钟、单IP、点击次数”。
    3.  **拦截策略：** 如果 `Count > Threshold`，将该 IP 写入 Redis 黑名单。
    4.  **工程难点：** 内存状态太大怎么办？（使用 Bloom Filter 过滤白名单，或 HyperLogLog 做非精确计数）。
    5.  **特征工程：** 什么是**点击注入（Click Injection）**？（比如监测到 Android 安装广播后瞬间伪造点击）。如何防？（检查 点击时间戳 和 安装时间戳 的差值，如果小于正常人类反应时间，判作弊）。

### 第一补缺：数据一致性与“钱”的深层逻辑（必杀技：复式记账）

我们之前提到了扣费，但还没挖到最底层。广告系统本质上是一个**金融系统**。

**1. 题目：广告主充值了100万，系统不仅要扣费，还要生成财务报表。如何设计数据库表结构，保证哪怕数据库崩了，账也不会乱？**
*   **普通回答：** 用事务，扣减余额表。
*   **满分回答（引入会计思维）：** **复式记账（Double-Entry Bookkeeping）**。
    *   **设计：** 不要只 Update `balance` 字段。要有**流水表（Ledger）**。
    *   **核心：** `Asset` (资产) = `Liability` (负债) + `Equity` (所有者权益)。
    *   **操作：** 每次点击扣费，插入两条记录：
        1.  借：广告主预存账户（-1元）。
        2.  贷：平台收入账户（+1元）。
    *   **优势：** 任何时候，把流水表加起来，如果不等于0，说明系统有Bug。这是财务审计的底线。

**2. 题目：高并发扣费时，MySQL 的 `UPDATE account SET balance = balance - 1 WHERE id = 1` 会导致严重的行锁竞争（Hot Row），怎么解？**
*   **普通回答：** 用 Redis。
*   **满分回答：** **合并写（Group Commit / Request Coalescing）**。
    *   **原理：** 在应用层（或者通过消息队列），把针对同一个广告主 ID 的 100 个扣费请求，合并成 1 个 DB 请求：`UPDATE account SET balance = balance - 100`。
    *   **代价：** 牺牲了毫秒级的实时性，换取了极高的吞吐量。

### 第二补缺：极高可用性架构（必杀技：单元化/Set化）

大厂广告系统不能只靠“集群”活着，必须靠“单元”。

**3. 题目：北京机房彻底断电了，怎么保证广告业务 0 中断？（异地多活）**
*   **盲区：** 很多人只知道“主备切换”，但不知道**流量怎么切**。
*   **满分回答：** **单元化架构（Unitization / Set-based Architecture）**。
    *   **核心思想：** 把流量按 UserID 拆分。
    *   **设计：**
        *   Set A（北京）：服务 UserID % 2 = 0 的用户（含全套 Web、Service、DB）。
        *   Set B（上海）：服务 UserID % 2 = 1 的用户。
    *   **数据同步：** 两个机房的数据库通过 DRC（Data Replication Center）做双向同步（解决冲突是难点）。
    *   **灾难恢复：** 北京挂了，流量切到上海。上海的 DB 里已经有北京用户的全量数据副本，可以直接承接。

### 第三补缺：底层存储引擎的选型（必杀技：LSM Tree vs B+ Tree）

面试官可能会问你：**为什么广告特征存储（KV）不用 MySQL，甚至不用 Redis，而要用 RocksDB（或类似的自研库）？**

**4. 题目：海量广告特征数据，写多读多，且数据量远超内存大小，Redis 存不下，MySQL 写入太慢。怎么办？**
*   **满分回答：** **LSM Tree (Log-Structured Merge-tree)** 原理（RocksDB/HBase/Cassandra 的核心）。
    *   **原理：**
        1.  **写：** 所有写入直接追加到内存（MemTable），变成顺序写，极快。
        2.  **读：** 内存查不到，去磁盘查 SSTable。
        3.  **合并：** 后台不断把小的 SSTable 合并（Compaction）成大的。
    *   **对比：** MySQL 的 B+ Tree 是随机写（页分裂），LSM 是顺序写。广告日志、特征更新是典型的**高吞吐写入**场景，LSM 完胜。

### 第四补缺：微服务治理与故障演练（必杀技：混沌工程）

面试官问：“你怎么保证你的代码上线不出事？”

**5. 题目：在这个庞大的微服务链路中，如果某一个非核心服务（比如‘获取广告图片尺寸’的服务）响应变慢，会不会拖垮整个广告引擎？**
*   **盲区：** 雪崩效应。
*   **满分回答：** **故障隔离与混沌工程（Chaos Engineering）**。
    *   **隔离：** 线程池隔离（Hystrix思想）。图片服务的线程池满了，不要占用召回服务的线程。
    *   **演练：** 主动在生产环境（或预发布环境）注入故障。比如人为把 Redis 延迟调大到 1秒，看系统会不会挂。
    *   **关键词：** 强弱依赖治理。系统启动时，必须明确哪些服务是 Weak Dependency（弱依赖），挂了直接忽略。

### 第五补缺：面试中的“软技能”与“价值观”（最后一公里）

有时候技术都对，但人挂了。因为你没表现出**Ownership（主人翁感）**。

**6. 题目：如果半夜3点，广告收入突然跌了 50%，你正好在 On-call（值班），你该怎么办？**
*   **错误回答：** “我看报错日志，修 Bug。”（太慢了！每分钟损失几百万）。
*   **满分流程（SRE 标准）：**
    1.  **止损第一（Mitigate First）：** 别管什么 Bug，先**回滚（Rollback）**最近一次上线。如果没上线，先**切流（Traffic Shift）**到备用机房。或者开启**降级开关**。
    2.  **通报（Communicate）：** 立刻拉起应急群（War Room），通报老板和上下游。
    3.  **排查（Debug）：** 止损后再看日志、监控（Metrics）、Trace。
    4.  **复盘（Post-mortem）：** 事后写 COE（Correction of Error）报告，分析根本原因（Root Cause），定下 Todo List 防止再犯。
    *   **金句：** **“先恢复业务，再定位问题。”**
