### 10.2 分布式预算控制方案

```
核心问题：多个广告引擎节点同时扣预算，如何保证不超投？

方案一：中心化扣减
  - 每次请求都去 Redis 原子扣减 → 性能瓶颈

方案二：预算分片 + 本地预扣（推荐）
  - 将日预算分配到各节点（如平均分配或按流量比例分配）
  - 每个节点在本地维护预算余额，本地扣减
  - 定期（如每秒）向中心汇报消耗
  - 快花完时向中心申请更多预算
  
  优点：减少中心化访问，提升性能
  缺点：可能存在少量超投（可接受范围内）

方案三：两级扣减
  - 第一级：本地粗扣（过滤明显超预算的）
  - 第二级：异步精确扣减（Kafka → 预算服务）
```

### 10.3 LRU Cache 实现（Go 版本）

```go
type LRUCache struct {
    capacity int
    cache    map[int]*list.Element
    list     *list.List
    mu       sync.Mutex
}

type entry struct {
    key   int
    value int
}

func Constructor(capacity int) LRUCache {
    return LRUCache{
        capacity: capacity,
        cache:    make(map[int]*list.Element),
        list:     list.New(),
    }
}

func (l *LRUCache) Get(key int) int {
    l.mu.Lock()
    defer l.mu.Unlock()
    
    if elem, ok := l.cache[key]; ok {
        l.list.MoveToFront(elem)
        return elem.Value.(*entry).value
    }
    return -1
}

func (l *LRUCache) Put(key int, value int) {
    l.mu.Lock()
    defer l.mu.Unlock()
    
    if elem, ok := l.cache[key]; ok {
        l.list.MoveToFront(elem)
        elem.Value.(*entry).value = value
        return
    }
    
    if l.list.Len() >= l.capacity {
        back := l.list.Back()
        l.list.Remove(back)
        delete(l.cache, back.Value.(*entry).key)
    }
    
    elem := l.list.PushFront(&entry{key: key, value: value})
    l.cache[key] = elem
}
```

## 1. Go 语言（字节/快手主力语言）

### 1.1 Goroutine 与调度器

```
Q1: GMP 模型详解
    - G（Goroutine）、M（Machine/OS Thread）、P（Processor）各自的职责？
    - P 的数量由什么决定？可以动态调整吗？
    - 一个 G 阻塞了会发生什么？M 和 P 怎么处理？

答题要点：
    - P 的数量默认等于 GOMAXPROCS（通常等于 CPU 核数）
    - G 阻塞分两种情况：
      ① 用户态阻塞（channel/mutex）：G 被放入等待队列，P 调度其他 G
      ② 系统调用阻塞（syscall）：M 和 G 绑定阻塞，P 会与 M 解绑，
         找一个空闲 M（或新建 M）继续执行其他 G
    - 调度触发时机：channel 操作、系统调用、go 关键字、GC

Q2: Goroutine 的栈管理
    - 初始栈大小是多少？
    - 栈增长和栈收缩的机制？
    - 连续栈（contiguous stack）vs 分段栈（segmented stack）的区别？

答题要点：
    - 初始栈大小：2KB（Go 1.4+）
    - 栈增长：函数调用前检查栈空间，不够则分配 2 倍大小的新栈，
      将旧栈数据拷贝过去（连续栈方案）
    - 栈收缩：GC 时检查栈使用率，低于 1/4 则缩小
    - 分段栈问题：hot split（频繁在栈边界来回导致性能抖动）

Q3: Goroutine 调度的抢占机制
    - Go 1.14 之前的协作式抢占有什么问题？
    - Go 1.14 的基于信号的异步抢占是怎么实现的？
    - for{} 死循环在 Go 1.14 前后的表现区别？

答题要点：
    - 1.14 前：只在函数调用时插入抢占检查点，纯计算的死循环
      无法被抢占，会导致其他 Goroutine 饿死
    - 1.14 后：通过向 M 发送 SIGURG 信号，在信号处理函数中
      将当前 G 的 PC/SP 保存，切换到调度器，实现真正的抢占
    - 注意：CGO 调用期间仍然无法抢占

Q4: work stealing 和 hand off 机制
    - P 的本地队列和全局队列的关系？
    - 当 P 的本地队列为空时怎么办？
    - 偷取的策略是什么？偷一半？

答题要点：
    - 每个 P 有本地队列（256 容量的环形队列）
    - 新创建的 G 优先放入当前 P 的本地队列，满了则放一半到全局队列
    - P 空闲时的查找顺序：
      ① 本地队列 → ② 全局队列 → ③ 网络轮询器 → ④ 从其他 P 偷取一半
    - hand off：当 M 因为系统调用阻塞，P 会被分离给其他 M
```

### 1.2 内存管理与 GC

```
Q5: Go 的内存分配器（TCMalloc 思想）
    - mcache、mcentral、mheap 的层级关系？
    - 小对象、大对象的分配策略？阈值是多少？
    - span 是什么？mspan 的结构？

答题要点：
    - 分配层级：
      mcache（P 级别，无锁）→ mcentral（全局，有锁）→ mheap（向 OS 申请）
    - 小对象（≤32KB）：从 mcache 的对应 size class 的 span 中分配
    - 微小对象（≤16B 且无指针）：tiny allocator，多个对象合并分配
    - 大对象（>32KB）：直接从 mheap 分配
    - span：连续的内存页（8KB/页），被切分成固定大小的格子

Q6: Go GC 的完整流程
    - 三色标记法的详细过程？白、灰、黑三色的含义？
    - 写屏障（write barrier）的作用？混合写屏障是什么？
    - STW 发生在哪些阶段？持续多久？
    - GC 触发条件？GOGC 参数的含义？

答题要点：
    - 三色标记：
      白色：未扫描（GC 结束后回收）
      灰色：已扫描自身，子对象未扫描
      黑色：已扫描自身和所有子对象
    - 流程：
      ① STW → 开启写屏障，扫描栈上根对象 → Start the World
      ② 并发标记（与用户代码并行）
      ③ STW → 重新扫描（Mark Termination）→ Start the World
      ④ 并发清除
    - Go 1.8+ 混合写屏障：结合插入屏障和删除屏障，
      栈上对象不需要重新扫描，减少 STW 时间到 < 1ms
    - GOGC 默认 100，表示堆增长 100% 时触发 GC
    - Go 1.19 引入 SetMemoryLimit，可以基于内存限制触发 GC

Q7: 内存逃逸分析
    - 什么情况下变量会逃逸到堆上？
    - 怎么查看逃逸分析结果？
    - 逃逸分析对性能的影响？

答题要点：
    - 逃逸场景：
      ① 返回局部变量的指针
      ② 发送到 channel 的指针
      ③ 在闭包中引用的变量
      ④ interface 类型参数（编译器无法确定具体类型）
      ⑤ 栈空间不足（如大数组）
      ⑥ slice/map 存储指针
    - 查看方式：go build -gcflags="-m -m" 
    - 影响：堆分配 → GC 压力增大 → 延迟升高
    - 优化：尽量值传递，避免不必要的指针，预分配 slice

Q8: Go 内存泄漏的常见场景和排查
    - goroutine 泄漏的常见原因？
    - 如何用 pprof 排查？
    - 常见的内存泄漏模式？

答题要点：
    - goroutine 泄漏：
      ① channel 无人读/写导致 goroutine 永久阻塞
      ② 忘记关闭 HTTP response body
      ③ context 未正确传递 cancel
      ④ 死锁
    - 内存泄漏：
      ① slice 的底层数组未释放（大切片中取小切片）
      ② time.After 在 for-select 中使用（每次创建新 timer）
      ③ 全局 map 只增不删
      ④ finalizer 引用导致对象无法回收
    - 排查工具：
      go tool pprof http://localhost:6060/debug/pprof/heap
      go tool pprof http://localhost:6060/debug/pprof/goroutine
      对比两次 heap profile 看增长
```

### 1.3 并发原语

```
Q9: channel 底层实现
    - channel 的数据结构（hchan）包含哪些字段？
    - 发送和接收的详细流程？
    - 有缓冲和无缓冲 channel 的区别？

答题要点：
    - hchan 结构：
      buf（环形缓冲区）、sendx/recvx（发送/接收位置）、
      sendq/recvq（等待队列，sudog 链表）、lock（互斥锁）
    - 发送流程：
      ① recvq 有等待者 → 直接将数据拷贝给等待的 G，唤醒它
      ② 缓冲区有空位 → 写入缓冲区
      ③ 缓冲区满 → 当前 G 封装成 sudog 放入 sendq，挂起
    - select：
      ① 将所有 case 的 channel 随机打乱顺序
      ② 依次加锁检查是否可以操作
      ③ 都不行则将当前 G 加入所有 channel 的等待队列
      ④ 任一 channel 就绪时唤醒 G

Q10: sync 包的核心组件
     - sync.Mutex 的实现？正常模式和饥饿模式？
     - sync.RWMutex 的实现？写优先还是读优先？
     - sync.WaitGroup 的实现？Add 和 Done 的原子操作？
     - sync.Once 的实现？为什么不能用 CAS 替代？
     - sync.Pool 的实现？和 GC 的关系？

答题要点（sync.Mutex）：
    - 正常模式：新来的 goroutine 和被唤醒的 goroutine 一起竞争锁
      新来的有优势（正在 CPU 上运行）
    - 饥饿模式：当一个等待者等待超过 1ms，切换到饥饿模式
      锁直接交给等待队列最前面的 goroutine，新来的不参与竞争
    - 饥饿模式退出条件：等待者是最后一个 或 等待时间 < 1ms

答题要点（sync.Pool）：
    - 每个 P 有私有对象和共享链表
    - Get：先取私有对象 → 取本地共享链表 → 从其他 P 偷 → 调用 New
    - 每次 GC 时 Pool 中的对象会被清除（victim cache 机制延迟一轮）
    - 适用场景：临时对象的复用，减少 GC 压力

Q11: 原子操作 vs 互斥锁
     - atomic 包的底层实现？

     - 什么时候用 atomic，什么时候用 mutex？

### 3.1 TCP 深度

```
Q1: TCP 三次握手的每个细节
    - SYN 包的序列号怎么生成？（ISN - Initial Sequence Number）
    - SYN 攻击的原理？SYN Cookie 怎么防御？
    - 半连接队列和全连接队列？backlog 参数的含义？
    - 全连接队列满了会怎样？半连接队列满了呢？

答题要点：
    Client                    Server
    SYN(seq=x) →              Server 分配半连接资源，放入 SYN 队列
                ← SYN+ACK(seq=y, ack=x+1)
    ACK(ack=y+1) →            Server 从 SYN 队列移到 ACCEPT 队列
    
    SYN Cookie：不分配资源，将信息编码在 ISN 中
    全连接队列满：默认丢弃 ACK（或发 RST，取决于 tcp_abort_on_overflow）
    相关参数：tcp_max_syn_backlog、somaxconn

      ① Leader 接收客户端请求 → 追加到日志 → 发送 AppendEntries RPC
      ② 多数节点确认 → 提交 → 应用到状态机
      ③ 日志一致性检查（prevLogIndex + prevLogTerm）
    - 安全性：Leader 必须包含所有已提交的日志
    - 集群成员变更：Joint Consensus
    - 和 Paxos 的区别？
```

### 6.2 分布式组件

```
Q4: 分布式锁
    
    方案一：Redis 分布式锁
    - 加锁：SET key value NX EX timeout
    - 解锁：Lua 脚本（检查 value 一致再删除）
    - 续期：看门狗（Watchdog）机制 → Redisson 的实现
    - 问题：
      ① 主从切换时锁丢失
      ② 时钟跳跃
    - Redlock 算法：向 N 个独立 Redis 实例加锁，多数成功即成功
    - Redlock 的争议：Martin Kleppmann vs Antirez 的论战
    
    方案二：etcd/ZooKeeper 分布式锁
    - etcd：基于 Lease + Revision 的公平锁
    - ZooKeeper：临时顺序节点 + Watch
    - 优势：CP 系统，更强的一致性保证
    - 劣势：性能不如 Redis
    
    广告系统用哪种？
    - 预算扣减：Redis（性能优先，允许少量误差）
    - 广告状态变更：etcd/ZooKeeper（正确性优先）

Q5: 分布式事务
    
    2PC（两阶段提交）：
    - 阶段一：Prepare（协调者询问参与者是否准备好）
    - 阶段二：Commit/Rollback
    - 问题：同步阻塞、单点故障、数据不一致
    
    3PC：增加 CanCommit 阶段 + 超时机制
    
    TCC（Try-Confirm-Cancel）：
    - Try：预留资源
    - Confirm：确认执行
    - Cancel：取消释放
    - 适用：预算扣减（Try 冻结预算，Confirm 真正扣除，Cancel 解冻）
    
    Saga：
    - 将长事务拆分为多个本地事务 + 补偿事务
    - 编排式 vs 协调式
    
    本地消息表：
    - 写业务数据 + 写消息表在同一个本地事务
    - 定时任务扫描消息表发送消息
    - 消费端幂等处理
    
    最大努力通知：
    - 适用于对一致性要求不高的场景

Q6: 分布式 ID 生成
    - UUID：不递增，不适合做索引
    - 数据库自增：单点瓶颈
    - 数据库号段模式：批量获取一段 ID
    - Redis INCR：性能好，持久化风险
    - Snowflake：
      ① 64位：1位符号 + 41位时间戳 + 10位机器ID + 12位序列号
      ② 时钟回拨问题的解决：等待 / 拒绝 / 使用上次的时间戳
    - Leaf（美团）：号段模式 + Snowflake 的双缓冲
    - 广告系统中的 ID：广告ID、请求ID（trace_id）、订单ID

Q7: 服务治理
    
    服务注册与发现：
    - etcd / ZooKeeper / Consul / Nacos 的对比
    - 健康检查机制？心跳 vs 主动探测
    
    负载均衡：
    - 随机 / 轮询 / 加权轮询 / 最少连接 / 一致性哈希
    - 一致性哈希的虚拟节点？
    - P2C（Power of Two Choices）：随机选两个节点，选负载低的
      → gRPC 默认的负载均衡策略
    
    限流：
    - 固定窗口 / 滑动窗口 / 漏桶 / 令牌桶
    - 单机限流：Go 的 golang.org/x/time/rate（令牌桶）
    - 分布式限流：Redis + Lua
    ```lua
    -- 滑动窗口限流 Lua 脚本
    local key = KEYS[1]
    local window = tonumber(ARGV[1])
    local limit = tonumber(ARGV[2])
    local now = tonumber(ARGV[3])
    
    redis.call('ZREMRANGEBYSCORE', key, 0, now - window)
    local count = redis.call('ZCARD', key)
    if count < limit then
        redis.call('ZADD', key, now, now .. math.random())
        redis.call('EXPIRE', key, window / 1000)
        return 1
    end
    return 0
    ```
    
    熔断：
    - 三种状态：Closed → Open → Half-Open
    - 触发条件：错误率 / 慢调用率超过阈值
    - 熔断期间快速失败，定期放行探测请求
    
    降级：
    - 非核心功能降级（如广告系统中：精排降级为粗排）
    - 返回兜底数据
    
    超时控制：
    - 超时传播：上游超时应传递给下游
    - 超时计算：deadline = 当前时间 + timeout，层层递减

Q8: 配置中心
    - 长轮询 vs 推送 vs Watch
    - 配置的版本管理和灰度发布
    - 广告系统中的动态配置：
      ① 广告引擎参数（超时、并发数、缓存策略）
      ② 流量分配比例
      ③ 实验配置
      ④ 频次控制规则
      ⑤ 反作弊规则

## 7.1 广告行业基础知识

```
Q1: 广告生态的参与方
    - 广告主（Advertiser）：想投广告的企业
    - 媒体/流量方（Publisher）：有用户流量的平台
    - 广告平台（Ad Platform）：字节巨量引擎、腾讯广告、百度凤巢
    - SSP（Supply Side Platform）：帮媒体管理广告位
    - DSP（Demand Side Platform）：帮广告主买流量
    - ADX（Ad Exchange）：广告交易平台
    - DMP（Data Management Platform）：数据管理平台
    - 联盟广告（Ad Network）：穿山甲、优量汇

Q2: 广告的计费模式详解
    - CPM（Cost Per Mille）：千次曝光出价
    - CPC（Cost Per Click）：按点击计费
    - CPA（Cost Per Action）：按转化计费
    - CPT（Cost Per Time）：按时间包段计费
    - oCPM（Optimized CPM）：
      广告主按转化出价，平台按曝光计费
      eCPM = pCTR × pCVR × 转化出价 × 1000
    - oCPC（Optimized CPC）：
      广告主按转化出价，平台按点击计费
      CPC 出价 = pCVR × 转化出价
    - ROAS 出价：按投入产出比出价
    
    为什么 oCPM 是主流？
    → 广告主关心效果（转化），平台有能力预估转化率，
      按曝光计费对平台更友好（风险在平台侧但平台有数据优势）

Q3: 广告的核心指标
    - CTR（Click-Through Rate）：点击率 = 点击数 / 曝光数
    - CVR（Conversion Rate）：转化率 = 转化数 / 点击数
    - eCPM（effective CPM）：千次曝光收入
      eCPM = CTR × CPC × 1000（CPC 模式）
      eCPM = CTR × CVR × CPA × 1000（CPA 模式）
    - ARPU：每用户平均收入
    - ROI / ROAS：投资回报率
    - Fill Rate：广告填充率
    - Win Rate：竞价胜出率
```

### 7.3 广告检索系统（工程重点）

```
Q5: 广告定向匹配
    - 定向条件类型：
      ① 地域定向：省/市/区/商圈
      ② 人群定向：年龄/性别/兴趣标签
      ③ 设备定向：操作系统/设备型号/网络类型
      ④ 时段定向：投放时间段
      ⑤ 关键词定向
      ⑥ 重定向（Retargeting）：针对已访问过的用户
      ⑦ Lookalike：相似人群扩展
      ⑧ 排除定向：排除某些人群
    
    - 定向匹配的实现：
      ① 正向匹配（用户属性 → 广告）：
         倒排索引：属性值 → 广告列表
         例：{北京 → [ad1, ad3, ad5], 上海 → [ad2, ad4]}
      
      ② 反向匹配（广告定向 → 是否匹配用户）：
         布尔表达式检索
         ad1: (age IN [18-24]) AND (city IN [北京, 上海]) AND (gender = male)

Q6: 倒排索引的设计

    数据结构：
    ```
    定向维度 → 定向值 → 广告 ID 列表（Posting List）
    
    city:
      北京 → [1001, 1003, 1005, 1007, ...]
      上海 → [1002, 1004, 1005, 1008, ...]
    
    age:
      18-24 → [1001, 1002, 1006, ...]
      25-34 → [1003, 1004, 1007, ...]
    
    gender:
      male   → [1001, 1003, 1005, ...]
      female → [1002, 1004, 1006, ...]
    ```
    
    多条件交集计算：
    - 对每个定向维度查询用户匹配的 Posting List
    - 取交集 → 得到候选广告
    - 优化：按 Posting List 长度从小到大求交集
    - 数据结构：Roaring Bitmap（压缩位图）高效求交/并集

Q7: 布尔表达式检索（DNF / CNF）
    
    DNF（析取范式）：
    (A1 ∧ A2 ∧ A3) ∨ (B1 ∧ B2) ∨ (C1)
    
    例：广告定向 = (city=北京 AND age=18-24) OR (city=上海 AND gender=male)
    
    实现思路：
    - 将每个合取式（conjunction）作为一个文档
    - 用户属性作为查询
    - 匹配任一合取式即命中
    
    工业实践：
    - 字节：自研的布尔表达式检索引擎
    - 业界：参考 "Indexing Boolean Expressions"（Yahoo Research 论文）

Q8: 广告索引的构建与更新

    全量索引：
    - 定时（如每小时）从 DB 全量构建索引
    - 生成索引文件 → 分发到各引擎节点 → 原子切换
    
    增量索引：
    - 监听 DB binlog（Canal / Debezium）→ 消息队列 → 索引更新
    - 或通过 API 推送增量变更
    
    双 Buffer 机制：
    - 维护两份索引：当前服务索引 + 后台更新索引
    - 更新完成后原子切换指针
    
    索引一致性保证：
    - 全量兜底 + 增量实时
    - 版本号/时间戳校验
    - 定期全量对账修复不一致
```

### 7.4 预算控制系统（工程重点）

```
Q9: 预算控制的详细设计

    需求：
    - 广告主设置日预算 1000 元
    - 多个引擎节点同时消耗
    - 不能超投（超投需要平台承担），但少量超投可接受（如 1-5%）
    - 支持匀速消耗（Pacing）

    方案：分层预算控制
    
    ┌─────────────────────────────────────────┐
    │  中心预算服务（Budget Server）              │
    │  - 存储每个广告的总预算和已消耗             │
    │  - 接受各节点的消耗汇报                     │
    │  - 分配预算配额给各节点                     │
    │  - Redis 存储：budget:{ad_id} → remaining  │
    └──────────────────┬──────────────────────┘
                       │  定期同步（如每秒）
    ┌──────────────────┼──────────────────────┐
    │                  │                       │
    ┌───────┐    ┌───────┐    ┌───────┐
    │Node 1 │    │Node 2 │    │Node 3 │
    │本地配额│    │本地配额│    │本地配额│
    │300 元  │    │400 元  │    │300 元  │
    └───────┘    └───────┘    └───────┘
    
    消耗流程：
    1. 每个节点从中心获取一定配额（如总预算/节点数）
    2. 每次广告曝光/点击，在本地原子扣减配额
    3. 本地配额不足 → 向中心申请更多配额
    4. 中心预算不足 → 该广告下线
    5. 每秒/每 N 次请求向中心汇报实际消耗
    
    匀速消耗（Pacing）：
    - 理想曲线：消耗 = 日预算 × (已过时间 / 总投放时间)
    - PID 控制器调节：
      误差 = 理想消耗 - 实际消耗
      调节：增大/减小该广告的竞价概率或出价
    - 简单实现：每隔 T 分钟释放一批预算配额
    
    超投控制：
    - 乐观扣减 + 异步对账
    - 预留安全余量（如预算的 95% 可用，5% 作为 buffer）
    - 实时监控，接近预算时切换为同步扣减

Q10: 频次控制的详细设计

    需求：
    - 用户 A 在 24 小时内最多看到广告 X 3 次
    - 多级频次：广告级 / 广告主级 / 行业级
    - 分布式环境下的精确性

    方案一：Redis 计数器
    ```
    Key: freq:{user_id}:{ad_id}:{date}
    Value: 曝光次数
    TTL: 24h
    操作: INCR + GET（或 Lua 脚本保证原子性）
    ```
    
    方案二：Redis 滑动窗口（更精确）
    ```
    Key: freq:{user_id}:{ad_id}
    Value: ZSet，score=时间戳，member=请求ID
    操作: ZADD + ZRANGEBYSCORE + ZCARD
    ```
    
    方案三：本地缓存 + 异步同步
    - 各节点本地维护频次计数（LRU 缓存）
    - 异步上报到中心
    - 优势：低延迟
    - 劣势：可能短暂超频（多个节点同时检查时）
    
    实际方案：
    - 先查本地缓存 → miss 时查 Redis → 回填本地缓存
    - 曝光后先更新本地缓存，异步更新 Redis
    - 允许少量超频（1-2 次），通过异步对账修正
```

### 7.5 广告计费系统

```
Q11: 计费系统的设计

    计费流程：
    1. 广告展示时生成曝光日志（包含预期计费信息）
    2. 用户点击时生成点击事件
    3. 反作弊过滤无效点击
    4. 计算实际扣费金额（GSP 第二价格）
    5. 扣减广告主余额
    6. 写入计费记录
    
    GSP（广义第二价格拍卖）：
    - 排序依据：eCPM（不是出价）
    - 扣费 = 下一名的 eCPM / 自身的 pCTR + 0.01
    - 例：
      广告A：出价 2元，pCTR 10%，eCPM = 200
      广告B：出价 3元，pCTR 5%，eCPM = 150
      广告A 赢得展示
      广告A 实际扣费 = 150 / 10% + 0.01 = 1.51 元（CPC 计费）
    
    计费的核心要求：
    ① 不重复计费（幂等性）
      - 每次计费事件有唯一 ID（impression_id / click_id）
      - Redis / DB 去重
    ② 不漏计费
      - 消息队列保证 at-least-once
      - 配合幂等实现 exactly-once
    ③ 准确性
      - 离线对账：展示日志 vs 计费日志 比对
      - 差异超过阈值告警
    ④ 实时性
      - 计费后实时更新预算消耗
      - Kafka → 计费服务 → Redis 预算更新 + DB 持久化

Q12: 广告日志系统

    日志类型：
    - 曝光日志（Show Log）：广告被展示时记录
    - 点击日志（Click Log）：用户点击广告时记录
    - 转化日志（Conversion Log）：用户完成目标行为（下载/注册/购买）
    - 引擎日志（Engine Log）：广告引擎的处理过程日志
    
    日志收集架构：
    客户端 → 日志 SDK → 日志收集服务 → Kafka → 
    ├→ Flink（实时处理）→ Redis/HBase
    └→ Spark/Hive（离线处理）→ HDFS/数据仓库
    
    展示-点击归因（Join）：
    - 用户看到广告（曝光）→ 过了一段时间 → 点击
    - 需要将点击关联到对应的曝光
    - 方案：在曝光时生成 impression_id，编码在点击 URL 中
    - 展示-转化归因：更复杂，需要归因窗口（7天/30天）
    
    日志可靠性：
    - 客户端：本地缓冲 + 批量上报 + 失败重试
    - 服务端：Kafka 多副本 + 消费确认
    - 数据质量：采样校验、端到端对账
```

### 7.6 特征系统

```
Q13: 广告特征系统设计

    特征类型：
    ┌────────────────────────────────────────┐
    │ 用户特征：                              │
    │ - 基础属性：年龄/性别/地域              │

    indices map[string]map[string]*roaring.Bitmap
}

// 正排数据

    AdID       int64
    CampaignID int64
    BidType    int
    BidPrice   float64
    Status     int
    Budget     float64
    Targeting  TargetingConfig
    Creative   CreativeInfo
}

    invertedIndex *InvertedIndex
    forwardIndex  map[int64]*AdInfo  // adID -> AdInfo

Step 4: 检索流程

func (idx *AdIndex) Search(req *AdRequest) []*AdInfo {
    // 1. 定向匹配 - 倒排索引求交集
    cityBitmap := idx.invertedIndex.Get("city", req.City)
    ageBitmap := idx.invertedIndex.Get("age", req.AgeRange)
    genderBitmap := idx.invertedIndex.Get("gender", req.Gender)
    
    // 求交集
    result := roaring.FastAnd(cityBitmap, ageBitmap, genderBitmap)
    
    // 2. 过滤 - 预算、频次、状态
    candidates := make([]*AdInfo, 0)
    iter := result.Iterator()
    for iter.HasNext() {
        adID := iter.Next()
        ad := idx.forwardIndex[int64(adID)]
        if ad.Status != StatusActive { continue }
        if !budgetChecker.HasBudget(adID) { continue }
        if freqController.IsExceeded(req.UserID, adID) { continue }
        candidates = append(candidates, ad)
    }
    
    // 3. 返回候选集
    return candidates
}

Step 5: 索引更新
- 全量：每小时从 DB dump → 构建新索引 → 原子切换（双 Buffer）
- 增量：监听 binlog → Kafka → 各节点消费 → 更新本地索引
  加锁策略：写时复制（COW）或 读写锁

Step 6: 性能优化
- Roaring Bitmap 压缩位图，高效交/并/差
- 按 Posting List 大小排序，短的先交（剪枝）
- SIMD 指令加速位运算
- 热点广告预计算
- 对象池减少 GC
- 索引数据内存对齐，利用 CPU 缓存

Step 7: 高可用
- 多副本部署，负载均衡
- 索引更新失败 → 使用旧索引 + 告警
- 服务降级：检索超时 → 返回热门广告兜底

## 设计题四：设计一个延迟任务系统（广告定时上下线）

```
需求：
- 广告主设置广告在某个时间开始/结束投放
- 精度要求：秒级
- 任务量：百万级

方案对比：

方案一：数据库轮询
- 每秒查询 DB：SELECT * FROM ad WHERE start_time <= NOW() AND status = 'pending'
- 问题：DB 压力大、延迟高

方案二：Redis ZSet
- Score = 执行时间戳，Member = 任务 ID
- 轮询：ZRANGEBYSCORE key 0 {now} LIMIT 0 100
- 执行后 ZREM
- 优化：分片 ZSet，多 worker 消费
- 问题：需要保证 exactly-once（分布式锁）

方案三：时间轮（Hierarchical Timing Wheel）
- 多层时间轮：秒级 → 分钟级 → 小时级 → 天级
- 高效：O(1) 添加/删除任务
- 适用：单机或少量节点
- Go 实现可参考 Kafka 的 DelayedOperationPurgatory

方案四：消息队列延迟消息
- RocketMQ 原生支持延迟消息（18个级别）
- Kafka + 外部延迟服务
- Pulsar 支持任意延迟

推荐方案（广告系统）：
Redis ZSet（短期任务，< 24h）+ 数据库兜底（长期任务）
- 创建广告时：
  ① 写入 DB（持久化）
  ② 如果 start_time 在 24h 内，加入 Redis ZSet
- 定时扫描 DB，将未来 24h 内的任务加入 Redis ZSet
- Worker 消费 Redis ZSet 中到期的任务
- 执行：更新广告状态 → 刷新广告索引

```
场景 1：广告引擎 P99 延迟从 50ms 飙升到 200ms

排查思路：
Step 1: 查看监控看板
  - 是所有节点还是个别节点？
  - 是所有请求还是特定类型请求？
  - 延迟升高的时间点有什么变更？（发版？配置变更？）

Step 2: 看链路追踪
  - 是哪个环节变慢了？（召回？排序？特征查询？）
  - Span 耗时分布变化

Step 3: 检查下游依赖
  - Redis 延迟？（INFO commandstats、slowlog get）
  - 特征服务延迟？
  - 模型服务延迟？

Step 4: 检查自身资源
  - CPU：是否打满？是否频繁 GC？（Go：GODEBUG=gctrace=1）
  - 内存：是否接近上限？是否在做大量内存分配？
  - 网络：是否有丢包？连接数是否正常？
  - 磁盘：是否有 IO 瓶颈？（日志写入？）

Step 5: 检查代码层面
  - 是否有锁竞争？（Go：mutex profile）
  - 是否有 goroutine 泄漏？（goroutine 数量是否在增长？）
  - 是否有慢查询？

常见原因：
- GC 导致 STW → 优化内存分配，减少堆上对象
- 下游 Redis 慢查询 → 大 Key、热 Key
- 索引更新导致锁竞争 → 优化为无锁方案
- 某个广告主投了大量广告导致检索变慢 → 加检索结果数量限制
- 网络抖动 → 重试风暴 → 雪崩 → 加熔断

场景 2：某广告主反馈 "今天的广告曝光量突然下降了 50%"

  - 其他广告主是否也受影响？

Step 2: 检查广告状态
  - 广告是否在投放中？有没有被审核下线？
  - 预算是否耗尽？
  - 出价是否有变更？

Step 3: 检查竞争环境
  - 是否有新的竞争广告主进入，推高了竞价？
  - 大盘 eCPM 是否上涨？

Step 4: 检查定向和频次
  - 定向设置是否被修改（缩小了人群）？
  - 频次控制是否生效（用户已经看够了）？

Step 5: 检查系统层面
  - 广告索引是否正确包含该广告？
  - 召回是否正常？（看引擎日志）
  - 模型预估的 CTR/CVR 是否下降？（模型问题？）

Step 6: 检查实验
  - 是否被分到了实验组？
  - 实验是否影响了该广告主？

场景 3：线上发现内存持续增长，疑似内存泄漏

Go 服务排查：
Step 1: 观察 Grafana 监控
  - RSS 内存持续增长，不会回落
  - goroutine 数量是否在增长？

Step 2: 获取 pprof heap profile
  curl http://localhost:6060/debug/pprof/heap > heap1.prof
  # 等待几分钟
  curl http://localhost:6060/debug/pprof/heap > heap2.prof
  
  go tool pprof -base heap1.prof heap2.prof
  (pprof) top 20
  → 看哪些函数在持续分配内存

Step 3: 获取 goroutine profile

  → 检查是否有大量相同的 goroutine 堆栈（泄漏特征）

Step 4: 常见原因
  - goroutine 泄漏：channel 没人读、HTTP 请求没设超时
  - 缓存无上限：map 只增不删 → 加 LRU 淘汰

  - slice 底层数组未释放 → copy 到新 slice
  - CGO 内存泄漏 → C 代码的内存需要手动释放

```go
package lru

import (
    "container/list"
    "sync"
)

type LRUCache struct {
    capacity int
    mu       sync.RWMutex
    cache    map[int]*list.Element
    list     *list.List
}

type entry struct {
    key   int
    value int
}

func NewLRUCache(capacity int) *LRUCache {
    return &LRUCache{
        capacity: capacity,
        cache:    make(map[int]*list.Element),
        list:     list.New(),
    }
}

func (c *LRUCache) Get(key int) (int, bool) {
    c.mu.Lock()
    defer c.mu.Unlock()

    if elem, ok := c.cache[key]; ok {
        c.list.MoveToFront(elem)
        return elem.Value.(*entry).value, true
    }
    return -1, false
}

func (c *LRUCache) Put(key, value int) {
    c.mu.Lock()
    defer c.mu.Unlock()

    if elem, ok := c.cache[key]; ok {
        c.list.MoveToFront(elem)
        elem.Value.(*entry).value = value
        return
    }

    if c.list.Len() >= c.capacity {
        oldest := c.list.Back()
        if oldest != nil {
            c.list.Remove(oldest)
            delete(c.cache, oldest.Value.(*entry).key)
        }
    }

    elem := c.list.PushFront(&entry{key: key, value: value})
    c.cache[key] = elem
}
```

package ratelimit

import (
    "sync"
    "time"
)

type TokenBucket struct {
    rate       float64   // 每秒生成的令牌数
    capacity   float64   // 桶容量
    tokens     float64   // 当前令牌数
    lastRefill time.Time // 上次补充时间
    mu         sync.Mutex
}

func NewTokenBucket(rate, capacity float64) *TokenBucket {
    return &TokenBucket{
        rate:       rate,
        capacity:   capacity,
        tokens:     capacity,
        lastRefill: time.Now(),
    }
}

func (tb *TokenBucket) Allow() bool {
    tb.mu.Lock()
    defer tb.mu.Unlock()

    now := time.Now()
    elapsed := now.Sub(tb.lastRefill).Seconds()
    tb.tokens += elapsed * tb.rate
    if tb.tokens > tb.capacity {
        tb.tokens = tb.capacity
    }
    tb.lastRefill = now

    if tb.tokens >= 1 {
        tb.tokens--
        return true
    }
    return false
}

```go
package bloom

import (
    "hash"
    "hash/fnv"
    "math"
)

type BloomFilter struct {
    bits    []bool
    size    uint
    hashNum uint
}

func NewBloomFilter(expectedItems uint, falsePositiveRate float64) *BloomFilter {
    size := optimalSize(expectedItems, falsePositiveRate)
    hashNum := optimalHashNum(size, expectedItems)
    return &BloomFilter{
        bits:    make([]bool, size),
        size:    size,
        hashNum: hashNum,
    }
}

func (bf *BloomFilter) Add(item []byte) {
    for i := uint(0); i < bf.hashNum; i++ {
        pos := bf.hash(item, i) % bf.size
        bf.bits[pos] = true
    }
}

func (bf *BloomFilter) Contains(item []byte) bool {
    for i := uint(0); i < bf.hashNum; i++ {
        pos := bf.hash(item, i) % bf.size
        if !bf.bits[pos] {
            return false
        }
    }
    return true
}

func (bf *BloomFilter) hash(item []byte, seed uint) uint {
    h := fnv.New64a()
    h.Write(item)
    h.Write([]byte{byte(seed)})
    return uint(h.Sum64())
}

func optimalSize(n uint, p float64) uint {
    return uint(math.Ceil(-float64(n) * math.Log(p) / (math.Log(2) * math.Log(2))))
}

func optimalHashNum(m, n uint) uint {
    return uint(math.Ceil(float64(m) / float64(n) * math.Log(2)))
}

### 1.2 广告召回的多路策略

```
Q: 广告召回只有倒排索引一种方式吗？实际系统中的多路召回是怎么做的？

答题要点：

实际的广告召回是多路并行的：

┌─────────────────────────────────────────────┐
│                 多路召回                       │
│                                               │
│  ┌──────────┐  ┌──────────┐  ┌──────────┐  │
│  │ 定向召回   │  │ 向量召回   │  │ 人群包召回│  │
│  │(倒排索引) │  │(ANN检索)  │  │(DMP匹配) │  │
│  └────┬─────┘  └────┬─────┘  └────┬─────┘  │
│       │              │              │         │
│  ┌────┴─────┐  ┌────┴─────┐  ┌────┴─────┐  │
│  │ 重定向召回 │  │ Lookalike│  │ 上下文召回│  │
│  │(用户行为) │  │(相似人群) │  │(内容匹配) │  │
│  └────┬─────┘  └────┬─────┘  └────┬─────┘  │
│       │              │              │         │
│       └──────────────┼──────────────┘         │
│                      ↓                        │
│              去重 + 合并候选集                  │
│                      ↓                        │
│              预算/频次/状态 过滤               │
│                      ↓                        │
│              送入粗排                          │
└─────────────────────────────────────────────┘

各路召回详解：

1. 定向召回（最基础）
   - 倒排索引匹配：用户属性 → 满足定向条件的广告
   - 前文已详细描述

2. 向量召回（User-Ad Embedding）★ 重要但前文遗漏
   - 将用户和广告映射到同一向量空间
   - 用 ANN（近似最近邻）检索最相关的广告
   - 工具：Faiss / Milvus / Annoy / HNSW
   - 工程实现：
     ① 离线训练 User Tower 和 Ad Tower（双塔模型）
     ② 广告向量建索引（HNSW / IVF-PQ）
     ③ 在线：用户向量实时计算 → ANN 检索 Top-K
   - 延迟要求：< 10ms
   - 索引更新：新广告上线时增量更新向量索引

3. 重定向召回（Retargeting）
   - 用户浏览过/点击过/加购过但未转化的广告
   - 实现：
     用户行为日志 → Flink 实时处理 → 
     Redis/HBase 存储用户近期行为 →
     召回时查询用户行为列表 → 匹配相关广告
   - 场景：电商广告主最常用
   
4. Lookalike 人群扩展
   - 广告主上传种子用户（如已付费用户）
   - 系统找到相似用户
   - 实现：
     ① 种子用户特征聚合 → 训练分类模型
     ② 全量用户打分 → 高分用户加入人群包
     ③ 定期更新人群包（每天/每小时）
   - 工程：人群包存储在 Bitmap 中，召回时直接检查

5. 上下文召回
   - 根据当前页面内容匹配广告
   - 如：用户在看体育新闻 → 召回运动品牌广告
   - 实现：内容分类/关键词提取 → 匹配广告定向标签

6. DMP 人群包召回
   - 广告主上传的自定义人群包（手机号/设备ID列表）
   - 用 Bloom Filter 或 Bitmap 存储
   - 召回时检查用户是否在人群包中

多路召回的工程挑战：
- 各路并行执行，控制总超时
- 去重：同一个广告可能被多路召回
- 配额控制：每路返回的数量上限
- 权重：不同召回路的广告可以有不同的优先级
```

### 1.3 粗排的工程实现

```
Q: 粗排和精排的区别？粗排的工程实现方式？

答题要点：

为什么需要粗排？
- 召回阶段可能返回数千甚至上万个广告
- 精排模型复杂（深度学习），不可能对所有候选打分
- 粗排用简单模型快速筛选，将候选集从数千缩减到数百

粗排 vs 精排：
┌────────┬────────────────┬────────────────┐
│        │     粗排        │     精排        │
├────────┼────────────────┼────────────────┤
│ 候选数  │ 数千 → 数百     │ 数百 → 数十     │
│ 模型    │ 简单（LR/小DNN）│ 复杂（大DNN）   │
│ 特征    │ 少量核心特征    │ 全量特征         │
│ 延迟    │ < 5ms          │ < 20ms          │
│ 目标    │ 快速过滤明显差的│ 精确排序         │
└────────┴────────────────┴────────────────┘

粗排工程方案：

方案一：简单规则 + 静态分数
- 预计算每个广告的质量分（历史CTR × 出价）
- 按质量分截断
- 优点：极快（纯内存计算）
- 缺点：没有个性化

方案二：轻量级模型（推荐）
- 模型：逻辑回归（LR）或小型 DNN（2-3 层，128维）
- 特征：用户少量核心特征 + 广告静态特征（预计算 embedding）
- 推理方式：
  ① SIMD 加速的矩阵运算
  ② 向量内积近似（用户向量 · 广告向量）
  ③ 量化：FP32 → INT8 降低计算量
- 延迟：< 5ms 完成数千个广告的打分

方案三：双塔模型 + 向量检索
- 将粗排和向量召回合并
- 用户侧和广告侧分别计算向量
- 用内积/余弦相似度排序
- 广告向量可以预计算，只需实时计算用户向量

粗排的截断策略：
- 固定数量：取 Top 300
- 动态截断：根据分数分布，分数差距过大的地方截断
- 多样性截断：保证不同广告主/行业/创意的多样性
```

答题要点：

模型推理架构：
┌─────────────────────────────────────────┐
│              广告引擎                     │
│                                           │
│  特征拼接 → 发送到模型服务 → 接收预估结果  │

延迟优化：
1. 批量推理（Batching）
   - 将多个候选广告的特征打包成一个 batch
   - GPU 并行计算
   - 动态 batching：等待一小段时间收集请求再一起推理

2. 模型优化
   - 模型蒸馏：大模型 → 小模型
   - 量化：FP32 → FP16 → INT8
   - 剪枝：去除不重要的连接
   - 算子融合：减少 GPU kernel 启动次数

3. 特征优化
   - 预计算：广告侧特征可以离线计算好
   - 特征缓存：相同用户的特征在一次请求中复用
   - 减少特征数量：特征重要性排序，去除贡献低的特征

4. 架构优化
   - GPU 推理 vs CPU 推理：大模型用 GPU，小模型 CPU 即可
   - 模型并行：将模型切分到多个 GPU
   - 异步推理：不等模型返回，先做其他工作

5. 超时兜底
   - 模型推理超时 → 使用粗排分数兜底
   - 部分候选超时 → 用已返回结果的排序

### 2.1 竞价排序公式

```
Q: 广告的排序不只是看 eCPM，实际的排序公式是什么？

答题要点：

实际排序分 = f(eCPM, 质量分, 用户体验分, 生态分)

完整排序公式（简化版）：
Score = eCPM × QualityScore × UserExperienceScore × EcoScore

其中：
1. eCPM = pCTR × pCVR × Bid × 1000（oCPM 模式）

2. QualityScore（质量分）：
   - 广告相关性
   - 落地页质量
   - 历史 CTR（平滑后的）
   - 广告主信誉

3. UserExperienceScore（用户体验分）：
   - 广告对用户体验的影响
   - 负反馈率（用户关闭/举报比例）
   - 广告密度控制（一页中广告占比）

4. EcoScore（生态分）：
   - 新广告主扶持（冷启动加权）
   - 行业均衡（避免某个行业垄断）
   - 中小广告主保护
   - 长期收入最大化 vs 短期收入

Q: 为什么不直接按 eCPM 排序？
- 纯 eCPM 排序 → 只有高出价广告展示 → 
  用户体验差 → 用户流失 → 长期收入下降
- 需要在「短期收入」和「用户体验」之间平衡
- 这就是为什么引入质量分和体验分

Q: 排序分中各因子的权重怎么确定？
- 通过 A/B 实验调整
- 多目标优化：收入、用户留存、广告主 ROI
- 约束优化：在用户体验不低于阈值的前提下最大化收入
```

### 2.2 广告定价机制详解

```
Q: GSP 之外还有哪些定价机制？深度 GSP 是什么？VCG 为什么没被广泛使用？

答题要点：

1. GFP（Generalized First Price，广义第一价格）
   - 支付自己的出价
   - 问题：出价策略不稳定（存在虚假出价动机）
   - 近年趋势：程序化广告（Header Bidding）回归 GFP
   - Google Ads 在 2019 年切换到 FPA

2. GSP（Generalized Second Price，广义第二价格）
   - 赢家支付第二名的价格 + 最小增量
   - 传统搜索广告的主流
   - 多广告位情况：
     位置1的广告支付 = 位置2广告的 eCPM / 位置1广告的 pCTR + δ
     位置2的广告支付 = 位置3广告的 eCPM / 位置2广告的 pCTR + δ
     ...
   - 优点：激励真实出价（近似）
   - 问题：多位置时不是 truthful 的（激励兼容）

3. VCG（Vickrey-Clarke-Groves）
   - 理论上最优的拍卖机制（truthful）
   - 每个广告主支付 = 他的参与给其他人带来的社会福利损失
   - 为什么没广泛使用？
     ① 计算复杂度高
     ② 收入通常低于 GSP
     ③ 广告主难以理解
     ④ 实现上需要计算组合优化

4. 深度 GSP（Deep GSP / Squashing）
   - 问题：标准 GSP 可能导致排名靠后的广告扣费极低
   - 解决：引入 squashing factor（挤压因子）
   - Score = eCPM ^ α （α < 1，如 0.7）
   - 效果：降低高 eCPM 广告的排序优势，让更多广告有展示机会
   - 同时提高底部广告的扣费

5. 保留价（Reserve Price / Floor Price）
   - 最低出价要求
   - 低于保留价的广告不参与竞价
   - 动态保留价：根据流量质量、历史 eCPM 动态调整
   
   工程实现：
   if ad.eCPM < floorPrice {
       filter(ad)  // 过滤掉
   }
   实际扣费 = max(第二名价格, 保留价)

Q: oCPM 模式下的计费怎么算？

oCPM 计费流程：
1. 广告主出价：目标转化出价 = 50 元/转化
2. 系统预估：pCTR = 2%, pCVR = 5%
3. eCPM = pCTR × pCVR × 转化出价 × 1000 = 0.02 × 0.05 × 50 × 1000 = 50
4. 参与竞价排序（按 eCPM）
5. 赢得展示 → 按 CPM 计费（每千次展示的实际扣费）
6. 实际 CPM 扣费 = 下一名 eCPM / 自身曝光（GSP 逻辑）
7. 广告主看到的是转化成本（消耗 / 转化数）

关键问题：如果系统预估不准怎么办？
- pCTR / pCVR 过高 → 广告主实际转化成本高于出价 → 广告主不满意
- pCTR / pCVR 过低 → 广告竞争力不足 → 没有展示
- 解决：智能出价（Smart Bidding）+ 赔付机制
```

### 2.3 智能出价（Smart Bidding / Auto Bidding）

```
Q: 智能出价系统是怎么工作的？工程上怎么实现？

答题要点：

智能出价的目标：
- 在广告主设定的成本约束下，最大化转化数量
- 即：max Σ(转化) s.t. CPA ≤ 目标CPA

工程实现：

1. 实时出价调整
   每次广告请求时，根据以下因素动态调整出价：
   
   actual_bid = base_bid × user_value_factor × 
                 context_factor × pacing_factor × 
                 cost_control_factor
   
   - user_value_factor：该用户的转化概率（pCVR 高的用户出价高）
   - context_factor：当前流量的竞争程度
   - pacing_factor：消耗进度（领先进度则降低出价）
   - cost_control_factor：实际成本 vs 目标成本的偏差修正

2. 成本控制（Cost Control）★ 核心工程
   
   问题：怎么保证广告主的实际转化成本接近目标出价？
   
   PID 控制器方案：
   ```
   error = 实际CPA - 目标CPA
   
   P（比例）：adjustment_p = Kp × error
   I（积分）：adjustment_i = Ki × Σ(历史error)
   D（微分）：adjustment_d = Kd × (error - 上次error)
   
   bid_multiplier = 1 + adjustment_p + adjustment_i + adjustment_d
   ```
   
   - 实际 CPA > 目标 CPA → 降低出价
   - 实际 CPA < 目标 CPA → 可以提高出价（争取更多转化）
   - 控制周期：通常 15分钟~1小时
   
   工程挑战：
   - 转化有延迟（用户可能几小时甚至几天后才转化）
   - 解决：使用预估转化数（而非实际转化数）来做实时控制
   - 转化延迟建模：预估 T 时间后的最终转化数

3. 探索与利用（Exploration & Exploitation）
   - 新广告冷启动：需要一定曝光量来积累数据
   - 探索：给新广告一些额外的曝光机会
   - 利用：对已有数据的广告用模型预估
   - 实现：Thompson Sampling / UCB / ε-greedy
   - 工程：新广告前 N 次曝光给予保底竞争力
```

## 三、广告合同与排期系统（保量/保价广告）

---

```
Q: 除了竞价广告，还有保量广告（GD - Guaranteed Delivery），怎么设计？

答题要点：

保量广告 vs 竞价广告：
┌────────────────┬──────────────────┬──────────────────┐
│                │    保量广告 (GD)   │    竞价广告 (RTB)  │
├────────────────┼──────────────────┼──────────────────┤
│ 价格          │ 预先约定           │ 实时竞价           │
│ 量级          │ 保证曝光量         │ 不保证              │
│ 优先级        │ 通常更高           │ 通常更低            │
│ 客户          │ 大品牌客户         │ 效果广告主          │
│ 售卖方式      │ 人工/合同          │ 自助投放平台        │
└────────────────┴──────────────────┴──────────────────┘

保量广告的核心工程问题：

1. 流量预测（Traffic Forecasting）
   - 卖出保量合同前，需要预测未来 N 天的可用流量
   - 输入：广告位、定向条件、时间段
   - 输出：预估可用曝光量
   - 实现：
     ① 历史数据统计：统计过去 7/30 天的各维度流量
     ② 时间序列预测：考虑周期性（周末/节假日）
     ③ 定向交叉：多个定向条件的交集估算
   - 难点：多个保量合同可能争抢同一批流量

2. 库存分配（Inventory Allocation）
   - 多个保量合同 + 竞价广告共享流量
   - 需要合理分配，保证所有合同都能完成
   
   算法：
   - 在线分配问题（Online Allocation Problem）
   - HWM（High Water Mark）算法：
     ① 计算每个合同的完成率
     ② 完成率最低的合同优先分配
   - SHALE 算法（Facebook 论文）：
     ① 离线阶段：计算每个合同的分配概率
     ② 在线阶段：按概率分配流量
   - 目标：最大化所有合同的满足率

3. 在广告引擎中的实现
   每次广告请求：
   ① 先匹配保量广告 → 按分配概率决定是否展示
   ② 保量广告未命中 → 进入竞价逻辑
   ③ 或者：保量广告和竞价广告统一竞价，保量广告有保底 eCPM

4. 欠投补偿
   - 前几天没有完成进度 → 后面几天需要加速
   - 实时监控每个合同的完成进度
   - 动态调整分配概率
```

## 四、广告创意优选与动态创意

---

```
Q: 一个广告计划可能有多个创意，怎么选择最优的创意展示？

答题要点：

1. 创意优选（Creative Optimization）
   
   问题：广告主上传了 5 个创意（不同图片/文案），选哪个展示？
   
   方案：Multi-Armed Bandit（MAB）
   
   - ε-Greedy：
     以概率 ε 随机选（探索），以概率 1-ε 选历史最优（利用）
   
   - Thompson Sampling（推荐）：
     ① 每个创意维护一个 Beta 分布 Beta(α, β)
        α = 点击数 + 1, β = 未点击数 + 1
     ② 每次从每个创意的分布中采样
     ③ 选采样值最大的创意展示
     ④ 优点：自动平衡探索和利用
   
   - UCB（Upper Confidence Bound）：
     Score = CTR均值 + C × sqrt(ln(N) / n_i)
     C：探索系数，N：总展示次数，n_i：该创意展示次数
   
   工程实现：
   - Redis 存储每个创意的曝光/点击统计
   - 在广告引擎中实时计算选择概率
   - 按用户分群做创意优选（不同用户群偏好不同创意）

2. 动态创意（Dynamic Creative Optimization, DCO）
   
   概念：系统自动组合创意元素（标题、图片、按钮文案、配色等）
   
   素材池：
   - 标题集合：["限时优惠", "新品首发", "爆款推荐"]
   - 图片集合：[img_a.jpg, img_b.jpg, img_c.jpg]
   - CTA按钮：["立即购买", "了解详情", "免费试用"]
   
   排列组合：3 × 3 × 3 = 27 种创意
   
   工程挑战：
   - 组合爆炸：元素多了之后组合数量巨大
   - 冷启动：新组合没有数据
   - 解决：
     ① 先独立评估每个元素的效果
     ② 再用贪心/Bandit 方法组合高效元素
     ③ 逐步探索更多组合

3. 创意和广告位的适配
   - 同一个广告在不同广告位需要不同尺寸/格式的创意
   - 信息流广告位（大图/小图/三图/视频）
   - 开屏广告位（全屏图/视频）
   - 激励视频广告位
   
   工程：
   - 创意预处理：裁剪、缩放、格式转换
   - CDN 缓存：不同尺寸的变体
   - 模板化：将创意元素填入广告位模板
```

## 五、广告冷启动

---

```
Q: 新广告/新广告主没有历史数据，CTR/CVR 预估不准，怎么办？

答题要点：

广告冷启动的三个层次：

1. 新广告（New Ad）冷启动
   - 问题：没有该广告的历史 CTR/CVR
   - 方案：
     ① 使用同广告主其他广告的平均 CTR
     ② 使用同行业同出价方式的平均 CTR
     ③ 使用广告特征（标题/图片/落地页）预估初始 CTR
     ④ 探索加速：前 N 次曝光给予一定的 eCPM 加成
     ⑤ 贝叶斯平滑：
        pCTR_smoothed = (α + clicks) / (α + β + impressions)
        α, β 为先验参数（来自同类广告的统计）

2. 新广告主（New Advertiser）冷启动
   - 比新广告更冷
   - 方案：
     ① 行业基准 CTR/CVR 作为初始值
     ② 新广告主保护期：前 7 天给予流量扶持
     ③ 人工审核后赋予初始质量分

3. 新用户冷启动
   - 没有用户画像和历史行为
   - 方案：
     ① 使用设备信息（机型、操作系统、APP 列表）推断
     ② 使用 IP 定位（城市、运营商）
     ③ 上下文特征（当前浏览内容、时间段）
     ④ 快速积累：前几次曝光后实时更新用户特征

工程实现：

## 六、广告混排（Ads + Organic Content）

---

```
Q: 广告和自然内容（如信息流中的新闻、视频）怎么混排？

答题要点：

场景：信息流中每隔几条自然内容插入一条广告

核心问题：
1. 广告在第几个位置插入？
2. 一页中最多展示几条广告？
3. 广告和自然内容的排序关系？

方案一：固定位置插入
- 规则：第 3、8、15、25 条位置固定为广告
- 优点：简单
- 缺点：不灵活，不能根据广告质量调整

方案二：动态位置插入（推荐）
- 统一排序：广告和自然内容统一打分
- 广告分 = eCPM × 质量分（转换为体验分）
- 自然内容分 = 相关性分 × 时效性分
- 约束：
  ① 广告密度上限（如不超过 20%）
  ② 相邻广告最小间隔（如至少间隔 3 条自然内容）
  ③ 同一广告主的广告间隔
  ④ 首屏保护（第 1 条不是广告，或第 1 条必须高质量）

工程实现：
```go
func MixAdsAndContent(organicItems []*Item, ads []*Ad, config *MixConfig) []*Item {
    result := make([]*Item, 0)
    adIndex := 0
    lastAdPos := -config.MinAdInterval  // 保证首条不是广告
    
    for i, item := range organicItems {
        result = append(result, item)
        
        // 检查是否可以插入广告
        if adIndex < len(ads) && 
           i - lastAdPos >= config.MinAdInterval &&
           float64(adIndex+1) / float64(i+2) <= config.MaxAdDensity {
            
            ad := ads[adIndex]
            if ad.QualityScore >= config.MinQualityScore {
                result = append(result, adToItem(ad))
                lastAdPos = len(result) - 1
                adIndex++
            }
        }
    }
    return result
}
```

Q: 混排中如何处理「广告对自然内容消费的影响」？
- 广告展示过多 → 用户刷信息流时间缩短 → 长期 DAU 下降
- 需要建立「用户体验」的量化指标：
  ① 用户停留时长
  ② 广告负反馈率
  ③ 次日留存率
- 通过 A/B 实验找到收入和用户体验的最优平衡点
```

## 七、转化回传与归因

---

```
Q: 广告转化数据是怎么回传的？归因是怎么做的？

答题要点：

转化回传链路：
1. 客户端 SDK 回传（应用内广告）
   用户看到广告 → 点击 → 下载 APP → 打开 APP → SDK 上报转化事件
   - 激活（install）
   - 注册（register）
   - 付费（purchase）
   
2. S2S（Server to Server）回传
   广告主服务器 → 广告平台服务器
   - 广告主在自己的后台检测到转化
   - 通过 API 回传给广告平台
   - 携带 click_id（点击时下发的追踪ID）

3. 网页转化追踪（Pixel）
   - 在广告主网页嵌入 1×1 像素图片或 JS 代码
   - 用户到达转化页面时触发
   - 类似 Google Analytics 的原理

归因模型：

1. 最后点击归因（Last Click Attribution）
   - 最简单，最常用
   - 转化归给用户最后点击的广告
   - 问题：忽略了前面的广告贡献

2. 最后触点归因（Last Touch）
   - 最后一次曝光或点击

3. 多触点归因（Multi-Touch Attribution, MTA）
   - 线性归因：功劳平均分配
   - 时间衰减：越近的触点权重越大
   - U 型/W 型：首尾触点权重大
   - 数据驱动归因：机器学习模型分配权重

归因窗口：
- 点击归因窗口：通常 7-30 天
  （用户点击广告后 30 天内发生的转化归给该广告）
- 曝光归因窗口：通常 1-7 天
  （用户看到广告后 1 天内发生的转化归给该广告）

工程实现：
┌─────────────────────────────────────────┐
│            归因系统架构                    │
│                                           │
│  曝光日志 ─┐                              │
│            ├→ Kafka → Flink Join → 归因  │
│  点击日志 ─┤          ↓                   │
│            │      转化事件匹配            │
│  转化日志 ─┘      (click_id/device_id)    │
│                      ↓                   │
│              归因结果写入                  │
│              ├→ 报表（广告主可见）         │
│              ├→ 计费                      │
│              └→ 模型训练样本               │
└─────────────────────────────────────────┘

Flink Join 的实现：
- 按 click_id 或 device_id 做窗口 Join
- 点击流 JOIN 转化流：
  clickStream
    .keyBy(click_id)
    .intervalJoin(conversionStream.keyBy(click_id))
    .between(Time.seconds(0), Time.days(30))
    .process(new AttributionFunction())

隐私合规（越来越重要）：
- iOS 14+ ATT（App Tracking Transparency）：用户可拒绝追踪
- SKAN（SKAdNetwork）：Apple 的隐私归因方案
  ① 延迟回传（24-48小时）
  ② 聚合数据（不提供用户级数据）
  ③ 有限的转化值（64个值）
- Android Privacy Sandbox：Google 的隐私方案
- GDPR / CCPA 合规：用户数据处理需要合法基础
- 工程影响：
  ① 无法获取 IDFA → 设备指纹退化 → 归因准确率下降
  ② 需要概率归因方案（Probabilistic Attribution）
  ③ 聚合建模（Aggregated Measurement）
```

```
Q: 广告上线前的审核流程是怎样的？违规广告怎么处理？

答题要点：

审核环节：
┌──────────────────────────────────────────────┐
│              广告审核流程                       │
│                                                │
│  广告主提交 → 机器审核 → 人工审核 → 上线        │

     ② NLP 语义理解（虚假宣传、违规表述）
     ③ 行业资质检查（医疗/金融广告需要资质证书）

     ① 色情/暴力/政治敏感检测（CV 模型）
     ② OCR 识别图片中的文字 → 文本审核
     ③ 水印/logo 检测
     ④ 图片质量检测（模糊/变形）
   
   - 视频审核：
     ① 关键帧提取 → 图片审核
     ② 音频转文字 → 文本审核
     ③ 视频质量检测
   
   - 落地页审核：
     ① 页面可访问性检查
     ② 内容安全检测
     ③ 和广告内容的一致性检查
     ④ 恶意代码检测

2. 人工审核
   - 机器不确定的 case 送人工
   - 审核系统：任务分配 + 审核规则 + 复审机制
   - SLA：普通广告 < 2小时，紧急通道 < 30分钟

3. 在线巡检
   - 广告上线后持续监控
   - 定期重新抓取落地页检查
   - 用户举报 → 触发复审
   - 舆情监控 → 相关广告快速下线

广告状态机：
┌─────────────────────────────────────────────────┐
│                                                   │
│  草稿 → 待审核 → 审核中 → 审核通过 → 投放中      │
│   ↑                  ↓         ↓        ↓         │
│   │              审核拒绝    暂停      到期/预算耗尽 │
│   │                  ↓                  ↓         │
│   └──── 修改重新提交 ←──── 已结束 ←──── ←──       │
│                              ↑                    │
│                          违规下线                  │
└─────────────────────────────────────────────────┘

工程实现（状态机）：
```go
type AdStatus int

const (
    StatusDraft       AdStatus = 0
    StatusPendingReview AdStatus = 1
    StatusReviewing    AdStatus = 2
    StatusApproved     AdStatus = 3
    StatusActive       AdStatus = 4
    StatusPaused       AdStatus = 5
    StatusRejected     AdStatus = 6
    StatusExpired      AdStatus = 7
    StatusViolation    AdStatus = 8
)

// 状态转移表
var validTransitions = map[AdStatus][]AdStatus{
    StatusDraft:         {StatusPendingReview},
    StatusPendingReview: {StatusReviewing},
    StatusReviewing:     {StatusApproved, StatusRejected},
    StatusApproved:      {StatusActive, StatusPaused},
    StatusActive:        {StatusPaused, StatusExpired, StatusViolation},
    StatusPaused:        {StatusActive, StatusExpired},
    StatusRejected:      {StatusDraft},   // 修改后重新提交
    StatusViolation:     {StatusDraft},   // 修改后重新提交
}

func (ad *Ad) TransitionTo(newStatus AdStatus) error {
    validNext, ok := validTransitions[ad.Status]
    if !ok {
        return fmt.Errorf("invalid current status: %d", ad.Status)
    }
    for _, s := range validNext {
        if s == newStatus {
            ad.Status = newStatus
            ad.UpdatedAt = time.Now()
            // 发送状态变更事件 → 通知索引更新、通知广告主
            publishEvent(AdStatusChangedEvent{
                AdID:      ad.ID,
                OldStatus: ad.Status,
                NewStatus: newStatus,
            })
            return nil
        }
    }
    return fmt.Errorf("invalid transition: %d → %d", ad.Status, newStatus)
}
```

## 九、广告的多目标优化

---

```
Q: 广告系统需要同时优化多个目标，怎么做？

答题要点：

多目标：
1. 平台收入（Revenue）
2. 广告主 ROI
3. 用户体验（User Experience）
4. 生态健康（Ecosystem Health）

这四个目标有时互相矛盾：
- 追求短期收入 → 多展示高 eCPM 广告 → 用户体验差 → 用户流失 → 长期收入下降
- 追求用户体验 → 少展示广告 → 短期收入下降
- 保护中小广告主 → 可能牺牲短期收入

解决方案：

1. 约束优化
   max Revenue
   s.t. 
     用户负反馈率 < 阈值
     广告密度 < 阈值
     广告主平均 ROI > 阈值

2. 多目标排序公式
   Score = w1 × eCPM + w2 × UserScore + w3 × EcoScore + w4 × DiversityScore
   
   权重通过 A/B 实验和在线学习调整

3. 分层决策
   - 机制层：控制广告的总量和密度（保底用户体验）
   - 排序层：在允许展示的位置选择最优广告
   - 出价层：通过智能出价控制广告主成本

4. 长期价值建模
   - 不只考虑当次曝光的收入
   - 考虑用户的 LTV（Lifetime Value）
   - 给高 LTV 用户少展示广告 → 提升留存 → 长期收入更高
   - 需要强化学习（RL）或因果推断方法

Q: 广告多样性怎么控制？
- 问题：排序后 Top K 可能全是同一个行业/广告主的广告
- 解决：
  ① MMR（Maximal Marginal Relevance）：
     Score = λ × Relevance - (1-λ) × max(Similarity to selected ads)
  ② 规则约束：同一广告主最多展示 N 条
  ③ 行业配额：各行业按比例分配展示份额
  ④ Determinantal Point Process (DPP)：数学上优雅的多样性方法
```

## 十、广告数据链路完整性

---

```
Q: 如何保证广告数据（曝光/点击/转化/计费）的完整性和一致性？

答题要点：

数据链路全景：
┌─────────────────────────────────────────────────────┐
│ 客户端                                                │
│ ├─ 广告请求 → 返回广告 → 渲染广告 → 上报曝光          │
│ ├─ 用户点击 → 上报点击 → 跳转落地页                    │
│ └─ 用户转化 → 上报转化事件                             │
├─────────────────────────────────────────────────────┤
│ 数据收集层                                            │
│ ├─ 曝光上报服务 → Kafka topic: ad_show                │
│ ├─ 点击上报服务 → Kafka topic: ad_click               │
│ └─ 转化上报服务 → Kafka topic: ad_conversion          │
├─────────────────────────────────────────────────────┤
│ 实时处理层 (Flink)                                    │
│ ├─ 实时计数 → Redis（曝光数/点击数/消耗）             │
│ ├─ 实时计费 → 预算扣减                                │
│ ├─ 实时归因 → 展示-点击-转化 Join                     │
│ └─ 实时反作弊 → 过滤无效流量                          │
├─────────────────────────────────────────────────────┤
│ 离线处理层 (Spark/Hive)                               │
│ ├─ T+1 数据对账                                      │
│ ├─ 离线报表生成                                       │
│ ├─ 模型训练样本                                       │
│ └─ 离线反作弊                                         │
├─────────────────────────────────────────────────────┤
│ 数据服务层                                            │
│ ├─ 广告主报表 API                                     │
│ ├─ 内部数据分析平台                                   │
│ └─ 财务结算系统                                       │
└─────────────────────────────────────────────────────┘

数据质量保障：

1. 端到端对账
   - 客户端上报数 vs 服务端接收数 vs Kafka 消费数 vs 最终存储数
   - 每个环节记录数量，比对差异
   - 差异超过阈值 → 告警 + 排查

2. 幂等性
   - 每个事件有唯一 ID（request_id + event_type + timestamp）
   - 处理前检查是否已处理过
   - Redis Set / BloomFilter 去重

3. 数据补偿
   - 客户端：本地缓存 + 重试（曝光/点击上报失败时）
   - 服务端：Kafka 消费失败 → 死信队列 → 人工/自动重处理
   - 离线对账发现缺失 → 从原始日志重新处理

4. 数据一致性
   - 实时数据和离线数据可能有差异（实时是近似值）
   - 最终以离线 T+1 数据为准（用于计费和结算）
   - 实时数据用于实时控制（预算、频次）

5. 监控和告警
   - 各环节的数据量监控（同比/环比异常检测）
   - 数据延迟监控（Kafka lag、Flink checkpoint）
   - 数据质量规则（如：点击数不可能大于曝光数的 30%）
```

## 十一、广告系统的多数据中心与容灾

---

```
Q: 广告系统的高可用架构怎么设计？如何做到多机房容灾？

答题要点：

多机房部署架构：
┌────────────────────┐    ┌────────────────────┐
│   机房 A（主）       │    │   机房 B（备）       │
│                      │    │                      │
│ ┌──────────────┐    │    │ ┌──────────────┐    │
│ │ 广告引擎集群  │←──同步──→│ 广告引擎集群  │    │
│ └──────────────┘    │    │ └──────────────┘    │
│ ┌──────────────┐    │    │ ┌──────────────┐    │
│ │ 索引服务      │←──同步──→│ 索引服务      │    │
│ └──────────────┘    │    │ └──────────────┘    │
│ ┌──────────────┐    │    │ ┌──────────────┐    │
│ │ Redis 集群    │←──同步──→│ Redis 集群    │    │
│ └──────────────┘    │    │ └──────────────┘    │
│ ┌──────────────┐    │    │ ┌──────────────┐    │
│ │ MySQL 主库    │────复制──→│ MySQL 从库    │    │
│ └──────────────┘    │    │ └──────────────┘    │
└────────────────────┘    └────────────────────┘

部署模式：

1. 单活（Active-Standby）
   - 主机房处理所有流量
   - 备机房只做数据同步，不处理请求
   - 主机房故障 → 切换到备机房
   - 切换时间：分钟级

2. 双活（Active-Active）
   - 两个机房同时处理流量
   - 流量按地域/用户 ID 路由
   - 需要解决数据同步和一致性问题
   - 切换时间：秒级

3. 多活（Multi-Active）
   - 三个及以上机房
   - 每个机房独立服务一部分流量
   - 故障时流量自动迁移到其他机房

广告系统的特殊考虑：
- 索引数据：每个机房独立构建（从同一数据源）
- 预算数据：需要跨机房同步（或使用中心化预算服务）
- 频次数据：可以容忍短暂不一致（降级为机房内频次控制）
- 计费数据：必须持久化到跨机房的存储中
```

## 十二、广告的实时数据分析与报表

---

```
Q: 广告主看到的实时报表数据是怎么计算出来的？

答题要点：

报表数据需求：
- 广告主要看：每个广告的曝光数、点击数、转化数、消耗、CTR、CVR、CPA
- 维度：按小时/天/广告计划/广告创意/地域/设备/人群
- 实时性：5分钟级别

实时报表架构：
┌─────────────────────────────────────────────┐
│                                               │
│  曝光/点击/转化事件 → Kafka                    │
│       ↓                                       │
│  Flink 实时聚合                                │
│  - GROUP BY ad_id, hour, dimension            │
│  - SUM(impressions), SUM(clicks), SUM(cost)   │
│       ↓                                       │
│  写入 OLAP 引擎                                │
│  ├─ ClickHouse（字节/快手常用）               │
│  ├─ Doris/StarRocks（百度/腾讯常用）          │
│  └─ Druid                                     │
│       ↓                                       │
│  报表查询 API                                  │
│  - 预聚合 + 实时查询                           │
│  - 缓存热门查询结果                            │
│       ↓                                       │
│  广告主报表页面                                │
└─────────────────────────────────────────────┘

预聚合 vs 现场计算：
- 预聚合：提前按常用维度组合计算好，查询直接读
  优点：查询快
  缺点：维度组合多时存储爆炸
- 现场计算：查询时实时聚合
  优点：灵活
  缺点：查询慢
- 实际方案：常用维度预聚合 + 长尾查询现场计算

ClickHouse 在广告报表中的应用：
- 列式存储 → 聚合查询极快
- 向量化执行引擎
- 分布式查询
- 典型查询：
  SELECT 
    ad_id, 
    toHour(event_time) as hour,
    sum(impressions) as imp,
    sum(clicks) as clk,
    sum(cost) as cost,
    clk / imp as ctr
  FROM ad_report
  WHERE advertiser_id = 12345
    AND event_date = '2024-01-15'
  GROUP BY ad_id, hour
  ORDER BY hour

## 十三、广告素材 CDN 与加载优化

---

```
Q: 广告素材（图片/视频）的加载性能怎么优化？

答题要点：

为什么重要？
- 广告加载慢 → 用户看不到广告 → 曝光丢失 → 收入损失
- 据统计，加载时间每增加 100ms，广告收入下降约 1%

优化方案：

1. CDN 加速
   - 广告素材上传后分发到全球 CDN 节点
   - 用户就近访问
   - CDN 预热：新素材上线前预热到各节点

2. 素材预加载
   - 在用户即将看到广告之前提前加载素材
   - 信息流场景：用户向下滑动时预加载下方的广告素材
   - 开屏广告：在 APP 启动时缓存下次的开屏素材

3. 多格式适配
   - 根据设备和网络选择最佳格式
   - 图片：WebP（比 JPEG 小 30%）、AVIF
   - 视频：H.265/HEVC、AV1（比 H.264 节省 30-50% 带宽）
   - 自适应码率：网络差时降低视频质量

4. 素材压缩
   - 有损压缩到视觉无损（SSIM > 0.95）
   - 图片：根据广告位尺寸裁剪/缩放，不传大图
   - 视频：转码到目标码率

5. 懒加载
   - 不在可视区域的广告延迟加载
   - Intersection Observer API

工程实现：
- 素材上传 → 异步转码/压缩 → 生成多种规格 → 分发 CDN
- 广告返回时根据设备/网络选择最优素材 URL
- 防盗链：URL 签名 + 有效期
```

## 十四、面试中可能被追问的边角问题

---

```
Q1: 广告的竞争隔离（Competitive Separation）
    - 同一页面不展示竞争对手的广告
    - 实现：广告打上行业标签，排序后去重同行业

Q2: 广告的时区处理
    - 广告主在东八区，用户在西五区
    - 日预算按哪个时区计算？
    - 通常按广告主设置的时区

Q3: 广告的多币种支持
    - 海外广告需要支持美元/欧元/日元等
    - 汇率更新频率？
    - 计费精度？（小数点后多少位）

Q4: 广告的品牌安全（Brand Safety）
    - 广告不展示在不适当的内容旁边
    - 如：奶粉广告不展示在负面新闻旁边
    - 需要对页面内容做分类/打标

Q5: 广告的可见性（Viewability）
    - 广告被展示 ≠ 用户真的看到了
    - MRC 标准：50% 像素可见 + 持续 1 秒（展示广告）
    - 视频广告：50% 像素可见 + 持续 2 秒 + 有声
    - 工程：客户端监控广告元素的可见状态上报

Q6: 广告的交叉销售（Cross-Selling）
    - 在不同广告产品之间的统一频次控制
    - 如：用户在抖音和今日头条看到的同一个广告主的广告
    - 需要跨产品的用户级频次控制

Q7: 广告的 Waterfall 和 Header Bidding
    - 传统 Waterfall：按固定优先级依次请求各广告源
    - Header Bidding：同时请求所有广告源，选最高出价
    - 工程：并行请求 + 统一竞价 + 超时控制

Q8: 广告的动态底价（Dynamic Floor Price）
    - 根据用户价值、广告位质量动态调整底价
    - 底价太低 → 低质量广告展示，影响体验
    - 底价太高 → 广告填充率低，浪费流量
    - 模型预测最优底价：max(Revenue) = 填充率 × 平均 eCPM

Q9: 广告沙盒（Sandbox / Test Mode）
    - 广告主在正式投放前的测试环境
    - 不计费，不影响正式数据
    - 可以测试创意效果、定向范围

Q10: 广告的季节性和大促
     - 双 11、618、春节等大促期间流量和竞争激烈变化
     - 系统容量规划：提前扩容
     - 预算控制：大促期间预算消耗速度可能是平时的 5-10 倍
     - 出价策略：自动调整智能出价的参数
     - 反作弊：大促期间作弊量也会增加

Q11: 隐私计算在广告中的应用
     - 联邦学习：不共享原始数据的前提下联合建模
     - 差分隐私：在统计结果中加噪声保护个人隐私
     - 安全多方计算（MPC）：多方联合计算但不泄露各自数据
     - TEE（可信执行环境）：数据在加密环境中处理
     - 场景：广告主数据 × 媒体数据 → 联合建模提升效果
       但双方都不想暴露自己的数据

Q12: 广告系统的成本优化
     - 计算成本：
       ① 模型推理占比最大 → 模型压缩/蒸馏
       ② 非高峰时段自动缩容
       ③ 用 Spot Instance 处理离线任务
     - 存储成本：
       ① 冷热数据分层（热：SSD，温：HDD，冷：对象存储）
       ② 日志保留策略（详细日志保留 7 天，聚合数据保留 1 年）
     - 带宽成本：
       ① 素材压缩
       ② 内部通信用 Protobuf 代替 JSON
       ③ gRPC 多路复用
```

# 一、用户标识体系与 ID-Mapping（前文完全遗漏 ⚠️）

> **这是广告系统最底层、最关键的基础设施之一，面试高频考点**

---

```
Q: 广告系统怎么识别一个用户？不同平台、不同设备上的同一个用户怎么关联？

答题要点：

1. 用户标识符的类型

┌──────────────┬───────────────────────┬──────────────────┐
│ 标识符        │ 说明                   │ 稳定性            │
├──────────────┼───────────────────────┼──────────────────┤
│ 手机号/邮箱   │ 注册用户的真实身份       │ 最稳定，但覆盖低  │
│ 账号ID        │ 平台内用户ID            │ 稳定，平台内有效   │
│ IDFA (iOS)    │ Apple 广告标识符        │ iOS 14后需授权    │
│ GAID (Android)│ Google 广告标识符       │ 用户可重置        │
│ OAID          │ 国内安卓广告标识符       │ 部分厂商支持      │
│ IMEI          │ 设备硬件标识            │ 稳定但隐私受限    │
│ Cookie        │ 浏览器标识              │ 不稳定，可清除     │
│ 设备指纹      │ 多维度特征组合生成       │ 近似标识，有误差   │
│ IP + UA       │ 网络+浏览器特征         │ 非常不稳定        │
└──────────────┴───────────────────────┴──────────────────┘

2. ID-Mapping（ID 图谱）系统

核心问题：同一个用户可能有多个标识符
  - 手机上用 OAID 看到广告
  - 电脑上用 Cookie 访问落地页
  - 最后用手机号注册转化
  → 需要把这三个标识关联为同一个人

ID 图谱的构建：

方式一：确定性匹配（Deterministic Matching）
  - 用户登录时，将设备 ID 和账号 ID 绑定
  - 手机号 ↔ 设备ID ↔ 账号ID
  - 准确率高，但覆盖率有限

方式二：概率性匹配（Probabilistic Matching）
  - 基于设备特征（IP、UA、屏幕分辨率、时区等）
  - 机器学习模型判断两个标识是否属于同一用户
  - 覆盖率高，但有误差

ID 图谱的存储：
  - 图结构：节点是各种 ID，边是关联关系
  - 存储方案：
    ① 图数据库（Neo4j / JanusGraph）→ 灵活但性能一般
    ② KV 存储 + 并查集 → 高性能
    ③ HBase：RowKey = canonical_id，Column = 各种 ID

  数据结构示例：
  ```
  canonical_user_001:
    phone    → 138xxxx1234
    oaid     → abc-def-123
    idfa     → xyz-789
    cookie   → ck_abcdef
    account  → user_56789
  ```

  查询流程：
  请求携带 OAID → 查 ID 映射表 → 找到 canonical_id → 
  → 用 canonical_id 查用户画像和历史行为

3. 设备指纹（Device Fingerprinting）

在无法获取 IDFA/OAID 的情况下（iOS 14+ 未授权）：
  - 采集多个弱特征：
    ① 屏幕分辨率 + 像素密度
    ② 操作系统版本
    ③ 时区 + 语言
    ④ 字体列表
    ⑤ 安装 APP 列表（Android）
    ⑥ IP 段
    ⑦ 网络类型
  - 组合生成 hash → 设备指纹 ID
  - 准确率：~85-95%（取决于特征丰富度）
  - 冲突处理：多个设备可能生成相同指纹 → 概率模型去歧义

4. 工程挑战

  - 数据量巨大：十亿级用户 × 多个标识 = 数十亿关系
  - 实时性要求：新绑定关系需要分钟级生效
  - 一致性：同一用户的不同 ID 必须关联到同一个 canonical_id
  - 隐私合规：ID 数据是最敏感的数据
  - 老化机制：设备被转手/重置后需要解除关联

面试追问：
Q: iOS 14 之后 IDFA 获取率大幅下降，对广告系统有什么影响？
A: ① 用户识别准确率下降 → 频次控制/归因不准
   ② CTR/CVR 预估模型效果下降（缺少用户历史行为）
   ③ 重定向广告效果大幅下降
   ④ 应对：设备指纹、概率归因、SKAdNetwork、聚合建模、
      上下文定向（不依赖用户身份的定向方式）
```

# 二、点击追踪与跳转服务（前文未深入 ⚠️）

---

```
Q: 用户点击广告后，从点击到到达广告主落地页的完整链路是什么？

答题要点：

点击链路：

用户点击广告 
    → 客户端发起点击请求
    → 点击追踪服务器（Click Server）
        ① 记录点击日志（用户ID、广告ID、时间、设备信息...）
        ② 反作弊校验（是否有效点击）
        ③ 计费触发（CPC 模式下扣费）
        ④ 生成追踪参数（click_id, 归因参数）
        ⑤ 302 重定向到落地页 URL
    → 用户浏览器跳转到广告主落地页
    → 落地页加载完成 → 触发到达事件上报

点击 URL 的结构：
https://click.ad-platform.com/click?
    ad_id=12345
    &creative_id=678
    &req_id=abc-def-123          # 请求ID
    &click_id=clk-xyz-456        # 点击ID（全局唯一）
    &user_id=u_789               # 加密的用户ID
    &ts=1705312800               # 时间戳
    &sign=a1b2c3d4               # 防篡改签名
    &redirect_url=https%3A%2F%2Fwww.advertiser.com%2Flanding
    &callback=https%3A%2F%2Ftrack.ad-platform.com%2Fcb  # 转化回调

签名验证（防止伪造点击）：
sign = HMAC_SHA256(secret_key, ad_id + click_id + ts + user_id)
服务端验证签名一致性 + 时间戳在有效期内（如 5 分钟）

点击服务的工程要求：
- QPS 极高（数万~数十万）
- 延迟极低（< 50ms，用户在等跳转）
- 高可用（点击丢失 = 收入丢失）
- 幂等（同一个点击不能重复计费）

去重策略：
- 同一 request_id 的重复点击（用户双击/网络重试）
- 短时间内同一用户对同一广告的重复点击
- 实现：Redis SET + TTL 或 BloomFilter

点击服务架构：
┌──────────────────────────────────────────────┐
│               点击服务（Click Server）          │
│                                                │
│  接收请求 → 参数校验 → 签名验证                 │
│     → 去重检查（Redis）                        │
│     → 反作弊（规则引擎）                        │
│     → 写点击日志（异步 → Kafka）                │
│     → 触发计费（异步 → Kafka）                  │
│     → 生成 click_id                            │
│     → 拼接落地页 URL + 追踪参数                  │
│     → 302 Redirect                             │
│                                                │
│  注意：整个流程必须在 50ms 内完成                │
│  非核心操作全部异步化                            │
└──────────────────────────────────────────────┘

Deeplink 与 Deferred Deeplink：
- Deeplink：点击广告 → 直接跳转到 APP 内指定页面
  URL scheme: myapp://product/12345
  Universal Links (iOS) / App Links (Android)
  
- Deferred Deeplink：用户未安装 APP 时
  点击广告 → 跳转应用商店 → 下载安装 → 首次打开 →
  自动跳转到广告对应的页面
  实现：设备指纹匹配 或 剪贴板传参

监控曝光（Impression Tracking）：
- 方式一：像素追踪（1×1 Pixel）
  <img src="https://track.ad-platform.com/imp?ad_id=123&..." width="1" height="1">
  广告展示时浏览器自动请求该图片 → 服务器记录曝光

- 方式二：JS SDK 上报
  广告渲染完成后通过 JS 发送曝光事件
  优势：可以判断「可见性」（是否真的在视口内）

- 方式三：客户端 SDK 上报
  原生 APP 内由 SDK 主动上报
```

# 三、Bid Shading（出价阴影，前文遗漏 ⚠️）

---

```
Q: 在第一价格拍卖（FPA）中，怎么避免广告主出价过高？

背景：
- 行业趋势：从 GSP（第二价格）转向 FPA（第一价格）
  Google Ads 在 2019 年切换到 FPA
- 在 FPA 中，赢家支付自己的出价 → 出价太高就亏了
- Bid Shading：在 FPA 中帮广告主降低出价，接近第二价格

原理：
optimal_bid = 预测的市场清算价格 × 调节系数
            ≈ 第二高出价的预估值

实现方案：

1. 历史数据方法
   - 统计同类广告位/定向条件下的历史成交价分布
   - 用分位数（如 P70）作为出价参考
   - 问题：历史不代表未来

2. 机器学习方法（推荐）
   - 训练模型预测：给定特征（广告位、用户、时段等），
     赢得竞价所需的最低价格是多少？
   - 特征：
     ① 广告位特征（位置、尺寸、媒体）
     ② 时间特征（时段、星期）
     ③ 用户价值特征
     ④ 历史竞争水平
   - 模型输出：market_price 的分布
   - 出价 = market_price 的某个分位数
   
3. 在线学习
   - 根据实时竞价结果不断调整
   - 赢了但价格远高于第二名 → 下次降低
   - 输了 → 下次提高
   - 类似 PID 控制

工程实现要点：
- Bid shading 的粒度：每次请求独立计算 or 按广告/广告位粒度
- 缓存：相同特征的请求可以复用 shading 系数
- 延迟：bid shading 计算必须包含在总竞价时间内
- A/B 实验：对比 shading 前后的广告主 ROI 和平台收入
```

# 四、人群包管理系统（DMP 工程，前文未深入 ⚠️）

---

```
Q: 广告主上传了一个 1000 万用户的手机号人群包，系统怎么处理？

答题要点：

人群包的类型：
1. 广告主自有人群包：广告主上传的用户列表（手机号/设备ID）
2. 平台人群包：平台根据用户行为/属性圈选的人群
3. 第三方 DMP 人群包：合作方提供的人群数据
4. Lookalike 扩展包：基于种子用户扩展的人群

完整流程：

Step 1: 上传与处理
  广告主上传 CSV/TXT 文件（手机号列表）
    → 后端接收 → 异步处理
    → 手机号加密（SHA256/MD5）→ 匹配平台用户
    → 记录匹配率（如：上传 1000 万，匹配到 600 万）

Step 2: 存储
  方案一：Bitmap（推荐）
    - 将用户 ID 映射到 bit 位
    - 10 亿用户 → 约 120MB
    - 支持高效的交集/并集/差集
    - 库：Roaring Bitmap（压缩，更省空间）
  
  方案二：BloomFilter
    - 更省空间，但有误判（假阳性）
    - 不支持删除
    - 适用于粗略过滤
  
  方案三：Set 存储（Redis Set / HBase）
    - 精确，支持动态增删
    - 空间大

Step 3: 在线查询
  广告检索时：
    判断当前用户是否在某个人群包中
    → Bitmap.contains(user_id) → O(1)
  
  需要支持复杂的人群组合逻辑：
    (人群包A AND 人群包B) OR (人群包C AND NOT 人群包D)
    → Bitmap 的位运算天然支持

Step 4: 人群包更新
  - 增量更新：新增/删除部分用户
  - 全量更新：重新上传
  - 实效性：Lookalike 包每天更新，广告主自有包实时更新
  - 版本控制：保留历史版本，支持回滚

人群包在广告引擎中的使用：
```go
// 人群包管理器
type AudienceManager struct {
    packages map[int64]*roaring.Bitmap  // packageID → bitmap
    mu       sync.RWMutex
}

// 检查用户是否在某个人群包中
func (am *AudienceManager) Contains(packageID int64, userID uint32) bool {
    am.mu.RLock()
    defer am.mu.RUnlock()
    
    bm, ok := am.packages[packageID]
    if !ok {
        return false
    }
    return bm.Contains(userID)
}

// 人群包组合查询
func (am *AudienceManager) EvaluateExpression(
    expr *AudienceExpression, userID uint32) bool {
    
    switch expr.Op {
    case AND:
        return am.Contains(expr.Left, userID) && 
               am.Contains(expr.Right, userID)
    case OR:
        return am.Contains(expr.Left, userID) || 
               am.Contains(expr.Right, userID)
    case NOT:
        return !am.Contains(expr.Left, userID)
    }
    return false
}
```

人群包的规模估算：
- 广告主上传人群包：需要计算与各定向条件交叉后的覆盖量
- 用于广告主设置定向时预估受众规模
- 实现：预计算 各人群包 × 各定向维度 的交集大小
  → 存储在 cube 中，查询时直接查表

# 五、特征一致性（Online-Offline Consistency，前文遗漏 ⚠️）

---

```
Q: 模型训练用的特征和在线推理用的特征不一致会怎样？怎么解决？

答题要点：

这是广告系统中一个非常常见且隐蔽的问题，被称为
"Training-Serving Skew"（训练-服务偏差）

不一致的来源：

1. 特征计算逻辑不一致
   - 训练时用 Python/Spark 计算特征
   - 在线用 Go/C++ 计算特征
   - 两套代码可能有细微差异（四舍五入、空值处理等）

2. 特征时间点不一致
   - 训练时用的是事件发生时的特征（回溯正确）
   - 但如果用的是当前时间的特征（穿越未来数据）→ 信息泄漏
   - 例：用户在点击后修改了年龄，训练时用修改后的年龄 → 不一致

3. 特征数据源不一致
   - 训练从 Hive 读特征
   - 在线从 Redis 读特征
   - 两个存储的数据可能不同步

4. 特征版本不一致
   - 特征定义变更了，模型还在用旧版本特征
   - 新增了某个特征，但在线服务还没有上线

影响：
- 模型离线 AUC 很高，上线后效果变差
- 这是广告模型效果衰减的第一大原因之一

解决方案：

方案一：统一特征计算（Feature Store）
┌──────────────────────────────────────────┐
│            Feature Store                   │
│                                            │
│  ┌──────────────────────────────────┐     │
│  │  特征定义层（Feature Definition）  │     │
│  │  - 统一的特征定义 DSL/Config      │     │
│  │  - 版本管理                       │     │
│  └──────────────┬───────────────────┘     │
│                 │                          │
│  ┌──────────────▼───────────────────┐     │
│  │  特征计算层                       │     │
│  │  - 离线计算引擎（Spark/Flink）    │     │
│  │  - 在线计算引擎（Go/C++）         │     │
│  │  ★ 使用同一份特征定义生成代码     │     │
│  └──────────────┬───────────────────┘     │
│                 │                          │
│  ┌──────────────▼───────────────────┐     │
│  │  特征存储层                       │     │
│  │  - 离线：Hive/HDFS               │     │
│  │  - 在线：Redis/RocksDB           │     │
│  │  - 数据同步保证一致               │     │
│  └──────────────────────────────────┘     │
└──────────────────────────────────────────┘

方案二：特征日志（Feature Logging）★ 推荐
  - 在线推理时，将实际使用的特征值记录到日志中
  - 训练时直接使用在线日志中的特征（而非重新计算）
  - 保证训练和推理使用完全相同的特征值
  
  流程：
  广告请求 → 特征查询 → 模型推理 → 返回结果
                ↓
        记录特征快照到 Kafka
                ↓
        存储到 Hive（训练样本的一部分）
                ↓
        模型训练直接使用这些特征

  优势：彻底消除 Training-Serving Skew
  劣势：存储量大（每次请求都记录所有特征）
  优化：采样记录（如 10% 的请求记录特征）

方案三：特征回溯（Point-in-Time Feature）
  - 存储特征的历史版本（带时间戳）
  - 训练时查询事件发生时刻的特征快照
  - 实现复杂但准确
```

# 六、样本构造与偏差处理（前文遗漏 ⚠️）

---

```
Q: CTR/CVR 模型训练的样本怎么构造？有哪些偏差问题？

答题要点：

1. CTR 样本构造
   正样本：用户点击了广告 → label = 1
   负样本：用户看到广告但没点击 → label = 0
   
   问题一：正负样本极度不平衡（CTR 通常 1-5%）
   解决：
   - 负采样：随机抽取部分负样本
   - 采样率校正：模型预测值需要除以采样率来恢复真实概率
     real_ctr = predicted_ctr / (predicted_ctr + (1 - predicted_ctr) / sampling_rate)

2. CVR 样本构造
   正样本：用户点击广告后发生了转化 → label = 1
   负样本：用户点击广告但没有转化 → label = 0
   
   问题二：样本选择偏差（Sample Selection Bias）★ 重要
   - CVR 模型只能在「点击」的样本上训练
   - 但我们想预测的是「曝光」的用户的转化率
   - 曝光但未点击的用户可能和点击的用户分布不同
   - 解决：
     ① ESMM（Entire Space Multi-Task Model）：
        同时预测 CTR 和 CVR，CVR 在全空间（曝光样本）上建模
        pCVR = pCTCVR / pCTR
     ② 全空间建模：用曝光样本训练，label = 是否最终转化

3. 延迟反馈（Delayed Feedback）★ 重要
   - 用户可能在点击后几小时甚至几天才发生转化
   - 如果训练时使用当前时刻的标签 → 很多真正的正样本被标为负样本
   - 解决：
     ① 等待窗口：训练样本等待 N 天再确定标签
        缺点：数据不够新鲜
     ② 延迟反馈建模：
        建模转化延迟的分布（如指数分布/Weibull 分布）
        预估最终转化概率 = 当前转化率 / 已到达的时间窗口占比
     ③ 重要性采样：对延迟回收的正样本给予更高权重

4. 位置偏差（Position Bias）
   - 用户更倾向点击排在前面的广告（不论广告本身好坏）
   - 排在第 1 位的广告天然 CTR 就高
   - 解决：
     ① 在模型中加入位置特征，推理时设为统一位置
     ② IPW（Inverse Propensity Weighting）：根据位置加权
     ③ PAL（Position-Aware Learning）：显式建模位置影响

5. 曝光偏差（Exposure Bias）
   - 只有被系统选中展示的广告才有训练样本
   - 从未展示过的广告缺乏数据 → 马太效应（强者越强）
   - 解决：
     ① 随机探索流量（1-5% 流量随机展示广告）
     ② 反事实学习（Counterfactual Learning）
     ③ IPS（Inverse Propensity Score）加权
```

# 七、模型校准（Calibration，前文遗漏 ⚠️）

---

```
Q: CTR 预估模型的校准是什么？为什么重要？怎么做？

答题要点：

什么是校准？
- 模型预测 CTR = 5%，实际上 100 次展示应该有约 5 次点击
- 如果实际只有 2 次 → 模型未校准（过度自信）
- 广告系统中，pCTR 直接参与 eCPM 计算和计费，
  不准确的 pCTR 会导致：
  ① 计费不准（GSP 扣费依赖 pCTR）
  ② 排序不公平
  ③ 广告主成本不可控

校准方法：

1. Platt Scaling
   - 在模型输出上拟合一个 sigmoid 函数
   - calibrated_p = 1 / (1 + exp(A × logit + B))
   - 用验证集学习 A 和 B

2. Isotonic Regression（保序回归）
   - 非参数方法
   - 将预测值分桶，每个桶内用实际正样本率替代
   - 保持单调性

3. 分桶校准（Binning Calibration）
   - 将预测概率分成 N 个桶
   - 每个桶内统计实际概率
   - 用查表方式校准
   
4. 后验校准（Prior Correction）
   - 负采样导致预测偏高 → 根据采样率校准
   - real_p = p / (p + (1-p) / w)  （w 为采样率）

5. 在线校准
   - 实时监控模型预测值和实际值的偏差
   - 计算校准系数 = 实际 CTR / 预测 CTR 的滑动平均
   - 实时乘以校准系数
   
   按维度校准（更精细）：
   - 按广告位校准
   - 按行业校准
   - 按人群校准

监控指标：
- Expected Calibration Error (ECE)：分桶后预测值和实际值的差距
- 校准曲线（Calibration Curve / Reliability Diagram）
```

```
Q: 广告引擎的代码变更怎么安全上线？灰度策略怎么设计？

答题要点：

广告系统发布的特殊性：
- 任何 bug 都直接影响收入（每分钟损失可能是数万元）
- 模型/策略变更的影响很难提前完全预估
- 需要极其谨慎的发布流程

完整发布流程：

Step 1: 离线验证
  - 代码 review
  - 单元测试 + 集成测试

    ① 录制线上真实请求
    ② 在测试环境回放

  ┌────────────────────────────────────────┐

  │ 阶段1: 1% 流量 → 观察 1 小时           │

  │   关注：eCPM、CTR、填充率、广告主消耗   │
  │                                        │
  │ 阶段3: 20% 流量 → 观察 4 小时          │
  │   关注：全面指标对比                    │
  │                                        │
  │ 阶段4: 50% 流量 → 观察 12 小时         │
  │   关注：长期指标趋势                    │
  │                                        │
  │ 阶段5: 100% 全量                       │
  └────────────────────────────────────────┘

Step 3: 自动回滚条件
  - 错误率 > 基线的 2 倍 → 自动回滚
  - P99 延迟 > 基线的 1.5 倍 → 自动回滚  
  - 收入同比下降 > 5% → 自动回滚
  - 自动回滚时间：< 2 分钟

# 十、财务结算系统（前文遗漏 ⚠️）

---

```
Q: 广告费用从计费到最终结算的完整流程是什么？

答题要点：

广告主充值 → 消耗（实时扣费）→ 对账 → 结算 → 开票

1. 账户体系
   ┌──────────────────────────────────────┐
   │ 广告主账户                            │
   │                                       │
   │ 充值账户余额（可消耗金额）              │
   │ 冻结金额（正在使用但未确认的金额）       │
   │ 赠送金额（平台赠送，有使用条件）         │
   │ 信用额度（大客户后付费额度）             │
   │ 退款金额                               │
   └──────────────────────────────────────┘

2. 消耗流程
   实时消耗（预扣）→ 确认消耗 → 回滚/补偿
   
   预扣：广告展示/点击时，从账户余额预扣费
   确认：反作弊过滤后，确认有效消耗
   回滚：反作弊判定为无效 → 回退预扣金额

3. 对账（T+1）★ 工程重点
   - 每天凌晨进行前一天的数据对账
   - 对比维度：
     ① 实时计费系统的消耗数据
     ② 离线日志系统的消耗数据
     ③ 账户系统的余额变动
   - 差异处理：
     差异 < 0.1% → 自动调整
     差异 0.1-1% → 告警 + 人工确认
     差异 > 1% → 紧急排查
   
   对账 SQL 示例：
   ```sql
   -- 对比实时消耗和离线消耗
   SELECT 
       a.advertiser_id,
       a.realtime_cost,
       b.offline_cost,
       ABS(a.realtime_cost - b.offline_cost) as diff,
       ABS(a.realtime_cost - b.offline_cost) / a.realtime_cost as diff_rate
   FROM realtime_billing a
   JOIN offline_billing b ON a.advertiser_id = b.advertiser_id
   WHERE a.date = '2024-01-15'
   HAVING diff_rate > 0.001  -- 差异率 > 0.1% 的需要排查
   ```

4. 结算与开票
   - 预付费模式：先充值后消耗
   - 后付费模式：月结/季结（大客户）
   - 开票：按实际消耗金额开具发票
   - 退款：账户关停时退回未消耗余额

5. 金额精度
   - 内部计算使用整数（分/厘为单位），避免浮点精度问题
   - 数据库使用 DECIMAL 类型
   - 计费精度：通常到厘（0.001 元）
   
   ```go
   // 使用整数存储金额（单位：厘）
   type Money int64  // 1 元 = 1000 厘
   
   func (m Money) Yuan() float64 {
       return float64(m) / 1000.0
   }
   
   func FromYuan(yuan float64) Money {
       return Money(math.Round(yuan * 1000))
   }
   ```

6. 防超投与负余额
   - 正常情况：余额 ≤ 0 时停止投放

   - 商圈多边形数据：每个商圈定义为一个多边形区域

     ② 多边形围栏：射线法判断点是否在多边形内

   - 将地球表面映射到正方体 → 四叉树分层编码

   - 用于：给定一个围栏，快速找到覆盖该围栏的 S2 Cell

Q: 用户的实时行为特征怎么计算？比如"用户最近 1 小时点击了哪些广告"？

实时特征的类型：

2. 实时序列特征：最近 N 次点击的广告 ID 序列
3. 实时上下文特征：当前会话的行为特征

实时特征计算架构：

方案一：Flink 流式计算
┌──────────────────────────────────────────┐
│  用户行为事件 → Kafka → Flink            │
│                           ↓              │
│  ┌──────────────────────────────┐        │
│  │ Flink 实时计算：              │        │
│  │                               │        │
│  │ 窗口统计：                    │        │
│  │ - 最近 10 分钟点击数          │        │
│  │ - 最近 1 小时行业点击分布     │        │
│  │                               │        │
│  │ 序列维护：                    │        │
│  │ - 最近 50 次行为序列          │        │
│  │ - 按时间衰减加权              │        │
│  └──────────────┬───────────────┘        │
│                 ↓                         │
│  写入 Redis / Feature Store              │
│  Key: rt_feat:{user_id}                  │

│          click_seq: [ad1, ad3, ad7, ...], │
│          industry_dist: {game: 0.3, ...}} │
└──────────────────────────────────────────┘

方案二：请求时实时计算
- 在广告引擎收到请求时，实时查询用户最近行为
- 从 Redis ZSet 中获取最近 N 次行为
- 在线实时计算统计特征
- 适用于特征计算简单、行为量不大的场景

方案三：近线计算（推荐组合方案）
- 分钟级更新的特征：Flink → Redis（周期性刷新）
- 秒级更新的特征：请求时实时查询 + 计算
- 小时/天级特征：Spark 离线计算 → Redis

   → 解决：训练样本构造时，严格使用事件发生前的特征

# 十三、Embedding 服务与向量检索工程（前文覆盖不够深 ⚠️）

---

```
Q: 广告系统中的 Embedding 表非常大（数亿特征），怎么管理和服务？

答题要点：

1. Embedding 表的规模
   - 用户 ID embedding：10 亿用户 × 64 维 × 4 字节 = 256 GB
   - 广告 ID embedding：1000 万广告 × 64 维 × 4 字节 = 2.56 GB
   - 特征交叉 embedding：可能更大
   - 总计：可能达到 TB 级别

2. Embedding 存储方案

   方案一：参数服务器（PS - Parameter Server）
   - 分布式存储大规模 Embedding 表
   - Pull：推理时拉取需要的 Embedding
   - Push：训练时推送梯度更新
   - 代表：BytePS、HugeCTR

   方案二：Redis + 分片
   - 将 Embedding 按 key 哈希分片到多个 Redis 实例
   - 适用于规模中等（百 GB 级别）
   - 优点：简单，延迟低
   - 缺点：内存成本高

   方案三：RocksDB（SSD）
   - 将 Embedding 存储在本地 SSD 上
   - LRU 缓存热门 Embedding 在内存中
   - 适用于超大规模，成本更低

   方案四：本地加载
   - 将 Embedding 文件直接加载到推理服务的内存中
   - 适用于小规模（数 GB）
   - 启动慢，但推理时无网络开销

3. 向量检索（ANN - Approximate Nearest Neighbor）

   用于向量召回：给定用户 Embedding，找到最相似的 Top-K 广告
   
   算法对比：
   ┌──────────┬────────────────┬────────┬──────────┐
   │ 算法      │ 原理            │ 速度    │ 精度     │
   ├──────────┼────────────────┼────────┼──────────┤
   │ Brute    │ 暴力计算所有距离  │ 慢      │ 100%    │
   │ IVF      │ 聚类分桶+桶内搜索│ 快      │ 高      │
   │ HNSW     │ 分层可导航小世界图│ 很快    │ 很高    │
   │ PQ       │ 乘积量化压缩     │ 很快    │ 中等    │
   │ IVF-PQ   │ IVF + PQ        │ 极快    │ 中等偏高│
   │ ScaNN    │ Google 的优化方案│ 极快    │ 高      │
   └──────────┴────────────────┴────────┴──────────┘
   
   工程实现：
   - Faiss（Facebook）：最常用的向量检索库
   - Milvus：分布式向量数据库
   - Annoy（Spotify）：简单高效，适合静态索引
   
   在广告系统中的应用：
   ```python
   import faiss
   
   # 构建索引
   d = 64  # embedding 维度
   nlist = 1000  # 聚类中心数
   quantizer = faiss.IndexFlatL2(d)
   index = faiss.IndexIVFPQ(quantizer, d, nlist, 8, 8)
   
   # 训练 + 添加广告向量
   index.train(ad_embeddings)  # shape: (n_ads, d)
   index.add(ad_embeddings)
   
   # 在线查询
   index.nprobe = 10  # 搜索的聚类数
   distances, ad_ids = index.search(user_embedding, k=100)
   ```

4. 向量索引的更新
   - 新广告上线 → 需要增量添加到向量索引
   - Faiss 的 IndexIVF 支持增量添加（add）
   - HNSW 也支持增量添加
   - 完全重建：定期（如每天）全量重建索引
   - 在线服务：双 Buffer 切换，重建期间使用旧索引
```

Q: 视频广告和图文广告在工程上有什么特殊考虑？

   - 贴片广告（Pre-roll / Mid-roll / Post-roll）：视频内容前/中/后

      - 视频文件大（几 MB ~ 几十 MB）

      - 播放完成（Complete）
      - 跳过（Skip）

```go
// 多路召回并行执行
func MultiRecall(ctx context.Context, req *AdRequest) ([]*Ad, error) {
    ctx, cancel := context.WithTimeout(ctx, 30*time.Millisecond)
    defer cancel()
    
    g, ctx := errgroup.WithContext(ctx)
    
    var (
        targetingAds []*Ad
        vectorAds    []*Ad
        retargetAds  []*Ad
    )
    
    g.Go(func() error {
        var err error
        targetingAds, err = targetingRecall(ctx, req)
        return err
    })
    
    g.Go(func() error {
        var err error
        vectorAds, err = vectorRecall(ctx, req)
        return err
    })
    
    g.Go(func() error {
        var err error
        retargetAds, err = retargetingRecall(ctx, req)
        return err
    })
    
    // 等待所有完成或超时
    // 注意：部分失败不应导致整个请求失败
    _ = g.Wait()
    
    // 合并去重
    return mergeAndDedup(targetingAds, vectorAds, retargetAds), nil
}

5. 本地缓存 + 分布式缓存二级策略
```go
type TwoLevelCache struct {
    local  *lru.Cache    // 本地 LRU（进程内）
    redis  *redis.Client // Redis（分布式）
    ttl    time.Duration
}

func (c *TwoLevelCache) Get(ctx context.Context, key string) ([]byte, error) {
    // L1: 本地缓存
    if val, ok := c.local.Get(key); ok {
        return val.([]byte), nil
    }
    
    // L2: Redis
    val, err := c.redis.Get(ctx, key).Bytes()
    if err == nil {
        c.local.Add(key, val)  // 回填本地缓存
        return val, nil
    }
    
    return nil, ErrCacheMiss
}

func main() {

    server.StopAccepting()
    
    // 2. 等待在途请求完成（最多等 30 秒）
    ctx, cancel := context.WithTimeout(context.Background(), 30*time.Second)
    defer cancel()
    server.DrainConnections(ctx)
    
    // 3. 刷新本地缓冲（未上报的日志、未同步的预算消耗等）
    flushBuffers()
    
    // 4. 关闭下游连接
    closeConnections()
    
    log.Info("server stopped gracefully")
}

# 十七、最容易被忽视的面试细节

---

```
1. 广告请求无广告返回（No Fill）的处理
   - 没有匹配的广告怎么办？
   - 返回空 vs 返回兜底广告（公益广告/自家产品推广）
   - No Fill 率是一个重要指标，太高意味着流量浪费

2. 广告的曝光去重（Show Dedup）
   - 同一个请求返回的多个广告位，不应该展示相同广告
   - 同一个用户在短时间内不应该连续看到相同广告
   - 实现：请求内去重（内存 Set）+ 跨请求去重（Redis）

3. 广告的优先级队列
   - 合约广告 > 品牌广告 > 竞价广告 > 兜底广告
   - 先填充高优先级的广告位，再处理低优先级

4. 广告的素材预审
   - 素材在正式投放前需要在各媒体上预审
   - 不同媒体有不同的审核标准
   - 工程：素材提交 → 分发到各媒体审核队列 → 
     收集审核结果 → 聚合状态

5. 广告的效果归因窗口设置
   - 不同行业的归因窗口不同
   - 游戏：通常 7 天
   - 电商：通常 1-15 天
   - 金融：通常 30 天
   - 需要灵活配置

6. 跨时区的广告投放
   - 全球投放的广告：不同时区的用户处于不同时段
   - 预算按哪个时区的"一天"计算？
   - 时段定向：需要转换为用户本地时间

7. 广告素材的 A/B 测试与自动淘汰
   - 自动淘汰 CTR 低的创意，将流量分配给高 CTR 创意
   - 需要足够的样本量才能做出可靠判断
   - 统计显著性检验：p-value < 0.05

8. 广告主的账户层级
   公司账户 → 多个广告账户 → 多个广告计划 → 多个广告组 → 多个创意
   - 预算可以在各层级设置
   - 预算继承：广告组预算不能超过广告计划预算
   - 工程：树形结构的预算管理

9. 广告的出价策略
   - 手动出价：广告主自己设置出价
   - 自动出价：平台自动调整出价
   - 目标出价：广告主设置目标 CPA，平台动态调整
   - 最大转化出价：在预算内最大化转化数
   - 最低成本出价：在保证量的前提下尽量降低成本

10. 广告索引的分片策略
    - 按广告 ID 分片 → 每个分片处理部分广告
    - 请求需要发送到所有分片 → 合并结果
    - 或按用户 ID 分片 → 每个分片包含全量广告
    - 广告系统通常选择每个节点全量索引（广告数量相对可控）
    - 如果广告量极大，则按某维度分片
```
