### 第一部分：广告业务架构（核心中的核心，必考）

如果你能清晰描述广告系统架构，面试官会认为你“很懂行”。

**1. 请画出广告投放系统的核心架构图**
*   **考察点：** 模块划分。
*   **关键模块：** **流量分发** -> **召回** -> **粗排/精排** -> **重排/混排** -> **竞价** -> **曝光/点击上报** -> **归因/结算**。
*   **工程难点：** 各环节的延迟控制（比如整体RT要求<100ms），RPC框架选型。

**2. 广告检索是如何实现的？**
*   **问题：** 如何从百万级广告库中快速筛选出符合用户标签的广告？
*   **关键词：** **倒排索引**、**位图**、**布尔表达式**。
*   **进阶：** 如果定向条件非常复杂（地域 AND 兴趣 OR 关键词），如何优化检索性能？（考察：ANTLR解析、DAG图优化）。

**3. 既然是工程岗，你怎么看“算法工程化”？**
*   **痛点：** 算法模型更新快，模型体积大（GB级），如何上线？
*   **答案方向：** 模型分层加载、TF Serving/Triton推理优化、特征工程流水线（Flink+Kafka）、向量检索引擎（Milvus/Faiss）。

### 第二部分：高并发与存储设计（字节/腾讯最爱问）

广告系统对Redis和MySQL的要求极高，这部分决定你是否能拿高薪。

**1. 【超高频】预算扣减如何设计？（防止超投/超支）**
*   **场景：** 双11大促，QPS暴增，如何保证广告主预算扣减不会出现超支，同时不卡顿？
*   **陷阱：** 直接数据库行锁？太慢。直接Redis incr？挂了丢数据怎么办？
*   **满分答案：**
    *   **方案一（实时性要求极高）：** Redis Lua脚本原子扣减 + 异步落库（兼顾性能与安全）。
    *   **方案二（超高并发）：** 预算分桶（将100万预算拆分到100个Key，随机扣，最后汇总）。
    *   **兜底：** 数据库乐观锁兜底。

**2. 广告频次控制如何设计？**
*   **场景：** 用户24小时内只能看到某广告3次。
*   **答案：** Redis `String` or `BitMap`。Key设计：`freq:uid:aid:date`。
*   **进阶：** 如果是“跨APP频控”或者“平滑频控”（不要集中在一小时内看完），怎么做？

**3. 海量日志处理**
*   **场景：** 每秒百万级的曝光/点击日志，怎么存？怎么实时计算？
*   **技术栈：** Kafka（削峰） -> Flink（实时流处理/Window聚合） -> Doris/ClickHouse（OLAP查询） -> HDFS（离线）。
*   **考察点：** 背压机制、Exactly-Once语义、水位线。

**4. 缓存一致性**
*   **经典题：** 广告物料更新了（比如素材被禁），如何保证Redis里的缓存立刻失效？
*   **答案：** 延迟双删、Binlog监听被动更新。

### 模块一：广告系统全链路架构（决定面试官对你的第一印象）

**核心考点：** 你必须具备宏观视野，能讲清楚一个广告请求从发起到展示的完整生命周期。

1.  **请详细描述广告投放的完整链路（从HTTP请求到广告返回）**
    *   **标准答案路径：** 流量接入（LB） -> 流量分发（反作弊/频控/分包） -> 召回（倒排索引/DNN召回） -> 粗排/精排（模型打分） -> 重排（打散/多样性） -> 竞价（RTB/一价二价） -> 组装返回 -> 曝光点击归因。

3.  **oCPM/oCPC 是如何实现的？工程侧需要做什么？**

### 模块三：高并发扣费与预算系统（最难的工程挑战，必考）

**核心考点：** 钱不能错，也不能慢。

7.  **高并发下预算扣减如何设计？（绝对高频）**
    *   **方案演进：**
        *   **L1（青铜）：** 数据库行锁 `update set budget = budget - cost`（死路，性能差）。
        *   **L2（白银）：** Redis单机扣减，Lua脚本保证原子性（有单点风险，丢数据风险）。
        *   **L3（黄金）：** **本地缓存预扣除 + 异步队列同步 + 数据库兜底**。
        *   **L4（王者）：** **预算分桶**。将100元拆成10个10元分布在10个Redis分片，随机扣，不够再借。解决热点Key问题。
    *   **必答细节：** 如何保证Redis挂了不丢钱？（AOF刷盘策略、Binlog同步）。

8.  **如何防止广告超投？**
    *   **场景：** 预算剩10元，同时来了100个请求，都通过检查，结果扣了1000元。
    *   **方案：**
        *   **前端限流：** 粗略控制。
        *   **中端控制：** Redis原子扣减。
        *   **后端兜底：** 数据库乐观锁/余额为负报警+自动停投。

9.  **分布式事务在广告计费中的应用**
    *   **场景：** 曝光日志写入了，但扣费失败了。
    *   **方案：** TCC（Try-Confirm-Cancel）还是 Saga？或者是基于消息队列的最终一致性？（广告通常用最终一致性，允许短暂超投，后续补扣或退费）。

### 场景一：Pacing（流量调控/预算平滑）—— 这里的水很深

**痛点：** 
如果不做控制，广告主100万预算可能在早上8点就花光了（因为早上流量大），导致晚上黄金时段没钱投，平台也损失了收益。
**面试题：** **如何设计一个Pacing系统，让广告预算匀速、平滑地花出去，同时追求收益最大化？**

*   **青铜回答：** 设置个QPS限流。
*   **王者回答（必须掌握）：**
    1.  **算法模型：** 经典的 **PID控制算法**（比例-积分-微分）。通过计算“当前消耗速度”与“理想消耗速度”的差值，动态调整出价或直接概率性丢弃流量。
    2.  **两层调控：**
        *   **Budget Pacing（预算级）：** 保证不超支。
        *   **Lifetime Pacing（生命周期级）：** 根据**流量预估曲线**分配预算。比如预判晚上流量贵且多，上午就要省着花。
    3.  **工程落地：** 
        *   **中心化：** Redis存储当前配额，每隔几秒推送到边缘节点。
        *   **去中心化：** 每个广告投放机节点自己维护一个令牌桶，定期向中心同步状态（解决Redis热点问题）。
    4.  **抢占：** 如果到了晚上预算还没花完怎么办？**提价**机制，加速消耗。

---

### 场景二：归因系统—— 钱是怎么算对的？

**痛点：** 
用户点了广告没下载，过了3天自己搜索App Store下载了，这算广告的功劳吗？如果是用户点了A广告，又点了B广告，最后买了，算谁的？
**面试题：** **设计一个实时归因系统，解决跨渠道、跨时间的转化归因问题。**

*   **核心考点：** 数据一致性、海量数据Join。
*   **技术方案：**
    1.  **归因逻辑：** **Last Click（最后一次点击）** 是业界主流。还有View-through（浏览归因）。
    2.  **工程架构：**
        *   **点击流：** Kafka传输点击日志 -> Flink实时清洗 -> 写入 **HBase/RocksDB**（KV存储，Key=设备ID，Value=点击时间戳+广告ID）。
        *   **转化流：** App激活/下单事件上来，去KV表里查：“这个设备过去7天有没有点过广告？”
    3.  **难点：** **数据乱序**。转化事件可能比点击事件先到（网络延迟）。
        *   **解法：** Flink的 **Watermark + Side Output**，或者设置一个等待窗口，把数据放在状态里Wait一会儿。
    4.  **海量数据：** 点击日志太大存不下怎么办？**布隆过滤器** 先过滤一遍绝对没点过的设备。

---

### 场景三：分层实验平台—— 大厂的业务基石

**痛点：** 
算法团队每天要上线100个模型，运营要搞50个活动，如何保证A/B测试互不干扰？如何让1%的流量准确命中实验？
**面试题：** **设计一个支持千亿级流量、上千个并发的分层实验平台（类似Google重叠实验框架）。**

*   **核心考点：** 正交性、流量分桶。
*   **技术方案：**
    1.  **分层模型：** 把流量分成 UI层、召回层、排序层、竞价层。不同层之间的流量要**正交**（互相独立）。
    2.  **分桶算法：** `Hash(UserID + LayerSalt) % 1000`。
    3.  **配置中心：** Etcd/Apollo 存储实验配置。
    4.  **工程难点：** **实验动态扩缩容**。想把实验组从1%扩大到10%，如何保证那1%的老用户还在原来的组？（也就是**一致性哈希**在流量分桶中的应用）。

### 场景四：反作弊—— 这是一个攻防战场

**痛点：** 
竞争对手用机器刷你的广告费，或者黑产通过点击赚钱。
**面试题：** **如何在100ms内识别出这是一个刷量的机器流量？**

*   **实时防御（工程侧）：**
    *   **IP黑名单：** Redis全局共享。
    *   **频控：** 单IP/设备 1分钟点击超过5次，直接拒绝。
    *   **人机验证：** 返回一个看不见的Challenge，或者让客户端跑一段JS做指纹校验。
*   **离线清洗（数据侧）：**
    *   Flink做复杂事件处理（CEP），比如：点击坐标完全一致、页面停留时间<0.1s。
    *   **图计算：** 识别点击团伙（同一个IP段关联大量设备）。

---

### 场景五：广告库存预估—— 别让销售卖超了

**痛点：** 
销售签了合同：“明天保量100万曝光”。但明天实际只有80万流量，怎么办？赔钱。
**面试题：** **如何精确预测明天的广告流量？**

*   **核心：** 时间序列预测 + 工程兜底。
*   **工程逻辑：**
    *   基于历史同环比（上周同期）。
    *   **超卖控制：** 预测100万，只敢卖80万，留20%Buffer。
    *   **动态调整：** 实时监控，如果发现流量不及预期，自动降低低优先级广告（CPM低的）的流量，保大客户。

### 场景六：动态创意优化—— 工程与艺术的结合

**痛点：** 
同一个商品，给男人看“性能强”，给女人看“颜值高”。
**面试题：** **如何设计一个动态创意渲染服务？**

*   **技术点：**
    *   **模版引擎：** 服务端渲染（SSR），把文字/图片填坑。
    *   **智能选图：** 召回阶段直接把“高CTR素材”捞出来。
    *   **端智能：** 下载一个轻量模型到手机，手机端决定展示哪张图（省去网络RTT）。

### 一、 数据与金钱的最后一道防线（兜底逻辑）

这一块如果答不上来，面试官会觉得你“不够稳”，不敢把核心系统交给你。

**1. 结算系统：T+1 对账与实时账本的差异怎么处理？**
*   **场景：** 实时扣费用Redis，凌晨离线算费用用Hive/Spark，结果两边对不上（比如Redis丢数据，或者Flink处理有延迟），钱少了谁补？
*   **必杀技：**
    *   **差异来源：** 网络丢包、超时未扣、延迟日志。
    *   **兜底方案：** 必须有 **T+1 离线对账系统**。以离线全量数据为准，生成“补扣/补加”单，在第二天凌晨自动修正账本。
    *   **面试话术：** “我在设计时，不仅保证了实时链路的高可用，还设计了一套基于离线大数据的**对账补偿流水线**，确保资金流的最终一致性。”

**2. 分布式ID生成：Snowflake算法的时间回拨问题**
*   **场景：** 机器时钟回拨，导致ID重复，广告日志混乱。
*   **解决方案：**
    *   短期回拨：等待时间追平（但这期间服务不可用）。
    *   **进阶：** 利用Zookeeper/Etcd记录上次的时间戳，如果发现时间倒退，拒绝服务或者抛出告警，甚至使用 **Clock-Sync** 守护进程。

---

### 二、 极端灾难场景（考察系统韧性）

大厂最怕P0级事故，这些问题是区分“码农”和“架构师”的分水岭。

**3. 热点Key问题：某大牌广告主（如苹果）突然投放，QPS打爆单个分片**
*   **场景：** 所有流量都去查这个广告主的素材，导致某一个Redis节点CPU 100%。
*   **必杀技：** **本地缓存 + 热Key探测**。
    *   机制：客户端或Proxy层监控Key访问频率，一旦发现热点，立刻广播给所有后端机器，把Value加载到**JVM/Go进程内存**中，后续直接读本地，不再访问Redis。

**4. 机房级故障：半个机房挂了怎么办？**
*   **考点：** 异地多活。
*   **核心逻辑：**
    *   广告业务对一致性要求不如金融高，但对可用性要求极高。
    *   **策略：** 用户流量通过DNS调度到存活机房。
    *   **数据同步：** 广告库（物料）是只读的，很容易同步；难点在**预算扣减**。
    *   **方案：** 同城双活（延迟低）可以同步扣；异地多活通常采用**单元化**，让同一用户的广告请求固定打到同一机房，避免跨机房锁。

---

### 三、 微观性能优化（压榨机器性能）

字节跳动尤其喜欢问这种“为了省机器成本”做的优化。

**5. 零拷贝与IO优化**
*   **场景：** 广告日志上报量极大，如何高效传输？
*   **必杀技：** 提到 **mmap（内存映射）** 和 **sendfile**。
    *   Kafka为什么快？就是用了零拷贝，数据直接从磁盘Buffer拷贝到网卡Buffer，不经过用户态。
    *   在日志采集Agent（如Logstash/Flume替代品）开发中，如何利用这些技术？

**6. Go语言特定的优化**
*   **内存对齐：** struct字段顺序调整，减少内存占用。
*   **GC调优：** 减小堆内存压力，把大对象变成小对象，或者用 `sync.Pool` 复用对象。
*   **避免Copy：** 知道切片作为参数传递时，到底有没有发生Copy？（只有Header被copy，底层数组共享）。

### 四、 容易被忽略的业务合规与体验

**7. 广告可见度**
*   **痛点：** 广告加载了但用户没看到（在屏幕下方），广告主不认账。
*   **技术：** 前端监听 `IntersectionObserver`，只有露出50%以上超过1秒才上报曝光。后端需要支持**反作弊过滤**和**计费逻辑调整**。

**8. 品牌安全**
*   **痛点：** 奔驰的广告出现在车祸新闻旁边。
*   **技术：** NLP实时分析页面内容，打标签，广告检索时做**标签互斥**。

### 五、 非技术决胜局（软实力与策略）

很多时候，技术答对了没给Offer，是因为这里没做好：

**1. 简历深挖防御（一定要准备！）**
面试官一定会拿着你简历上的**任意一行**代码问：“这里为什么要这么写？有什么缺点？如果重来你会怎么写？”
*   **策略：** 简历上不要写你不精通的技术栈。对于写上去的项目，必须准备三个版本的说辞：
    *   **给HR听：** 讲业务价值，赚了多少钱。
    *   **给一线Leader听：** 讲技术难点，解决了什么性能瓶颈。
    *   **给总监听：** 讲架构演进，为什么选这个技术栈，成本收益比。

**2. 沟通的艺术（结构化表达）**
*   **错误：** 面试官问“Redis怎么用”，你直接开始背命令。
*   **正确（STAR法则 + 结论先行）：**
    *   “针对这个问题，我通常的方案是X（结论）。”
    *   “具体来说，在Y场景下，因为Z的限制，我选择了X（背景）。”
    *   “实施过程中，我解决了A难点（行动）。”
    *   “最终上线效果是B（结果）。”

**3. 最后的反问环节**
*   千万别问：“咱们公司加班吗？”
*   **要问：** “咱们广告团队目前的架构瓶颈主要是在召回侧还是排序侧？” 或者 “咱们团队怎么看深度学习在召回落地中的工程挑战？” —— **这显示出你是一个来干活的合伙人，而不是一个来乞讨工作的打工仔。**
