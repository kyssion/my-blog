
# 广告召回核心解决的问题

广告召回主要解决的就是为筛选出符合基本条件且最有可能转化的广告。

这个过程有几个核心要点。

1. 广告本身的限制：比如广告本身就配置了定向要求，预算问题，广告场景，可用的范围，可以投放的媒体等等
2. 转化预期：满足限制条件下，初步判断是否可以满足广告展示或者转化的预期。
3. 性能要求：对于广告投放系统这种高并发的场景，必须要满足快速准确召回。 
4. 需要保证召回的广告存在差异化，理想的情况下希望千人千面


# 广告系统中的广告召回流程与关键节点


## 一、整体定位

广告召回（Ad Retrieval / Candidate Generation）是广告投放链路中 **粗筛** 阶段，目标是从 **数亿级广告库** 中，在 **10~30ms** 内检索出 **数百到数千** 条候选广告，交给后续精排（Ranking）和机制（Auction）环节。

完整链路大致如下：

```
用户请求 → 流量准入 → 上下文解析 → 定向过滤（Targeting） → 多路召回 → 合并去重 → 粗排/预估 → 送入精排
```

## 二、全链路详解

### 1. 请求准入与上下文解析

> 这一步相当于搜索和划分出我查询广告的条件，知道我有哪些参数和维度要去搜索广告

**做什么：** 当一次广告请求到达（App刷新、搜索、页面加载），广告引擎首先解析请求上下文,获取用户的各种标签和权重。 

具体内容见博客 广告(3.1)-DSP广告召回-上下文解析篇

**上下文特征大致有什么**

| 上下文类别 | 具体特征 | 注意点 |
|-----------|---------|-----------|
| 用户侧 | user_id、设备ID（IDFA/OAID/GAID）、用户画像标签、实时行为序列 | 新用户冷启动时画像缺失，需 fallback 到设备指纹或 IP 地理位置 |
| 场景侧 | 需要填充的广告位 ID（slot_id）、App/页面类型、网络制式、操作系统 | 不同广告位支持的素材格式不同，需要在召回阶段就过滤 |
| 内容侧 | 请求的广告位位于的场景，比如当前阅读的文章/视频/搜索 query（搜索广告场景） | 信息流场景要做上下文理解，搜索场景需要 query 改写与扩展 |
| 时间/地理 | 时间戳、GPS/IP 定位 | LBS 广告（本地生活、O2O）对地理精度要求高 |

**实际流程：** 请求到达时，会调用 **User Profile Service（UPS）**等系统拉取用户画像标签（年龄段、兴趣标签、消费层级、历史转化品类等），同时从 **实时特征服务** 获取用户最近 N 次点击/转化的广告 ID 序列。注意：这一步必须在 **5ms 以内** 完成。

#### **用户画像标签、实时行为序列 在上下文解析中都包括哪些内容**

- 画像标签强调：描述用户的基本信息，覆盖面、稳定性、可解释，一般来自离线（T+1）+ 准实时（分钟级）融合；在线只做读取和轻量组合。用户画像是对用户中长期特征的结构化描述。在头部广告平台中，画像标签体系通常包含 6 大类、数十个子类、数万个具体标签。

- 实时序列强调：短期意图、强时效、可做频控/抑制。一般由流式系统（Kafka/Flink）实时聚合后写入 KV/FeatureStore，在线请求时一次性取回。是 "原始行为的有序列表" (具体到每一次操作)保留了 时间顺序 + 具体对象 + 行为类型，序列中蕴含了 "兴趣演化"、"意图变化"、"行为模式"

- 权重计算公式  基于时间衰减的频次加权

离线+实时计算 (spark,flink)

`W_raw(tag) = Σ action_weight(i) × time_decay(Δt_i) × tag_confidence(i)`


- 参数解释

- 1. action_weight(i)：第 i 次行为的类型权重（点击1.0、收藏3.0、转化10.0 等）
- 2. time_decay(Δt_i)：第 i 次行为距当前时刻的衰减系数，exp(-λ × Δt_i)
- 3. tag_confidence(i)：第 i 次行为对应内容上，这个标签的置信度（NLP打标时给的，比如0.92）
- 4. W_raw(tag): 最终权重

**action_weight** 如何确定 整体分为几个流程

1. **第一阶段:冷启动阶段** 靠业务直觉先拍一版,比如点击点击:1.0深度阅读:2.0收藏:3.0购买:10.0

2. **第二阶段:数据回归校准**

系统跑起来有数据之后，就用数据来反推每个行为到底值多少分。核心思路是：看某个行为发生后，对后续转化的提升有多大。

**这里主要有两种方法**

1. 方法一：条件转化率反推
统计每种行为发生后，用户对同标签广告的后续点击率/转化率提升倍数：

```
-- 简化的SQL逻辑
-- 基准：全体用户对"健身"标签广告的平均点击率
base_ctr = 0.02  (2%)

-- 做过不同行为的用户，对"健身"广告的点击率
曝光未点击过健身内容的用户 → ctr = 0.018  → 提升倍数 0.9
点击过健身内容的用户       → ctr = 0.035  → 提升倍数 1.75
收藏过健身内容的用户       → ctr = 0.058  → 提升倍数 2.9
购买过健身商品的用户       → ctr = 0.12   → 提升倍数 6.0
```

这就是数据告诉你的真实权重，跟拍脑袋差异可能很大。比如你可能直觉觉得购买应该是点击的 10 倍，但真实的数据报告可能只有 3.4 倍——因为买完的人可能短期内不会再买同类东西了。所以这种方法也会有偏差


2. 方法二：逻辑回归学权重

把各种行为作为特征，用户是否点击/转化广告作为 label，跑一个逻辑回归：

```
- 特征：用户最近对该标签的各类行为次数
features = [
    click_count,        # 点击次数
    deep_read_count,    # 深度阅读次数
    like_count,         # 点赞次数
    collect_count,      # 收藏次数
    purchase_count,     # 购买次数
]

- label：是否点击了该标签的广告
label = [0, 1, 1, 0, ...]

- 训练逻辑回归
model = LogisticRegression()
model.fit(features, label)

- 模型学出来的系数就是 action_weight
print(model.coef_)
- 输出类似: [0.12, 0.28, 0.31, 0.45, 0.83]
- 归一化后: 点击=1.0, 深度阅读=2.3, 点赞=2.6, 收藏=3.75, 购买=6.9
```

这个方法的好处是模型自动学出了各行为之间的相对重要性，而且考虑了行为之间的共线性。

3. **第三阶段：分场景差异化**

跑出数据后你会发现一个重要的事实：**不同品类/场景下，同一个行为的权重完全不同。**
```
电商-快消品（零食、日用品）：
  点击: 1.0  收藏: 1.5  购买: 2.0   ← 购买权重低，因为买完很快会复购

电商-3C数码（手机、电脑）：
  点击: 1.0  收藏: 4.0  购买: 1.2   ← 收藏权重极高，因为用户会长期比价
                                       购买反而低，因为买完就不看了

信息流-新闻资讯：
  点击: 1.0  深度阅读: 5.0  分享: 8.0  ← 阅读和分享才是强信号

短视频广告：
  完播: 1.0  重复观看: 3.0  评论: 4.0  分享: 6.0
```

所以会**按业务线分别训练一套 action_weight**，不会全局共用。

> **把上面三个阶段串起来，流程是这样的：**
>
>  1. 冷启动 → 人工拍一版，先跑起来
>  2. 积累1-2周数据 → 用条件转化率反推，粗调一版
>  3. 积累1-2个月数据 → 用LR/GBDT学权重，精调
>  4. 持续运行 → 每周/每月用最新数据重新跑一次回归，更新权重
>  5. 按品类/场景 → 拆分成多套权重体系


**time_decay(Δt_i)** 中的 exp(-λ × Δt_i) λ 和 Δt_i 如何确定呢？

1. **Δt_i：直接算，没什么悬念**

就是第 i 次行为发生的时间到当前时刻的时间差，从日志里直接减出来：

```
Δt_i = now - action_timestamp_i
```

唯一需要确定的是**时间单位**，这取决于业务节奏：

- 短视频/信息流：用**小时**，因为兴趣以小时为粒度变化
- 电商：用**天**，购物意图持续数天
- 房产/汽车：用**周**，决策周期很长

单位选错会导致 λ 的数值不好调。比如电商场景你用秒做单位，Δt 动辄几十万，λ 就得设成 0.000001 这种极小值，容易出精度问题。 ???

2. **λ：核心超参数，三种确定方法**



然后把提升倍数归一化，就得到了 action_weight：
```
点击:  1.75 / 1.75 = 1.0   (以点击为基准)
收藏:  2.9  / 1.75 = 1.66
购买:  6.0  / 1.75 = 3.43
```


**time_decay** 中 recency_decay = exp(-λ × Δt) **λ** 如何找到




- 阈值判断

| 权重范围 | 结果             |
|----------|------------------|
| weight > 0.3 | 赋予该兴趣标签    |
| weight > 0.7 | 标记为强兴趣标签 |

注意 ： 实际生产中不会只算一个总分，而是区分时间窗口：

实时窗口（最近30分钟）：捕捉即时意图，权重最高
短期窗口（最近24小时）：近期兴趣
中期窗口（最近7天）：稳定偏好
长期窗口（最近30天）：基础画像

每个窗口独立计算权重，最终在召回或排序阶段作为不同特征分别输入模型。这样做的好处是让模型自己学习不同时间粒度的重要性，而不是人工拍一个衰减系数。



**最新的方法**

头部公司（字节、阿里、腾讯）的做法已经不再手动算权重了，而是把原始行为序列直接喂进深度模型，让模型自己学权重：
DIN（Deep Interest Network，阿里） 的做法是：用当前候选广告作为 query，对用户历史行为序列做 attention，算出每个历史行为对当前广告的相关性权重。也就是说，权重不是固定的，而是随候选广告动态变化的。用户同时对"防晒"和"游戏"有兴趣，当候选广告是防晒霜时，防晒相关行为的 attention 权重自动变高，游戏行为权重接近0。
SIM（Search-based Interest Model，阿里） 更进一步，面对超长行为序列（上万条），先用硬检索缩小范围，再用 attention 精排。


### 2. 广告资格过滤（Eligibility / Targeting Filter）

**做什么：** 在召回之前或与召回并行，对广告库做 **硬性过滤**，去掉不满足基本条件的广告。

```
全量广告库（~千万级）
    │
    ▼ 过滤层层递减
┌─────────────────────────────┐
│  ① 广告状态过滤              │  ← 暂停/预算耗尽/素材审核未通过/已过期
│  ② 频次控制(Frequency Cap)   │  ← 同一用户7天内已见过3次
│  ③ 定向条件匹配              │  ← 广告主设置的地域/性别/年龄/兴趣定向
│  ④ Pacing/预算控制           │  ← 今日预算已消耗80%，按节奏投放
│  ⑤ 合规过滤                  │  ← 行业限制（金融广告不投未成年人）
│  ⑥ 屏蔽关系                  │  ← 广告主屏蔽竞品媒体、竞品行业互斥
└─────────────────────────────┘
    │
    ▼
候选集缩减至 ~百万~十万级
```

**生产关键点：**

- **倒排索引（Inverted Index）：** 阿里妈妈和Google Ads 大量使用类似搜索引擎的倒排索引。例如以 `<城市=北京, 性别=女, 年龄=25-34>` 为 key，对应的广告 ID 列表为 posting list。匹配时取多个 posting list 的交集。
- **布尔表达式引擎（Boolean Expression Engine）：** Meta（Facebook）使用 **DNF/CNF 表达式** 来表达广告主定向条件，论文 *"Realtime Ad Targeting with Boolean Expression Indexing"* 描述了其实现。每条广告的定向是一个布尔表达式，匹配引擎能在亚毫秒级完成百万级广告的匹配。
- **预算与 Pacing：** 预算控制通常采用 **分布式计数器（如 Redis + 本地缓存）**，允许一定超投容忍度（通常 1%~5%），用异步对账修正。字节跳动使用 **Pacing Server** 控制每分钟消耗速率，避免广告预算在早高峰瞬间花完。

---

### 3. 多路召回（Multi-Channel Recall） ⭐ 核心环节

这是广告召回最核心的部分。真实生产系统通常采用 **多路并行召回**，每路召回策略侧重不同信号，最终合并。

```
                    ┌─────────────────┐
                    │   请求上下文      │
                    └───────┬─────────┘
          ┌─────────┬───────┼───────┬──────────┐
          ▼         ▼       ▼       ▼          ▼
     ┌────────┐ ┌───────┐ ┌─────┐ ┌──────┐ ┌───────┐
     │定向召回 │ │关键词  │ │向量 │ │Look- │ │重定向  │
     │(Tag    │ │召回   │ │召回 │ │alike │ │Retgt  │
     │Match)  │ │(Query)│ │(ANN)│ │召回  │ │召回   │
     └────────┘ └───────┘ └─────┘ └──────┘ └───────┘
          │         │       │       │          │
          └─────────┴───────┴───────┴──────────┘
                            │
                    ┌───────▼─────────┐
                    │   合并 & 去重     │
                    └─────────────────┘
```

#### 3.1 定向召回（Tag-based / Targeting Recall）

- **原理：** 根据用户标签与广告定向条件的匹配，用倒排索引查询。
- **典型路数：** 地域召回、兴趣标签召回、人群包召回、设备类型召回等。
- **例子：** 广告主在阿里妈妈选择定向「25-35岁+一线城市+母婴兴趣」，系统通过标签倒排索引召回所有匹配广告。

#### 3.2 关键词/Query 召回（搜索广告场景）

- **原理：** 用户搜索 query → query 理解（分词、纠错、同义改写、意图识别）→ 用改写后的词去匹配广告主竞价的关键词。
- **匹配方式：** 精确匹配、短语匹配、广泛匹配。
- **生产案例（Google Ads / 百度凤巢）：** query "便宜的跑步鞋" → 改写为 {"跑步鞋", "运动鞋", "跑鞋 性价比"} → 在关键词-广告倒排索引中检索。Google 使用 **BERT-based query-ad 相关性模型** 扩展广泛匹配。

#### 3.3 向量召回（Vector-based / Embedding Recall） ⭐ 近年来最核心的创新

- **原理：** 将用户和广告分别编码为稠密向量（Embedding），通过 **近似最近邻搜索（ANN）** 召回与用户向量最相似的广告。
- **模型：**
  - **双塔模型（Two-Tower / DSSM）：** 用户塔和广告塔分别编码，在线只需计算用户向量，然后在 ANN 索引中检索。Facebook 在 2019 年发表了 [*Embedding-Based Retrieval in Facebook Search*](https://arxiv.org/abs/2006.11632) 描述了其 EBR 系统。
  - **字节跳动的实践：** 训练了多个双塔模型分别优化不同目标（点击、转化、视频播放），每路作为独立的向量召回通道。
  - **阿里妈妈 COLD 模型：** 在向量召回和粗排之间引入了 Computing power aware Online and Lightweight Deep model。
- **ANN 引擎：**
  - **Facebook → FAISS**（自研，开源）
  - **Google → ScaNN**
  - **阿里 → Proxima / Aitheta**
  - **字节跳动 → 自研 ANN 引擎**
  - **开源方案 → Milvus, HNSWlib**
- **索引更新：** 广告素材和出价频繁变化，ANN 索引需要 **准实时更新（分钟级到小时级）**。通常采用 **全量索引 + 增量索引** 双层架构，增量索引覆盖最近几小时的变更。

**生产性能要求：** 在千万级广告向量库中，ANN 检索 Top-K（K=200~500）需在 **2~5ms** 内完成。

#### 3.4 Lookalike 召回

- **原理：** 广告主上传种子用户包（如已购买用户），系统找到与种子用户相似的人群。
- **实现：** 
  - 离线：用种子用户训练 Lookalike 模型（如 LR/XGBoost/GNN），对全量用户打分，选出高分人群建立人群包。
  - 在线：判断当前用户是否在 Lookalike 人群包中，如果是则召回对应广告。
- **案例（Meta/Facebook）：** Lookalike Audience 是 Facebook 广告最核心的功能之一，官方支持 1%~10% 相似度的扩展。

#### 3.5 重定向召回（Retargeting）

- **原理：** 用户之前浏览/加购/点击过某广告主的商品但未转化，召回该广告主的广告。
- **实现：** 维护 `user_id → {recently_interacted_advertiser/product}` 的映射表（通常用 Redis/Tair），在线直接查询。
- **案例：** 你在淘宝浏览了某款手机但没买，之后在今日头条信息流中看到该手机的广告——这就是跨平台 retargeting（通过 DMP/RTA 实现）。

#### 3.6 RTA 实时召回（Real-Time API）

- **原理：** 媒体平台在召回/粗排阶段，实时调用广告主的 API，由广告主返回「是否要竞价这个用户」以及「出价调整系数」。
- **案例（字节跳动/腾讯广告）：** 腾讯广告的 RTA 接口，广告主（如京东、拼多多）在自己侧部署模型，实时判断当前用户价值，决定是否参与竞价、出多少价。要求 **P99 延迟 < 30ms**。

---

### 4. 合并与去重（Merge & Dedup）

**做什么：** 多路召回的结果可能有重叠（同一广告被多路召回），需要合并去重。

```
多路召回结果（可能 2000~5000 条）
    │
    ▼
去重（按 ad_id / creative_id 去重）
    │
    ▼
截断（保留 Top N，如 1000~2000 条）
    │
    ▼
送入粗排
```

**关键决策：**
- **多路配额（Quota）管理：** 每路召回分配多少候选名额？通常通过离线 A/B 实验确定各路最优配额比例。例如：向量召回 300 条，定向召回 200 条，Retargeting 100 条……
- **去重策略：** 同一广告被多路召回时，保留哪一路的分数？通常取最高分或加权融合。

---

### 5. 粗排 / 预排序（Pre-Ranking / Light Ranking）

**做什么：** 对合并后的候选集（~千量级）做轻量级打分，进一步筛选到 ~百量级，送入精排。

**为什么需要粗排？** 精排模型非常重（如包含数百个特征交叉、多目标多任务网络），在线推理一条广告可能需要 0.5~1ms。如果精排要处理 2000 条候选，耗时 1~2 秒，不可接受。所以需要粗排先筛选。

| 对比 | 粗排 | 精排 |
|------|------|------|
| 候选量 | ~1000-3000 | ~100-500 |
| 模型复杂度 | 小模型（双塔/浅层NN） | 大模型（多任务/多目标/交叉特征） |
| 延迟要求 | 总计 5~10ms | 总计 20~50ms |
| 特征 | 简单特征（用户/广告各自的特征） | 丰富交叉特征 |

**生产案例：**
- **阿里妈妈 COLD：** Computing power aware Online and Lightweight Deep pre-ranking model，可以动态调整模型复杂度以适应流量高峰。
- **字节跳动：** 粗排使用知识蒸馏（Knowledge Distillation），用精排模型作为 Teacher 训练一个轻量 Student 模型。

---

### 6. 送入精排 & 后续环节（简要）

召回+粗排之后，进入：

```
精排（CTR/CVR/多目标预估）→ 机制层（eCPM排序/GSP/VCG竞价）
→ 策略层（多样性打散、频控、品牌保护）→ 最终广告展示
```

这已超出「召回」范畴，但需要强调：**召回的质量直接决定了精排和最终效果的上限**——精排无法排出召回阶段未被检索到的优质广告。

---

## 三、生产环境中的关键技术挑战

### 挑战 1：索引实时性

广告状态极度动态——每秒都有广告被新建、暂停、预算花完、出价调整、素材更新。

| 方案 | 更新延迟 | 使用场景 |
|------|---------|---------|
| 全量索引重建 | 小时级 | 倒排/ANN 索引定期重建 |
| 增量索引 | 秒~分钟级 | 实时消息队列（Kafka）驱动的增量更新 |
| 实时预算过滤 | 毫秒级 | 不更新索引，在召回后用 budget server 做实时校验 |

**生产实践：** 大多系统采用 **"大索引+小索引"** 策略。大索引每小时全量更新，小索引接收 Kafka 消息做分钟级增量合并。对于预算耗尽这类高频变化，不通过索引过滤，而是在召回后通过 Budget Service 实时拦截。

### 挑战 2：冷启动

- **新广告冷启动：** 没有历史 CTR 数据，向量表征不准确。应对方法：对新广告给予 **探索流量（Exploration Boost）**，在召回阶段预留专门的"新广告召回通道"。
- **新用户冷启动：** 无画像数据。应对方法：使用设备属性/LBS 做粗粒度定向召回，随着行为数据积累逐步引入个性化召回。

### 挑战 3：召回多样性 vs 精度的平衡

多路召回天然带来多样性，但各路配额比例需要仔细调优：

- **偏向精度：** 向量召回权重高 → 可能导致"信息茧房"，反复给用户看同类广告
- **偏向多样性：** 均匀分配各路 → 可能拉低整体 CTR/CVR

**解法：** 通过离线/在线 A/B 实验 + **Bandit 算法** 动态调整各路配额。

### 挑战 4：性能与资源

| 指标 | 典型要求 |
|------|---------|
| 召回总耗时（含多路并行） | P99 < 20~30ms |
| QPS（单节点） | 数千~数万 |
| 全系统 QPS | 百万级（头部平台） |
| 广告库规模 | 千万~亿级 creative |

**架构关键：**
- 多路召回并行（Go/C++ 协程并发请求各召回服务）
- ANN 索引常驻内存（SSD 做 fallback）
- 本地缓存 + 分布式缓存（Redis/Tair）两级缓存用户画像和广告特征

## 四、一次完整请求的时序示意

```
T=0ms    用户刷新信息流，广告请求到达 Ad Server
T=1ms    解析请求，提取 user_id, slot_id, device_info, geo
T=2ms    并行调用: UPS(用户画像) + 实时特征服务 + Budget Service
T=5ms    画像返回，构建用户特征向量
T=5ms    并行触发多路召回：
           ├─ 定向召回（倒排索引查询）     → 返回 300 条  ~8ms
           ├─ 向量召回（ANN 检索）         → 返回 400 条  ~5ms
           ├─ Retargeting 召回（Redis）    → 返回  50 条  ~3ms
           ├─ Lookalike 人群包召回         → 返回 100 条  ~4ms
           └─ RTA 召回（调用广告主API）    → 返回 200 条  ~15ms
T=20ms   多路结果合并、去重 → 800 条候选
T=20ms   Budget/Pacing 实时校验 → 过滤掉预算耗尽的 → 700 条
T=22ms   粗排模型打分（轻量双塔） → 取 Top 200
T=30ms   送入精排模型（多目标 DNN）
T=60ms   精排完成 → eCPM 排序 → 竞价机制 → 选出最终广告
T=65ms   返回广告素材 + 曝光监测链接
T=70ms   客户端渲染广告
```

---

## 五、总结：关键节点清单

| 序号 | 关键节点 | 核心考量 |
|------|---------|---------|
| 1 | 用户画像服务(UPS) | 延迟、覆盖率、冷启动 |
| 2 | 定向过滤/倒排索引 | 布尔表达式匹配性能、索引更新时效 |
| 3 | 多路召回策略 | 向量/标签/Retarget/Lookalike/RTA 各路的设计 |
| 4 | ANN 向量检索 | 索引结构（HNSW/IVF）、更新策略、召回率 |
| 5 | 预算/Pacing 控制 | 分布式计数、超投容忍、匀速消耗 |
| 6 | 各路配额分配 | 离线评估 + 在线 Bandit 调优 |
| 7 | 粗排模型 | 知识蒸馏、模型轻量化、延迟控制 |
| 8 | 索引实时更新 | 全量+增量双层架构 |
| 9 | 冷启动机制 | 新广告探索流量、新用户 fallback 策略 |
| 10 | 端到端延迟监控 | 每个子服务的 P50/P99、降级熔断策略 |

> **一句话总结：** 广告召回的本质是在极短时间内，从海量广告中高效筛选出"有资格且相关"的候选集。真实系统通过 **多路并行召回 + 布尔索引 + 向量检索 + 实时预算管控** 的协同配合来实现，其核心工程挑战在于 **实时性、规模性、准确性** 三者的平衡。




# 广告系统召回全链路深度解析（基于真实生产环境）

---

## 第一部分：广告召回在系统全局中的位置

### 1.1 端到端广告投放链路

在头部平台（字节跳动、阿里妈妈、Google Ads、Meta Ads、腾讯广告）中，一次广告请求的完整链路如下：

```
┌────────────────────────────────────────────────────────────────────┐
│                     一次广告请求的完整生命周期                        │
│                                                                    │
│  客户端请求 → SSP/AdX请求 → Ad Server 接收                         │
│      │                                                             │
│      ▼                                                             │
│  ┌──────────┐    ┌───────────┐    ┌──────────┐    ┌────────────┐  │
│  │ 请求解析  │ →  │ 定向过滤   │ →  │ 多路召回  │ →  │  粗排(预排) │  │
│  │ + 特征获取│    │(Targeting)│    │(Retrieval)│    │(Pre-Rank)  │  │
│  └──────────┘    └───────────┘    └──────────┘    └────────────┘  │
│       ~5ms           ~5ms           ~10-15ms          ~5-10ms      │
│                                                         │          │
│                                                         ▼          │
│  ┌──────────┐    ┌───────────┐    ┌──────────┐    ┌────────────┐  │
│  │ 广告返回  │ ←  │ 策略调控   │ ←  │ 竞价机制  │ ←  │   精排     │  │
│  │ + 计费   │    │(频控/多样) │    │(Auction) │    │(Deep Rank) │  │
│  └──────────┘    └───────────┘    └──────────┘    └────────────┘  │
│       ~2ms           ~3ms            ~2ms           ~20-30ms       │
│                                                                    │
│  总耗时目标: P99 < 100ms (搜索广告), P99 < 80ms (信息流广告)        │
└────────────────────────────────────────────────────────────────────┘
```

### 1.2 各阶段的数量级漏斗

这是理解召回价值的关键——每个阶段都在做"候选集缩减"：

```
全量广告库                    ~千万 ~ 亿级 (creative 粒度)
    │
    ▼ 广告状态过滤（在线、有预算、审核通过）
有效广告池                    ~百万级
    │
    ▼ 定向过滤（地域/年龄/性别/设备/行业限制）
定向匹配广告                  ~十万 ~ 百万级
    │
    ▼ 多路召回（相关性/个性化筛选）
召回候选集                    ~2000 ~ 5000 条
    │
    ▼ 粗排
粗排候选集                    ~200 ~ 500 条
    │
    ▼ 精排
精排候选集                    ~50 ~ 100 条
    │
    ▼ 竞价 + 策略调控
最终展示广告                  1 ~ 3 条
```

> **核心认知：召回决定了效果的天花板。** 一条优质广告如果在召回阶段被漏掉，后续再精准的排序模型也无法挽回。Google 内部的实验表明，召回质量提升 1%，最终收入可以提升 0.3%~0.5%。

## 第二部分：请求解析与特征获取

### 2.1 请求到达时的信息解析

当一次广告请求到达 Ad Server，首先需要解析和补全上下文信息：

#### 2.1.1 请求中直接携带的信息

| 字段 | 来源 | 示例 |
|------|------|------|
| `user_id` / `device_id` | 客户端 SDK | IDFA, OAID, GAID, Cookie ID |
| `slot_id` (广告位ID) | 媒体方定义 | `feed_ad_slot_001`, `banner_top_002` |
| `app_id` / `media_id` | 媒体方 | 今日头条、抖音、番茄小说 |
| `device_info` | SDK 采集 | 设备型号、OS版本、屏幕分辨率、网络类型 |
| `geo_info` | GPS/IP | 经纬度、城市、区县 |
| `context` | 媒体方 | 当前浏览内容ID、搜索query、视频分类 |
| `timestamp` | 系统 | 请求时间戳 |

#### 2.1.2 需要实时获取的用户特征

这一步需要调用多个微服务，是召回前的关键依赖：

```
Ad Server 请求入口
    │
    ├─→ User Profile Service (UPS)     获取用户画像标签
    │     返回: 年龄段、性别、兴趣标签集合、消费等级、
    │           生命周期阶段、历史广告互动品类
    │     延迟要求: P99 < 5ms
    │     存储: 分布式KV(Tair/Redis Cluster) + 本地LRU Cache
    │
    ├─→ 实时行为序列服务 (Real-time Behavior Service)
    │     返回: 最近N次（如50次）点击/转化的广告ID、品类ID、
    │           商品ID，带时间戳
    │     延迟要求: P99 < 3ms
    │     存储: Flink 实时写入 Redis/Tair
    │
    ├─→ 实时特征服务 (Feature Service)
    │     返回: 用户实时CTR统计、当前Session行为统计、
    │           上一次广告曝光距今间隔
    │     延迟要求: P99 < 5ms
    │
    └─→ 频控服务 (Frequency Control Service)
          返回: 用户对各广告/广告主/行业的已曝光次数
          延迟要求: P99 < 3ms
          存储: Redis bitmap / 布隆过滤器
```

**真实案例 —— 字节跳动 UPS 系统：**

字节跳动的 User Profile Service 管理着数十亿用户的画像数据。其架构特点：

- **三级缓存：** L1 本地缓存（进程内 LRU，命中率约 30-40%）→ L2 同机房 Redis Cluster → L3 跨机房主存储（ByteKV）
- **画像更新频率：** 离线画像每天更新一次（通过 Spark/Flink 批处理），实时画像通过 Flink 秒级更新
- **画像标签体系：** 分为 3 级：一级类目（如"电商"）→ 二级类目（如"美妆"）→ 三级标签（如"口红"），总标签数约数万个
- **冷启动处理：** 对于首次出现的 `device_id`，返回默认画像（基于设备型号+操作系统+IP所在城市的统计先验）

**真实案例 —— 阿里妈妈实时特征系统 (ABFS)：**

阿里妈妈的 Advertiser-side and Buyer-side Feature Service 采用 **Lambda 架构**：
- **Batch Layer：** 每天凌晨通过 ODPS（MaxCompute）计算前N天的用户行为统计特征
- **Speed Layer：** 通过 Blink（阿里版 Flink）实时计算近几小时的行为特征
- **Serving Layer：** 两者合并后写入 IGRAPH（阿里图存储）和 Tair，供在线查询

## 第三部分：定向过滤（Targeting / Eligibility Filtering）

### 3.1 广告状态过滤

在进入定向匹配之前，需要先过滤掉不具备投放资格的广告。这些过滤条件由 **广告管理系统** 提供，通常以 **广告状态位图（bitmap）** 的形式缓存在 Ad Server 本地。

```
广告状态过滤规则（按优先级排列）：
─────────────────────────────────────────
① 广告状态 ≠ "投放中"（暂停/删除/待审核/审核拒绝）
② 广告计划/广告组状态 ≠ "投放中"（层级继承）
③ 投放时段不匹配（广告主设置了分时段投放）
④ 预算已耗尽（日预算/总预算）
⑤ 素材格式与当前广告位不兼容（如广告位要求视频，但广告只有图片）
⑥ 出价方式与广告位不兼容（如广告位仅支持CPM，但广告设置CPA出价）
⑦ 合规限制（如金融类广告不能投放在教育类App）
```

**生产关键点 —— 预算过滤的精度问题：**

预算消耗是一个 **全局状态**，在分布式系统中精确维护成本极高。真实系统的做法：

- **字节跳动方案：** 采用 **分布式 Budget Server** + **本地缓存** 架构。Budget Server 维护每个广告的实时消耗，每 100ms 向各 Ad Server 节点广播"预算耗尽广告列表"。允许 **1%~3%** 的超投，通过异步扣费对账修正。
- **Google Ads 方案（已公开）：** 使用 **Paxos/Raft 一致性协议** 管理核心预算状态，但为了性能在广告服务层使用 **乐观并发控制**，即先假设有预算，曝光后再扣减，定期对账。

### 3.2 定向条件匹配 —— 核心中的核心

定向过滤是召回的第一道"粗筛"。广告主在投放时设置的定向条件决定了广告的投放人群范围。

#### 3.2.1 定向类型全景

| 定向维度 | 具体细分 | 匹配方式 | 数据来源 |
|---------|---------|---------|---------|
| **地域定向** | 国家/省/市/区/商圈/POI半径 | 用户地理位置 ∈ 广告地域集合 | GPS/IP定位 |
| **人口属性定向** | 年龄段、性别、学历、婚姻状态 | 标签匹配 | 用户画像 |
| **兴趣定向** | 兴趣标签（多级分类） | 用户兴趣标签 ∩ 广告兴趣定向 ≠ ∅ | 用户画像 |
| **行为定向** | 近N天搜索/浏览/购买行为 | 用户行为标签匹配 | 行为日志 |
| **设备定向** | 操作系统、设备品牌、网络类型、运营商 | 精确匹配 | SDK上报 |
| **人群包定向** | 广告主上传的自定义人群（DMP） | user_id ∈ 人群包 | 广告主CRM数据 |
| **排除定向** | 已转化用户排除、竞品行业排除 | user_id ∉ 排除集合 | 转化回传数据 |
| **内容定向** | 投放到特定类型内容旁（如体育类文章） | 内容标签匹配 | 内容理解系统 |

#### 3.2.2 定向匹配的工程实现 —— 倒排索引

**核心思想：** 不是"遍历每条广告看它是否匹配当前用户"（正排，O(N)复杂度），而是"根据用户的属性直接查找所有匹配的广告"（倒排，O(1)~O(logN)）。

```
倒排索引结构示例：
─────────────────────────────────────────────────

索引Key (定向条件)          →  Posting List (广告ID集合)
───────────────────          ─────────────────────────
city=北京                   →  {ad_1, ad_5, ad_23, ad_89, ...}
city=上海                   →  {ad_2, ad_5, ad_34, ...}
gender=female               →  {ad_1, ad_3, ad_5, ...}
age=25-34                   →  {ad_1, ad_2, ad_5, ad_67, ...}
interest=美妆               →  {ad_1, ad_15, ad_89, ...}
os=iOS                      →  {ad_5, ad_23, ad_67, ...}
crowd_pack=pack_12345       →  {ad_100, ad_101, ...}
ALL（不限定向）              →  {ad_200, ad_201, ...}

匹配过程（当前用户: 北京, 女, 28岁, 兴趣=美妆, iOS）：
result = city=北京 ∩ gender=female ∩ age=25-34 ∩ os=iOS
       ∪ (interest=美妆 对应的广告)
       ∪ (ALL 不限定向的广告)
       = {ad_1, ad_5, ...}
```

**但实际比上面复杂得多，原因是定向条件之间存在 AND/OR/NOT 的组合逻辑。**

#### 3.2.3 布尔表达式匹配引擎 —— Meta（Facebook）的方案

Meta 在 2014 年发表的论文 *"Conjunctive filtering for fast ad retrieval"* 和相关工程博客中描述了他们的定向匹配系统。

**核心思路：** 每条广告的定向条件表示为一个 **DNF（析取范式）布尔表达式**：

```
广告A的定向条件 (DNF形式):
  (city=北京 AND gender=female AND age∈[25,34])
  OR
  (city=上海 AND gender=female AND interest=美妆)

即: 北京的25-34岁女性  或  上海的对美妆感兴趣的女性
```

**匹配引擎的索引结构：**

```
Step 1: 将所有广告的 DNF 拆解为独立的 conjunction（合取项）
  conjunction_1: city=北京 ∧ gender=female ∧ age∈[25,34] → ad_A
  conjunction_2: city=上海 ∧ gender=female ∧ interest=美妆 → ad_A
  conjunction_3: city=北京 ∧ os=Android → ad_B
  ...

Step 2: 按 conjunction 的 SIZE（包含的属性数量）分桶
  size=2 的 conjunctions: {conjunction_3, ...}
  size=3 的 conjunctions: {conjunction_1, conjunction_2, ...}

Step 3: 在每个 size 桶内，对每个属性建倒排索引
  桶 size=3:
    city=北京    → {conjunction_1}
    city=上海    → {conjunction_2}
    gender=female → {conjunction_1, conjunction_2}
    age∈[25,34]  → {conjunction_1}
    interest=美妆 → {conjunction_2}

Step 4: 匹配时，对于用户的属性集合，在每个桶中查找倒排，
        取交集（至少命中 size 个属性的 conjunction 才算匹配）
```

**性能：** Meta 的博客中提到，该引擎可以在 **亚毫秒级** 完成 **数百万条** 广告的定向匹配。

#### 3.2.4 真实生产架构 —— 定向过滤与召回的融合

在实际系统中，定向过滤和召回并非严格串行，而是常常**融合**：

```
方案A：先过滤后召回（Filter-then-Retrieve）
  所有广告 → 定向过滤 → 合格广告集 → 在合格集中做向量召回
  优点：召回搜索空间小，速度快
  缺点：倒排索引需要与ANN索引耦合，工程复杂

方案B：先召回后过滤（Retrieve-then-Filter）  
  所有广告 → 向量召回 → 候选集 → 定向过滤
  优点：解耦，工程简单
  缺点：向量召回可能检索出大量不满足定向的广告，浪费计算

方案C：混合方案（最常用）
  定向倒排索引作为一路召回
  向量召回作为另一路召回（在全量库中检索，后过滤定向）
  两路结果合并
```

**字节跳动的做法（根据公开的技术博客和招聘JD推断）：** 采用 **方案C**。定向匹配引擎和向量召回引擎是两个独立服务，并行执行，结果合并后做统一的资格校验（预算、频控、合规等）。

## 第四部分：多路召回详解

### 4.1 多路召回的设计哲学

**为什么要多路而不是单路？**

| 原因 | 解释 |
|------|------|
| **信号互补** | 不同召回路利用不同信号，互相补充。标签召回擅长精确匹配，向量召回擅长泛化发现 |
| **容错性** | 某路召回服务故障时，其他路仍可工作，系统可降级 |
| **可解释性** | 标签召回结果可追溯为什么被召回，向量召回可量化相似度分数 |
| **冷启动支持** | 新广告没有行为数据，可走标签/关键词通道；有行为数据的广告可走向量通道 |
| **生态平衡** | 避免过度依赖单一策略导致的马太效应 |

### 4.2 各路召回通道深度解析

#### 4.2.1 定向/标签召回（Tag-based Recall）

**这是最基础也是最稳定的召回通道。**

```
用户画像标签:
  {gender: female, age_bucket: 25-34, city: 北京, 
   interests: [美妆, 健身, 旅行], device_price: 高端,
   purchase_power: 高}

倒排索引查询过程:
  ① 从 interest=美妆 的 posting list 取出广告集合 S1
  ② 从 interest=健身 的 posting list 取出广告集合 S2  
  ③ 从 interest=旅行 的 posting list 取出广告集合 S3
  ④ 从 city=北京 的 posting list 取出广告集合 S4
  ⑤ 结果 = (S1 ∪ S2 ∪ S3) ∩ S4 ∩ (满足年龄/性别/设备条件)
  ⑥ 按广告质量分(quality_score = 历史CTR × bid) 排序取 Top-K

典型返回量: 200-500 条
延迟: 3-8ms
```

**生产细节：**

- **Posting List 排序：** 实际系统中，每个标签的 posting list 不是无序的，而是按 `quality_score`（综合考虑出价、历史 CTR、相关性）**预排序**的。这样取 Top-K 时只需截断即可，不需要全量排序。
- **索引更新：** 每当广告的出价/预算/状态变化，通过 **消息队列（Kafka/RocketMQ）** 异步更新倒排索引。通常有两份索引：**主索引**（每小时全量重建）和 **增量索引**（分钟级更新），查询时合并结果。

#### 4.2.2 向量召回（Vector-based / Embedding Recall） ⭐

**这是近年来广告召回领域最重要的技术演进。**

##### 4.2.2.1 模型架构 —— 双塔模型（Two-Tower Model）

```
              User Tower                    Ad Tower
              ─────────                     ────────
              
    [用户特征输入]                    [广告特征输入]
    ┌──────────────┐                 ┌──────────────┐
    │ user_id emb  │                 │ ad_id emb    │
    │ age_bucket   │                 │ advertiser_id│
    │ gender       │                 │ category     │
    │ city_emb     │                 │ creative_type│
    │ interest_seq │                 │ title_emb    │
    │ behav_seq    │                 │ bid_bucket   │
    │ device_emb   │                 │ hist_ctr     │
    └──────┬───────┘                 └──────┬───────┘
           │                                │
    ┌──────▼───────┐                 ┌──────▼───────┐
    │   MLP层       │                 │   MLP层       │
    │ (3层, ReLU)   │                 │ (3层, ReLU)   │
    └──────┬───────┘                 └──────┬───────┘
           │                                │
    ┌──────▼───────┐                 ┌──────▼───────┐
    │ 用户向量 u    │                 │ 广告向量 a    │
    │ (128维/256维) │                 │ (128维/256维) │
    └──────┬───────┘                 └──────┬───────┘
           │                                │
           └────────────┬───────────────────┘
                        │
                   sim(u, a) = <u, a> / (||u|| × ||a||)
                   或 sim(u, a) = u · a  (内积)
```

**训练数据与目标：**

```
正样本: 用户点击/转化过的广告 (label=1)
负样本: 
  ├─ 随机负采样: 从全量广告中随机采样 (easy negatives)
  ├─ 曝光未点击: 已曝光但用户未点击 (hard negatives)  
  └─ batch内负采样: 同一batch中其他样本的广告作为负样本
        (in-batch negatives, Facebook EBR论文推荐)

损失函数:
  Softmax Cross-Entropy Loss (最常用)
  或 Triplet Loss / Contrastive Loss
  
训练规模 (以字节跳动级别为例):
  - 训练数据: 数十亿曝光/点击样本（近30天日志）
  - 模型参数: 数十亿（主要是 embedding table）
  - 训练框架: 参数服务器（PS）架构，数百GPU并行
  - 训练周期: 全量训练数天，增量训练每天更新
```

##### 4.2.2.2 多目标双塔

真实系统中通常不只训练一个双塔，而是训练 **多个双塔模型**，每个优化不同目标：

```
双塔模型1: 优化点击率(CTR) → 向量索引1
双塔模型2: 优化转化率(CVR) → 向量索引2  
双塔模型3: 优化视频完播率(VCR) → 向量索引3（视频广告场景）
双塔模型4: 优化长期价值(LTV) → 向量索引4

每路向量召回独立执行，结果合并
```

**Meta（Facebook）的 EBR 系统（Embedding-Based Retrieval）**

根据 Facebook 2020 年发表的论文 *"Embedding-Based Retrieval in Facebook Search"*，其关键设计包括：

1. **Unified Embedding Model：** 用一个统一的双塔模型处理多种类型的实体（用户、广告、帖子、Group等）
2. **Hard Negative Mining：** 使用上一版本模型的 ANN 检索结果作为当前版本的 hard negative，迭代提升
3. **Training Data：** 使用 **Impression-level** 数据（有曝光的样本）+ **Random negative**，发现 in-batch negatives 在广告场景效果最好
4. **Embedding 维度：** 最终使用 **256维**，在 recall 和 latency 之间取得平衡
5. **在线检索：** 使用自研的 **FAISS** 库（Approximate Nearest Neighbor），在 **数亿级向量库** 中做 Top-K 检索

##### 4.2.2.3 ANN 检索引擎 —— 生产级细节

| 平台 | ANN 引擎 | 索引结构 | 向量库规模 | 检索延迟 |
|------|---------|---------|-----------|---------|
| Meta | FAISS (自研开源) | IVF-PQ + HNSW | ~亿级 | 2-5ms |
| Google | ScaNN (自研开源) | Anisotropic Vector Quantization | ~亿级 | 1-3ms |
| 阿里 | Proxima / Aitheta (自研) | HNSW + PQ | ~千万级 | 2-5ms |
| 字节 | 自研 ANN | HNSW 为主 | ~千万级 | 2-5ms |
| 通用方案 | Milvus / Pinecone / Weaviate | 多种 | 取决于部署 | 5-10ms |

**HNSW（Hierarchical Navigable Small World）的生产使用细节：**

```
HNSW 参数调优（生产经验值）:
  - M (每层最大邻居数): 16-64, 越大精度越高但内存越大
  - ef_construction (建索引时搜索宽度): 200-400
  - ef_search (检索时搜索宽度): 100-300, 影响 recall 和 latency 的 tradeoff
  
性能基准 (1000万向量, 128维, 单机):
  - ef_search=100: recall@100 ≈ 95%, latency ≈ 1ms
  - ef_search=200: recall@100 ≈ 98%, latency ≈ 2ms
  - ef_search=300: recall@100 ≈ 99%, latency ≈ 3ms

内存占用:
  1000万 × 128维 × float32 = ~5GB (纯向量)
  + HNSW 图结构 ≈ 2-3GB
  总计 ≈ 7-8GB per shard
```

##### 4.2.2.4 索引更新策略 —— 生产中的核心难题

广告系统的向量索引面临一个搜索/推荐系统没有的特殊挑战：**广告的生命周期极短，状态变化极频繁**。

```
索引更新策略（典型架构）:
─────────────────────────────────────────────

┌─────────────┐     ┌──────────────────────┐
│ 全量索引(Base)│     │  增量索引(Realtime)    │
│              │     │                      │
│ 每4-6小时     │     │ 接收Kafka消息         │
│ 全量重建      │     │ 分钟级更新            │
│              │     │                      │
│ 包含所有      │     │ 只包含最近变更的广告    │
│ 有效广告向量   │     │ (新增/修改/删除)       │
└──────┬──────┘     └──────────┬───────────┘
       │                       │
       └──────────┬────────────┘
                  │
           ┌──────▼──────┐
           │  检索时合并   │
           │  Base结果 ∪   │
           │  Realtime结果 │
           │  - 已删除的   │
           └─────────────┘

特殊处理:
  - 新创建的广告: 立即写入增量索引（用 default embedding 或 
    基于广告属性的 cold-start embedding）
  - 预算耗尽的广告: 不从索引删除，而是在召回后由 Budget 
    Service 过滤（避免频繁更新索引）
  - 向量更新: 模型更新后需要重新计算所有广告向量，
    全量索引重建（约1-2小时，灰度切换）
```

#### 4.2.3 关键词/Query 召回（搜索广告场景）

搜索广告（如 Google Search Ads、百度凤巢、淘宝直通车搜索场景）的召回流程与信息流广告有显著差异：

```
用户搜索 query: "便宜好用的跑步鞋推荐"
         │
         ▼
┌──────────────────────────────────────────┐
│           Query 理解模块                   │
│                                          │
│  ① 分词: "便宜" "好用" "跑步鞋" "推荐"    │
│  ② 纠错: 无需纠错                         │
│  ③ 意图识别: 商品购买意图 (购物类query)     │
│  ④ 同义改写: "跑步鞋"→"跑鞋","运动鞋"     │
│  ⑤ query扩展: 增加 "性价比","平价"         │
│  ⑥ 品牌识别: 无明确品牌                    │
│  ⑦ 品类映射: → 运动鞋靴 > 跑步鞋           │
└──────────────┬───────────────────────────┘
               │
     ┌─────────┼─────────┐
     ▼         ▼         ▼
 精确匹配    短语匹配    广泛匹配
 ────────    ────────    ────────
 广告主竞价   query包含   语义相关
 关键词 =    广告主竞价   的关键词
 query分词   关键词      (用NLP模型
              或query    判断相关性)
              包含在
              关键词中

 返回50条    返回200条   返回500条
```

**百度凤巢的做法（基于公开技术分享）：**

百度搜索广告的 query 召回分为：
1. **字面匹配召回：** 基于 query 分词结果在关键词倒排索引中精确/短语匹配
2. **语义匹配召回：** 使用 ERNIE（百度预训练模型）做 query-keyword 的语义相似度计算，扩展匹配范围
3. **触发词召回：** 将 query 映射到预定义的"触发词"集合，再用触发词去匹配关键词
4. **query-ad 直接召回：** 跳过关键词，直接计算 query 与广告创意的语义相似度（双塔模型 + ANN）

**Google Ads 的做法（基于公开论文和博客）：**

Google 在 2020 年前后将 **BERT-based 语义匹配** 应用于广泛匹配（Broad Match），使得广泛匹配的质量大幅提升，成为默认推荐的匹配方式。其具体做法：
- 训练一个 **跨语言 BERT 模型**，输入为 `[query, keyword]` pair，输出相关性分数
- 在线使用双塔架构的蒸馏版本做 ANN 检索
- 离线使用全量 BERT 做 teacher 模型训练

#### 4.2.4 Retargeting 召回（重定向）

```
Retargeting 的数据链路:
──────────────────────────────────────

① 用户在广告主网站/App产生行为（浏览商品、加购、搜索）
② 广告主通过 Pixel/SDK 将行为数据回传给广告平台
   或通过 S2S (Server-to-Server) API 回传
③ 广告平台将数据写入用户行为表:
   user_device_id → [{advertiser_A, product_123, "view", T1},
                     {advertiser_B, product_456, "add_cart", T2},
                     ...]
④ 在线召回时:
   查询 user_device_id 的最近行为
   → 找到 advertiser_A, advertiser_B
   → 召回这些广告主的相关广告（特别是用户看过的商品的广告）
   
存储: Redis / Tair (key: device_id, value: 行为列表)
TTL: 通常 7-30 天
延迟: 1-3ms

典型返回量: 10-100 条（取决于用户的广告主交互历史）
```

**DPA（Dynamic Product Ads / 动态商品广告）—— Retargeting 的高级形态：**

Meta 和 Google 的 DPA 是 retargeting 的典型应用：

1. 广告主上传商品目录（Product Catalog），可能包含数百万SKU
2. 用户浏览了某个SKU
3. 广告平台召回该SKU对应的动态创意广告
4. 动态生成包含该商品图片、价格、折扣信息的广告素材

**阿里妈妈的实现：** 在淘宝/天猫生态中，用户浏览过的商品信息直接存储在用户行为日志中。智钻（展示广告）和万相台的 retargeting 召回通过 IGRAPH（阿里的图存储系统）查询 `user → 最近交互商品 → 关联广告计划` 的路径。

#### 4.2.5 Lookalike 召回

```
Lookalike 人群扩展流程:
──────────────────────────────────────

离线阶段（每天/每周更新）:
① 广告主上传种子用户包 (seed users), 如10万已购买用户的device_id
② DMP 系统对种子用户做画像分析, 提取共性特征
③ 训练 Lookalike 模型:
   - 方法1 (经典): 用种子用户作正样本, 随机采样作负样本, 
     训练 LR/GBDT/DNN 二分类模型
   - 方法2 (Graph-based): 在用户社交图/行为图上做 Graph 
     Embedding, 找到与种子用户在图空间中距离近的用户
   - 方法3 (向量检索): 计算种子用户的平均向量, 
     ANN 检索最相似的用户
④ 对全量用户打分, 按分数阈值划定 Lookalike 人群包
   (通常分 1%, 3%, 5%, 10% 等多个粒度)
⑤ 将人群包 (user_id集合) 写入在线 KV 存储

在线阶段:
⑥ 请求到达, 查询当前 user_id 是否属于某个 Lookalike 人群包
⑦ 如果是, 召回该人群包关联的广告

实现方式:
  - 大人群包 (百万级以上): 用 Bitmap / Bloom Filter 判断成员
  - 小人群包 (十万级以下): 用 HashSet
  
存储: 分布式 Bitmap 服务 (如 Roaring Bitmap on Redis)
```

**Meta Lookalike Audience 的真实规模：** Meta 的 Lookalike 支持 1%~10% 的扩展比例（以国家为基数）。在美国，1% Lookalike ≈ 230 万用户。Meta 使用基于 **用户行为序列 + 社交图谱** 的深度模型计算相似度，被认为是 Meta 广告生态最核心的竞争壁垒之一。

#### 4.2.6 RTA 召回（Real-Time API / 实时竞价接口）

**RTA 是近年来国内广告平台（字节跳动、腾讯广告、快手）的重要创新。**

```
RTA 调用流程:
──────────────────────────────────────

媒体侧 (Ad Platform)              广告主侧 (Advertiser)
────────────────────              ────────────────────

① 用户请求到达                     
② 判断哪些广告主开通了RTA
③ 向广告主RTA服务发送请求 ──────→  ④ 接收请求
   请求内容:                          {device_id/oaid,
   {device_id, slot_id,               ip, ua, ...}
    ip, ua, timestamp,             ⑤ 广告主侧模型预测
    ad_ids(可选)}                     (查询自有DMP,
                                       判断用户价值)
⑥ 接收响应 ←────────────────────   ⑦ 返回响应
   响应内容:                          {is_target: true/false,
   {ad_id_1: {bid_ratio: 1.2},        bid_ratio: 1.0~3.0}
    ad_id_2: {is_target: false},
    ad_id_3: {bid_ratio: 0.8}}

RTA 的延迟要求:
  - 字节跳动: P99 < 50ms (超时则视为放弃竞价)
  - 腾讯广告: P99 < 40ms
  - 快手: P99 < 60ms
  
QPS 规模 (头部广告主):
  - 京东/拼多多等大型广告主: 峰值 数十万 QPS
  - 需要广告主自建高性能服务, 通常部署在云上, 
    接入平台提供的IDC专线
```

**RTA 的价值：**

- **广告主视角：** 可以用自己的一方数据（用户是否是老客、LTV预估、是否在自有App活跃等）来决定出价，比平台的二方/三方数据更精准
- **平台视角：** 引入广告主的私域数据能力，提升整体转化率和广告主 ROI，从而增加广告主预算投入

**真实案例（腾讯广告 RTA）：**

腾讯广告的 RTA 已经被大量电商、游戏、金融类广告主接入。典型场景：
- **电商广告主（如京东）：** 判断用户是否是 App 活跃用户、是否近期有购买意图（基于京东自有数据），对高价值用户提高出价
- **游戏广告主：** 判断用户是否已经安装了该游戏（排除已转化用户），避免浪费预算

#### 4.2.7 上下文/内容召回（Context-based Recall）

```
信息流场景:
  用户正在阅读一篇关于"健身减脂"的文章
  → 上下文理解: 提取文章标签 = [健身, 减脂, 运动, 蛋白粉]
  → 在广告索引中查找品类标签 ∈ {健身器材, 运动服饰, 营养补剂} 的广告
  → 召回与内容相关的广告

搜索场景:
  已在 Query 召回中覆盖

视频场景:
  用户正在观看一个美食烹饪视频
  → 视频理解: 标签 = [美食, 烹饪, 厨具, 家居]
  → 召回相关品类广告
```

#### 4.2.8 协同过滤召回（CF-based Recall）

```
基于 Item-CF 的思路:
  与当前用户相似的用户点击过的广告 → 召回

基于 User-CF 的思路:
  当前用户历史点击的广告的相似广告 → 召回

实现:
  离线: 计算 ad-ad 相似度矩阵 (基于共现/embedding相似度)
  在线: 根据用户最近点击的 N 个广告, 
        查询每个广告的 Top-K 相似广告
        合并去重后返回

存储: ad_id → [similar_ad_1, similar_ad_2, ...] 
      写入 Redis/Tair

典型返回量: 100-300 条
```

**阿里妈妈的 Swing 算法：** 阿里在计算 item-item 相似度时使用了改进的 Swing 算法（而非传统的 Jaccard/Cosine），考虑了用户交互的多样性，减少热门物品的影响。

## 第五部分：多路召回的合并与管理

### 5.1 合并策略

```
多路召回结果合并流程:
──────────────────────────────────────

输入:
  路1 (标签召回):    {(ad_1, 0.8), (ad_3, 0.7), (ad_5, 0.6), ...}  共300条
  路2 (向量召回-CTR): {(ad_2, 0.9), (ad_1, 0.85), (ad_7, 0.5), ...} 共400条
  路3 (向量召回-CVR): {(ad_4, 0.7), (ad_2, 0.6), ...}               共200条
  路4 (Retargeting):  {(ad_10, 0.95), (ad_11, 0.8), ...}            共50条
  路5 (RTA):          {(ad_20, 0.7), (ad_1, 0.6), ...}              共200条

Step 1: 按 ad_id 去重
  ad_1 同时被 路1, 路2, 路5 召回
  ad_2 同时被 路2, 路3 召回
  
Step 2: 分数融合 (多种策略)
  策略A: 取各路最高分 → ad_1.score = max(0.8, 0.85, 0.6) = 0.85
  策略B: 加权求和 → ad_1.score = w1*0.8 + w2*0.85 + w5*0.6
  策略C: 被召回路数作为 bonus → ad_1.score = 0.85 + 0.1 * (被3路召回)
  
Step 3: 保留来源标记 (用于后续分析)
  ad_1: {recall_sources: ["tag", "vec_ctr", "rta"], score: 0.85}

Step 4: 截断取 Top-N (N = 2000~3000)

输出: 合并去重后的候选集, 送入粗排
```

### 5.2 各路配额（Quota）管理

**这是影响召回效果的关键决策。** 每路召回分配多少候选名额？

```
配额管理策略:
──────────────────────────────────────

方式1: 固定配额 (最简单)
  标签召回: 300条
  向量召回: 500条
  Retargeting: 100条
  ...
  问题: 不同请求特征不同, 固定配额不灵活

方式2: 动态配额 (基于用户特征)
  新用户 → 增大标签召回和热门召回的配额
  老用户 → 增大向量召回和Retargeting的配额
  高价值用户 → 增大所有路的配额 (总候选量更大)

方式3: Bandit-based 自适应 (最先进)
  将每路召回视为一个 arm
  收益 = 该路召回的广告最终被精排选中并产生点击/转化的比例
  用 Thompson Sampling / UCB 算法动态调整各路配额
```

**字节跳动的做法（根据公开技术博客推断）：** 采用 **方式2 + 方式3 的混合**。有一个基础配额（方式2），在此基础上通过在线 Bandit 实验微调各路比例。每周根据实验数据更新一次配额分配。

## 第六部分：粗排（Pre-Ranking）

### 6.1 为什么需要粗排

```
计算量对比:
──────────────────────────────────────

精排模型 (典型):
  - 模型: 多目标多任务 DNN (如 MMoE/PLE/ESMM)
  - 特征数: 数百个 (含大量交叉特征)
  - 推理耗时: 0.3~1ms per ad (GPU) 或 1~3ms per ad (CPU)
  - 如果精排处理 3000 条候选: 3000 × 1ms = 3000ms ❌ 不可接受

粗排模型 (典型):
  - 模型: 轻量双塔 或 浅层 DNN (2-3层)
  - 特征数: 数十个 (主要是用户侧和广告侧各自的特征, 少量交叉)
  - 推理耗时: 0.01~0.05ms per ad
  - 处理 3000 条候选: 3000 × 0.05ms = 150ms → batch推理后 ~10ms ✅

所以粗排的作用: 将 ~3000 条筛选到 ~200-500 条, 控制精排计算量
```

### 6.2 粗排模型的设计

```
粗排模型演进 (以阿里妈妈为例):
──────────────────────────────────────

V1: 简单 LR 模型 (逻辑回归)
  特征: 广告历史CTR, 出价, 品类匹配度
  优点: 极快
  缺点: 表达能力差

V2: 轻量 DNN
  特征: 用户embedding + 广告embedding + 少量统计特征
  结构: 2-3层 MLP, 隐层宽度 128-256
  优点: 比LR效果好很多
  缺点: 与精排模型差距仍然大

V3: COLD 模型 (阿里妈妈, 2020年KDD论文)
  全称: Computing power aware Online and Lightweight Deep model
  核心思想:
    ① 使用与精排相似的网络结构, 但通过 SE(Squeeze-and-Excitation) 
       模块动态选择特征, 降低计算量
    ② 根据当前系统负载动态调整模型复杂度:
       - 低峰期: 使用更多特征, 更深网络 → 更高精度
       - 高峰期: 使用更少特征, 更浅网络 → 更低延迟
    ③ 使用精排模型作为 Teacher 进行知识蒸馏

V4: 向量化粗排 (最新趋势)
  在召回阶段的双塔向量基础上, 加入少量在线交叉特征
  实现方式: 预计算广告塔向量, 在线只计算用户塔 + 内积 + 
            少量在线特征修正
```

**字节跳动的粗排实践（基于公开分享）：**

- 使用 **知识蒸馏（Knowledge Distillation）** 训练粗排模型：精排模型作为 Teacher，粗排模型作为 Student
- Teacher 提供 soft label（精排预估的 pCTR/pCVR），Student 学习拟合这些 soft label
- 蒸馏后的粗排模型与精排模型的排序一致性（NDCG）可以达到 **0.85~0.90**
- 粗排服务部署在 CPU 集群上，使用 **ONNX Runtime** 做推理加速

## 第七部分：生产环境的关键工程节点

### 7.1 系统可用性与降级策略

```
降级策略 (按优先级):
──────────────────────────────────────

场景1: 用户画像服务(UPS) 超时/不可用
  降级: 使用设备属性(型号+OS+IP城市)做粗粒度定向召回
        跳过个性化向量召回
        使用热门广告召回兜底

场景2: 向量召回服务 超时
  降级: 增大标签召回和热门召回的配额
        总候选量减少, 但不影响有广告返回

场景3: RTA 服务超时 (广告主侧)
  降级: 该广告主的广告按默认出价参与竞价
        (或直接剔除, 取决于业务策略)

场景4: 粗排服务超时
  降级: 使用召回阶段的分数直接排序
        (即跳过粗排, 增大精排候选量, 但可能导致精排超时)

场景5: 全链路过载 (大促/突发流量)
  降级: 
    ① 减少每路召回的候选数 (如从300降到100)
    ② 关闭低优先级的召回路 (如关闭Lookalike路)
    ③ 降低粗排模型复杂度 (COLD的动态调节)
    ④ 减少精排候选量
    ⑤ 极端情况: 返回预计算的广告缓存 (cache兜底)
```

### 7.2 索引一致性保障

```
索引一致性挑战:
──────────────────────────────────────

问题: 广告在管理后台被暂停, 但索引中仍存在该广告
  → 被召回 → 被展示 → 广告主投诉 "我已暂停为什么还在花钱"

解决方案 (多层保障):
  
  Layer 1: 索引增量更新 (分钟级)
    广告状态变更 → Kafka → 索引更新服务 → 更新倒排/ANN索引
    延迟: 1-5分钟
    
  Layer 2: 实时状态校验 (秒级)  
    在召回结果返回后, 批量查询 Ad Status Cache (Redis)
    过滤掉已暂停/预算耗尽的广告
    延迟: <1ms
    
  Layer 3: 计费前兜底校验
    在最终计费(billing)前, 再次校验广告状态
    如果已暂停, 不计费 (虽然已曝光)
    
  Layer 4: 异步对账
    每小时/每天对账, 发现不应计费的曝光, 给广告主退款
```

### 7.3 预算与 Pacing 控制 —— 深度解析

```
Pacing 控制的核心问题:
──────────────────────────────────────

场景: 广告主日预算 10000元, 投放时段 8:00-24:00 (16小时)
目标: 让预算在16小时内均匀消耗, 而非在前2小时花完

方案1: Throttling (概率限流)
  计算目标消耗速率: 10000/16 = 625元/小时
  当前实际速率: 通过 Budget Server 实时统计
  如果实际速率 > 目标速率 × 1.2 → 对该广告降低参竞概率
  具体: 在召回阶段, 以 (1 - 超速比例) 的概率丢弃该广告
  
方案2: Bid Modification (出价调整)  
  当消耗过快 → 降低出价 → 在竞价中胜出概率降低 → 自然减速
  当消耗过慢 → 提高出价 → 在竞价中胜出概率增加 → 自然加速
  Google Ads 采用此方案, 通过 PID 控制器动态调节出价乘数
  
方案3: Budget Allocation (时段预算分配)
  离线: 根据历史流量分布, 将日预算分配到每个小时
  例如: 午高峰12:00-13:00分配8% (800元), 
        凌晨2:00-3:00分配1% (100元)
  在线: 每小时预算独立控制

实际系统: 通常是三种方案的组合

Budget Server 架构 (字节跳动风格):
  ┌─────────────────────────────────┐
  │          Budget Server          │
  │  (独立集群, 高可用主从部署)       │
  │                                 │
  │  数据结构:                       │
  │  ad_id → {                      │
  │    daily_budget: 10000,         │
  │    spent_today: 6234.5,         │
  │    hourly_target: 625,          │
  │    current_hour_spent: 312,     │
  │    pacing_ratio: 0.85,          │
  │    is_budget_exhausted: false   │
  │  }                              │
  │                                 │
  │  更新方式:                       │
  │  - 每次广告曝光/点击/转化,       │
  │    通过Kafka异步更新消耗          │
  │  - 聚合延迟: 约 1-5 秒           │
  │                                 │
  │  向 Ad Server 广播:             │
  │  - 每 100ms 推送"预算耗尽列表"    │
  │  - 每 1s 推送"pacing_ratio更新"  │
  └─────────────────────────────────┘
```

### 7.4 监控指标体系

```
召回阶段核心监控指标:
──────────────────────────────────────

性能指标:
  ├─ 各路召回 P50/P99 延迟
  ├─ 各路召回 QPS
  ├─ 各路召回超时率 (目标 < 0.1%)
  ├─ 总召回耗时 P99 (含合并)
  └─ ANN 检索延迟分布

质量指标:
  ├─ 平均召回候选数 (总量 & 各路)
  ├─ 召回→精排 转化率 (召回的广告中有多少进入精排 Top-K)
  ├─ 召回→展示 转化率 (召回的广告中有多少最终被展示)
  ├─ 各路召回的 "独占贡献" (只被该路召回且最终展示的广告占比)
  ├─ 空召回率 (召回结果为空的请求比例, 目标 < 1%)
  └─ 新广告召回覆盖率 (新创建广告在N小时内被召回的比例)

业务指标:
  ├─ 整体 CTR/CVR (受召回质量间接影响)
  ├─ eCPM (千次曝光收入)
  ├─ 广告主 ROI
  └─ 广告填充率 (有广告请求中成功返回广告的比例)
```

## 第八部分：一次完整请求的全时序图

以 **字节跳动信息流广告** 为参考（基于公开技术分享推断），完整还原一次请求：

```
T=0.0ms  用户在抖音刷到一个内容推荐位（同时包含广告位slot）
         客户端SDK向Ad Server发送广告请求

T=0.5ms  Ad Server 接收请求, 解析参数
         提取: user_id=U123, device=iPhone14Pro, city=北京,
               slot_id=feed_video_ad, network=WiFi
         
T=1.0ms  并行发起特征获取请求:
         ├─ UPS: 获取用户画像 ──────────────────────→ T=4ms 返回
         │  结果: age=28, gender=F, interests=[美妆,健身,旅行],
         │        purchase_power=high, life_stage=white_collar
         │
         ├─ 实时行为服务: 获取最近行为序列 ──────────→ T=3ms 返回
         │  结果: 最近点击广告 = [ad_A(美妆), ad_B(运动鞋), ad_C(旅游)]
         │        最近转化 = [ad_A(美妆)]
         │
         ├─ 频控服务: 获取用户频控状态 ────────────→ T=2ms 返回
         │  结果: advertiser_X今日已曝光3次(上限3), 
         │        ad_D本周已曝光2次(上限5)
         │
         └─ Budget Service: 获取预算耗尽广告列表 ──→ T=1ms (本地缓存)
            结果: [ad_100, ad_234, ad_567, ...] 已耗尽

T=5.0ms  特征准备完成, 构建用户特征向量 user_vec (128维)
         同时构建用户标签集合 user_tags

T=5.5ms  并行触发多路召回:
         │
         ├─ 路1: 定向标签召回 (倒排索引)
         │  查询: city=北京 ∩ gender=F ∩ age=25-34
         │  返回: 350条, 耗时 5ms ──────────────→ T=10.5ms
         │
         ├─ 路2: 向量召回-CTR优化 (ANN-HNSW)
         │  输入: user_vec, Top-K=400
         │  返回: 400条, 耗时 4ms ──────────────→ T=9.5ms
         │
         ├─ 路3: 向量召回-CVR优化 (ANN-HNSW)
         │  输入: user_vec_cvr, Top-K=300
         │  返回: 300条, 耗时 4ms ──────────────→ T=9.5ms
         │
         ├─ 路4: Retargeting 召回 (Redis)
         │  查询: user_id → 最近交互广告主
         │  返回: 45条, 耗时 2ms ───────────────→ T=7.5ms
         │
         ├─ 路5: 上下文召回
         │  当前视频标签=[美食,烹饪] → 匹配品类
         │  返回: 80条, 耗时 3ms ───────────────→ T=8.5ms
         │
         ├─ 路6: 协同过滤召回
         │  基于最近点击ad_A,ad_B → 相似广告
         │  返回: 150条, 耗时 3ms ──────────────→ T=8.5ms
         │
         └─ 路7: RTA 召回 (调用广告主API)
            向3个开通RTA的广告主发请求
            返回: 120条(含出价调整系数), 耗时 25ms ──→ T=30.5ms
            (注: RTA是最慢的路, 但异步等待, 不阻塞其他路)

T=12ms   路1~路6结果已返回, 开始合并 (不等RTA)
         合并去重: 350+400+300+45+80+150 → 去重后 ≈ 950条

T=13ms   预算/频控/合规过滤:
         - 移除预算耗尽的广告: -30条
         - 移除频控超限的广告: -15条
         - 移除合规限制的广告: -5条
         剩余: 900条

T=15ms   粗排模型推理 (轻量双塔 + 少量交叉特征)
         输入: 900条候选广告的特征
         批量推理 (GPU/CPU): 耗时 8ms
         输出: 每条广告的 pCTR_coarse 分数
         取 Top-300 ──────────────────────────→ T=23ms

T=23ms   等待RTA结果 (如果还没返回)
         将RTA返回的广告补充进候选集 (去重后新增约80条)
         用粗排模型快速评分: 耗时 2ms
         最终粗排候选: 300+80=380条 → 取 Top-300

T=25ms   送入精排模型
         精排模型: 多目标多任务 DNN (MTL)
         预估: pCTR, pCVR, p完播率, p负反馈率
         输入: 300条广告, 丰富的交叉特征
         推理耗时: 25ms (GPU)
         输出: 多目标综合分数 ──────────────────→ T=50ms

T=50ms   竞价机制 (Auction)
         计算 eCPM = pCTR × pCVR × bid × 1000
         按 eCPM 排序
         应用 GSP (Generalized Second Price) 计费逻辑
         选出 Top-1 广告 (信息流单坑位场景)

T=52ms   策略调控层
         检查: 多样性约束、品牌安全、竞品隔离
         确认最终展示的广告

T=55ms   返回广告素材URL + 曝光追踪链接 + 点击追踪链接
         
T=60ms   客户端接收并渲染广告

总耗时: ~60ms (P50), 目标 P99 < 100ms
```

## 第十部分：总结 —— 关键节点与核心挑战

```
广告召回核心节点优先级排序:
──────────────────────────────────────

P0 (最关键, 直接影响收入):
  ① 多路召回策略设计 (向量+标签+retargeting+...)
  ② ANN 向量检索引擎 (性能与精度)
  ③ 粗排模型 (精度与延迟平衡)
  ④ 预算/Pacing 控制 (影响广告主满意度)

P1 (重要, 影响系统健壮性):
  ⑤ 索引实时更新机制 (全量+增量)
  ⑥ 用户画像服务 (覆盖率与时效性)
  ⑦ 降级与容灾策略
  ⑧ 各路配额动态管理

P2 (锦上添花, 持续优化):
  ⑨ 冷启动策略 (新广告/新用户)
  ⑩ RTA 接入与优化
  ⑪ 召回多样性控制
  ⑫ 监控与自动报警体系
```

> **最终总结：** 广告召回系统是一个 **高并发、低延迟、强一致性** 要求的复杂分布式系统。它的核心挑战不仅是"找到相关的广告"（算法问题），更是在 **数十毫秒内、在数千万广告中、考虑数百个约束条件、处理每秒数百万请求** 的情况下做到这一点（工程问题）。真正的生产系统需要算法、工程、产品的深度协同，持续迭代优化。
