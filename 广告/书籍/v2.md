## 三、核心组件详解

### 3.1 特征计算层 —— 三级计算引擎

这是整个架构最核心的设计，**将特征按时效性需求分为三级**：

```
┌──────────────────────────────────────────────────────────────────────────┐
│                        特征计算三级架构                                   │
├────────────┬──────────────┬──────────────────┬──────────────────────────┤
│            │  批量计算     │  流式计算          │  实时计算               │
│            │  Batch       │  Streaming        │  Real-time             │
├────────────┼──────────────┼──────────────────┼──────────────────────────┤
│ 计算引擎    │ Spark / MR   │ Flink            │ 服务进程内直接计算        │
├────────────┼──────────────┼──────────────────┼──────────────────────────┤
│ 延迟        │ 小时~天级     │ 秒~分钟级         │ 毫秒级                  │
├────────────┼──────────────┼──────────────────┼──────────────────────────┤
│ 调度方式    │ 定时任务      │ 持续运行的流作业   │ 请求触发                │
├────────────┼──────────────┼──────────────────┼──────────────────────────┤
│ 输出目的地   │ Hive→同步到KV │ 直写在线KV       │ 内存中直接传模型         │
├────────────┼──────────────┼──────────────────┼──────────────────────────┤
│ 典型特征    │ • 用户30天画像│ • 近1h点击数      │ • 当前session行为       │
│            │ • 广告生命周期 │ • 近实时CTR       │ • 请求时间/位置         │
│            │   统计        │ • 实时热度        │ • 当前展示序号          │
│            │ • 内容质量分   │ • 用户近期兴趣    │ • 竞价环境              │
│            │ • 用户长期兴趣 │ • 广告实时消耗    │ • 频次计数              │
│            │ • 行业基准线   │ • 预算剩余比例    │ • 上下文匹配分          │
├────────────┼──────────────┼──────────────────┼──────────────────────────┤
│ 数据量      │ 全量用户/物料 │ 增量事件流        │ 单次请求                │
├────────────┼──────────────┼──────────────────┼──────────────────────────┤
│ 容错要求    │ 可重跑        │ Exactly-once     │ 尽力而为               │
├────────────┼──────────────┼──────────────────┼──────────────────────────┤
│ 计算成本    │ 高(大规模集群) │ 中(持续占用资源)  │ 低(边际成本)            │
├────────────┼──────────────┼──────────────────┼──────────────────────────┤
│ 复杂度      │ 低           │ 中               │ 高(受延迟约束)           │
└────────────┴──────────────┴──────────────────┴──────────────────────────┘
```

**为什么要分三级？**

| 决策考量 | 解释 |
|---------|------|
| **不是所有特征都需要实时** | 用户的性别、城市等级、设备价格——这些几乎不变，完全没必要实时计算 |
| **实时计算的能力有限** | 在线服务的延迟预算只有 5~10ms 给特征，复杂统计不可能在线算 |
| **成本控制** | 全部实时计算代价极高，按需分级是最佳性价比 |
| **容错隔离** | 流式计算挂了不应该影响批量特征，批量任务延迟不影响实时特征 |
| **特征新鲜度与准确性的权衡** | 越新鲜的特征统计量越少、越不稳定；长窗口特征更稳定但不够及时 |

**关键设计细节：**

- **批量计算** 通常按天 (T+1) 或按小时调度，计算完写入 Hive 分区表，再通过 **同步管道** (Sync Pipeline) 批量导入在线 KV 存储
- **流式计算** 消费 Kafka 实时事件流，维护滑动窗口状态 (如 1h/6h/24h 内的点击数)，增量更新在线 KV
- **实时计算** 不落存储，在服务进程的内存中直接完成，比如从请求体中提取时间/地域，或者在请求链路中统计 "本次 session 已展示广告数"

### 3.2 特征存储层 —— Feature Store

```
┌────────────────────────────────────────────────────────────────────────────────┐
│                         Feature Store 架构                                     │
│                                                                                │
│  ┌──────────────────────────────────────────────────────────────────────────┐  │
│  │                     离线存储 (Offline Store)                              │  │
│  │                                                                          │  │
│  │  存储介质: Hive / HDFS / Iceberg / Delta Lake                           │  │
│  │  数据格式: Parquet (列式, 高压缩, 高效扫描)                               │  │
│  │  组织方式: 按 entity_type + 日期分区                                      │  │
│  │                                                                          │  │
│  │  user_features/dt=2024-01-15/                                           │  │
│  │    ├── user_id | f1 | f2 | f3 | ... | f500                              │  │
│  │    └── (数十亿行 × 数百列)                                               │  │
│  │                                                                          │  │
│  │  核心能力:                                                               │  │
│  │    • Point-in-Time Join (用特征的历史版本, 防数据穿越)                     │  │
│  │    • 全量回溯 (Backfill) — 新特征可追溯计算历史值                          │  │
│  │    • 支撑训练样本的大规模拼接                                              │  │
│  └──────────────────────────────────────────────────────────────────────────┘  │
│                                                                                │
│  ┌──────────────────────────────────────────────────────────────────────────┐  │
│  │                     在线存储 (Online Store)                               │  │
│  │                                                                          │  │
│  │  存储介质: 自研KV (如ByteKV/Abase) / Redis Cluster                      │  │
│  │  数据模型:                                                               │  │
│  │    Key:   {entity_type}:{entity_id}     如 "user:12345"                 │  │
│  │    Value: Protobuf序列化的特征向量       如 {f1:0.3, f2:5, f3:[1,2,3]}  │  │
│  │                                                                          │  │
│  │  性能要求:                                                               │  │
│  │    • 读延迟: p99 < 2ms                                                  │  │
│  │    • 吞吐: 数千万 QPS                                                    │  │
│  │    • 可用性: 99.99%                                                      │  │
│  │                                                                          │  │
│  │  优化手段:                                                               │  │
│  │    • 多级缓存: 本地缓存 → 集群缓存 → 持久KV                              │  │
│  │    • 批量读取: 一次 mget 取回一个用户的所有特征                             │  │
│  │    • 就近部署: 与推理服务同机房                                            │  │
│  │    • 特征打包: 同一entity的特征打成一个Value, 减少IO次数                    │  │
│  │    • TTL淘汰: 不活跃用户特征自动过期                                      │  │
│  └──────────────────────────────────────────────────────────────────────────┘  │
│                                                                                │
│  ┌──────────────────────────────────────────────────────────────────────────┐  │
│  │                     近线存储 (Nearline Store)                             │  │
│  │                                                                          │  │
│  │  介于离线和在线之间, 存放流式计算产出的特征                                │  │
│  │  典型方案: Flink State Backend + 异步写KV                                │  │
│  │  特点: 数据新鲜度秒~分钟级, 支持窗口聚合状态                              │  │
│  └──────────────────────────────────────────────────────────────────────────┘  │
│                                                                                │
└────────────────────────────────────────────────────────────────────────────────┘
```

**离线 vs 在线存储的核心取舍：**

| 维度 | 离线存储 | 在线存储 |
|------|---------|---------|
| **目的** | 训练样本生成 | 在线模型推理 |
| **优化方向** | 吞吐量 (TB级扫描) | 延迟 (毫秒级读取) |
| **存储成本** | 低 (HDFS, 廉价磁盘) | 高 (内存/SSD) |
| **容量** | 无限 (PB级) | 有限 (TB级, 成本约束) |
| **时间维度** | 保留历史所有版本 | 只保留最新值 |
| **访问模式** | 全量扫描 + Join | 点查 (key-value lookup) |
| **数据格式** | Parquet 列式 | Protobuf/FlatBuffers 行式 |

**为什么不直接在线存储里查训练数据？**
- 在线存储只有最新值，没有历史快照，无法做 Point-in-Time Join
- 在线存储容量有限，存不下全量历史
- 训练需要批量扫描，KV 存储不适合全表扫描

```
│                         ▼                                     │
```

```
│  │ 快照     │     │ (HDFS)       │     │              │          │
│  └──────────┘     └──────────────┘     └──────┬───────┘          │
│                                                │                  │
│  ┌──────────┐                                  │                  │
│  │ 展示/点击 │                                  ▼                  │
│  │ /转化日志 │────▶ Join on request_id ────▶ 训练样本              │
│  │ (Label)  │      (展示→负样本, 点击→正样本)  {features + label}  │
│  └──────────┘                                                     │
│                                                                    │
│  优点: 特征100%与Serving一致, 无训练-服务偏差                       │
│  缺点: 新增特征无法追溯历史, 需等线上日志积累                        │
│                                                                    │
│  ════════════════════════════════════════════                      │
│                                                                    │
│  方案B: "离线重算" (补充方案)                                      │
│  ──────────────────────────                                       │
│                                                                    │
│  ┌──────────┐     ┌──────────────┐     ┌──────────────┐          │
│  │ 行为日志  │     │ 离线特征表    │     │  Temporal     │          │
│  │ (Label)  │────▶│ (Hive分区)   │────▶│  Join         │          │
│  └──────────┘     └──────────────┘     └──────┬───────┘          │
│                                                │                  │
│                   按event_time关联              ▼                  │
│                   对应日期分区的特征  ────▶  训练样本               │
│                                                                    │
│  优点: 新特征可以回溯计算历史值, 灵活性高                            │
│  缺点: 可能引入训练-服务偏差, 需要Point-in-Time Join保证正确性       │
│                                                                    │
│  实际做法: A为主 + B为辅, 稳定特征走A, 新增探索特征先走B验证         │
└────────────────────────────────────────────────────────────────────┘
```

**为什么 Feature Logging 如此关键？**

这是字节体量级系统的**最重要设计决策之一**：

> **训练-服务一致性 (Training-Serving Consistency)** 是大规模推荐系统中最容易被低估、造成损失最大的问题。

| 偏差来源 | 举例 | 后果 |
|---------|------|------|
| 计算逻辑不一致 | 训练用 Python，服务用 C++，浮点精度不同 | 模型效果无法复现 |
| 数据版本不一致 | 训练用 T-1 的特征，但服务用 T 的特征 | 特征分布不match |
| 时间穿越 | 离线拼接时意外用了未来的数据 | 线上效果远不如离线指标 |
| 特征缺失处理不一致 | 离线填0，在线填均值 | 性能下降 |

**Feature Log 直接记录 Serving 时使用的特征 → 训练用同一份 → 完全消除一致性问题。** 这是以日志存储成本换取模型效果确定性，在字节的规模和收入体量下完全值得。

**为什么需要特征注册中心？**

在字节的组织规模下（数千名算法工程师，数百个模型），如果没有统一管理：
- **重复计算**：5 个团队各自计算 "用户 7 日点击数"，浪费 5 倍资源
- **口径不一致**：同一概念的特征，不同团队定义不同，导致模型效果差异难以归因
- **变更失控**：上游修改特征逻辑，下游模型不知情，线上效果突然恶化
- **资源浪费**：大量"僵尸特征"占用计算和存储但已无人使用

## 四、特征类型体系 (在深度学习模型视角下)

字节的 CTR/CVR 模型（如 DIN → DIEN → SIM 系列）不是简单的 "一个大表"，而是**按特征类型做不同的模型输入处理**：

```
┌──────────────────────────────────────────────────────────────────────────┐
│                    模型输入的特征类型体系                                  │
│                                                                          │
│  ┌─────────────────────────────────────────────────────────────────┐    │
│  │  类型1: ID 类特征 (Sparse / Categorical)                       │    │
│  │                                                                 │    │

│  │  • industry_id, ad_format, os_type ...                         │    │

│  │  处理方式: Embedding Table 查表 → 得到稠密向量                  │    │

│  │  关键:    Embedding 维度选择, 低频ID的处理 (hash bucket)        │    │
│  │  存储:    ID本身很小, 关键是模型里的 Embedding Table 很大        │    │
│  └─────────────────────────────────────────────────────────────────┘    │
│                                                                          │
│  ┌─────────────────────────────────────────────────────────────────┐    │

│  │  数量:    通常数百个                                            │    │
│  └─────────────────────────────────────────────────────────────────┘    │
│                                                                          │
│  ┌─────────────────────────────────────────────────────────────────┐    │
│  │  类型3: 序列特征 (Sequence / Behavioral)  ⭐ 极其重要           │    │

│                                                                          │
│  ┌─────────────────────────────────────────────────────────────────┐    │
```

## 五、特征 DSL 与统一计算

字节级别不会让每个算法工程师自己写 Spark/Flink 代码，而是提供**特征 DSL (领域特定语言)**：

```
┌────────────────────────────────────────────────────────────────────┐
│                      特征定义 DSL (示意)                           │
│                                                                    │
│  feature {                                                        │
│    name:    "user_7d_click_count"                                 │
│    entity:  USER                                                  │
│    type:    INT64                                                 │
│    desc:    "用户过去7天的广告点击次数"                              │
│                                                                    │
│    source {                                                       │
│      table: "dwd.ad_click_log"                                   │
│      filter: "event_type = 'click'"                              │
│    }                                                              │
│                                                                    │
│    transform {                                                    │
│      aggregate: COUNT(*)                                          │
│      group_by:  user_id                                          │
│      window:    SLIDING(7, DAY)                                  │
│    }                                                              │
│                                                                    │
│    output {                                                       │
│      offline: "hive://user_features/user_7d_click_count"         │
│      online:  "abase://cluster01/user_features"                  │
│      default_value: 0                                            │
│    }                                                              │
│                                                                    │
│    schedule {                                                     │
│      batch:  "0 4 * * *"    // 每天凌晨4点                       │
│      stream: ENABLED        // 同时开启流式更新                    │
│    }                                                              │
│                                                                    │
│    quality {                                                      │
│      null_rate_max:  0.05                                        │
│      value_range:    [0, 100000]                                 │
│      drift_threshold: 0.15                                       │
│    }                                                              │
│  }                                                                │
│                                                                    │
│  ─────────────────────────────────────────────                    │
│  平台根据 DSL 自动:                                               │
│    1. 生成 Spark SQL / Flink SQL 计算逻辑                         │
│    2. 配置调度任务                                                 │
│    3. 配置离线→在线的同步管道                                      │
│    4. 注册到 Feature Registry                                     │
│    5. 配置质量监控告警                                             │
│    6. 生成特征文档                                                │
└────────────────────────────────────────────────────────────────────┘
```

**为什么用 DSL 而不是让工程师直接写代码？**

| 原因 | 解释 |
|------|------|
| **一致性保证** | 同一份定义自动生成离线 + 在线的计算逻辑，避免两套代码出现偏差 |
| **降低门槛** | 算法工程师不需要精通 Spark/Flink，只需声明 "要什么" |
| **批流一体** | 平台自动判断一个特征是否需要流式更新，同一定义产出两种计算 |
| **变更可控** | 修改 DSL → 自动重新生成代码 → 自动做 backfill → 减少人为错误 |
| **优化空间** | 平台可以对 DSL 做全局优化：合并相同 source 的特征计算，减少重复扫表 |

## 六、关键设计决策 & 取舍总结

### 6.1 核心取舍矩阵

```
┌──────────────────────────────────────────────────────────────────────────────────┐
│                          关键架构决策 & 取舍                                     │
├─────────────────────┬──────────────────────┬──────────────────────────────────────┤
│      决策点          │     选择              │         取舍分析                     │
├─────────────────────┼──────────────────────┼──────────────────────────────────────┤
│ 训练数据中的特征     │ 优先用 Feature Log   │ ✅ 完全消除训服偏差                   │
│ 来源               │ (Serving时记录)       │ ❌ 新特征无法回溯历史                  │
│                     │                      │ ❌ 日志存储成本极高 (PB级/天)          │
│                     │                      │ 折中: 主路Log + 新特征离线回算         │

│                     │                      │ ✅ 成本可控 (Redis全内存太贵)          │
│                     │                      │ ❌ 研发维护成本高                      │
│                     │                      │ 折中: 热数据内存, 温数据SSD            │

│                     │                      │ ❌ 不同频率特征的一致性时间点不同       │
```

## 十、一句话总结每个关键设计选择

| # | 设计 | 一句话原因 |
|---|------|-----------|
| 1 | **三级计算引擎** | 因为不同特征对时效性的需求差异巨大，统一用一种会在成本或延迟上不可接受 |
| 2 | **Feature Log 驱动训练** | 因为训练-服务一致性是影响数十亿收入的最大风险点，用空间换确定性 |
| 3 | **在线 KV 存储** | 因为 3ms 内必须取回特征，只有 KV 点查能满足，关系型数据库和列存都不行 |
| 4 | **特征打包存储** | 因为一次请求需要一个用户的 500 个特征，500 次 KV 查询不可接受，打成 1 次 |
| 5 | **统一 DSL** | 因为数千人手写代码无法保证一致性，声明式定义让平台托管一致性 |
| 6 | **Feature Registry** | 因为数万个特征没有注册中心就是灾难——重复计算、口径混乱、变更失控 |
| 7 | **贝叶斯平滑** | 因为展示量不足时原始 CTR 极不可靠，平滑能在冷启动时给出更合理的估计 |
| 8 | **序列特征 + 注意力** | 因为用户的下一次点击与最近行为强相关，序列建模是 CTR 提升最大的单一技术 |
| 9 | **特征分桶离散化** | 因为深度模型中 Embedding 查表比直接输入连续值效果更好，且更鲁棒 |
| 10 | **Point-in-Time Join** | 因为不做时间对齐就会数据泄露，离线指标虚高但线上崩塌 |
